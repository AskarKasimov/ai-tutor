# Правила работы в репозитории

Действуют для всего репозитория. При изменениях frontend также прочитайте [локальный AGENTS.md](services/frontend/AGENTS.md). Видение, термины, статус реализации, запуск и проверки — в [README.md](README.md).

## Порядок работы

1. Определите слой изменения: services/backend, services/frontend, services/postgresql, services/caddy, api или documents.
2. Для учебной логики сверяйте [сценарий](documents/voice-trainer-scenarios.md) и [алгоритм варианта](documents/Алгоритм_составления_варианта.md). Наблюдения перед реализацией диагностики — [PLAN.md](PLAN.md); схема и импорт — [backend README](services/backend/README.md#бд-и-импорт); авторизация — [auth.md](documents/auth.md).
3. Для HTTP сверяйте код и [единый OpenAPI](api/openapi.yaml). implemented означает подключённую операцию, planned — проект. При изменении DTO/аннотаций обновляйте контракт генератором и соответствующие тесты.
4. В backend сохраняйте слои и направление зависимостей из [архитектуры](documents/backend-architecture.md). SQLC генерируйте из запросов. Применённые миграции дополняйте следующей версией; согласованный сброс расходной dev-БД допускает переработку начальной схемы без переноса старых данных.
5. Проверяйте затронутые сервисы командами из README и их локальной документации. В результате указывайте выполненные проверки и пропуски интеграционных DB-тестов.
6. При расхождении кода, требований и документации фиксируйте его явно. Доступность моделей и применение миграций подтверждайте фактическими запросами; успешный health проверяет backend и БД.

## Учебные правила для текущей работы

- Основа — текущая карта ML CSV/XLSX; формат сохраняется, добавляются полные задания и TRUE. Сборка не требует ручной линковки ОР или дополнительных документов.
- Вариант строится по всей карте без выбора темы. Первичный фильтр — минимум трёх разных готовых TRUE-ОР. Основной выбирается по сумме ранга Блума и важности; при равной сумме выигрывает большая важность. Два базовых выбираются только из ОР с меньшим рангом Блума; если таких меньше двух, компетенция пропускается. Все три ОР одной компетенции различны.
- Основной выбирается по сумме ранга Блума и важности; при равной сумме приоритет у важности. Рандом применяется только внутри пула выбранного ОР. Seed не нужен.
- Variantgen реализован для сборки, сохранения снимков и доступа. Четыре операции `/variants` описаны в едином OpenAPI. Приём ответов, грейдинг, прохождение и тренировка вне его scope. Действующие taskgen и assessment сохраняются.
- ОС связана с ОР 1:1; отсутствие текста — NULL. Неполные фрагменты источника не выдаются как задания. Имена таблиц и полей — английские.
- Импорт атомарно заменяет активную карту и банк; пользователи и расшифровки сохраняются. Ошибка откатывает замену. Сохранённые варианты читаются из собственных снимков после переимпорта.
- В общем продукте основной оценивается в 0/1/2, базовый — в 0/1; диагностическая сумма учитывает только основные. Непроверенные ОР не объявляются пробелами, техническая ошибка не считается учебным нулём, тренировка не меняет исходную диагностику.

## Интеграции и данные

Настройки моделей и секреты находятся на backend; VITE_* доступны браузеру. Frontend обращается к backend через Caddy. Эталоны и criteria не выдаются студенческим каталогом.

STT принимает multipart audio (WAV/Ogg/WebM до 25 МиБ), TTS — JSON text до 500 символов и возвращает WAV. Для длинной речи GigaAM нужны longform/VAD зависимости на сервере модели. В целевом прохождении TTS читает голосовую инструкцию; frontend сейчас озвучивает вопрос/варианты. Интеграция инструкции относится к модулю прохождения. Ответ — голосовой выбор и объяснение, без ручной правки расшифровки; если инструкция требует назвать вариант и объяснить, отсутствие названия словами даёт 0, одного номера недостаточно.

В dev корневой Compose запускает Vite и Air с исходниками; сервисные Compose для production запускают nginx и готовый бинарник. PostgreSQL хранит данные в постоянном volume: down сохраняет его, down -v удаляет данные. Удаление volume не является обычным перезапуском.
