# План реализации диагностической сессии backend

Дата: 7 октября 2026. Статус: API и orchestration сессии реализованы. Real-mode grader adapter пока отвечает 503: приложение ещё не передаёт снимок варианта в `ContextProvider`. Выбранный контракт сверялся с [PR #10](https://github.com/AskarKasimov/ai-tutor/pull/10); этот документ описывает поведение текущей ветки и не утверждает текущий статус PR.

## Цель и границы

Backend проходит сохранённый вариант, выдаёт задания и голосовые инструкции, вызывает STT/TTS и грейдинг, выбирает следующее задание по оценке. Состояние сессии, ответы и статистика хранятся в памяти процесса. Структурированный результат доступен для будущих сервисов итогового фидбэка и тренировки. Frontend, генерация итогового фидбэка и реализация тренировки в этот план не входят.

Вариант и расшифровки уже сохраняются в PostgreSQL. Новых DB-миграций для состояния диагностики не требуется. Заготовки `learning_sessions`, `task_assignments`, `assignment_responses` пока не подключаются. Учебная сессия отличается от auth-сессии: `internal/entities/session` сейчас относится к авторизации.

## Что доступно сейчас

| Возможность | Подключённый доступ в текущей ветке | Ограничения |
| --- | --- | --- |
| Создать вариант | `POST /variants`, обязательный `Idempotency-Key` | Сохранённый план main/basic, успешный повтор возвращает тот же вариант. |
| Прочитать вариант и позицию | `GET /variants/{id}`, `GET /variants/{id}/tasks/{task_id}` | Доступ владельца; публичные DTO скрывают эталоны, criteria и ОС. |
| Получить полный снимок | Domain port `variant.TaskReader`, реализованный variantgen application и PostgreSQL adapter | Используется сессией при запуске; читает связанный снимок владельца вместе с ролью и свойствами задания. SQL выполняется через сгенерированные sqlc методы. |
| STT | `POST /voice/transcriptions`, multipart `audio` | WAV/Ogg/WebM до 25 МиБ; ID и текст расшифровки, сохранённой за владельцем. |
| TTS | `POST /voice/syntheses`, JSON `text` | До 500 символов, ответ WAV. Для диагностики озвучивается `voice_instruction`. |
| Прототип грейдинга | `POST /assessments/evaluate` | В этой ветке принимает `transcription_id`, вопрос, варианты, инструкцию и необязательный эталон; возвращает score 0–2 и три строки feedback. |

Все перечисленные HTTP-операции подключены и требуют авторизации. Доступность внешних моделей этой проверкой не подтверждается.

## Согласованный контракт грейдинга

Для реализации выбран контракт [PR #10](https://github.com/AskarKasimov/ai-tutor/pull/10): `POST /assessments/evaluate`, запрос `task_id` и `transcription_id`; ответ `score`, `verdict` (`correct`, `partial`, `incorrect`), `criterion_results` (`key`, `satisfied`, `explanation`) и три строки `feedback`. Результат сам assessment не сохраняет. Контекст задания backend получает через `ContextProvider`; `Grader` принимает контекст и текст ответа. Старый контракт с вопросом в запросе для сессии не используется. Будущие изменения API адаптируются отдельно, ожидать их для разработки сессии не требуется.

Грейдер возвращает 0–2 независимо от роли. Сессия преобразует оценку на своей стороне:

| Роль | Оценка грейдера `grader_score` | Оценка сессии `score` |
| --- | --- | --- |
| Main | 0, 1, 2 | Без изменений: 0, 1, 2. |
| Basic | 2 | 1. |
| Basic | 0 или 1 | 0. |

Сохранять обе оценки. Переходы, статистика и данные для тренировки используют `score` сессии. `verdict`, `criterion_results` и фидбэк одного ответа сохраняются как результат грейдера и относятся к `grader_score`; например, basic с `verdict=partial` получает `score=0`. Недопустимые оценки вне 0–2 не преобразуются в учебный ноль, а возвращают техническую ошибку. Передавать роль или добавлять `max_score` в API грейдера сейчас не требуется.

### Известные ограничения интеграции

- Реальный provider контракта PR #10 ещё не подключён в текущей ветке. Mock-порт позволяет проверить переходы и хранение результата; real-режим возвращает 503 без score и перехода, пока `ContextProvider` не передаст контекст сохранённого задания. При подключении сохранить wiring variantgen и обновить единый `api/openapi.yaml`; файл `services/backend/backend.api.yaml` уже удалён.
- Каталог PR содержит 18 задач с ID `ml_*`; ID импортированного банка и позиций variantgen там отсутствуют. `variant_task_id` обозначает позицию, `task_id` — задание в контексте грейдера. Адаптер должен использовать подтверждённое соответствие ID, а не подменять один другим. Пока соответствия нет, реальный вызов для задания варианта возвращает ошибку контекста без оценки и продвижения. Это ограничение фиксируется при интеграционной проверке; разработка и тестирование сессии выполняются через порт и тестовый грейдер.
- Исторические профили, эталоны, criteria и ОС остаются в снимках вариантов. Сессия сохраняет ссылки и связанные свойства; она не вводит отдельный ручной каталог, обязательную разметку критериев или дополнительные документы. Поддержка снимков и необязательных criteria/ОС в грейдере относится к его дальнейшей интеграции.
- Замечания PR об отсутствующем/null `satisfied` и обязательном названии варианта остаются ответственностью грейдера. Сессия использует его текущий результат и проверяет доступную структуру ответа; она не пересчитывает критерии и не исправляет оценивание текста самостоятельно. Исправления этих замечаний не являются условием начала разработки сессии.

## Учебные переходы

| Текущая позиция | Результат | Следующая позиция |
| --- | --- | --- |
| Main | 2 | Main следующей компетенции; оба basic отмечаются как непредъявленные. |
| Main | 0 или 1 | Первый basic той же компетенции. |
| Первый basic | 0 или 1 | Второй basic той же компетенции. |
| Второй basic | 0 или 1 | Main следующей компетенции. |
| Последняя необходимая позиция | Успешная оценка | Диагностика завершена. |
| Любая позиция | Ошибка STT/грейдинга, недопустимый результат или отмена запроса до принятия результата | Позиция не меняется, score не записывается. |

В таблице используется преобразованная оценка сессии. Порядок компетенций и basic берётся из сохранённого варианта. Диагностическая сумма учитывает только main, максимум — 2N. Базовые уточняют пробелы. Непредъявленные задания и пропущенные при сборке компетенции не считаются проверенными пробелами. Тренировка не меняет исходную диагностику. Ручное исправление расшифровки в сценарий не входит.

## Слои и зависимости

- `entities/diagnostic`: состояние сессии, предъявленная позиция, попытка и результат диагностики.
- `entities/assessment`: доменные типы результата с verdict/criterion_results, соответствующие контракту PR. Существующие типы assessment переводятся адаптером без обязательного рефакторинга грейдера.
- `features/diagnostic/application`: запуск, чтение, обработка ответа, преобразование оценок, переходы и агрегация. Порты чтения варианта/снимка, STT, TTS, грейдинга, хранилища состояния, ID и времени.
- `features/diagnostic/infrastructure`: хранилище в памяти и адаптеры портов. Переиспользуются действующие voice-адаптеры; real grader adapter ожидает интеграции `ContextProvider` из PR #10.
- `features/diagnostic/transport/http`: авторизация, multipart/JSON, DTO, ошибки и аннотации OpenAPI.
- `app`: composition root для всех зависимостей. Application сессии не импортирует application других features и не делает HTTP-запросы к собственным обработчикам.

При запуске сессии прочитать вариант с проверкой владельца и зафиксировать его порядок/позиции в состоянии. Роль main/basic и связанные свойства берутся из этой доверенной структуры и исторических снимков; публичные DTO эталон/criteria/ОС не раскрывают. Текущий грейдер получает свой контекст по task_id; переход на контекст снимка выполняется при дальнейшей интеграции его provider.

Application-порт грейдинга принимает owner ID, transcription ID и source task ID и возвращает structured evaluation. В mock подключён демонстрационный адаптер. В real режиме временный адаптер возвращает 503; фактический PR #10 provider должен читать связанный снимок и передавать грейдеру контекст и текст ответа. Сессия применяет шкалу роли и сохраняет `variant_task_id` отдельно. HTTP-вызовы собственных обработчиков не требуются; при интеграции заменяется адаптер, переходы остаются в application.

## Реализованные операции сессии

Операции ниже реализованы и отмечены как implemented в едином OpenAPI. Все операции проверяют владельца сессии.

| Операция | Запрос и результат |
| --- | --- |
| `POST /diagnostic-sessions` | JSON `variant_id`, обязательный `Idempotency-Key`; создать сессию и вернуть её ID, прогресс и текущее задание. Генерация нового варианта остаётся отдельной операцией. |
| `GET /diagnostic-sessions/{id}` | Статус, прогресс и текущая позиция с публичными полями задания. Чтение не продвигает сессию. |
| `GET /diagnostic-sessions/{id}/current/audio` | Озвучить голосовую инструкцию текущей позиции через TTS, вернуть WAV. Ошибка озвучивания не меняет сессию. |
| `POST /diagnostic-sessions/{id}/answers` | Multipart `audio` и `variant_task_id`, обязательный `Idempotency-Key`; вызвать STT и grader port, преобразовать и принять оценку. При доступном grader вернуть `score`, `grader_score`, verdict/criterion_results/фидбэк одного ответа, прогресс и следующую позицию либо завершение. В real-режиме сейчас 503 без оценки и перехода. |
| `GET /diagnostic-sessions/{id}/result` | Для завершённой сессии вернуть диагностическую сумму, результаты по проверенным ОР, непроверенные позиции, принятые оценки и данные для выбора тренировки. Итоговый текст не формируется, модель не вызывается. Для незавершённой — ошибка состояния. |

Эталоны, rubric, роль и score клиент не задаёт. `variant_task_id` должен совпадать с текущей позицией. Готовая расшифровка после STT сохраняется стандартным voice-сценарием. Дополнительная ручка приёма произвольного текста/исправленной расшифровки не требуется.

## Состояние, повторы и конкурентные запросы

Хранить session/owner/variant ID, статус, текущую позицию, снимок порядка, попытки и состояния ключей запросов, включая незавершённые и технически неуспешные. Для каждой принятой оценки сохранять variantTaskID, исходный task ID и ID контекста грейдера, компетенцию/ОР и связанные свойства снимка, роль, transcriptionID и текст, grader_score, score, verdict, criterion_results, feedback и время. Отдельно учитывать непредъявленные позиции и технические ошибки; они не имеют учебного score.

Хранилище в памяти защищено общим `RWMutex`; операции копирования состояния короткие, а внешние STT/grader вызовы выполняются без блокировки. Проверка на 2 000 параллельных пользователей покрывает конкурентную работу store (создание, чтение и резервирование), но не пропускную способность PostgreSQL, STT/TTS или реального grader. Обработка ответа:

1. Под блокировкой проверить владельца и ключ/fingerprint. Успешный повтор вернуть из сохранённого результата до проверки текущей позиции и завершённости: после принятия ответа они уже изменились. Для новой обработки проверить активность и текущую позицию, зарезервировать попытку; второй ответ во время её обработки отклонить ошибкой состояния.
2. Освободить блокировку до STT/LLM. Не держать общий mutex хранилища или mutex сессии во время сетевого ожидания.
3. Получить расшифровку и оценку; проверить исходный диапазон 0–2 и структуру результата, преобразовать оценку по доверенной роли.
4. Под блокировкой повторно проверить идентификатор зарезервированной попытки и отмену context, затем одним действием записать оценку, статистику, следующий шаг и результат для повтора ключа. Это точка принятия ответа; отмена после неё не откатывает оценку.
5. При технической ошибке снять резерв и оставить текущую позицию. Если STT уже завершён, сохранить transcriptionID для повторной попытки грейдинга без повторного распознавания того же запроса. После принятия результата потеря HTTP-ответа не отменяет оценку: повтор ключа возвращает сохранённый результат.

Одинаковый ключ с другим variant_task_id или другим аудио отклоняется; fingerprint учитывает содержимое аудио, а не multipart boundary. При запуске сессии ключ связан с владельцем и variant_id, успешный повтор возвращает ту же сессию. Нельзя дважды принять один ответ или применить опоздавший результат к следующей позиции. Грейдинг выполняется в запросе; отдельные фоновые goroutines для продвижения сессии не требуются.

## Структурированный результат

Агрегация сессии рассчитывает сумму main, максимум, результаты только проверенных ОР и отдельный список непредъявленных позиций и пропущенных при сборке компетенций. Для подготовки тренировки сохраняются основной с 0/1, базовые с 0 и их профили/результаты по критериям; используются преобразованные оценки сессии. Этот список не объявляет пробелами остальные ОР компетенции.

Сохранять фидбэк каждого ответа из assessment без повторного вызова грейдера. Генерация общего фидбэка будет отдельным сервисом: в scope сессии нет его provider, HTTP-операции, вызова LLM, статусов генерации и повторов. Будущий сервис сможет получить статистику и результаты ответов через чтение завершённой сессии с проверкой владельца.

Результат диагностики фиксируется при завершении. Переданные будущим сервисам фидбэка и тренировки исходные результаты грейдера и преобразованные оценки остаются неизменными.

## Реализация и проверки

Сессия, application, memory store, HTTP handlers, composition wiring и OpenAPI реализованы. Тесты покрывают переходы, шкалы оценок, владельца, идемпотентность/конкурентные ответы, отмену, ошибки интеграций, структуру ответа грейдера и 2 000 одновременных обращений к store. DB-интеграционные проверки применяются к чтению variant snapshot; реальные внешние сервисы в unit/HTTP тестах не вызываются.

Для повторной проверки: `go test -race ./... -count=1`, `go vet ./...`, `go build ./cmd/api`, `bash scripts/generate-openapi.sh`, `bash scripts/generate-sql.sh`. Полная нагрузка на API с реальными DB/STT/TTS/grader требует отдельного нагрузочного окружения; тест store сам по себе такую производительность не подтверждает.

## Ограничения текущей реализации

- Сессии и idempotency keys хранятся до перезапуска процесса; store ограничен 10 000 сессий за время жизни процесса. После перезапуска восстановление и совместная память нескольких экземпляров не поддерживаются.
- Один пользователь может создать несколько сессий для одного варианта с разными ключами запуска. После принятия ответа результат повторяется только с тем же ключом и fingerprint; новая оценка той же позиции не создаётся.
- Голосовые инструкции длиннее лимита TTS 500 символов завершаются ошибкой; молчаливое обрезание не выполняется.
