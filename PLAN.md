# Диагностическая сессия backend: наблюдения перед реализацией

Дата: 7 октября 2026. Проверены текущий router, application-сервисы и [OpenAPI](api/openapi.yaml). Документ фиксирует доступные зависимости и недостающие части; реализация сессии не начата.

## Запрошенный сценарий

Backend проходит сохранённый вариант, выдаёт вопросы и голосовые инструкции, использует STT/TTS и грейдинг, выбирает следующее задание по оценке. Состояние и статистика диагностики хранятся в памяти backend для итогового фидбэка и последующего выбора тренировки. Frontend в эту работу не входит.

Учебная сессия отличается от auth-сессии. `internal/entities/session` сейчас относится к авторизации.

## Доступные зависимости

| Возможность | Текущий доступ | Ограничения |
| --- | --- | --- |
| Создание варианта | `POST /variants`, обязательный `Idempotency-Key` | Вариант сохраняется в PostgreSQL; успешный повтор ключа возвращает тот же вариант. |
| План и задания | `GET /variants/{id}`, `GET /variants/{id}/tasks/{task_id}` | Публичное чтение содержит main и оба basic, проверяет владельца и скрывает эталоны, criteria и ОС. |
| Полный снимок для грейдинга | `variant.TaskReader.TaskForGrading(ownerID, variantID, variantTaskID)` | Проверяет владельца; возвращает эталон, criteria, ОС и связанные свойства карты после переимпорта. Доступ предоставлен через `App.VariantTaskReader()`. |
| STT | `POST /voice/transcriptions`, multipart `audio` | WAV/Ogg/WebM до 25 МиБ; расшифровка сохраняется в БД с владельцем, ответ содержит ID и текст. |
| TTS | `POST /voice/syntheses`, JSON `text` | Текст до 500 символов, результат WAV. Для целевого сценария озвучивается голосовая инструкция. |
| Оценка одного ответа | `POST /assessments/evaluate` | Принимает ID расшифровки и произвольное задание с необязательным эталоном; возвращает score 0–2 и три строки feedback, результат не сохраняет. |

Все перечисленные HTTP-операции подключены и требуют авторизации. Внешняя доступность моделей этой проверкой не подтверждается.

## Недостающие части

### Грейдинг задания варианта

Текущий assessment — прототип: он не принимает `variant_task_id`, не читает снимок варианта, не получает роль main/basic, criteria и профиль ОР. Шкала всегда 0–2. Новый грейдинг другого разработчика в текущем router не подключён.

Для интеграции нужен серверный контракт оценивания, который получает ответ и позицию варианта, использует сохранённый эталон и роль. Main оценивается в 0/1/2, basic — в 0/1. Техническая ошибка возвращается отдельно от учебной оценки. Конкретный контракт нужно согласовать с разработчиком грейдинга; новые ручки пока не объявлены в OpenAPI.

### Итоговый фидбэк

Отдельного модуля или API итогового фидбэка нет. `feedback` в assessment относится к одному ответу: вердикт, причина и совет. Он не агрегирует диагностику и не определяет набор ОР для тренировки.

Нужна агрегация результатов по компетенциям и ОР: диагностическая сумма, проверенные пробелы, непроверенные ОР и данные для выбора тренировки. Генерация итогового текста и её контракт ещё не определены.

### Управление сессией

Нет application-модуля и HTTP-операций запуска диагностики, получения текущего задания, приёма ответа в сессии и чтения результата. Нет backend-хранилища состояния в памяти, переходов main/basic, защиты от повторной обработки ответа и одновременного продвижения одной сессии.

В БД существуют заготовки `learning_sessions`, `task_assignments`, `assignment_responses` и SQLC-запросы записи; они не подключены к учебному сценарию. Их наличие не означает готовую сессию и не меняет запрошенное хранение её состояния в памяти.

## Зафиксированные учебные правила

- Вариант проходит по включённым компетенциям в сохранённом порядке.
- Main с оценкой 2 пропускает базовые этой компетенции; main с 0/1 требует двух basic, затем перехода к следующему main.
- Диагностическая сумма учитывает только main; максимум — 2N для N включённых компетенций.
- Непроверенный ОР не объявляется пробелом. Пропуск компетенции при сборке, непредъявленный basic и техническая ошибка должны отличаться от оценки 0.
- Тренировка строится по проверенным пробелам и не меняет исходную диагностику.
- Ответ голосовой, без ручного исправления расшифровки. Если инструкция требует назвать вариант словами и объяснить выбор, одного номера недостаточно.

## Данные и интеграционные решения перед реализацией

Для результата и тренировки предлагается сохранять в состоянии сессии owner/session/variant ID, позицию варианта, компетенцию и ОР, роль задания, расшифровку и её ID, score, feedback, статус обработки и время ответа. Данные непредъявленных заданий не должны выглядеть как проверенные пробелы.

В одном backend зависимости следует связывать через порты в `app`. HTTP-операции остаются внешним интерфейсом; application сессии получает доступ к вариантам, voice, грейдингу и фидбэку через внедрённые зависимости согласно [архитектуре](documents/backend-architecture.md).

До технического плана остаётся определить срок жизни состояния в памяти, поведение после restart, число активных сессий пользователя, повторы ответа и правила обработки одновременных запросов. Хранение в памяти процесса само по себе не обеспечивает восстановление после restart или общую сессию между несколькими экземплярами backend.

Схема БД и импорт описаны в [backend README](services/backend/README.md#бд-и-импорт); источником схемы остаются SQL-миграции. Правила варианта — в [алгоритме](documents/Алгоритм_составления_варианта.md), сценарий — в [документе прохождения](documents/voice-trainer-scenarios.md).
