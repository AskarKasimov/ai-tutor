# Geek — устный AI-экзамен по университетскому курсу

Geek — цифровой педагог: проводит со студентом устный экзамен по конкретному курсу, находит пробелы и тренирует по ним в диспуте. Содержание берётся только из материалов курса (лекции, лабы, туториалы). Знания курса заранее раскладываются в граф тем и подтем с зависимостями, и Geek ведёт экзамен по этому графу. Исходное видение — [концепция проректора «Репетитор устного экзамена»](documents/Концепция_Репетитор_устного_экзамена.md); ниже — принятая для нас трактовка.

## Курс

- **Демонстрационный курс** — Б1.О.17 Philosophy II (Introduction to AI) / Философия II (Введение в искусственный интеллект), профиль «Анализ данных и искусственный интеллект» (DSAI), Университет Иннополис, 4-й семестр, 144 ч, экзамен.
- **Источник содержания — материалы курса**: лекции, лабы и туториалы по неделям. У демокурса 16 недель × 3 вида = 48 документов. Структура у курсов разная: 8 недель, курс без лаб или туториалов, только лабы. Число недель и видов материалов не фиксируется в коде.
- **Предварительная оценка** диагностики — по шкале A «отлично», B «хорошо», C «удовлетворительно», D «неудовлетворительно». Каждая проверенная тема получает оценку A–D по критериям; оценка курса — средний балл верхнеуровневых тем (A = 4, B = 3, C = 2, D = 1; темы со статусом «недостаточно данных» исключаются) в процентах от максимума 4: не меньше 90% — A, не меньше 75% — B, не меньше 60% — C, иначе D. Это ориентир для студента; итоговую оценку на аттестации ставит преподаватель.
- **Всё на русском**: материалы, граф, вопросы, диалог, интерфейс. Русскоязычные материалы курса команда загрузит в ближайшее время.

## course-graph: граф знаний курса

Состоит из двух частей. Python-сервис `services/course-graph` выполняет этапы обработки (OCR, очистка, юниты, дедупликация, зависимости, валидация): у них тяжёлые зависимости (Docling, PyTorch), а распознавание долгое и нагружает CPU и память, поэтому сервис изолирован от API и масштабируется отдельно. Модуль backend запускает этапы, хранит граф в PostgreSQL и показывает результат в админке. Материалы курса загружаются в админке. Это сервис с повторяемыми этапами, а не набор разовых скриптов. LLM вызываются через клиент к 4 LLM: backend — напрямую, сервис `services/course-graph` — по gRPC. Результат — граф курса в PostgreSQL, по которому работает Geek.

| № | Этап | Что делает |
| --- | --- | --- |
| 1 | OCR | PDF материалов → текстовые документы, по одному на лекцию, лабу и туториал каждой недели. |
| 2 | Очистка | LLM удаляет всё, что не относится к предмету: сведения о лекторе и команде курса, office hours, организационные объявления, «спасибо за внимание» и т. п. |
| 3 | Извлечение юнитов | Каждый документ недели (отдельно лекция, лаба, туториал) → несколько атомарных подтем. Пример: лекция «Матрицы» → умножение матриц, нахождение обратной, транспонирование. |
| 4 | Дедупликация | Первый проход убирает дубли внутри недели, второй — одинаковые подтемы между неделями. |
| 5 | Зависимости | Для каждой подтемы — стрелки на подтемы курса, которые нужно знать, чтобы её понять. Пример: «ранг матрицы» → метод Гаусса, определение матрицы, миноры. |
| 6 | Валидация | Несколько прогонов LLM проверяют корректность стрелок и отсутствие циклов. |
| 7 | Сохранение | Граф записывается в PostgreSQL для Geek. |

**Структура графа**

- Верхнеуровневые вершины — темы курса. Их примерно столько же, сколько тем курса (не подтем).
- Рёбра двух видов: иерархия «тема → подтема» и пререквизиты «подтема требует подтему». Граф пререквизитов ацикличен; у вершины может быть несколько пререквизитов.
- Вершина хранит текст темы из материалов, номер недели и источники: лекция, лаба, туториал.
- Ручной проверки нет: граф публикуется после LLM-валидации. Красивая визуализация графа для собственного фактчекинга — в планах.
- На курс хранится одна версия графа. Пересборка заменяет граф целиком; у уже пройденных диагностик остаётся только фидбэк.
- Вопросы к вершинам можно сгенерировать на этапе препроцессинга; недостающие Geek генерирует в рантайме.

## Geek: устный экзамен и тренировка

Geek проводит диагностику и тренировку только по графу курса.

### Диагностика — устный экзамен

1. Диалог ведёт LLM. Цель — выявить пробелы студента по материалам курса.
2. Вопросы — в формате устного экзамена: на рассуждение, с развёрнутым ответом. Тестовых вопросов по возможности нет.
3. Обход начинается с верхнеуровневых вершин (тем). Тема с оценкой A, B или C засчитана и засчитывает всё своё поддерево: такие подтемы получают отдельный статус «засчитано по вышестоящей теме», чтобы не смешивать их с проверенными. Тема с оценкой D — пробел: Geek спрашивает по каждому пререквизиту, спускаясь к более простым темам.
4. На одну тему — основной вопрос и не больше одного дополнительного. Дополнительный вопрос углубляет проверку (пример, обоснование, контрпример, изменённые условия) или проясняет неоднозначный ответ.
5. Если студент затрудняется, Geek может один раз переформулировать вопрос. Других подсказок в диагностике нет; студент не может попросить повторить вопрос. «Не знаю» — пробел по этой теме.
6. Модель оценивает ответ по тексту вершины из материалов отдельно по каждому из четырёх критериев: 0 — не показал, 1 — частично, 2 — полностью.
   - К1. Предметная корректность и владение терминологией.
   - К2. Логичность суждений и обоснованность выводов.
   - К3. Способность отвечать на возражения и рассматривать контрпримеры.
   - К4. Применение знания в изменённых условиях и понимание ограничений ответа.

   Уверенность, скорость речи и красноречие не оцениваются. Из уровней критериев получается оценка темы:

   | Оценка темы | Условие |
   | --- | --- |
   | A | Ответ самостоятельный, все четыре критерия на 2. |
   | B | К1 и К2 на 2, К3 и К4 не ниже 1; либо ответ с помощью, все критерии не ниже 1. |
   | C | К1 не ниже 1 и хотя бы один критерий на 2; ответ с помощью, не дотянувший до B. |
   | D | Всё, что не дотянуло до C: К1 на 0, «не знаю», все критерии не выше 1 — пробел. |

   Ответ с помощью (после переформулировки) получает только B или C; если и после переформулировки тема на D, её статус — «пробел».
7. Статус темы — один из:
   - **самостоятельный ответ** — оценка A, B или C без переформулировки;
   - **ответ с помощью** — оценка B или C после переформулировки;
   - **пробел** — оценка D;
   - **недостаточно данных** — вывод сделать нельзя;
   - **засчитано по вышестоящей теме** — подтема не спрашивалась.

   Для каждой проверенной темы фиксируются глубина понимания и фрагменты диалога, на которых основан вывод. Непроверенная тема не считается неосвоенной.
8. **Пробел** — самая глубокая неосвоенная вершина, все пререквизиты которой освоены.
9. Реплики Geek показываются текстом и дублируются голосом (TTS). Студент отвечает голосом или текстом.
10. Итог для студента: предварительная оценка A/B/C/D (по среднему баллу верхнеуровневых тем) и список пробелов с неделями и источниками (лекция / лаба / туториал).

### Тренировка — обучение в диспуте

1. После итога задаётся вопрос «Сколько у тебя часов?».
2. План — пробелы в порядке пререквизитов, снизу вверх.
3. По каждой подтеме: теория из текста лекции, практика по лабе или туториалу, затем диспут. Студент предлагает ответ; Geek задаёт уточняющие вопросы, предъявляет возражения и контрпримеры, помогает сопоставить альтернативные объяснения; студент дополняет аргументацию или пересматривает вывод.
4. Подсказки в тренировке допустимы, каждая фиксируется. Объём поддержки сокращается по мере освоения; в конце студент применяет материал в новой задаче без подсказки.
5. Студент может задавать свои вопросы. Источники ответа Geek:
   - материалы курса — основной источник;
   - если вопрос слишком простой и его нет в материалах — пререквизиты, найденные в листьях графа;
   - если вопрос слишком сложный и его нет в материалах — Geek называет тему, которую стоит изучить, без ссылки на внешний источник.

   Ответ вне материалов курса явно помечается и не расширяет объём проверки.
6. Тренировка не меняет результат диагностики.

### Материалы для преподавателя

После диагностики формируется пакет; преподаватель смотрит его в админке:

- транскрипт диалога с разделением реплик студента и Geek и нумерацией строк;
- карта покрытия знаний — статус каждой темы графа по правилам выше;
- наблюдения по критериям оценки для пробелов со ссылками на номера строк транскрипта.

Смысловое сжатие беседы, события прокторинга и визуальное отображение карты — в будущем.

## Клиент к 4 LLM

На серверах команды развёрнуты четыре модели уровня gpt-oss-120b. Коллега пишет к ним «клиент к 4 LLM» — отдельный модуль backend на Go с очередью и балансировкой. Для Geek и course-graph это одна модель: запросы отправляются параллельно, распределение по моделям и очередь — на стороне клиента. Geek вызывает клиент внутри backend, сервис `services/course-graph` — по gRPC. Настройки моделей и секреты остаются на backend; браузер их не видит.

## Текущая реализация

Код пока реализует прежнюю модель. Студент выбирает предмет, проходит диагностику по варианту из карты компетенций CSV/XLSX (на компетенцию основное и два базовых задания, оценки 0/1/3 и 0/1), получает итог с баллом и фидбэком, выбирает часы и учится по плану с чатом наставника.

| Часть | Состояние |
| --- | --- |
| Backend | Go: auth с cookies, предметы и карты, variantgen, STT/TTS, S3-озвучка, диагностики, общий фидбэк, планы обучения, прежняя тренировка без UI, taskgen. Хранение — PostgreSQL. |
| Frontend | Главная с одной кнопкой «Начать/Продолжить обучение», диагностика с подтверждением расшифровки, итог, вопрос о часах и план обучения с чатом. Админка `/admin` — импорт карты. |
| Инфраструктура | PostgreSQL, локальный RustFS S3, Caddy HTTPS и Swagger UI через Docker Compose. |

Админ-панель на `/admin` сама входит без пароля в общий аккаунт admin. У админки отдельная сессия (свои cookies), поэтому оба сайта можно держать открытыми в одном браузере.

## Запуск

```bash
cp .env.example .env
# Задайте пароль БД и режимы API.
./dev.sh -d
```

На Windows вместо `dev.sh` используйте `.\up.ps1` из PowerShell: скрипт запускает Docker Desktop, при отсутствии создаёт `.env` из `.env.example` в режиме real со случайными секретами, выпускает сертификаты, поднимает стек, ждёт health и открывает сайт ученика и админ-панель. `.\up.ps1 -Logs` показывает логи, `.\up.ps1 -Down` останавливает стек с сохранением данных. Если PowerShell блокирует скрипты, один раз выполните `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`.

Локально нужны Docker Compose и mkcert. Сайт ученика: https://localhost:8443, админ-панель: https://localhost:8443/admin, публичный API: `/api/v1`, health: `/api/v1/health`. Swagger доступен на `/docs/` при `COMPOSE_PROFILES=swagger`.

Для сервера: `.env.prod.example` → `.env`, готовые `certs/server.pem`/`server-key.pem`, сеть `ai-tutor_default`, затем `./prod.sh`. Dev-стек и серверные Compose используют общие имена сети и volumes; одновременно их не запускают.

- Frontend использует HTTP API для auth, предметов, диагностики, итогового фидбэка и плана обучения. ID сессии сохраняется в sessionStorage; учебные данные хранятся в PostgreSQL и переживают перезапуск backend. В dev VITE_* передаются контейнеру; после изменения .env пересоздайте frontend. В production значения применяются при сборке.
- Backend всегда использует действующие модели; STT/TTS и настройки assessment/taskgen из `.env.example` обязательны. Worker готовит озвучку после импорта, а браузер получает сохранённый WAV через авторизованный backend.
- STT принимает WAV/Ogg/WebM до 25 МиБ и возвращает сохранённую расшифровку. TTS принимает до 500 символов и возвращает WAV. Без longform/VAD весов на сервере модели GigaAM отклоняет записи длиннее ~25 с, поэтому браузер переводит ответ длиннее 20 с в WAV 16 кГц, а backend режет его по паузам на части до 20 с и склеивает текст. Запись ответа автоматически останавливается через 1,5 минуты.
- PostgreSQL и S3 хранят данные в отдельных volumes. `down` сохраняет их; `down -v` удаляет. Миграции `00001`–`00010` применяются при запуске API; удалять volumes для обновления не нужно.

### Live reload в Docker

Корневой `./dev.sh -d` запускает dev-образы: Vite HMR для frontend и Air для backend. Исходники подключены через bind mount; polling включён для Docker Desktop. HTTPS и HMR WebSocket проходят через Caddy.

Vite подхватывает изменения frontend. Air пересобирает и перезапускает API при изменениях Go, SQL, go.mod/go.sum; SQLC-код требует отдельной генерации. node_modules, модули Go, кеш сборки и dev-бинарник хранятся в отдельных volumes.

- Изменение .env: `docker compose up -d api frontend` для пересоздания затронутых контейнеров.
- Изменение package-lock.json: `docker compose restart frontend`; при старте dev-контейнер выполняет npm ci.
- Изменение Dockerfile: `docker compose up -d --build api frontend`.
- Изменение OpenAPI: `docker compose up -d --force-recreate swagger`; Swagger читает api/openapi.yaml.

Локальные Compose сервисов, используемые prod.sh, запускают готовый backend-бинарник и frontend с nginx.

## Проверки перед PR

Для разработки вне Docker нужны Go версии из services/backend/go.mod и Node.js 22 с npm.

```bash
# Из services/frontend:
npm ci
npm run lint
npm run typecheck
npm test -- --run
npm run build

# Из services/backend:
go test -race ./... -count=1
go vet ./...
go build -o bin/api ./cmd/api
```

Backend DB-тесты требуют TEST_DATABASE_URL; без него пропускаются. Генерация OpenAPI и пример тестовой БД — в [backend README](services/backend/README.md). CI проверяет затронутые сервисы и Compose; для backend поднимает PostgreSQL.
