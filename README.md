# Голосовой AI-репетитор

Студент отвечает голосом на задания карты компетенций. Продукт предусматривает диагностику, оценку ответов и тренировку по проверенным пробелам. Состояние проекта: 9 октября 2026. Целевой сценарий для AI Journey согласован на встрече 10 октября 2026 — см. [решения встречи](documents/ai-journey-plan.md).

## Текущая реализация

| Часть | Состояние |
| --- | --- |
| Backend | Go: auth с cookies, предметные карты и варианты, STT/TTS, S3-озвучка, диагностики, тренировки и постоянный Socratic-чат с хранением в PostgreSQL. |
| LLM-генерация | Отдельный `taskgen` создаёт и сохраняет задания. Импорт текстовых материалов и PostgreSQL FTS реализованы. |
| Frontend | В real и mock один сценарий выбора предмета, диагностики и тренировки. Ученик диктует реплики в чате; репетитор сам определяет готовность ответа и запускает проверку, а отдельная кнопка переводит к следующему упражнению. История real-чата хранится в PostgreSQL. |
| Варианты и прохождение | Backend собирает, сохраняет и читает варианты. API диагностической сессии выдаёт задания и инструкции, принимает голосовые ответы, передаёт оценку модулю assessment по variant ID/позиции и возвращает структурированный результат. Frontend в real подключён к этому API. |
| Инфраструктура | PostgreSQL, локальный RustFS S3, Caddy HTTPS и Swagger UI через Docker Compose. |

Для локального mock без backend установите `VITE_API_MODE=mock`: тот же экран
выбора предмета, диагностики и тренировки использует демонстрационные данные в памяти браузера.

## Согласованное видение

Источник — карта выбранного предмета CSV/XLSX. Формат сохраняется; преподаватель добавляет полные задания и включает больше ОР в тест. Сборка варианта не требует ручных связей между ОР или дополнительных документов.

Вариант строится по всей карте без выбора темы:

- В вариант попадают только ОР с TRUE в «Что должно войти в тест», допустимыми таксономией/важностью и готовым заданием.
- На компетенцию выбираются основной и ровно два базовых задания разных ОР. Компетенция с меньше чем тремя такими ОР пропускается с причиной.
- Основной ОР — наибольший ранг Блума; при равном ранге приоритет у большей важности, при полном равенстве — порядок источника. Базовые — самые простые из остальных ОР, их ранг может совпадать с рангом основного.
- Случайность применяется только к выбору конкретного задания из пула того же выбранного ОР. Остальные решения детерминированы; seed не нужен.
- Вариант сохраняет выбранные задания, их профили, порядок и пропуски в PostgreSQL. Чтение использует снимки и работает после переимпорта карты.

Модуль `internal/features/variantgen` собирает, сохраняет и читает варианты выбранного предмета через `/variants`. Исторические снимки включают эталон и свойства карты; публичное API их скрывает. Диагностика оценивается по снимку варианта, тренировка — по собственному снимку упражнения. Итоговый фидбэк формируется отдельным модулем. Frontend F1 подключает выбор предмета, явный запуск диагностики и тренировку с gate, preview, продолжением и историей. Новые LLM-упражнения требуют отдельного ExerciseProvider; текущая тренировка использует снимки банка и не обещает генерировать свежий вопрос.

Версия алгоритма — `competency-map-v4`. В [описании алгоритма](documents/Алгоритм_составления_варианта.md) приведены фильтры, API и правила снимков.

### Целевой сценарий AI Journey

Решения встречи 10.10.2026, пока не реализованные в коде; подробности и статус — в [ai-journey-plan.md](documents/ai-journey-plan.md).

- Для студента диагностика и тренировка — один процесс: проверка → итог → план → тренировка. Загрузка карты компетенций в демо не показывается: карта будет генерироваться отдельными процессами.
- Студент отвечает голосом на все задания, включая multiple choice, через кнопку микрофона. Голос наставника — мужской, взрослый, низкий.
- После ответа балл и вердикт не показываются; прогресс — status bar в процентах. Сначала видно больше заданий, выполненные «схлопываются».
- Итог — фидбэк без балла и пометки «Не проверено»: где всё хорошо и какие темы не освоены, с ОР. Внутренние шкалы и сумма на backend сохраняются.
- Затем план «тема — ОР» с временем на теорию и на отработку и кнопка «Начать тренировку». Вопрос «сколько у тебя времени на тренировку?» предусмотрен, но до AI Journey не показывается.
- После тренировки — обратная связь, прогресс-бар слева и кнопка «Продолжить тренировку». Стратегию тренировки, правила теории и практики и промпты генерации готовит Марина.

## Термины

| Термин | Значение |
| --- | --- |
| Компетенция | Верхний учебный узел карты; включается в вариант после фильтра достаточности заданий. |
| Составляющая | Действие внутри компетенции, объединяющее ОР. |
| Образовательный результат (ОР) | Проверяемое действие студента. Принадлежит одной составляющей, может содержать несколько заданий. |
| ОС | Учебное содержание из колонки «ОС», связь 1:1 с ОР; значение может отсутствовать. |
| Задание | Вопрос, необязательные варианты, голосовая инструкция и эталон. Колонка «Задание N» не задаёт роль или сложность. |
| Профиль задания | Компетенция, составляющая, ОР и свойства карты: Блум, ALDs, важность, TRUE/FALSE, ОС, уровень темы и связи РПД. |
| Аналоги | Для сборки — готовые задания одного ОР с одинаковыми унаследованными свойствами. Номер колонки сам по себе не подтверждает эквивалентность вопросов. |
| Вариант | Сохранённый план: основной и два базовых на каждую включённую компетенцию, снимки заданий и список пропусков. |
| Выдача (assignment) | Задание, предъявленное студенту при прохождении. Позиция варианта и выдача имеют разные назначения. |
| Учебная сессия | Прохождение варианта с ответами и результатами; отличается от auth-сессии с cookies. |
| Пробел | Проверенный ОР, владение которым не подтверждено ответом. Непроверенный ОР не объявляется пробелом. |

В текущем источнике нет дерева дочерних ОР или отдельной сущности темы.

Диагностика сохраняет прохождение в PostgreSQL. Основной оценивается в 0/1/2, basic — в 0/1. При 2 на основном basic пропускаются, при 0/1 предъявляются доступные базовые. Сумма учитывает только основные, максимум 2N. После завершения доступны фидбэк и preview тренировки. Тренировка работает по блокам — компетенциям с подтверждёнными пробелами и частичными результатами; при отличной диагностике — по всем компетенциям варианта. Блок начинается с главной задачи (основной ОР); решённая на 2/2 ведёт к следующему блоку. Иначе локальная модель тутора делает выжимку теории по ОС всех ОР компетенции, включая FALSE, затем идут две базовые задачи блока; при ошибке теория и базовые повторяются, при успехе снова предъявляется главная задача (подробнее — в [backend README](services/backend/README.md)). Ученик может неограниченно обсуждать упражнение в отдельном Socratic-чате, проверить финальный ответ (оценка 0/1/2 сохраняется на backend и не показывается студенту) и перейти дальше явным действием. Обычная реплика не создаёт попытку и не меняет упражнение; история чата сохраняется отдельно от диагностики и attempts.

## Карта и данные

Текущий CSV: 13 компетенций, 17 составляющих, 101 ОР, 18 ОР с TRUE, 13 готовых заданий и 41 неполная ячейка задания. Покрытие варианта определяется отдельно для каждой компетенции по числу готовых TRUE-ОР.

В ML-формате полная ячейка содержит `Экран:`, `Голосовая инструкция:` и `Ответ:`; варианты необязательны. Поддерживается произвольное число колонок `Задание N`. Неполные ячейки сохраняются как источник с предупреждениями и не становятся заданиями. Старый парный формат CSV поддержан текущим кодом.

Импорт атомарно заменяет активную карту и задания, выдаёт новые ID и ревизию. Варианты сохраняют независимые снимки и остаются читаемыми после переимпорта. Миграция `00003_task_audio.sql` добавляет устойчивую очередь озвучки; файлы сохраняются в приватный S3, а HTTP-чтение не вызывает TTS. Схема описана в [backend README](services/backend/README.md#бд-и-импорт) и [S3 README](services/s3/README.md).

Сайт ученика и админ-панель — два отдельных сайта на одном адресе. Ученик на `/`

открытыми в одном браузере. Сценарий доступен во всех режимах.

## Запуск

```bash
cp .env.example .env
# Задайте пароль БД и режимы API.
./dev.sh -d
```

На Windows вместо `dev.sh` используйте `.\up.ps1` из PowerShell: скрипт запускает Docker Desktop, при отсутствии создаёт `.env` из `.env.example` в режиме real со случайными секретами, выпускает сертификаты, поднимает стек, ждёт health и открывает сайт ученика и админ-панель. `.\up.ps1 -Logs` показывает логи, `.\up.ps1 -Down` останавливает стек с сохранением данных. Если PowerShell блокирует скрипты, один раз выполните `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`.

Локально нужны Docker Compose и mkcert. Сайт ученика: https://localhost:8443, админ-панель: https://localhost:8443/admin, публичный API: `/api/v1`, health: `/api/v1/health`. Swagger доступен на `/docs/` при `COMPOSE_PROFILES=swagger`.

Для сервера: `.env.prod.example` → `.env`, готовые `certs/server.pem`/`server-key.pem`, сеть `ai-tutor_default`, затем `./prod.sh`. Dev-стек и серверные Compose используют общие имена сети и volumes; одновременно их не запускают.

- `VITE_API_MODE=real` включает HTTP auth, предметов, диагностики и тренировок; остальные значения используют локальное демо. ID сессии сохраняется в sessionStorage; real учебные данные хранятся в PostgreSQL и переживают перезапуск backend. В dev VITE_* передаются контейнеру; после изменения .env пересоздайте frontend. В production значения применяются при сборке.
- `BACKEND_API_MODE=mock` заменяет модели; auth, БД и S3 остаются настоящими. В real обязательны STT/TTS и настройки assessment/taskgen из `.env.example`. Worker готовит озвучку после импорта, а браузер получает сохранённый WAV через авторизованный backend.
- STT принимает WAV/Ogg/WebM до 25 МиБ и возвращает сохранённую расшифровку. TTS принимает до 500 символов и возвращает WAV. Длинным записям GigaAM нужны longform/VAD зависимости на сервере модели.
- PostgreSQL и S3 хранят данные в отдельных volumes. `down` сохраняет их; `down -v` удаляет. Миграции `00002_variants.sql` и `00003_task_audio.sql` применяются при запуске; удалять volumes для обновления не нужно.

### Live reload в Docker

Корневой `./dev.sh -d` запускает dev-образы: Vite HMR для frontend и Air для backend. Исходники подключены через bind mount; polling включён для Docker Desktop. HTTPS и HMR WebSocket проходят через Caddy.

Vite подхватывает изменения frontend. Air пересобирает и перезапускает API при изменениях Go, SQL, go.mod/go.sum; SQLC-код требует отдельной генерации. node_modules, модули Go, кеш сборки и dev-бинарник хранятся в отдельных volumes.

- Изменение .env: `docker compose up -d api frontend` для пересоздания затронутых контейнеров.
- Изменение package-lock.json: `docker compose restart frontend`; при старте dev-контейнер выполняет npm ci.
- Изменение Dockerfile: `docker compose up -d --build api frontend`.
- Изменение OpenAPI: `docker compose up -d --force-recreate swagger`; Swagger читает api/openapi.yaml.

Локальные Compose сервисов, используемые prod.sh, запускают готовый backend-бинарник и frontend с nginx.

## Проверки перед PR

Для разработки вне Docker нужны Go версии из services/backend/go.mod и Node.js 22 с npm.

```bash
# Из services/frontend:
npm ci
npm run lint
npm run typecheck
npm test -- --run
npm run build

# Из services/backend:
go test -race ./... -count=1
go vet ./...
go build -o bin/api ./cmd/api
```

Backend DB-тесты требуют TEST_DATABASE_URL; без него пропускаются. Генерация OpenAPI и пример тестовой БД — в [backend README](services/backend/README.md). CI проверяет затронутые сервисы и Compose; для backend поднимает PostgreSQL.
