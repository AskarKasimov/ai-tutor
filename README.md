# Голосовой AI-тренажёр

Монорепозиторий учебного голосового тренажёра. Студент выбирает дисциплину и тему, получает **готовые задания преподавателя**, отвечает голосом, видит оценку и объяснение, проходит диагностику пробелов и затем тренируется на других заданиях по тем же образовательным результатам (ОР). Генерация новых заданий в MVP не предусмотрена.

Этот README — входная точка для разработчика и ИИ-агента. Он различает **состояние кода сейчас** и **целевое поведение**, иначе легко принять спроектированный OpenAPI за работающую функцию. Подробные контракты, методика и правила конкретных сервисов остаются в документах по ссылкам ниже.

> **На 2 октября 2026:** в коде есть авторизация, импорт CSV карты компетенций, голосовые API и интерфейс-прототип с одним фиксированным вопросом. Для этого прототипа подключена синхронная LLM-оценка одного сохранённого голосового ответа с баллом 0/1/2 и тремя строками обратной связи. Каталог дисциплин, оценка по опубликованной рубрике и материалам, диагностическая сессия и тренировка ещё не реализованы. Рабочий MVP со сквозной диагностикой и тренировкой нужен к **14 октября 2026**; после этой даты до **1 ноября** — стабилизация и доработка.

## 1. Результат и границы

Пользовательский результат MVP: подготовленный учебный набор загружен и опубликован; студент выбирает дисциплину и тему, проходит голосовую диагностику из готовых заданий, видит оценку каждого ответа и итоговые пробелы, после чего в **той же учебной сессии** решает другие похожие задания по неподтверждённым ОР. Система сохраняет результаты и может показать баллы и объяснение, опираясь на загруженные материалы и критерии.

В образовательный контур входят **четыре вида входных данных**:

| Вход | Для чего нужен |
| --- | --- |
| Учебные материалы | Контекст и проверяемые источники для оценки, объяснения и рекомендаций по пробелам. |
| РПД | Структура и содержание дисциплины, к которым привязана тема. |
| Карта компетенций | Составляющие РПД, ОР, их иерархия и связи. |
| Банк заданий | Готовые основные, базовые и тренировочные задания, рубрики/критерии и, если есть, эталонные ответы. |

Преподаватель готовит и загружает эти данные; система использует их при выдаче, оценке и обратной связи. **Рубрика обязательна у задания** в целевом контракте. Оценка должна опираться на задание, рубрику, карту ОР и релевантные фрагменты материалов. Самостоятельная генерация заданий LLM, произвольный диалог вне банка и создание заданий на лету не входят в MVP.

МVP рассчитан на демонстрационный учебный набор, в первую очередь на дисциплину «Прикладная статистика». Архитектура и модель данных не должны быть зашиты под эту дисциплину. Для демо нужен **полный работающий сценарий**, включая тренировку; статичный макет или оценка одного ответа не являются итоговым MVP.

### Основные ограничения продукта

- Оба формата задания: **открытый голосовой ответ** и **голосовой выбор варианта с объяснением**. Вопрос и варианты, если они есть, видны на экране; система произносит отдельную короткую инструкцию для ответа, а не текст вопроса.
- Пользователь сам нажимает «Начать запись» и «Завершить запись». После завершения аудио сразу отправляется на распознавание; промежуточного подтверждения расшифровки и перезаписи успешного ответа нет. Повторная запись нужна только после технического сбоя.
- В целевом сценарии озвучка инструкции начинается при показе задания. Доступны остановка текущего воспроизведения и повтор инструкции; управление остаётся на одном месте независимо от типа и длины вопроса. В текущем прототипе воспроизведение запускается кнопкой.
- На экране результата сохраняются вопрос, варианты (если были) и распознанный ответ студента. Балл **0, 1 или 2** показывается отдельно от текстового объяснения; правильные варианты визуально не подсвечиваются.
- После отдельного ответа показываются его балл и объяснение. После всей диагностики — итоговая статистика, список пробелов и темы для проработки. Уточняющие базовые ответы не улучшают общий диагностический балл.
- Сессия не завершается досрочно из-за хорошего результата в первых заданиях. После итогового диагностического фидбека тренировка идёт по **другим, ещё не использованным** заданиям соответствующих ОР; студент не повторяет буквально задания, на которых ошибся.

## 3. Пользователи и сквозной сценарий

**Преподаватель/admin** готовит дисциплину: РПД, карту компетенций, учебные материалы, готовые задания и критерии. Основные задания привязаны к проверяемым ОР; для ветвления указаны два более базовых ОР и готовые задания для них. Тренировочный банк содержит другие задания по тем ОР, где возможен пробел. В целевом сценарии преподаватель редактирует черновик и публикует проверенную версию. Публикация должна проверять полноту дерева, рубрик и банка; начатые сессии сохраняют свою версию данных.

**Студент**:

1. Входит, выбирает опубликованную дисциплину и ОР/тему. Отдельной параллельной сущности `Topic` в актуальной модели нет: тема — выбранный ОР.
2. Начинает учебную сессию. Система фиксирует опубликованную версию курса и семь **основных** заданий выбранного ОР, выбранных без повторов из подходящего банка.
3. Получает очередное задание, слушает его, записывает ответ. Сервис речи возвращает сохранённую расшифровку. Студент видит её, но не редактирует и не подтверждает.
4. Модуль оценивания получает `transcription_id`, текст задания, рубрику, возможный эталон и найденные фрагменты учебных материалов. LLM возвращает структуру оценки; сервер проверяет допустимые поля и диапазон балла до сохранения. UI показывает балл и объяснение рядом с исходным заданием и ответом студента.
5. Если основной ответ частично верен или неверен, перед следующим основным заданием система выдаёт **по одному базовому заданию для каждого из двух привязанных базовых ОР**. На ошибке в базовом задании новая ветка не открывается.
6. После всех семи основных и назначенных базовых заданий студент получает диагностический итог: баллы только по основным, подтверждённые и неподтверждённые ОР, конкретные направления для проработки.
7. Если пробелов нет, сессия завершается. Если есть — студент запускает тренировку в **том же `Session.id`**. На каждый неподтверждённый ОР закрепляются два разных неиспользованных тренировочных задания, насколько позволяет банк.
8. Результаты тренировки показываются отдельно. Они не меняют исходный диагностический балл и исходный список пробелов. После закреплённого набора сессия завершается; бесконечный подбор и повторная диагностика в MVP отсутствуют.

**Система** управляет выдачей и состоянием сессии, но не придумывает новые учебные задания. Ветвление определяется опубликованными связями ОР и результатом оценивания; конкретное задание выбирается из подходящего банка без повторов и фиксируется в сессии. Для одного и того же сохранённого состояния дальнейшее назначение должно быть воспроизводимым и не дублироваться при повторном запросе.

### Правила диагностики, оценки и пробелов

- Основных заданий — **7**. Согласованный экран результата для **обоих форматов** показывает балл `0/1/2`. Общий диагностический балл складывается только из основных заданий; базовые служат уточнению и в эту сумму не входят. Если все основные задания имеют `max_score=2`, максимум диагностики — **14**. Однако текущий проект OpenAPI допускает произвольный положительный `max_score` и содержит пример с максимумом 7; до реализации эти контракт и шкалу нужно согласовать, а сумму считать по фактическим `max_score` закреплённых основных заданий.
- Для каждого основного задания должны существовать два **разных** базовых ОР внутри его составляющей/иерархии и готовые базовые задания. Это явные связи в данных (`basic_outcome_ids`), а не свободный выбор LLM.
- Ошибка или частичный ответ по основному заданию запускает два базовых. Ошибка в базовом ответе не запускает рекурсивное углубление в MVP.
- Неподтверждённый ОР — только **проверенный** ОР, для которого есть ответ с `outcome_confirmed=false`. Повторы в итоговом списке удаляются; непроверенное нельзя автоматически объявлять пробелом.
- Вердикт `correct | partial | incorrect`, балл, результаты критериев и `outcome_confirmed` должны согласовываться по правилам рубрики. Не следует заменять эти данные эвристикой вроде «0 баллов = нет знаний по всей дисциплине».
- Критерии и эталонные ответы не показываются студенту как внутренние данные; объяснение формулируется понятным учебным языком. Технический сбой STT/LLM — **не** неправильный ответ и **не** ноль баллов.
- Итоговый фидбек должен говорить, что подтверждено и какие ОР/темы подтянуть, с опорой на карту компетенций и материалы. При неполном банке тренировки выдаются доступные задания с причиной `tasks_exhausted`, а не вымышленные новые.

[Подробный контракт сессии и инвариантов](documents/voice-trainer-scenarios.md). [Методика открытых заданий и оценивания](documents/AIAssistantGrading.md) — методический источник, а не инструкция генерировать задания в MVP.

## 4. Учебная модель и данные

```text
Course (дисциплина, опубликованная версия)
  └─ Constituent (составляющая РПД)
      └─ Outcome (ОР = выбираемая тема; может иметь дочерние ОР)
          └─ Task (готовое задание: main | basic | training)
              ├─ текст/варианты и отдельная голосовая инструкция
              ├─ рубрика, максимальный балл, необязательный эталон
              └─ связи с двумя базовыми ОР для main
Session (владелец, версия курса, выбранный ОР, фаза)
  └─ Assignment (конкретная выдача Task, порядок, статус)
      └─ Answer (Transcription, оценка, объяснение либо техническая ошибка)
```

Термины закреплены в [CONTEXT.md](CONTEXT.md). Здесь `Session` — **учебная** сессия; её нельзя смешивать с auth-сессией и refresh-токенами. `Task` — запись в банке, `Assignment` — её выдача конкретному студенту. `Transcription` хранит владельца, распознанный текст и время. Оценка хранит снимок критериев и использованных материалов, чтобы последующее редактирование курса не меняло прошлый результат.

Целевые фазы `Session.phase`: `diagnostic` → `diagnostic_feedback` → `training` → `completed`; завершение: `no_gaps`, `training_completed` или `tasks_exhausted`. Текущее задание одно: `current_assignment_id`. Статусы выдачи: `awaiting_submission`, `processing`, `evaluated`, `processing_failed`. При ошибке обработки пользователь остаётся на задании и может повторить запись; оценённый ответ нельзя заменить.

**Публикация:** черновик может меняться; опубликованная версия неизменна для уже начатых сессий. Нельзя выдавать задание без рубрики, конфликтующие связи ОР или неготовый набор. Для ОР, допущенного к диагностике, нужен банк как минимум из семи основных заданий и покрытие базовых веток. Режим неполного тренировочного банка описан выше.

**Импорт v0:** уже реализован `POST /admin/competency-map/import` — **один CSV**, целиком заменяющий текущую карту в транзакции. Это не универсальная загрузка всех четырёх видов данных. CSV содержит `Ком`, `Сост`, `ОР` и пары `Задание N`/`Критерии N`; объединённые поля могут наследоваться из строки выше. Критерии сохраняются как текст без интерпретации. Формат и ограничения: [backend README](services/backend/README.md#преподаватель-и-csv) и [API README](api/README.md#учебная-база-v0). Целевые отдельные формы/загрузка материалов ещё не реализованы.

### Материалы и RAG

Целевой поток: материал загружается и индексируется → при оценке ответа находятся релевантные фрагменты опубликованной версии → в LLM передаются только нужные фрагменты вместе с заданием и рубрикой → объяснение и рекомендации должны быть проверяемы относительно этих источников. Загрузка, хранение, индексирование и поиск — функции учебной базы; они не заменяют рубрику. Нельзя считать RAG реализованным лишь по наличию поля `materials` в OpenAPI. Точный формат хранения, стратегия разбиения, модель эмбеддингов и метрики качества поиска пока не закреплены; решения должны быть записаны в документации и тестах, когда появятся.

## 5. Архитектура и границы модулей

Пять **логических** модулей не требуют пяти отдельных процессов:

| Модуль | Ответственность |
| --- | --- |
| **Учебная база** | Дисциплины, РПД, дерево ОР, готовые задания/рубрики, материалы, публикация, поиск фрагментов. |
| **Сессия** | Выбор и закрепление заданий, фазы, ветвление после оценки, итог диагностики и тренировки. |
| **Грейдинг и фидбек** | Один голосовой ответ после расшифровки, LLM-проверка по критериям, балл, объяснение, подтверждение ОР. |
| **Голос** | Приём и проверка аудио, STT, сохранение расшифровки, TTS. |
| **Auth** | Пользователи, роли, cookies, доступ к собственным данным и admin-операциям. |

Сейчас это монорепозиторий с React frontend, Go backend, PostgreSQL и Caddy. Backend вызывает отдельные HTTP-сервисы GigaAM STT и VoxCPM2 TTS; браузер напрямую к моделям не обращается. Для прототипа оценки подключён локальный OpenAI-совместимый endpoint `gpt-oss-120b`, настраиваемый через `BACKEND_ASSESSMENT_BASE_URL` и `BACKEND_ASSESSMENT_MODEL`. Это не реализация целевого оценивания по опубликованным рубрикам и материалам.

```text
Браузер ─HTTPS─> Caddy ─/api/v1/*─> Go API ─> PostgreSQL
    │                                ├─> GigaAM STT (/transcribe)
    └─ прочие пути ─> React/nginx     ├─> VoxCPM2 TTS (/synthesize)
                                     └─> LLM / поиск материалов (цель MVP)
```

Caddy удаляет публичный префикс `/api/v1` перед передачей в backend. Frontend использует относительный API URL и `credentials: include`. В backend соблюдается направление зависимостей `transport → application → entities`, инфраструктурные адаптеры подключаются в `app`; подробности и правила новых features — в [архитектуре backend](documents/backend-architecture.md). Frontend-структура и локальные правила — в [frontend README](services/frontend/README.md) и [AGENTS.md](services/frontend/AGENTS.md).

### API: рабочее и целевое

Рабочий backend сейчас предоставляет `/auth/*`, `POST /admin/competency-map/import`, `POST /voice/transcriptions`, `POST /voice/syntheses` и `GET /health`. Полный список и схемы: [backend.api.yaml](services/backend/backend.api.yaml). В OpenAPI пути идут от корня; публично к ним добавляется `/api/v1`.

[Контракты этапов](api/README.md) накопительные: `01-voice` → `02-assessment` → `03-mvp` → `04-demo` (функционально как MVP) → `05-release`. Они описывают план, а не готовность кода. Целевой запросный путь: `POST /sessions` → `POST /voice/transcriptions` → `POST /assignments/{assignmentId}/answer` → `GET` состояния и результата → диагностический итог → `POST /sessions/{sessionId}/training`. Вне сессии контракт также позволяет проверить отдельное задание; это промежуточная функция, не замена MVP.

Ожидаемые HTTP-семантики целевого MVP: STT/TTS синхронны (`200` с текстом или WAV), оценивание и индексирование материалов асинхронны (`202` и чтение результата `GET`). Текущая прототипная ручка `POST /assessments/evaluate` отвечает синхронно `200` и не сохраняет оценку. Все времена в API — Unix timestamp в **секундах**, `int64`. Права проверяются на сервере: студент получает только свои расшифровки и учебные результаты, admin управляет базой. Нельзя показывать эталоны/служебные критерии в студенческом каталоге.

## 6. Голосовой контур и известный риск

Публичный `POST /api/v1/voice/transcriptions` принимает multipart-поле `audio`: WAV, Ogg/Opus либо WebM/Opus, максимум **25 МиБ**. Browser `MediaRecorder` обычно выдаёт WebM/Opus. Backend проверяет контейнер/кодек и пересылает файл во внутренний STT как multipart-поле `file`; ответ `{text}` сохраняется с владельцем. Публичный `POST /api/v1/voice/syntheses` принимает JSON `{text}` (до 500 символов) и возвращает `audio/wav`. Голосовые операции пока синхронные; отдельного polling/job API нет.

**Важно: размер ≠ длительность.** STT `/transcribe` автоматически выбирает обычное распознавание до 25 секунд включительно и longform для более длинных записей; публичный контракт ограничивает размер, а не длительность. Для длинных записей серверу моделей нужны longform-зависимости и VAD-веса. Успешный тест на короткой фразе не доказывает работу долгого ответа. Адрес STT берётся из **фактического `BACKEND_STT_URL` окружения**, а не только из `.env.example`. Для диагностики сравнивайте окружение запущенного backend и фактический ответ его `/voice/transcriptions`.

В текущем frontend любая ошибка распознавания, кроме `401`, сводится к общей надписи «Не удалось распознать ответ». По этому экрану нельзя определить, был ли `422`, `502`, `503`, `504`, таймаут или пустой текст. Проверяйте статус и тело `POST /api/v1/voice/transcriptions` в Network, затем логи `proxy`/`api` и прямой вызов STT с **тем же форматом и длительностью**. `GET /health` backend проверяет API и БД, но не доступность моделей. Технический сбой не должен превращаться в учебный ноль.

## 7. Этапы и критерии готовности

| Срок | Результат, проверяемый пользователем | Основная работа |
| --- | --- | --- |
| **До 1 октября — основа системы и голос** | Экран вопроса, запись ответа, распознанный текст и озвучивание инструкции; компоненты связаны через API. | Проектирование API, развёртывание STT/TTS, интерфейс и состояния записи; подготовка РПД, карты, материалов и банка начинается параллельно. |
| **До 7 октября — учебная база и оценивание** | Студент выбирает дисциплину/тему, получает готовое задание, отправляет голосовой ответ и видит балл с объяснением для одного ответа. | Загрузка/публикация четырёх видов данных, подготовка критериев, поиск фрагментов, подключение LLM и проверка оценки. |
| **До 14 октября — сборка и демо MVP** | Рабочая сессия: вопросы → голосовые ответы → объяснения → следующие задания → итог диагностики → тренировка на других заданиях пробельных ОР. | Семь основных заданий, базовые ветки, итог и тренировочный набор; полный демонстрационный учебный набор; техническая проверка и репетиция сквозного сценария. |
| **После 14 октября до 1 ноября — доработка** | Уже работающий MVP устойчив к сбоям и восстановлению; качество и скорость проверены на подготовленных сценариях. | Устранение дефектов, обработка длинной речи, повтор обработки, идемпотентность создающих запросов, восстановление сессии и контроль качества. |

Это **целевые результаты этапов**, а не утверждение об их текущем выполнении. Не переносите функцию из результата 14 октября в «потом» только потому, что её сейчас нет в коде. Подготовка учебных материалов идёт параллельно разработке с первого этапа; без достаточного банка диагностику и тренировку невозможно проверить.

**Минимальная сквозная проверка MVP:** опубликован набор; студент выбирает дисциплину и ОР; вопрос виден, инструкция озвучена; запись WebM/WAV распознана; ответ оценён в 0/1/2 с понятным объяснением; после ошибки выданы два базовых задания; основная диагностика завершена без досрочного выхода; диагностический балл считает только основные; фидбек показывает проверенные пробелы; тренировка даёт другие задания тех же ОР в том же `Session.id`; итог и история сохраняются. Отдельно проверить технический сбой STT/LLM, отсутствие дублей после повтора и права доступа.

## 8. Запуск и окружение

Для серверного запуска нужны Docker с Compose и готовый TLS-сертификат
для имени сервера. Положите сертификат и ключ в `certs/server.pem` и
`certs/server-key.pem` (PEM, сертификат с цепочкой). Скрипт не выпускает
сертификаты и не устанавливает локальный CA.

```bash
cp .env.prod.example .env
# Замените пароль БД и адреса моделей.
# Шаблон включает реальные API, HTTPS на 0.0.0.0:443 и выключает Swagger.
# Подготовьте certs/server.pem и certs/server-key.pem для имени сервера.
# Один раз создайте сеть вручную, если её ещё нет:
docker network create ai-tutor_default
./prod.sh
```

`prod.sh` проверяет все локальные Compose, затем запускает отдельные проекты:
PostgreSQL → backend (и Swagger по env) → frontend → Caddy. Каждый шаг
использует `up --build --wait`: запуск выполняется в фоне, следующий шаг
начинается после готовности предыдущего. При ошибке скрипт останавливается.
Настройки читаются из корневого `.env`; режимы API не переопределяются.
Дополнительные параметры `up` передаются каждому проекту, например
`./prod.sh --wait-timeout 180`. На Windows используйте Git Bash.
Не коммитьте `.env`, сертификаты и cookies. Адреса моделей должны быть доступны
из контейнера backend. API — `/api/v1`, проверка — `/api/v1/health` на HTTPS
адресе сервера. Микрофон и `Secure` cookies требуют доверенного HTTPS.

Для локального dev-стека нужны Docker с Compose и
[mkcert](https://github.com/FiloSottile/mkcert). После настройки `.env`:

```bash
cp .env.example .env
./dev.sh -d
```

`dev.sh` проверяет корневой Compose, устанавливает доверие к CA mkcert,
выпускает localhost-сертификаты в `certs/` и запускает единый корневой
`docker-compose.yaml` с пересборкой. Корневой Compose сам создаёт dev-сеть
перед запуском контейнеров. Оба скрипта сохраняют режимы API и Swagger из `.env`.

При `PROXY_HTTPS_BIND=127.0.0.1` и `PROXY_HTTPS_PORT=8443` приложение доступно
на [https://localhost:8443](https://localhost:8443). Общий dev-стек и серверные
проекты не запускайте одновременно на одном хосте.

| Настройка | Значение |
| --- | --- |
| `DB_PASSWORD` | Пароль локального PostgreSQL; обязателен. |
| `BACKEND_API_MODE` | Обязателен: `mock` — локальные STT/TTS/оценивание, `real` — действующие модели. Авторизация и PostgreSQL настоящие в обоих режимах. |
| `BACKEND_STT_URL`, `BACKEND_TTS_URL` | Полные внутренние URL моделей; обязательны только при `BACKEND_API_MODE=real`. Локальные значения могут отличаться от `.env.example`. |
| `BACKEND_LISTEN_ADDRESS` | Адрес HTTP-сервера backend; обязателен, в Compose используйте `:8002`. |
| `BACKEND_ASSESSMENT_BASE_URL`, `BACKEND_ASSESSMENT_MODEL` | Адрес и имя модели оценивания; обязательны только при `BACKEND_API_MODE=real`. |
| `BACKEND_VOICE_TIMEOUT`, `BACKEND_ASSESSMENT_TIMEOUT` | Таймауты голоса и оценивания; все обязательны. |
| `BACKEND_MAX_UPLOAD_BYTES` | Максимальный размер файла в байтах; обязателен, не больше 26214400 (25 МиБ). |
| `VITE_API_BASE_URL` | Публичный префикс frontend, по умолчанию `/api/v1`; значение встраивается в сборку. |
| `VITE_API_MODE` | `mock` — локальные ответы в браузере, `real` — запросы к backend. Для проверки моков backend используйте `real`. |
| `VITE_API_PROXY_TARGET` | Backend для локального Vite dev, по умолчанию `http://127.0.0.1:8002`. |
| `PROXY_HTTPS_BIND`, `PROXY_HTTPS_PORT` | Привязка Caddy и локальный HTTPS-порт, по умолчанию `127.0.0.1:8443`. |

Подробнее: [backend README](services/backend/README.md), [frontend README](services/frontend/README.md), [auth](documents/auth.md). Swagger читает **текущий** `services/backend/backend.api.yaml`; после генерации схемы пересоздайте контейнер `swagger` (`docker compose up -d --force-recreate swagger`) и обновите страницу. Войти через `POST /auth/login` в Try it out, затем cookies отправляются браузером автоматически. Контейнер Swagger описан в Compose backend и подключён корневым dev-стеком через `extends`. `COMPOSE_PROFILES=swagger` включает его, пустое значение отключает. YAML смонтирован в Swagger, и UI сам отдаёт спецификацию.

`BACKEND_API_MODE=mock` возвращает фиксированную демонстрационную расшифровку,
короткий WAV-сигнал и оценку 2/2 с демонстрационным фидбэком. После переключения
режима пересоздайте API: `docker compose up -d --build api`.
Swagger управляется через `COMPOSE_PROFILES` независимо от режима backend. При отключении `/docs` и `/docs/*` возвращают 404.

### Полезные команды

Чтобы включить Swagger, задайте в `.env` `COMPOSE_PROFILES=swagger` и выполните
`docker compose up -d swagger proxy`. Чтобы отключить, задайте
`COMPOSE_PROFILES=` и выполните:

```bash
docker compose --profile swagger rm -sf swagger
docker compose up -d proxy
```

Смена профиля не удаляет ранее запущенный контейнер автоматически.
При раздельном запуске удалите Swagger через Compose backend, а Caddy
пересоздайте через его Compose с тем же обновлённым `.env`.

### Compose по сервисам

Корневой `docker-compose.yaml` берёт определения сервисов через `extends`
из четырёх папок: `services/backend/`, `services/frontend/`, `services/postgresql/`
и `services/caddy/`. В нём же объявлены общая dev-сеть, volumes и ожидание здоровых
зависимостей. Swagger принадлежит backend и включается через env.
Конфигурация прокси находится в `services/caddy/Caddyfile`.
`prod.sh` использует локальные Compose для сервера. `dev.sh`, корневые команды
и явный `-f docker-compose.yaml` запускают общий dev-стек.

Для пересборки сервиса уже запущенного общего dev-стека используйте
`docker compose up -d --build --no-deps api` или аналогично `frontend`.

Отдельные Compose запускаются как отдельные проекты. Они подключаются к
существующей внешней сети `ai-tutor_default`. Пример отдельного запуска из корня репозитория:

```bash
# Один раз создать сеть, если её ещё нет.
docker network create ai-tutor_default

docker compose --env-file .env -f services/postgresql/docker-compose.yaml up -d
# Дождаться healthy у db перед первым запуском backend.
docker compose --env-file .env -f services/postgresql/docker-compose.yaml ps
docker compose --env-file .env -f services/backend/docker-compose.yaml up -d --build
docker compose --env-file .env -f services/frontend/docker-compose.yaml up -d --build
# Сертификаты certs/server.pem и certs/server-key.pem должны уже существовать.
docker compose --env-file .env -f services/caddy/docker-compose.yaml up -d
```

Из папки любого сервиса передавайте `--env-file ../../.env`. Межпроектного `depends_on` нет:
зависимости должны быть доступны до запуска сервиса. Для внешней БД задайте
`BACKEND_DATABASE_URL`; иначе backend использует `db:5432` и `DB_PASSWORD`.
Для Swagger UI на `/docs/` включите `COMPOSE_PROFILES=swagger` при запуске
backend и Caddy. UI и YAML отдаёт контейнер `swagger:8080`; Caddy только проксирует.
На отдельных хостах адреса upstream в `services/caddy/Caddyfile` нужно настроить явно.

Выбирайте один способ запуска на хосте: общий dev-стек либо отдельные проекты.
Не запускайте оба одновременно: они используют одинаковые порты, DNS-имена
и данные. При переходе остановите прежние контейнеры без `-v`.
Имена volumes сохранены: `ai-tutor_postgres_data`, `ai-tutor_caddy_data`,
`ai-tutor_caddy_config`. Имена сети и volumes фиксированы в Compose-файлах.
Данные и сертификаты остаются вне пересборки backend/frontend.

```bash
docker compose ps
docker compose logs -f proxy api
docker compose up -d --build api frontend proxy
# Изменение Caddyfile без пересборки backend:
docker compose exec proxy caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile
```

Запуск отдельных сервисов, миграции и примеры HTTP-запросов находятся в README сервисов. Применённые SQL-миграции не редактируйте: добавляйте следующую версию. `docker compose down` сохраняет PostgreSQL volume; `down -v` удаляет данные — не используйте его как обычный restart.

### Проверка разработки

```bash
# Из services/backend: после запуска PostgreSQL
export TEST_DATABASE_URL='postgres://ai_tutor:YOUR_PASSWORD@localhost:5432/ai_tutor?sslmode=disable'
go test -race ./... -count=1
go vet ./...
go build -o bin/api ./cmd/api

# Из services/frontend
npm ci
npm run lint
npm run typecheck
npm test -- --run
npm run build
```

CI поднимает PostgreSQL; без `TEST_DATABASE_URL` интеграционные backend-тесты пропускаются. Тесты с моками моделей проверяют контракт, но не реальную доступность GPU-сервисов. Для проверки интеграции отдельно прогоняйте короткий и длинный голосовой ответ в браузере и сверяйте сетевой статус; проверка `/health` не заменяет это.

Общий workflow `.github/workflows/ci.yaml` запускается на каждом PR и push в ветку. Job `detect-changes` на Bash определяет изменённые сервисы и выдаёт флаги `backend`/`frontend`. Отдельные jobs напрямую вызывают reusable backend/frontend workflows и выполняются параллельно, когда выбраны оба сервиса. Для PR учитываются все изменения относительно merge base; для push — изменения между предыдущим и новым коммитами. Изменения `.github/**`, `api/**`, `docker-compose*.yaml`, `services/postgresql/**`, `services/caddy/**`, `prod.sh`, `dev.sh` и `.env*.example` запускают оба сервиса; новая ветка также проверяется целиком. При изменениях только документации сервисные jobs пропускаются. Отдельный job `compose` на каждом запуске проверяет общий dev-стек со Swagger и без него, а также четыре локальных Compose; он также проверяет синтаксис `prod.sh` и `dev.sh`. Его результат входит в обязательный `ci-passed`.

Итоговая проверка `CI passed` проходит, только если определение сервисов успешно и все выбранные пайплайны завершились успешно, либо список сервисов пуст. Для защиты `master` создайте активный Ruleset в GitHub Settings → Rules → Rulesets: выберите ветку `master`, включите **Require a pull request before merging** и **Require status checks to pass**, добавьте **CI passed** как обязательную проверку и оставьте Bypass list пустым. Проверка появится в списке после первого запуска нового workflow. Старые отдельные backend/frontend checks не нужно оставлять обязательными: теперь они запускаются выборочно. Само изменение workflow не включает защиту ветки в GitHub.

Для нового сервиса добавьте его workflow с `workflow_call`, флаг в `detect-changes`, условный job с прямым вызовом workflow и проверку результата в `ci-passed` (зависимость `needs`, переменные окружения и вызов `check_service`). Если сервис зависит от общих файлов или другого сервиса, включите эти пути в правила определения изменений.

## 9. Безопасность и доступ

Auth реализован через `Secure; HttpOnly; SameSite=Lax` cookies. Access действует до 15 минут, auth-сессия — до 30 суток; refresh ротируется, replay старого refresh отзывает сессию. Роли: саморегистрация создаёт только `student`, `admin` назначается вручную. Студент не должен получить чужие расшифровки/сессии, закрытые критерии и черновики. Пароли и токены не логируются. Полное описание — [documents/auth.md](documents/auth.md).

В разработке модели могут быть на внутреннем IP, но браузер вызывает только HTTPS приложения. Секреты провайдеров и `BACKEND_DATABASE_URL` остаются на backend; переменные `VITE_*` публичны. Для корпоративного доступа на IP нужен сертификат с IP в SAN и доверенная CA. Любые решения по срокам хранения **аудио, расшифровок, результатов оценки и персональных данных** требуют явного согласования; действующий контракт срок хранения не задаёт.

| Длина записи | Пользователь свободно объясняет ответ; публичный API ограничивает размер, не время. | STT `/transcribe` автоматически использует longform после 25 секунд; нужны VAD-веса и зависимости. | Проверить длинный WebM из браузера на развёрнутом сервисе и согласовать пределы/таймауты. |
| Ошибка распознавания | UI должен дать понятную причину и безопасный повтор записи. | Прототип объединяет большинство ошибок в «Не удалось распознать ответ». | Показывать различимые состояния по кодам API, не записывая технический сбой как учебный ноль. |

## 11. Что не считать согласованным

- Для текущего прототипа оценки настроена `gpt-oss-120b`; выбор модели и промпта для целевого MVP, провайдер эмбеддингов, формат индекса и показатели качества/задержки ещё требуют оценки. Прототипная интеграция не закрепляет их как требования к полному MVP.
- Долгие голосовые ответы обрабатываются `/transcribe` через longform; работоспособность зависит от VAD-весов, зависимостей и таймаутов развёрнутого сервиса.
- Способ подготовки рубрик из четырёх входов не следует подменять автоматической генерацией заданий. Если понадобится автоматическое составление рубрик, отдельно определите границы, проверку преподавателем и версионирование.
- Срок хранения исходного аудио, нормативная политика по данным и стратегия удаления ещё требуют решения.
- Ранние концепции «свободная беседа по любой теме», «пять вопросов за десять минут», «одно задание на каждую составляющую всей дисциплины» и отдельная тренировочная сессия **не являются текущим сценарием MVP**.

## 12. Правила работы для следующего разработчика или ИИ-агента

1. Перед изменением найдите слой ответственности: `services/frontend`, `services/backend`, `api` или `documents`. Сверьте текущий код с нужным этапным контрактом; не объявляйте план уже готовой функцией.
2. Для учебных правил сначала читайте [сценарий](documents/voice-trainer-scenarios.md), для HTTP — нужный [OpenAPI этапа](api/README.md), для текущего поведения — код и [генерируемый контракт backend](services/backend/backend.api.yaml). `CONTEXT.md` задаёт термины. Методический документ — источник требований к качеству, не runtime-спецификация.
3. При конфликте требований явно запишите: что реализовано, что ожидается и какое решение нужно. Не меняйте молча число заданий, расчёт балла, условия ветвления, состав тренировки или срок MVP.
4. Сохраняйте инварианты: готовые задания, два формата ответа, один `Session.id`, 7 основных и отдельные базовые, балл только по основным, тренировка на **других** заданиях по неподтверждённым ОР, отсутствие рекурсивной ветки и досрочного завершения.
5. Не направляйте браузер прямо к внутренним STT/TTS/LLM и не кладите ключи в `VITE_*`. Проверяйте фактические env запущенного контейнера, а не одни лишь примеры настройки.
6. Реальные интеграционные ошибки разбирайте по HTTP статусу и телу ответа. UI может показывать общую фразу для разных причин. Не делайте вывод о работоспособности всего сценария по одному успешному `curl` к TTS или `/health`.
7. Изменения API синхронизируйте с кодом, тестами, `services/backend/backend.api.yaml` и актуальным этапным контрактом. Правки бизнес-правил обновляйте в `documents/voice-trainer-scenarios.md` и здесь.
8. Для frontend следуйте [локальному AGENTS.md](services/frontend/AGENTS.md). Для backend сохраняйте границы feature/application/infrastructure и выполняйте релевантные проверки. Для документации проверяйте ссылки и отсутствие противоречий.
