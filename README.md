# Голосовой AI-репетитор

Студент отвечает голосом на задания карты компетенций. Продукт предусматривает диагностику, оценку ответов и тренировку по проверенным пробелам. Состояние проекта: 7 октября 2026.

## Текущая реализация

| Часть | Состояние |
| --- | --- |
| Backend | Go: auth с cookies, STT/TTS, импорт карты CSV/XLSX, чтение карты и банка, прототипная оценка без сохранения результата. |
| LLM-генерация | Отдельный `taskgen` создаёт и сохраняет задания. Импорт текстовых материалов и PostgreSQL FTS реализованы. |
| Frontend | Семь фиксированных mock-заданий; прогресс в памяти вкладки. В режиме real auth, STT/TTS и прототипная оценка используют backend. |
| Варианты и прохождение | Сборка, хранение и HTTP-доступ к вариантам ещё не реализованы. В БД есть заготовки учебных сессий, выдач и ответов. |
| Инфраструктура | PostgreSQL, Caddy HTTPS и Swagger UI через Docker Compose. |

## Согласованное видение

Источник — текущая карта «Введение в ML». Формат сохраняется; преподаватель добавляет полные задания и включает больше ОР в тест. Сборка варианта не требует ручных связей между ОР или дополнительных документов.

Вариант строится по всей карте без выбора темы:

- Компетенция включается, если минимум три разных ОР имеют TRUE в «Что должно войти в тест» и хотя бы одно готовое задание каждый. Остальные компетенции пропускаются с причиной.
- На компетенцию выбираются основной и два базовых задания трёх разных ОР этой компетенции.
- Основной ОР — максимум `ранг Блума + важность`; при равной сумме приоритет у большей важности, при полном равенстве — порядок источника.
- Случайность применяется только к выбору конкретного задания из пула того же выбранного ОР. Остальные решения детерминированы; seed не нужен.
- Вариант сохраняет выбранные задания, их профили, порядок и пропуски в PostgreSQL. Чтение использует снимки и работает после переимпорта карты.

Планируемый модуль `internal/features/variantgen` отвечает за сборку, сохранение и чтение. Приём ответов, грейдинг, прохождение и тренировка реализуются другим разработчиком. Действующие `taskgen` и прототипное assessment сохраняются. Старые данные разработки переносить не требуется.

В [описании алгоритма](documents/Алгоритм_составления_варианта.md) предложен порядок выбора базовых: Блум по возрастанию, важность по убыванию, затем источник; строго меньший Блум не требуется.

## Термины

| Термин | Значение |
| --- | --- |
| Компетенция | Верхний учебный узел карты; включается в вариант после фильтра достаточности заданий. |
| Составляющая | Действие внутри компетенции, объединяющее ОР. |
| Образовательный результат (ОР) | Проверяемое действие студента. Принадлежит одной составляющей, может содержать несколько заданий. |
| ОС | Учебное содержание из колонки «ОС», связь 1:1 с ОР; значение может отсутствовать. |
| Задание | Вопрос, необязательные варианты, голосовая инструкция и эталон. Колонка «Задание N» не задаёт роль или сложность. |
| Профиль задания | Компетенция, составляющая, ОР и свойства карты: Блум, ALDs, важность, TRUE/FALSE, ОС, уровень темы и связи РПД. |
| Аналоги | Для сборки — готовые задания одного ОР с одинаковыми унаследованными свойствами. Номер колонки сам по себе не подтверждает эквивалентность вопросов. |
| Вариант | Сохранённый план: основной и два базовых на каждую включённую компетенцию, снимки заданий и список пропусков. |
| Выдача (assignment) | Задание, предъявленное студенту при прохождении. Позиция варианта и выдача имеют разные назначения. |
| Учебная сессия | Прохождение варианта с ответами и результатами; отличается от auth-сессии с cookies. |
| Пробел | Проверенный ОР, владение которым не подтверждено ответом. Непроверенный ОР не объявляется пробелом. |

В текущем источнике нет дерева дочерних ОР или отдельной сущности темы.

Общие учебные правила: основной оценивается в 0/1/2, базовый — в 0/1. Диагностическая сумма учитывает только основные задания, максимум 2N для N включённых компетенций. Тренировка не изменяет исходную диагностику. Эти правила реализуются модулем прохождения.

## Карта и данные

Текущий CSV: 13 компетенций, 17 составляющих, 101 ОР, 18 ОР с TRUE, 13 готовых заданий и 41 неполная ячейка задания. Покрытие варианта определяется отдельно для каждой компетенции по числу готовых TRUE-ОР.

В ML-формате полная ячейка содержит `Экран:`, `Голосовая инструкция:` и `Ответ:`; варианты необязательны. Поддерживается произвольное число колонок `Задание N`. Неполные ячейки сохраняются как источник с предупреждениями и не становятся заданиями. Старый парный формат CSV поддержан текущим кодом.

Импорт атомарно заменяет активную карту и задания, выдаёт новые ID и ревизию. Сохранение исторических вариантов снимками входит в план variantgen. Текущая схема описана в [PLAN.md](PLAN.md).

## Запуск

```bash
cp .env.example .env
# Задайте пароль БД и режимы API.
./dev.sh -d
```

Локально нужны Docker Compose и mkcert. Приложение: https://localhost:8443, публичный API: `/api/v1`, health: `/api/v1/health`. Swagger доступен на `/docs/` при `COMPOSE_PROFILES=swagger`.

Для сервера: `.env.prod.example` → `.env`, готовые `certs/server.pem`/`server-key.pem`, сеть `ai-tutor_default`, затем `./prod.sh`. Dev-стек и серверные Compose используют общие имена сети и volumes; одновременно их не запускают.

- `VITE_API_MODE=real` включает HTTP auth/voice/assessment; остальные значения — моки. Учебная сессия пока моковая в обоих режимах. В dev VITE_* передаются контейнеру; после изменения .env пересоздайте frontend. В production значения применяются при сборке.
- `BACKEND_API_MODE=mock` заменяет модели, auth и БД настоящие. В real обязательны STT/TTS и настройки assessment/taskgen из `.env.example`.
- STT принимает WAV/Ogg/WebM до 25 МиБ и возвращает сохранённую расшифровку. TTS принимает до 500 символов и возвращает WAV. Длинным записям GigaAM нужны longform/VAD зависимости на сервере модели.
- PostgreSQL хранит данные в volume. `down` их сохраняет; `down -v` удаляет. Пересоздание БД для новой схемы относится к будущей реализации variantgen.

### Live reload в Docker

Корневой `./dev.sh -d` запускает dev-образы: Vite HMR для frontend и Air для backend. Исходники подключены через bind mount; polling включён для Docker Desktop. HTTPS и HMR WebSocket проходят через Caddy.

Vite подхватывает изменения frontend. Air пересобирает и перезапускает API при изменениях Go, SQL, go.mod/go.sum; SQLC-код требует отдельной генерации. node_modules, модули Go, кеш сборки и dev-бинарник хранятся в отдельных volumes.

- Изменение .env: `docker compose up -d api frontend` для пересоздания затронутых контейнеров.
- Изменение package-lock.json: `docker compose restart frontend`; при старте dev-контейнер выполняет npm ci.
- Изменение Dockerfile: `docker compose up -d --build api frontend`.
- Изменение OpenAPI: `docker compose up -d --force-recreate swagger`; Swagger читает api/openapi.yaml.

Локальные Compose сервисов, используемые prod.sh, запускают готовый backend-бинарник и frontend с nginx.

## Проверки перед PR

Для разработки вне Docker нужны Go версии из services/backend/go.mod и Node.js 22 с npm.

```bash
# Из services/frontend:
npm ci
npm run lint
npm run typecheck
npm test -- --run
npm run build

# Из services/backend:
go test -race ./... -count=1
go vet ./...
go build -o bin/api ./cmd/api
```

Backend DB-тесты требуют TEST_DATABASE_URL; без него пропускаются. Генерация OpenAPI и пример тестовой БД — в [backend README](services/backend/README.md). CI проверяет затронутые сервисы и Compose; для backend поднимает PostgreSQL.
