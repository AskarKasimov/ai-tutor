# Голосовой тренажёр v0: диагностика и тренировка

## Назначение

Студент проходит короткую диагностику университетского курса (примерно одного семестра), получает обратную связь по компонентам РПД и, если обнаружены трудности, выполняет тренировку на более простых заданиях. Задания, образовательные результаты (ОР), дерево ОР и критерии оценки заранее задаёт преподаватель. Система не генерирует задания для v0.

Этот документ фиксирует поведение продукта и данные, на которых позднее будет основан публичный HTTP-контракт. Он не задаёт имена ручек, транспорт для длительных операций или формат авторизации.

## Участники и исходные данные

- **Студент** выбирает курс, проходит диагностику и назначенную тренировку. Каждый ответ — отдельная голосовая запись на конкретное задание.
- **Преподаватель** готовит компоненты РПД, дерево ОР, пул диагностических ОР и заданий, более простые задания для тренировки и критерии оценки. Критерии содержат правила, по которым LLM должна вынести вердикт и объяснить его.
- **Система** выбирает задания, распознаёт речь, передаёт ответ и критерии на оценку LLM, сохраняет результаты и формирует обратную связь.

Одна компонента РПД содержит доступный для диагностики пул ОР. Каждый такой ОР связан хотя бы с одним диагностическим заданием. Для проблемной компоненты преподаватель заранее определяет более простые ОР и задания, пригодные для тренировки. Связь «диагностический ОР → более простые ОР» хранится в дереве преподавателя, а не выводится LLM из текста задания.

## Сценарий 1: диагностика

1. Студент запускает диагностику выбранного курса.
2. Для **каждой компоненты РПД** система случайно выбирает **один ОР** из диагностического пула преподавателя, а для него — **одно случайное задание**. Число диагностических заданий равно числу компонент РПД курса. Выбранный набор сохраняется на всё прохождение; повторное чтение не меняет задания.
3. Студент получает задания и сдаёт на каждое одну голосовую запись. Ответ всегда относится к конкретному выданному заданию.
4. Система распознаёт запись. Студент не сверяет и не подтверждает расшифровку. Распознанный текст вместе с версией критериев задания передаётся LLM для оценки.
5. LLM возвращает структурированный вердикт по критериям, объяснение и признак наличия трудностей по этой компоненте. Решение принимается по правилам, которые преподаватель включил в критерии. Система сохраняет использованные критерии и результат проверки, чтобы фидбек можно было объяснить после прохождения.
6. Когда оценены все диагностические задания, система показывает итоговый фидбек по каждой компоненте РПД. Для компонент с трудностями она назначает тренировку. Если трудностей нет, диагностика заканчивается без тренировки.

Сбой распознавания или оценки не является вердиктом о знаниях студента. Такой ответ остаётся без оценки; диагностика не завершается, пока по каждому заданию не получен результат или пока сбой не устранён.

## Сценарий 2: тренировка

1. Тренировка создаётся только по итогам диагностики, в которой хотя бы одна компонента отмечена как проблемная.
2. По **каждой проблемной компоненте РПД** система назначает **два разных более простых задания** из заранее подготовленного преподавателем дерева ОР и пула заданий. Задания тренировки связаны с соответствующей компонентой и результатом диагностики, который стал причиной назначения.
3. Студент сдаёт отдельную голосовую запись на каждое задание. Распознавание и проверка LLM работают так же, как в диагностике: без подтверждения расшифровки студентом, по критериям преподавателя.
4. После проверки всех тренировочных ответов студент получает итоговый фидбек. Тренировка завершается. Автоматического повторного прохождения диагностики и бесконечного цикла заданий в v0 нет.

## Состояния прохождения

Диагностика и тренировка — разные типы прохождения с общей логикой ответа на задание.

| Состояние прохождения | Значение |
| --- | --- |
| `in_progress` | Задания выданы; студент сдаёт ответы, либо часть ответов обрабатывается. |
| `evaluating` | Все ответы получены; остаётся распознавание, оценка или сбор итогового фидбека. |
| `completed` | Все ответы оценены, итоговый фидбек доступен. |

У ответа на задание отдельно фиксируются `awaiting_submission`, `processing`, `evaluated` и `processing_failed`. Неуспешная техническая обработка позволяет повторно отправить запись для **того же** задания; она не подменяет учебный вердикт. Повторная отправка уже оценённого ответа не меняет завершённый результат.

Переход к тренировке возможен только из завершённой диагностики. Назначение двух заданий на каждую проблемную компоненту выполняется один раз; повторное чтение результата не создаёт новые задания.

## Данные, которые должны сохраняться

| Сущность | Существенные данные |
| --- | --- |
| Курс и компонента РПД | Идентификаторы, название и порядок компонент курса. |
| ОР | Идентификатор, компонента, место в дереве, допуск к диагностике или тренировке. |
| Задание | Идентификатор, ОР, текст задания, критерии преподавателя и их версия. |
| Диагностика | Студент, курс, выбранные пары «компонента → ОР → задание», состояние, время создания и завершения. |
| Тренировка | Исходная диагностика, проблемные компоненты, назначенные два задания на компоненту, состояние. |
| Ответ | Прохождение, задание, ссылка на запись, распознанный текст для внутренней обработки, состояние обработки. |
| Оценка | Версия критериев, вердикт LLM, результаты по критериям, объяснение и признак трудностей. |
| Фидбек | Итог по компонентам и объяснение для студента, составленные из сохранённых оценок. |

Для внешнего студенческого интерфейса расшифровка не является шагом согласования. Хранение расшифровки и аудио нужно для обработки и разбора ошибок; сроки хранения и доступ к ним определяются отдельно до реализации.

## Границы модулей и поток данных

Модуль **прохождений** выбирает и закрепляет задания, управляет состояниями и решает, когда результат готов. Модуль **каталога заданий** отдаёт опубликованные преподавателем компоненты, ОР, связи дерева, задания и версии критериев. Модуль **проверки ответа** принимает запись для выданного задания, получает расшифровку от GigaAM и вердикт LLM по критериям. Модуль **фидбека** собирает сохранённые оценки по компонентам. Способ предъявления фидбека студенту не влияет на правила оценки и назначения тренировки.

Для моделирования прохождений есть два разумных подхода: один универсальный тип с режимом `diagnostic | training` либо два отдельных типа со связью «тренировка назначена диагностикой». Для v0 предлагаются **два типа прохождения** и общий внутренний ответ на задание: у них разные правила назначения и завершения, а клиенту не нужно разбирать сочетания полей, допустимых только в одном режиме.

## Ошибки и инварианты

- До публикации курса проверяется, что у каждой компоненты есть хотя бы один диагностический ОР с заданием и достаточно подготовленных более простых заданий для возможной тренировки. Неполная конфигурация не запускается для студента.
- Запись привязывается только к заданию, выданному в этом прохождении. Нельзя отправить ответ на произвольное задание из каталога.
- Неизвестный формат записи, пустая запись, сбой распознавания и сбой LLM показываются как технические ошибки обработки. Они не превращаются в отрицательную оценку.
- Если LLM вернула результат вне ожидаемой структуры или без вердикта по правилам преподавателя, система не считает ответ оценённым и переводит обработку в `processing_failed`.
- Завершённая диагностика и тренировка неизменяемы; повторный запрос их результата возвращает сохранённый фидбек.

## Проверка сценария

При реализации нужно проверить на уровне контрактов: ровно одно диагностическое задание на компоненту; выбор только из опубликованного пула преподавателя; неизменность выданного набора; два разных тренировочных задания на каждую проблемную компоненту; отсутствие тренировки при успешной диагностике; завершение только после оценки всех ответов; отделение технического сбоя от учебного вердикта; отсутствие шага подтверждения расшифровки.
