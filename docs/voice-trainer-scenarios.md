# Голосовой тренажёр v0: диагностика и тренировка

## Назначение

Студент проходит короткую диагностику университетского курса (примерно одного семестра), получает обратную связь по составляющим РПД и, если обнаружены трудности, выполняет тренировку на более простых заданиях. Задания, образовательные результаты (ОР), дерево ОР и критерии оценки заранее задаёт преподаватель. Система не генерирует задания для v0.

Этот документ фиксирует поведение продукта и данные, на которых позднее будет основан публичный HTTP-контракт. Он не задаёт имена ручек, транспорт для длительных операций или формат авторизации.

## Участники и исходные данные

- **Студент** выбирает курс, проходит диагностику и назначенную тренировку. Каждый ответ — отдельная голосовая запись на конкретное задание.
- **Преподаватель** через форму создаёт и редактирует по одной записи составляющие РПД, дерево ОР, пул диагностических ОР и заданий, более простые задания для тренировки и критерии оценки. Критерии содержат правила, по которым LLM должна вынести вердикт и объяснить его.
- **Система** выбирает задания, распознаёт речь, передаёт ответ и критерии на оценку LLM, сохраняет результаты и формирует обратную связь.

Одна составляющая РПД содержит доступный для диагностики пул ОР. Каждый такой ОР связан хотя бы с одним диагностическим заданием. Для проблемной составляющей система берёт более простые задания из **дочерних ОР** того диагностического ОР, на котором возникли трудности. Эту связь задаёт преподаватель в дереве; LLM не выводит её из текста задания.

## Сценарий 1: диагностика

1. Студент запускает диагностику выбранного курса.
2. Для **каждой составляющей РПД** система случайно выбирает **один ОР** из диагностического пула преподавателя, а для него — **одно случайное задание**. Число диагностических заданий равно числу составляющих РПД курса. Выбранный набор сохраняется на всё прохождение; повторное чтение не меняет задания.
3. Студент получает задания и сдаёт на каждое одну голосовую запись. Ответ всегда относится к конкретному выданному заданию.
4. Система распознаёт запись. Студент не сверяет и не подтверждает расшифровку. Распознанный текст вместе с версией критериев задания передаётся LLM для оценки.
5. LLM возвращает структурированный вердикт по критериям, объяснение и признак наличия трудностей по этой составляющей. Решение принимается по правилам, которые преподаватель включил в критерии. Система сохраняет использованные критерии и результат проверки, чтобы фидбек можно было объяснить после прохождения.
6. Когда оценены все диагностические задания, система показывает итоговый фидбек по каждой составляющей РПД. Для составляющих с трудностями она назначает тренировку. Если трудностей нет, диагностика заканчивается без тренировки.

Сбой распознавания или оценки не является вердиктом о знаниях студента. Такой ответ остаётся без оценки; диагностика не завершается, пока по каждому заданию не получен результат или пока сбой не устранён.

## Сценарий 2: тренировка

1. Тренировка создаётся только по итогам диагностики, в которой хотя бы одна составляющая отмечена как проблемная.
2. По **каждой проблемной составляющей РПД** система назначает **два разных более простых задания** из дочерних ОР неудачного диагностического ОР. Задания тренировки связаны с соответствующей составляющей и результатом диагностики, который стал причиной назначения.
3. Студент сдаёт отдельную голосовую запись на каждое задание. Распознавание и проверка LLM работают так же, как в диагностике: без подтверждения расшифровки студентом, по критериям преподавателя.
4. После проверки всех тренировочных ответов студент получает итоговый фидбек. Тренировка завершается. Автоматического повторного прохождения диагностики и бесконечного цикла заданий в v0 нет.

## Состояния прохождения

Диагностика и тренировка — разные типы прохождения с общей логикой ответа на задание.

| Состояние прохождения | Значение |
| --- | --- |
| `in_progress` | Задания выданы; студент сдаёт ответы, либо часть ответов обрабатывается. |
| `evaluating` | Все ответы получены; остаётся распознавание, оценка или сбор итогового фидбека. |
| `completed` | Все ответы оценены, итоговый фидбек доступен. |

У ответа на задание отдельно фиксируются `awaiting_submission`, `processing`, `evaluated` и `processing_failed`. Неуспешная техническая обработка позволяет повторно отправить запись для **того же** задания; она не подменяет учебный вердикт. Повторная отправка уже оценённого ответа не меняет завершённый результат.

Переход к тренировке возможен только из завершённой диагностики. Назначение двух заданий на каждую проблемную составляющую выполняется один раз; повторное чтение результата не создаёт новые задания.

## Данные, которые должны сохраняться

| Сущность | Существенные данные |
| --- | --- |
| Курс и составляющая РПД | Идентификаторы, название и порядок составляющих курса. |
| ОР | Идентификатор, составляющая, место в дереве, допуск к диагностике или тренировке. |
| Задание | Идентификатор, ОР, текст задания, критерии преподавателя и их версия. |
| Диагностика | Студент, курс, выбранные пары «составляющая → ОР → задание», состояние, время создания и завершения. |
| Тренировка | Исходная диагностика, проблемные составляющие, назначенные два задания на составляющую, состояние. |
| Ответ | Прохождение, задание, ссылка на запись, распознанный текст для внутренней обработки, состояние обработки. |
| Оценка | Версия критериев, вердикт LLM, результаты по критериям, объяснение и признак трудностей. |
| Фидбек | Итог по составляющим и объяснение для студента, составленные из сохранённых оценок. |

Для внешнего студенческого интерфейса расшифровка не является шагом согласования. Хранение расшифровки и аудио нужно для обработки и разбора ошибок; сроки хранения и доступ к ним определяются отдельно до реализации.

## Границы модулей и поток данных

Модуль **прохождений** выбирает и закрепляет задания, управляет состояниями и решает, когда результат готов. Модуль **каталога заданий** отдаёт опубликованные преподавателем составляющие, ОР, связи дерева, задания и версии критериев. Модуль **проверки ответа** принимает запись для выданного задания, получает расшифровку от GigaAM и вердикт LLM по критериям. Модуль **фидбека** собирает сохранённые оценки по составляющим. Способ предъявления фидбека студенту не влияет на правила оценки и назначения тренировки.

Для моделирования прохождений есть два разумных подхода: один универсальный тип с режимом `diagnostic | training` либо два отдельных типа со связью «тренировка назначена диагностикой». Для v0 предлагаются **два типа прохождения** и общий внутренний ответ на задание: у них разные правила назначения и завершения, а клиенту не нужно разбирать сочетания полей, допустимых только в одном режиме.

## Решения HTTP-контракта

Контракт находится в [openapi.yaml](../openapi.yaml). Диагностика и тренировка представлены отдельными ресурсами; выданное задание (`assignment`) отличается от задания в каталоге (`task`). Одна общая ручка принимает голосовой ответ на выданное задание в обоих режимах.

| Группа | Основные операции |
| --- | --- |
| Каталог студента | Список опубликованных курсов и составляющие выбранного курса. |
| Диагностика | Запуск, история, задания и итог прохождения. |
| Тренировка | Список назначенных тренировок, задания и итог прохождения. Создаётся системой после диагностики. |
| Ответы | Загрузка одной записи через `multipart/form-data`, затем чтение состояния обработки. |
| Преподаватель | Создание курса, чтение черновика, поштучное создание, изменение и удаление составляющих, ОР и заданий; публикация курса. |

Загрузка записи возвращает `202 Accepted`; клиент получает состояние обработки отдельным запросом. Проверка всего прохождения завершается автоматически после получения и оценки всех ответов. Индивидуальные оценки и итоговый фидбек открываются студенту после завершения прохождения. Тренировка закрепляется до завершения диагностики, поэтому готовый результат уже содержит её идентификатор.

Преподаватель правит черновик курса. Публикация проверяет его полноту и сохраняет неизменяемую версию. Первая правка после публикации открывает следующую черновую версию; студенты продолжают получать последнюю опубликованную. Прохождение хранит номер версии, поэтому последующие изменения заданий и критериев не меняют уже выданные задания. Удаление составляющей или ОР с вложенными записями отклоняется; преподаватель сначала удаляет вложенные записи.

Критерии задания в контракте представлены списком с устойчивыми ключами и отдельным текстовым правилом итогового вердикта. LLM возвращает результат по каждому ключу и вердикт, применяя правило преподавателя. Bearer-токен определяет пользователя и его права; выдача токена относится к системе авторизации. Студент не передаёт свой идентификатор в теле запроса.

В v0 контракт принимает WAV, Ogg/Opus и WebM/Opus до 25 МиБ. Он не устанавливает предел длительности записи. Текущий внутренний адаптер GigaAM принимает только короткие записи до 25 секунд: реализация общего API должна добавить обработку длинных ответов через long-form распознавание или разбиение записи. Это необходимая работа для соответствия контракту, а не реализованная возможность текущего сервиса.

## Ошибки и инварианты

- До публикации курса проверяется, что у каждой составляющей есть хотя бы один диагностический ОР с заданием, а у каждого такого ОР — не менее двух разных тренировочных заданий в дочерних ОР. Неполная конфигурация не запускается для студента.
- Запись привязывается только к заданию, выданному в этом прохождении. Нельзя отправить ответ на произвольное задание из каталога.
- Неизвестный формат записи, пустая запись, сбой распознавания и сбой LLM показываются как технические ошибки обработки. Они не превращаются в отрицательную оценку.
- Если LLM вернула результат вне ожидаемой структуры или без вердикта по правилам преподавателя, система не считает ответ оценённым и переводит обработку в `processing_failed`.
- Завершённая диагностика и тренировка неизменяемы; повторный запрос их результата возвращает сохранённый фидбек.

## Проверка сценария

При реализации нужно проверить на уровне контрактов: ровно одно диагностическое задание на составляющую; выбор только из опубликованного пула преподавателя; неизменность выданного набора; два разных тренировочных задания на каждую проблемную составляющую; отсутствие тренировки при успешной диагностике; завершение только после оценки всех ответов; отделение технического сбоя от учебного вердикта; отсутствие шага подтверждения расшифровки.
