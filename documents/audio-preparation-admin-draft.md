# Прогресс фоновой озвучки в админке

Статус: реализация одобрена владельцем задачи 04.11.2026. Историческая пометка о приостановке ниже снята этим решением. Подготовлено после коммита `b6a45a23` со статусами подготовки курса.

## Пользовательская задача

Внутри административного экрана курса видеть, сколько озвучки уже подготовлено, сколько ожидает и сколько выполняется или повторяется после ошибок. Показать это отдельно для экзамена и обучения, рядом с существующими блоками подготовки. Готовность учебного содержания и готовность аудио — независимые показатели: курс доступен по действующим правилам, даже когда аудио ещё готовится.

Пример: «Озвучка вопросов: готово 82 из 120 (68%)», ниже — «В очереди: 35 · Готовится: 1 · Ожидает повтора: 2».

Первый объём: подробный блок в двух направлениях одного курса. Общую страницу мониторинга всех очередей, точное место в очереди, управление приоритетами, массовую регенерацию и прогноз времени вынести за границы этой задачи. В списке курсов пока сохранить существующие статусы содержания.

## Что существует сейчас

| Направление | Очередь | Что сохраняется в S3 | Как узнать прогресс |
| --- | --- | --- | --- |
| Экзамен | `geek.Warmer`, одна очередь в памяти процесса | Полный WAV нормализованного текста, ключ зависит от текста и текущей `voiceName` | Сейчас есть только глобальный `Pending()`, нет общего total, completed и привязки к курсу |
| Обучение | PostgreSQL `learning_audio_assets`, leases и retries | WAV голосовой инструкции задания, ключ зависит от asset ID | Можно агрегировать сохранённые статусы активной ревизии карты |

Источники: [Warmer](../services/backend/internal/features/geek/application/warm.go), [SpeechCache](../services/backend/internal/features/geek/application/speech.go), [инициализация и voiceName](../services/backend/internal/app/app.go), [учебный worker](../services/backend/internal/features/taskaudio/application/worker.go), [SQL очереди](../services/backend/internal/shared/postgres/queries/learning_task_audio.sql).

Экзаменационная очередь получает вопросы и заранее подготовленные переформулировки всех вариантов, до подтверждения публикации графа. На старте backend туда повторно ставятся тексты опубликованных графов. Кроме них очередь содержит общие фиксированные реплики. Глобальную длину очереди нельзя показывать как остаток конкретного курса. [Постановка перед публикацией](../services/backend/internal/features/coursegraph/application/worker.go), [фиксированные реплики](../services/backend/internal/features/geek/infrastructure/llm/transitions.go).

Успех Geek SpeechCache означает успешное чтение существующего объекта либо успешный синтез всех частей, объединение WAV и запись в S3. Начало TTS и окончание отдельной части не означают готовность записи. Динамические ответы студентам и персонализированные реплики не входят в total курса.

Учебный worker ставит `ready` после проверки/повторного использования объекта или после успешной записи нового WAV. Он может скопировать озвучку такой же инструкции из другой записи, поэтому число готовых assets не равно числу фактических запросов TTS. [Worker](../services/backend/internal/features/taskaudio/application/worker.go).

## Предлагаемый интерфейс

Блок «Озвучка вопросов» в экзаменационном направлении; «Озвучка инструкций» в учебном. Подпись и стандартный progress bar показывают `ready / total`, процент — `floor(100 * ready / total)`. При total=0 процент не показывать, вместо него «Нет текстов для предварительной озвучки».

Состояния блока:

- «Проверяем готовую озвучку» — экзаменационная статистика восстанавливается после старта/смены версии.
- «Озвучка в очереди» — есть ожидающие записи, фактически выполняемых нет.
- «Идёт подготовка озвучки» — есть выполняемые записи.
- «Ожидает повторной попытки» — остались только автоматические повторы.
- «Часть озвучки не подготовлена» — есть окончательные ошибки или отсутствующие ожидаемые assets, а активной работы нет.
- «Озвучка готова» — total>0 и ready=total.
- «Не удалось загрузить прогресс» — ошибка запроса статистики; это не ошибка синтеза.

Показывать все ненулевые счётчики, даже если основное состояние описывает выполняемую работу. Например, ошибка одной записи не скрывается на фоне подготовки другой. Цвет и подпись не должны быть единственным различием состояний. Все строки через i18n; адаптивность 360/600/1000px и обе темы.

Остаток — `total - ready`, а не глобальная длина очереди. Нельзя выдавать время ожидания backoff за ETA завершения курса. Не добавлять управление очередями в кнопки мониторинга.

## Единицы и версии

### Экзамен

Total — множество уникальных ключей SpeechCache для `TopicQuestions` текущего опубликованного графа курса. Включить вопросы и переформулировки всех вариантов; убрать пустые тексты, нормализовать точно как `SpeechCache.Part`, дедуплицировать по тому же ключу. Длинный текст, разбитый для TTS на несколько частей и склеенный в один WAV, считается одной записью.

Один ключ, используемый в нескольких курсах, учитывается один раз в каждом курсе; успешное событие обновляет все связанные наборы. Нельзя суммировать totals разных курсов и объявлять это длиной общей очереди.

До первой публикации показать «Озвучка будет учтена после публикации графа». Синтез уже может идти в существующей очереди, но незавершённый/отклонённый граф не является опубликованной версией курса. При пересборке показывать аудио старого опубликованного графа с пояснением «Для текущей опубликованной версии»; переключать набор только после принятой публикации. Устаревшие callbacks не увеличивают total/ready новой версии.

Идентичность набора включает опубликованную версию и текущую `voiceName` (seed/cfg/steps/style). Смена настроек голоса создаёт другие ключи по действующему правилу; старое аудио не делает новый набор готовым. Не менять правило генерации ключей в рамках мониторинга.

### Обучение

Total — ожидаемые уникальные аудиозаписи задач активной ревизии учебной карты курса с инструкциями, допустимыми для озвучки по `audioasset.CanSynthesize`. Не ограничивать только ОР, отобранными для диагностики: очередь импортирует и другие задания банка.

Одна запись = asset голосовой инструкции, не число слов/частей/попыток. Старые ревизии, сохранённые сессии и тренировки не увеличивают total текущего курса. При отсутствующей обязательной ссылке/asset либо неожиданном cancelled у текущей задачи показать «Не подготовлено», не уменьшать total до искусственных 100%. Пустые/невалидные инструкции не входят в total; при необходимости показать отдельное информационное число пропущенных инструкций.

Ревизия меняется атомарно с импортом. Нельзя смешивать denominator старой карты и ready новой в одном ответе. Учебный ключ и reuse сейчас не учитывают voiceName; мониторинг описывает готовность существующих assets, а не соответствие текущему голосу. Миграция ключей и переозвучка при смене настроек — отдельная задача.

## Учёт состояний

Канонические непересекающиеся счётчики: `unchecked`, `queued`, `processing`, `retry_wait`, `ready`, `failed`, `unavailable`. Сумма всегда равна total; поле version обязательно для защиты от смешивания снимков.

Для экзамена `unchecked` — ещё не проверенные после восстановления ключи; `processing` включает фактическое чтение/проверку кэша или синтез с записью. Успешный cache hit или Put переводит в ready. Ошибка возвращает запись в автоматический retry; terminal failed у текущего Warmer отсутствует, поэтому для него failed=0. Не прекращать существующие бесконечные повторы ради красивого статуса ошибки. `Pending()` включает выполняемый головной элемент — нельзя прибавлять processing к нему без исключения этого элемента.

У Warmer пауза retries сейчас общая для цикла, не отдельный таймер на запись. Не придумывать per-item next_attempt_at. Минимальная инструментализация должна отличать ожидающую запись после ошибки от текущей выполняемой и от ещё не начатой. Изменение алгоритма retries не входит в задачу.

Для обучения pending, допускающий retry в будущем (`next_attempt_at > now`, после неуспешной попытки), — retry_wait; другой pending — queued. Processing с действующим lease — processing; expired lease, ожидающий reclaim, — queued, без дополнительных изменений БД из GET. Ready/failed — соответствующие счётчики. Отсутствующая запись/cancelled для ожидаемого asset — unavailable. Повторные попытки увеличивают attempts, а не total. После рестарта использовать сохранённые статусы и действующее восстановление leases. Если worker ещё не запустился из-за недоступного бакета, записи могут оставаться pending: по одному этому статусу нельзя заявлять ни работу TTS, ни установленную причину остановки.

## Восстановление экзаменационного счётчика после рестарта

Рекомендуемый вариант для первого объёма: сохранить текущую очередь в памяти, без новой таблицы. При запуске восстановить наборы из опубликованных графов, показывать проверку кэша и использовать результаты штатного чтения SpeechCache для восстановления ready. S3 сохраняет файлы между перезапусками: существующие файлы не синтезировать повторно.

Наблюдение не должно инициировать дополнительный синтез из admin GET. Восстановление запускается фоновым lifecycle, не открытием страницы. Не обходить бакет целиком и не выполнять N S3-запросов на каждый polling: GET читает уже собранный снимок. Не менять существующие дедупликацию/singleflight и очередь запросов студентов.

Владелец задачи утвердил этот вариант для реализации. Если потребуется сохранять готовые счётчики без восстановления после рестарта или обслуживать несколько backend-процессов с единым прогрессом, нужен отдельный дизайн сохранённого реестра/координации. Не изображать один локальный snapshot распределённой статистикой.

## API и архитектура

Один admin-only GET для курса: `GET /api/v1/exam/admin/subjects/{subject_id}/audio-preparation`. Роль проверяется в application, неизвестный курс — 404, student — 403, отсутствие сессии — 401.

Ответ (все числа — неотрицательные целые, timestamp — RFC3339 UTC):

```json
{
  "subject_id": "subject_123",
  "exam": {"version": "pg:0123456789abcdef|seed=1 cfg=2 steps=3 style=calm-v1", "published": true, "state": "checking", "total": 10, "unchecked": 3, "queued": 2, "processing": 1, "retry_wait": 0, "ready": 4, "failed": 0, "unavailable": 0, "observed_at": "2026-11-04T10:00:00Z"},
  "learn": {"version": "revision:12", "revision": 12, "state": "queued", "total": 7, "unchecked": 0, "queued": 2, "processing": 1, "retry_wait": 1, "ready": 2, "failed": 1, "unavailable": 0, "observed_at": "2026-11-04T10:00:00Z"}
}
```

`state` enum: `no_graph`, `checking`, `queued`, `processing`, `retry_wait`, `partial`, `ready`, `empty`. Precedence: no published graph → `no_graph`; total=0 → `empty`; unchecked>0 → `checking`; processing>0 → `processing`; queued>0 → `queued`; retry_wait>0 → `retry_wait`; failed+unavailable>0 → `partial`; ready=total → `ready`; otherwise `partial`. Thus active processing masks queued/retry/failed only for the headline, never for counters. Learning uses the same precedence except no graph is not applicable; revision 0 and total 0 → `empty`. Counts are mutually exclusive and sum to total. `failed` is reserved for terminal learning assets; exam warmer has no terminal failure, so its failed is always zero. On inconsistent internal snapshots return a server error and log the invariant violation; never normalize by dropping total.

Exam `version` combines the published graph content version (`pg:` + first eight SHA-256 bytes in hex, matching `geekgraph.Stored.Current`) and the exact `voiceName`; learning `version` is `revision:<active_revision>`. Each set contains total unique normalizable cache keys / valid task asset IDs. `observed_at` changes when a direction snapshot changes and does not assert live S3 availability.

Учебные ready — сохранённые статусы БД, не HEAD-проверка каждого объекта в момент открытия админки. Даже экзаменационный ready — последнее подтверждённое чтение/запись, а не гарантия отсутствия внешнего удаления прямо сейчас. Сбой запроса S3 не считать cache miss/готовностью; не стирать статистику при сетевой ошибке мониторинга.

Данные обучения получать одним read-only batch SQL для `subject_id`: snapshot active revision, все текущие eligible tasks (включая задачи вне ОР диагностики), `CanSynthesize` instructions, asset ID/status/attempts/next_attempt_at/lease_until. Левое соединение должно сохранять ожидаемые задачи без asset; итоговая ревизия в ответе должна совпасть с revision запроса/снимка. Не вызывать `taskaudio.Service.Metadata()` по каждому asset: этот метод повышает приоритет pending-записей, и одно открытие админки изменит порядок студенческой очереди. [Побочный эффект Metadata](../services/backend/internal/features/taskaudio/application/service.go).

Точные порты: `coursegraph/application.Repository.Published` возвращает `[]PublishedGraph{SubjectID string, Graph json.RawMessage}`; `coursegraph/application.Voices` оставляет `Prepare([]string) int` и добавляет `TrackPublished(subjectID string, graphVersion string, texts []string)`. `geek/application` владеет `ExamAudioProgress` портом с `Snapshot(subjectID string) (ExamAudioSnapshot, bool)` и `TrackPublished(...)`; `SpeechCache` владеет `Key(text string) string` (тот же trim, voiceName и SHA-256, что `Part`) и сообщает только результат завершённой проверки/Put. `Warmer` передаёт переходы `queued → processing → ready|retry_wait` в runtime registry, не меняя порядок, backoff или дедупликацию очереди. `subject/application` получает read-only интерфейсы `ExamProgressReader` и `LearningProgressReader`; общий application coordinator и repository adapters связываются в `internal/app`. Features не импортируют друг друга. Runtime registry ограничен опубликованными ключами текущих курсов; `TrackPublished` атомарно заменяет предыдущую версию курса. Callback обновляет все курсы, связанные с ключом, только если их текущая версия/key set ещё совпадают. Персонализированные тексты не регистрируются.

Успешная публикация вызывает `TrackPublished` только после `Repository.Finish` подтвердил публикацию; при старте фоновый `PrepareVoices` получает ID и данные published graphs, регистрирует наборы и запускает существующую очередь. Регистрация создаёт все записи `unchecked`; `Warmer` берёт запись, читает/синтезирует через обычный `SpeechCache.Part`, а его единый кэш-hit/Put результат помечает ready. Ошибка помечает запись `retry_wait`; следующий запуск снова делает её processing. Это позволяет проверить существующие S3 объекты штатным чтением без повторного синтеза и без дополнительного чтения из GET. Успешные записи, завершившиеся до регистрации нового графа, всё равно проверяются cache read при обычном прогреве. Набор старой опубликованной версии остаётся текущим до успешной публикации новой.

Learning batch классифицирует строку по приоритету: отсутствующая ссылка/строка либо `cancelled`/неожиданный asset → `unavailable`; valid `ready` → `ready`; `failed` → `failed`; `processing` с действующим lease → `processing`; `processing` с истёкшим lease → `queued`; `pending` с attempts>0 и next_attempt_at > captured now → `retry_wait`; другой `pending` → `queued`. Повторные строки одного asset дедуплицируются по ID. Не изменять статусы, leases, приоритеты или очередь из read path.

Frontend: endpoint adapter в `entities/subject` и query hook в `features/subject-selection`; query key `userId + subjectId`. Polling 5 секунд только на видимой смонтированной странице курса, refetch по фокусу; запрет N+1 по файлам/вопросам. После успешного изменения карты/графа инвалидировать статистику (polling также увидит принятую версию). Исходный экран содержания сохраняет собственную загрузку/ошибку; ошибка прогресса аудио не блокирует весь экран. UI размещается рядом с блоками подготовки в обоих course detail screens; все строки в i18n. График/проценты считают `floor(100*ready/total)` только при total>0. Exam no_graph показывает «Озвучка будет учтена после публикации графа», revision 0 — аналогичное состояние для карты. Stale published graph сохраняет snapshot и пояснение «Для текущей опубликованной версии» пока новая версия не принята.

## Проверки для итогового ТЗ

- Готовый файл S3 засчитывается без вызова синтезатора; запись увеличивает ready только после успешного Put.
- Ошибка TTS/записи S3 остаётся retry/failed по действующим правилам, не рисует 100%.
- Дубли одного текста, пересечение курсов и запрос студента одновременно с прогревом не дублируют работу/счётчик.
- Несколько TTS-частей одного экзаменационного текста считаются одной записью; падение одной части не считается готовностью.
- Замена/отклонение графа, старые callbacks и смена voiceName не смешивают наборы; подготовка нового графа не скрывает состояние опубликованного.
- После рестарта существующий экзаменационный кэш проходит проверку, учебные leases восстанавливаются; transient checking не выдаётся за потерю файлов.
- Учебная ревизия с pending/processing/ready/failed/cancelled и отсутствующими ожидаемыми assets; сумма счётчиков, неизменность total при retries, отсутствие старых revisions.
- Reuse инструкции из другой записи засчитывается только после готовности собственного asset; мониторинг не меняет приоритеты, не вызывает синтез и не делает S3 scan на GET.
- Empty, loading, error, partial retry, all ready, stale snapshot, auth isolation; API контракт, race tests, DB-тесты и frontend scenarios по AGENTS.

Проверки реализации: backend unit/race tests для классификатора, версий, registration/callback races и доступа; repository DB test на coherent active revision, недостающие assets и retry/lease precedence (только с `TEST_DATABASE_URL`); HTTP contract/auth tests и `bash scripts/generate-openapi.sh`; frontend API schema/query/UI tests для обоих направлений и polling/error/unavailable/no-graph/ready states, затем форматирование, lint, typecheck, Vitest и build последовательно по AGENTS. Не запускать ревью-агента по просьбе владельца задачи.
