# Авторизация голосового тренажёра

Контракты запросов и ответов находятся в [API по этапам](../api/README.md). Авторизация включена в каждый контракт, начиная с этапа «Основа системы и голос». В v0 пользователь самостоятельно регистрируется по email и паролю, получает роль `student` и сразу входит в систему. Преподаватель имеет роль `admin`. Админов создают или назначают вручную через SQL; публичная регистрация не принимает поле `role`.

## Ручки

| Метод и путь | Запрос | Результат |
| --- | --- | --- |
| `POST /v1/auth/register` | `email`, `password`, необязательное `display_name` | `201`: пользователь и сроки сессии; две cookies через `Set-Cookie`. |
| `POST /v1/auth/login` | `email`, `password` | `200`: пользователь и сроки новой сессии; две cookies через `Set-Cookie`. |
| `POST /v1/auth/refresh` | Без тела, refresh-cookie | `200`: сроки сессии; обновлённые cookies через `Set-Cookie`. |
| `POST /v1/auth/logout` | Без тела, необязательная refresh-cookie | `204`: сессия отозвана, обе cookies удалены. |
| `GET /v1/auth/me` | Access-cookie | `200`: текущие данные пользователя и роль. |

Регистрация и вход доступны без сессии. Обновление требует refresh-cookie; выход принимает её при наличии и возвращает `204` даже без неё. Остальные ручки API, включая `/v1/auth/me`, требуют access-cookie.

## Сессии и токены

Access- и refresh-токены — непрозрачные строки в `HttpOnly` cookies. Сервер устанавливает их через **два отдельных** заголовка `Set-Cookie`. Браузер сохраняет и отправляет их; JavaScript не читает значения токенов и не хранит их в localStorage. Access-токен действует до 15 минут и не дольше самой сессии. Сессия действует 30 суток с регистрации или входа. JSON содержит только абсолютные сроки `access_expires_at` и `refresh_expires_at` — Unix timestamp в секундах. При регистрации и входе они находятся в поле `session`, рядом с `user`; при обновлении — непосредственно в теле ответа.

| Cookie | Атрибуты |
| --- | --- |
| `access_token` | `Path=/; Secure; HttpOnly; SameSite=Lax`, без `Domain`. |
| `refresh_token` | `Path=/v1/auth; Secure; HttpOnly; SameSite=Lax`, без `Domain`. |

`Max-Age` каждой cookie равен оставшемуся сроку соответствующего токена в секундах. Для первой сессии пример ответа содержит два отдельных заголовка:

```http
Set-Cookie: access_token=<token>; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=900
Set-Cookie: refresh_token=<token>; Path=/v1/auth; Secure; HttpOnly; SameSite=Lax; Max-Age=2592000
```

На последующих обновлениях остаток 30 суток уменьшается. Заголовки `Set-Cookie` не объединяются через запятую. Обе cookies имеют атрибут `Secure`.

Refresh-токен одноразовый. Успешное обновление атомарно заменяет его и выдаёт новый access-токен через `Set-Cookie`. Ротация не продлевает исходные 30 суток. Старый access-токен остаётся действительным до своего срока, пока сессия не отозвана. Клиент выполняет обновления последовательно; cookies обновляет браузер. Повторное использование старого refresh-токена отзывает всю сессию. Если ответ на обновление потерян, повтор со старой cookie может потребовать нового входа. При `401 INVALID_REFRESH_TOKEN` сервер удаляет обе cookies.

Выход отзывает все токены одной сессии, включая access-токены, даже если их срок ещё не истёк. Другие входы пользователя сохраняются. Сервер удаляет обе cookies, устанавливая пустое значение и `Max-Age=0` с теми же `Path` и атрибутами. Повторный выход, отсутствующая, неизвестная или уже истёкшая refresh-cookie возвращает `204` и также удаляет cookies. Реализация сохраняет связь токенов с сессией и проверяет её активность при защищённых запросах.

Ответы, содержащие токены, отправляются с `Cache-Control: no-store`. В v0 frontend и доступный браузеру API работают по HTTPS с доверенным сертификатом, в том числе на IP-адресах внутри корпоративной сети через VPN. Cookies имеют `Secure`, `HttpOnly` и `SameSite=Lax`; `Domain` не устанавливается.

## Браузер и HTTPS

Frontend и API публикуются через общий HTTPS reverse proxy: страницы frontend и `/v1`
доступны на одном хосте и порту. Клиент обращается к API по относительным путям,
браузер автоматически отправляет cookies. Cookies привязаны к хосту и пути.

Запись с микрофона через `getUserMedia()` требует secure context. Для HTTPS на IP
сертификат содержит этот IP в SAN; корневой сертификат корпоративного или локального
CA установлен как доверенный на клиентских машинах. Такой frontend поддерживает
запись с микрофона и `Secure` cookies.

## Пользователи и права

`student` работает с опубликованным каталогом и своими учебными сессиями, расшифровками и ответами. Сервер определяет владельца по сессии авторизации; пользователь не выбирает владельца в теле запроса. Чужой ресурс возвращает `404`.

`admin` — преподаватель с правами на управление всеми курсами через `/v1/admin/*`; он также может проходить диагностику как обычный пользователь. Изменение роли через SQL действует со следующего запроса, поскольку сервер проверяет текущую роль в базе. Пароли в базе хранятся только как стойкие хеши: при ручном создании админа нельзя записывать пароль открытым текстом.

Email нормализуется удалением внешних пробелов и приведением к нижнему регистру. Нормализованный email уникален. Для нового пароля предлагается политика 15–128 символов, с поддержкой Unicode и пробелов, без обрезания или изменения регистра. Распространённые и скомпрометированные пароли отклоняются. Это соответствует ориентирам [OWASP для аутентификации без MFA](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html). Для хранения используется подход из [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

При неизвестном email или неверном пароле вход возвращает одинаковый `401 INVALID_CREDENTIALS`. Занятый email при регистрации возвращает `409 EMAIL_ALREADY_REGISTERED`; неверные поля — `422`; превышение частоты запросов — `429` с `Retry-After` в секундах. Устаревший, повторно использованный или отозванный refresh-токен возвращает `401 INVALID_REFRESH_TOKEN`. Ротация и обнаружение повторного использования опираются на описанный в [RFC 9700](https://datatracker.ietf.org/doc/html/rfc9700#section-4.14) подход; эти собственные ручки не объявляются OAuth-сервером.

Реализация v0 использует Argon2id для хранения пароля и проверяет известные утечки через
[HIBP Pwned Passwords](https://haveibeenpwned.com/API/v3#PwnedPasswords): передаётся только
пятисимвольный префикс SHA-1, с padding; исходный пароль и полный хеш не передаются.
Если проверка недоступна, регистрация возвращает `503 PROCESSING_UNAVAILABLE`, не создавая
аккаунт. Вход и обновление существующих сессий не зависят от HIBP.

Текущий контракт активирует аккаунт сразу после регистрации. Почтовое подтверждение, восстановление пароля и MFA требуют отдельных сценариев и в эту версию контракта не включены.
