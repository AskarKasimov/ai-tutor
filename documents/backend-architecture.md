# Архитектура backend

> Описывает текущий код (прежняя модель). Планируемые части нового видения — Geek, course-graph и клиент к 4 LLM — будут отдельными модулями backend с теми же слоями; этапы обработки course-graph выполняет отдельный Python-сервис `services/course-graph`, который вызывает клиент по gRPC. Описание — в [README](../README.md).

Дата: 15 октября 2026. Код находится в `services/backend`, Go-модуль — `github.com/AskarKasimov/ai-tutor/services/backend`.

## Реализованные части

| Путь | Ответственность |
| --- | --- |
| `cmd/api` | Запуск, миграции, healthcheck, shutdown. |
| `internal/app` | Конфигурация, зависимости, router, auth middleware и HTTP logging. |
| `features/auth` | Регистрация/вход, refresh/logout/me, PostgreSQL и Argon2id. |
| `features/voice` | STT/TTS, проверка входа, сохранение расшифровки владельца. |
| `features/subject` | Каталог предметов и создание предмета admin. |
| `features/competency` | CSV/XLSX парсер, атомарная замена карты, чтение дерева. |
| `features/taskbank` | SQL-каталог и профиль задания без эталона. |
| `features/assessment` | Контекстное оценивание по сохранённой позиции варианта; результат не сохраняется самим assessment. |
| `features/taskgen` | Генерация новых заданий, сохранение контекста, импорт материалов. |
| `features/variantgen` | Отбор ОР и аналогов, сохранение снимков, список и чтение вариантов. |
| `features/diagnostic` | Постоянная сессия, переходы main/basic, пропуск задания, STT, результат и предметный learning-state. |
| `features/diagnosticfeedback` | Общий фидбэк завершённой диагностики: детерминированный разбор + абзац модели, хранение в PostgreSQL. |
| `features/learning` | План обучения по часам, уроки наставника (теория и вопрос), проверка голосовых ответов и чат урока. |
| `features/training` | Preview, замороженный план, бесконечные упражнения, голосовые ответы, история и Socratic-чат. Работает без UI. |
| `features/taskaudio` | Durable PostgreSQL очередь, worker с ограниченной concurrency, S3 storage и авторизованная выдача сохранённых WAV. |
| `entities` | Пользователь, auth-сессия, карта, аудио, расшифровка, вариант и снимки профилей. |
| `shared` | Fault, security, HTTP helpers, миграции/SQLC и транзакционный enqueue helper с primitive inputs. |

Каждый feature содержит `application`, `infrastructure`, `transport/http`. Application определяет сценарии и порты; инфраструктура реализует порты; HTTP переводит запросы/ответы. `app` связывает зависимости. Сценарии и entities не импортируют HTTP, pgx или собственные адаптеры. Features не импортируют сценарии друг друга; общие доменные типы находятся в entities.

SQL находится в `shared/postgres/queries`; PostgreSQL-адаптеры вызывают сгенерированные SQLC-методы. Случайный выбор задания реализован в `variantgen/infrastructure/random`, генератор ID — в `shared/security`.

Авторизация выполняется middleware: auth возвращает principal, HTTP handler передаёт его сценарию. Импорт карты/материалов повторно проверяет admin внутри application. `shared` не содержит учебных правил и не зависит от features/entities.

## Учебные данные

Карта: компетенция → составляющая → ОР → задания. Источник — текущий ML CSV/XLSX; старый парный формат поддержан кодом. ОС 1:1 с ОР. Задания хранят отдельные вопрос, варианты, инструкцию и эталон. Импорт выдаёт новую ревизию и ID и заменяет активную карту одной транзакцией.

Диагностики и ответы сохраняются миграцией 00004, тренировки/цели/упражнения/ответы — 00005, приоритет озвучки — 00006, чат тренировки — 00007, планы обучения и минуты ОР — 00008, общий фидбэк диагностики — 00009. Legacy learning_sessions/task_assignments/assignment_responses не подключены. Отдельные variants/variant_tasks со снимками добавлены миграцией 00002. `entities/session` относится к авторизации. Учебные снимки независимы от удаляемой активной карты.

`00003_task_audio.sql` добавляет `audio_assets` и ссылки на активные задачи и
снимки вариантов. Импорт только ставит задания в очередь; worker запускается явным
app lifecycle после миграций, использует существующий TTS client, валидирует WAV и
сохраняет его в приватный S3 bucket. Очередь ограничивает параллельность, lease
восстанавливается после истечения; после пяти попыток asset получает failed.
Перед вызовом TTS worker ищет готовый asset с тем же текстом инструкции и копирует
его WAV под ключ текущего asset, поэтому переимпорт карты не озвучивает
неизменённые инструкции заново, а ID и доступ к снимкам остаются раздельными.
HTTP чтение никогда не вызывает TTS: diagnostic metadata показывает статус и
внутренний `/task-audio/{id}/file` URL, а file handler читает объект по bucket/key,
сохранённым с asset. `/health` проверяет API/БД, но не TTS или S3. При смене S3
endpoint объекты нужно скопировать отдельно до изменения сохранённых bucket/key.

## Variantgen

Модуль `internal/features/variantgen` собирает вариант из активной карты предмета. Компетенция включается, только если в ней не меньше трёх разных готовых TRUE-ОР; иначе она пропускается с причиной. Основной — наибольший ранг Блума, при равенстве — большая важность; два базовых — самые простые из остальных (`competency-map-v4`).

Application выполняет детерминированный отбор ОР, используя chooser только для случайного выбора задачи того же ОР. Создание требует `subject_id`; repository держит share lock выбранного предмета, читает его активную ревизию и атомарно сохраняет снимки с ID и названием предмета. `GET /variants` требует `subject_id` и фильтрует историю по нему. Повтор ключа с другим предметом возвращает конфликт. Вариант не содержит seed, ответов студента, оценки или фазы прохождения. Доменный `variant.TaskReader` предоставляет грейдингу полный исторический снимок с проверкой владельца; публичные DTO скрывают эталон/criteria/ОС. Taskgen сохраняется без изменений. Правила отбора — [алгоритм](Алгоритм_составления_варианта.md), HTTP-доступ — [OpenAPI](../api/openapi.yaml).

## API и модели

Единственный контракт — [api/openapi.yaml](../api/openapi.yaml). `x-implementation` отличает работающие операции от планируемых; наличие planned в Swagger не означает наличие handler. Этапных контрактов больше нет.

Frontend вызывает общий HTTPS API `/api/v1`; Caddy удаляет префикс. STT/TTS/LLM вызываются backend через HTTP-адаптеры; настройки моделей находятся только на сервере. `/health` проверяет backend/БД, не модели.

Действующие конфигурация и маршруты taskgen/assessment сохраняются; их замена не входит в scope variantgen. Перенос старых данных разработки не требуется; новые варианты и выбранные задания должны сохраняться после restart/reimport.

## Диагностическая сессия

`features/diagnostic/application` зависит от портов варианта, голоса, грейдера и store. PostgreSQL-store сериализует резервирование и принятие ответа транзакцией; сетевые STT/grader выполняются вне неё. Idempotency-Key возвращает принятый результат после рестарта. Lease позволяет повторить ответ после падения процесса, а смена token отклоняет устаревшую обработку.

Текущая позиция и счётчики прогресса вычисляются методами `entities/diagnostic.Session`. Store копирует изменяемые данные при сохранении и выдаче, включая ответы повтора; вызывающий код не получает ссылки на внутренние срезы и указатели store.

Клиенту выдаются только публичные поля задания; эталон и критерии остаются в доверенном снимке. Session вызывает `assessment.Service.EvaluateVariant` с owner, transcription, variant и variant task IDs. Assessment загружает снимок по владельцу, применяет max_score по роли (main 3, basic 1, training 2) и проверяет structured evaluation; оценка main может быть только 0, 1 или 3. Сессия сохраняет возвращённую шкалу без повторного преобразования. Основной с оценкой 3 пропускает basic. Сумма включает основные и предъявленные базовые, максимум 3 на компетенцию. Пропуск (`/skip`) сохраняется как ответ с оценкой 0. Результат доступен по завершении; общий текст обратной связи строит `diagnosticfeedback`.

Mock-режим удалён: assessment всегда вызывает API модели. `assessment.Service` реализует порт диагностики и возвращает `entities/assessment.Evaluation`. Memory-store остаётся тестовым адаптером; production использует PostgreSQL.

## План обучения

`features/learning/application` зависит от репозитория планов, store диагностики, голоса и порта `Teacher` (`learning/infrastructure/modelapi`, настройки `BACKEND_TUTOR_*`). План строится по завершённой диагностике из тех же выводов, что и итог (`diagnostic.OutcomeFindings`): непроверенные полным ответом ОР, включая пропущенные, а при нуле по основному и двум разным базовым ОР одной составляющей — все ОР этой составляющей из той же ревизии карты. ОР сортируются по важности и укладываются в часы студента (`BuildItems`). Урок генерирует теорию и вопрос; ответ проверяется моделью, после `MaxAttempts = 3` неверных ответов ОР получает статус «надо повторить». План не меняет диагностику.

## Тренировка

Модуль сохранён на backend; текущий frontend его не использует.

Одна тренировка связана с завершённой диагностикой. `entities/diagnostic.TrainingTargets` классифицирует только принятые ответы и используется фидбэком и тренировкой. Focused-план хранит снимки проверенных ОР; free_practice фиксирует все готовые TRUE-задания предмета при запуске. Непроверенные ОР имеют null исходной оценки.

`features/training/application` зависит от портов диагностики, repository, голоса, оценивания, озвучки и `ExerciseProvider`. Snapshot-provider копирует доверенное задание; будущий генератор сможет использовать цель и контекст предыдущих попыток. `app/training.go` соединяет оценивание со снимком и ролью training (0/1/2). История хранится отдельно от состояния сессии и читается страницами. Принятый ответ и следующее упражнение фиксируются одной транзакцией. Сетевые вызовы выполняются после резервации и вне транзакции; повтор ключа возвращает сохранённый ответ.

В тренировочном чате `training-tutor-v2` возвращает структурированный `answer_ready`: репетитор решает, достаточно ли полно студент сформулировал ответ. При готовности application передаёт assessment полные последние реплики студента из ограниченного контекста (без сообщений репетитора и сокращённых сводок), затем повторно вызывает Tutor с доверенным результатом проверки. Ответ, проверка и сообщение репетитора сохраняются одной транзакцией. Ошибки готовности/assessment/Tutor сохраняют возможность retry и не создают учебный ноль. Frontend отправляет только `message`; `check` остаётся совместимым с прежними клиентами и историей.
