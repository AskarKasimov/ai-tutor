# Статусы подготовки курса — спецификация для Luna

Статус документа: предложение к реализации по запросу владельца продукта. Это задание, а не описание уже реализованного поведения. Действующие правила готовности и допуска студентов остаются в README. Дата анализа: 03.11.2026.

## Задача и границы

В административном списке курсов и в заголовке каждого направления различать отсутствие источников, ожидание, реальную подготовку, необходимость действий и ошибку. Нельзя называть любое `ready=false` отсутствием материалов или активной подготовкой.

Выполнить backend + HTTP-контракт + frontend + тесты + документацию. Не менять критерии готовности, отбор заданий, доступ студентов, публикацию графов, алгоритмы импорта, retries, LLM и TTS. Не добавлять миграции, новые workers, endpoint на каждый курс, SSE, WebSocket, зависимости или настройки. Существующих таблиц достаточно.

Авторские решения этой спецификации: поля API, перечисления, приоритеты, тексты и период обновления ниже. Они предложены на основании анализа; пользователь пока отдельно их не утверждал.

## Что установлено по коду

1. Общий каталог содержит только `ready`, `exam_ready`, `learning_ready`. Admin видит все курсы; студент — готовые для выбранного API. `ready` — проекция соответствующего направления. Источники: [модель](../services/backend/internal/entities/subject/model.go), [сервис](../services/backend/internal/features/subject/application/service.go), [SQL](../services/backend/internal/shared/postgres/queries/subject.sql).
2. Список `/admin/courses` выбирает одну из двух подписей по boolean; заголовок направления делает то же самое. Реального состояния задачи эти подписи не читают: [список](../services/frontend/src/pages/admin-courses/ui/admin-courses-screen.tsx), [shell](../services/frontend/src/widgets/admin-course-detail-shell/ui/admin-course-detail-shell.tsx).
3. Внутри экзаменационного направления уже есть обработка файлов, этапы сборки, progress и ошибки. Сохранять их: [экран](../services/frontend/src/pages/competency-map/ui/competency-map-screen.tsx), [обработка материалов](../services/frontend/src/features/import-competency-map/model/material-processing.ts).
4. Backend-сборка имеет `not_requested/pending/processing/ready/failed`; frontend преобразует их в отсутствие задачи / `queued/running/succeeded/failed`. `pending` после сбоя означает автоматический повтор, даже при непустом `error_message`: [SQL задач](../services/backend/internal/shared/postgres/queries/course_graph.sql), [HTTP-адаптер](../services/frontend/src/entities/course-graph/api/course-graph-api.ts).
5. Опубликованный старый граф сохраняется при подготовке/сбое новой версии; `exam_ready=true` совместимо с активной или failed-сборкой и с устаревшим графом. Карта компетенций может готовить экзамен без PDF. См. [README frontend](../services/frontend/README.md#экзаменационная-карта), SQL выше.
6. Учебный импорт синхронный: сервер не хранит отдельную фоновую задачу импорта. Успешный импорт ещё не означает `learning_ready=true`: нужны подходящие задания по действующим правилам. Сбой замены не уничтожает прежнюю карту. [Правила](../services/backend/README.md#учебная-диагностика), [hook](../services/frontend/src/features/import-learning-competency-map/model/use-competency-map.ts).
7. Кэш каталогов exam и learn раздельный. Инвалидация только learn-каталога после учебного импорта не обновляет уже закэшированный общий административный список. [Ключи exam](../services/frontend/src/entities/subject/model/query-keys.ts), [ключи learn](../services/frontend/src/entities/learning-subject/model/query-keys.ts).

## Контракт

Расширить существующий Subject необязательным полем `preparation`. Backend обязательно заполняет его для admin в обоих GET-каталогах и обоих POST создания. Для студентов поле отсутствует; фильтрация каталогов и три boolean остаются прежними.

```ts
type ExamPreparationState =
  | 'empty' | 'queued' | 'processing' | 'failed'
  | 'needs_metadata' | 'needs_build' | 'ready'
type LearningPreparationState = 'empty' | 'needs_tasks' | 'ready'
type CoursePreparation = {
  exam: {
    state: ExamPreparationState
    source: 'materials' | 'competency_map' | null
    stale: boolean
  }
  learn: { state: LearningPreparationState }
}
// Subject.preparation?: CoursePreparation
```

Пути: `GET /api/v1/exam/subjects`, `GET /api/v1/learn/subjects`, `POST /api/v1/exam/admin/subjects`, совместимый `POST /api/v1/learn/admin/subjects`.

Новый курс: оба state=`empty`, source=null, stale=false, все boolean=false. В обеих GET-ручках `preparation` одинаково для одного курса; отличается только совместимый `ready`.

Не включать в каталог progress, исходные сообщения моделей, имена/содержимое файлов, S3 keys, lease tokens или fingerprint. `stale` имеет ту же семантику, что в существующем snapshot: опубликованный граф перестал соответствовать своему источнику. Отсутствующий граф даёт false. Различие source новой задачи и старого графа дополнительно учитывается при вычислении state.

Ответ собирается из БД пакетно: постоянное число SQL-запросов независимо от числа курсов, без вызовов других features, S3, course-graph или LLM. Признаки и ready должны относиться к согласованному снимку чтения — предпочтительно один SQL statement с агрегатами/CTE, без размножения строк JOIN-ами материалов и заданий.

## Вычисление exam.state

Подготовка описывает выбранный источник текущей/последней подготовки; доступность старой публикации описывает `exam_ready`. Это разные оси, не заменять boolean перечислением. Даже `empty` выбранного нового источника может сочетаться с `exam_ready=true`, если сохранилась доступная публикация другого source.

Определить effective source: source существующей последней задачи; иначе source опубликованного графа (`built` нормализовать в `materials`); иначе сохранённая exam-карта; иначе материалы. При полном отсутствии источников source=null.

Если выбран `competency_map`, PDF, их метаданные, очистка и OCR не блокируют его статус. При выбранном `materials` само наличие ранее импортированной, но не выбранной карты не делает PDF-подготовку готовой. Нельзя автоматически переключать источник без существующего пользовательского действия.

Вычислять состояние первым подходящим правилом:

1. Нет источника для effective source: `empty`. Для materials это отсутствие всех сохранённых материалов; для map — отсутствие сохранённой карты. Старая задача/ошибка сама по себе не является источником. В этом случае source=null.
2. Есть фактически выполняющаяся задача сборки выбранного source либо выполняющиеся OCR/очистка выбранных materials: `processing`. Выполняющуюся задачу не скрывать из-за смены fingerprint; принятие результата по-прежнему регулирует существующий worker.
3. У выбранных текущих materials есть terminal failure OCR/очистки/материала: `failed`.
4. У materials не заполнены неделя или вид: `needs_metadata`. Это остановка, требующая человека; pending-сборка, ожидающая эти поля, не должна выглядеть активно готовящейся.
5. Есть ожидающие OCR/очистка materials либо pending-задача сборки выбранного source: `queued`. Непустой error_message при pending не превращает состояние в failed. Очередь/автоматический backoff — действительно запланированная работа.
6. Последняя задача выбранного source terminal failed и её fingerprint соответствует текущему источнику: `failed`. Ошибка предыдущей редакции не переносится на новые материалы/карту. Проверять соответствие существующими правилами fingerprint; не вводить альтернативное хеширование.
7. Есть доступный опубликованный граф выбранного source, соответствующий текущему источнику, без stale: `ready`.
8. Источник есть, но актуальной публикации выбранного source нет: `needs_build`. Включает первую сборку, ещё не запрошенную пользователем, изменение источника и устаревшую публикацию.

Обработка материалов должна учитывать и `subject_materials`, и OCR/cleaning jobs, а не только верхний status файла. Не считать отсутствующую job активной. Использовать реальные terminal/nonterminal значения действующих таблиц. Если после удаления/замены старый failed-job остался, он не должен описывать удалённый ресурс.

Если одновременно идут обработка и ошибка другого файла, агрегат показывает processing; подробный список сохраняет ошибку. Когда активная обработка завершится, агрегат покажет failed. Queued при ошибке другого текущего файла показывается как failed по приоритету выше.

`needs_build` ничего не запускает автоматически. Исправление метаданных и загрузка сами по себе не должны добавлять новый способ запуска сборки.

## Вычисление learn.state

- Нет успешно опубликованной активной ревизии учебной карты: `empty`.
- Активная ревизия есть и `learning_ready=true`: `ready`.
- Активная ревизия есть и `learning_ready=false`: `needs_tasks`.

Проверять наличие активной ревизии, не число компетенций/заданий. Карта с нулём подходящих заданий — загруженная карта, не empty. Не повторять SQL-критерии готовности в новом месте: использовать тот же результат `learning_ready`.

Для learn сервер не возвращает queued/processing/failed: сохранённого источника этих фактов нет. Во время `upload.isPending` только на текущем экране заголовок показывает «Обучение: идёт импорт карты»; это локальное наложение, не изменение каталога/готовности. После ошибки запроса показать существующую ошибку импорта, перечитать карту и оба каталога; итоговое состояние определяется сохранённой ревизией. При неоднозначном timeout не заявлять, что сервер ничего не сохранил. Другие вкладки увидят результат после commit, без фиктивного состояния импорта. Не вводить durable jobs ради этого задания.

Генерация коротких подписей, озвучка/TTS и загрузка предпросмотра не являются подготовкой карты и не меняют эти состояния.

## Тексты и отображение

Одинаковые правила в списке и заголовках направлений. Все строки через i18n; существующие ключи со словами Preparing не использовать как fallback для `!ready`. При необходимости переименовать только задействованные ключи. В общем shell не показывать статус, пока нет достоверных данных: `undefined ready` сейчас ошибочно выглядит как подготовка.

Для экзамена добавлять префикс «Экзамен: »:

| state | exam_ready=false | exam_ready=true |
| --- | --- | --- |
| empty | материалы не загружены | готов · материалы обновления не загружены |
| queued | подготовка в очереди | готов · обновление в очереди |
| processing | идёт подготовка | готов · идёт обновление |
| failed | ошибка подготовки | готов · ошибка обновления |
| needs_metadata | заполните данные материалов | готов · заполните данные новых материалов |
| needs_build | требуется сборка графа | готов · требуется обновление |
| ready | недопустимое сочетание: исправить backend/тест | готов |

Для обучения добавлять «Обучение: »: empty → «материалы не загружены», needs_tasks → «недостаточно заданий для диагностики», ready → «готово». needs_tasks/empty совместимы только с learning_ready=false; ready — с true.

Цвета Radix: empty=gray; queued/processing=blue; needs_metadata/needs_build/needs_tasks=amber; failed=red; ready=green. При доступном старом графе сохраняется текст «готов», цвет определяется состоянием обновления. Spinner допустим только для фактически выполняющейся работы и локального импорта; queued не изображать выполняющимся процессом. Не помещать каждое обновление всей карточки в live region.

Карточки остаются ссылками с прежним поведением. На ширинах 360/600/1000px длинные статусы переносятся и не вызывают горизонтальный скролл; проверить светлую и тёмную темы. Не вводить фиксированную ширину бейджа.

Неполный/неизвестный preparation в ответе admin — ошибка контракта, не empty. Пока данные не получены, показывать загрузку; при ошибке — явную ошибку с повтором. Старый успешный снимок при фоне допустимо сохранять с сообщением «Не удалось обновить статусы» и повтором, без подмены подготовки ошибкой сети. Сохранить auth epoch, отмену запросов и обработку 401.

## Обновление данных

1. Каталоги на административных экранах перечитываются раз в 5 секунд, только при смонтированном observer и видимом документе (`document.visibilityState === 'visible'`, `refetchIntervalInBackground: false`); при возврате фокуса — refetch. Видимая вкладка в окне без фокуса не считается скрытой. Polling работает и при empty/ready/needs_build, иначе работа из другой вкладки останется незамеченной. Не включать такой polling на студенческих экранах: параметр hook/observer для admin-сценария, default выключен.
2. Один запрос каталога на observer/query key, никаких запросов материалов/графов для каждой карточки. Существующий подробный polling графа и материалов сохраняется.
3. После загрузки/замены/удаления PDF, изменения метаданных, импорта exam-карты, запуска/retry/исключения заданий, завершения сборки и импорта learn-карты инвалидировать оба каталога текущего пользователя. После неудачного мутирующего запроса тоже перечитать, если commit мог произойти до ошибки/timeout. Не инвалидировать кэш другого пользователя.
4. При каждом обнаруженном подробным polling переходе обработки/сборки в другое агрегатное состояние инвалидировать каталоги один раз на переход, не на каждый render. Даже если сохранён старый граф, карточка должна показывать начало обновления.
5. Не объединять keys exam/learn и не менять смысл совместимого ready. Использовать существующий exam-prefix `subjectQueryKeys.subjects(userId)` (`['subjects', userId]`) с `exact: false`: он уже охватывает learn-key `['subjects', userId, 'learn']` и связанные learning-state queries. В местах, где доступен только learn-key, подключать разрешённый entity API с соблюдением FSD. Не создавать новый shared helper и не импортировать feature из feature ради инвалидации.

## Приёмка и регрессионные проверки

Табличные unit-тесты backend должны покрывать каждую ветку вычисления и приоритетов, integration — фактические сочетания таблиц и сериализацию DTO. Минимальные обязательные сценарии:

| Сценарий | Ожидаемый результат |
| --- | --- |
| Новый курс | exam/learn empty, false; точные подписи отсутствия материалов |
| Локально выбран, но не отправлен файл | не меняет серверный статус |
| Материал принят, только очередь OCR | queued, если нет metadata-блокировки |
| OCR/очистка реально выполняется | processing, включая parsed-файл с активной cleaning job |
| Метаданные отсутствуют, работы не выполняются | needs_metadata, включая pending граф, ожидающий данные |
| PDF готовы, сборка ещё не запрашивалась | needs_build; не «идёт подготовка» |
| pending граф, error_message предыдущей попытки | queued, не failed |
| terminal failed текущего источника | failed |
| Старый failed fingerprint, материалы заменены | ошибка старой редакции не переносится |
| Один файл failed, другой processing | processing, затем failed после остановки обработки |
| Map-сборка без PDF | queued → processing → ready, без metadata/PDF блокировок |
| Map-сборка при ошибочном/обрабатываемом PDF | статус карты не зависит от PDF |
| Старый граф + queued/processing/failed замены | exam_ready остаётся true; точный текст о готовности и обновлении |
| Старый граф стал stale без новой задачи | needs_build, exam_ready по прежнему правилу |
| Источник новой сборки отличается от старой публикации | старый граф не доказывает готовность новой версии |
| Последний PDF удалён, старая job осталась | empty для materials; exam_ready=false для публикации из PDF, но может остаться true для старой публикации из карты |
| Карта learn импортирована, подходящих заданий недостаточно | needs_tasks; не empty и не processing |
| Learn импорт выполняется в текущем экране | локальное «идёт импорт карты», прежняя готовность сохранена |
| Ошибка/timeout замены learn-карты | refetch; статус по реально сохранённой ревизии |
| Импорт learn завершился, возврат в общий список | обновлены оба раздельных каталога |
| TTS/подписи/предпросмотр грузятся или упали | preparation/ready не меняются |
| Работа запущена из другой вкладки при idle-списке | видна после очередного polling; после фокуса refetch |
| Невалидный/отсутствующий admin preparation, сеть/401 | явная ошибка/существующая auth-обработка, без ложного empty |
