# Проверка комплекта и совместимости, 16.10.2026

## Вывод

Граф переносится в текущий формат Феди без структурных изменений: 132 активные темы, 145 рёбер, прежние ID, 15 атомарных и 69 терминальных тем. Формат общего DAG уже подходит, менять его на дерево или добавлять фиктивные зависимости не требуется. Полный исследовательский датасет в шесть полей Node без потерь не помещается. Поэтому проекция сопровождается неизменённым каноническим пакетом.

Сам экспорт не означает готовности к применению текущих правил Geek. Ниже перечислены различия данных, контрактов и педагогической политики; действующие контракты и production-код в этой ветке не менялись.

## Фактические проверки

- Все **5/5** исходных unit-тестов прошли на Python 3.13.11.
- Штатный `qa/check_artifact.py`: JSON Schema, DAG, 132 available / 5 missing, 145 уникальных рёбер, 15 atomic, 69 terminal, 20 групп, ровно одно назначение каждой терминальной темы, корректные closure, запрет auto-close — PASS.
- Длина максимального пути — 7; 80 unmapped requirements. Все рёбра provisional. Вопросы групп: 13 integrated_pilot / 7 routing_only, все draft_unvalidated.
- SHA256 канонического файла совпадает с manifest: `d9195f7c830b4dda8893e4126a075fbb324fb397595fd74ff27ab3a4d0f70f20`.
- Дополнительно проверены уникальность ID групп, совпадение ID тем с provenance, точное восстановление множества рёбер из проекции и порядок каждой предпосылки раньше зависимой темы.
- Проекция проверена по `Graph` из `api/course-graph.yaml`; все её вершины — по `geek.GraphNode` из `api/openapi.yaml`. Исходная фикстура Феди из 10 нод также проходит схему Graph.
- Полный `geek.Graph` требует runtime-поля `subject_id` и `built_at`; экспорт намеренно является внутренним Graph, а не выдуманным ответом публичного API.
- В исходном QA нет проверки SHA256 и уникальности ID групп; дополнительные проверки добавлены отдельно, оригинальный QA сохранён.
- Backend/frontend и интеграционные DB-тесты не запускались: runtime, БД, API и UI не изменялись. HTML-прототипы сохранены, интерактивная браузерная проверка не проводилась. Экспертная проверка текстов, зависимостей и оригинальных PDF не проводилась.

## Расхождения с master

1. **Закрытие предков.** README/AGENTS master: оценка A/B/C засчитывает предпосылки; handoff и прямое требование пользователя: успешный ответ подтверждает только проверенную тему. Это изменение политики диагностики, не задача сериализации. Для этого набора нужен режим без автоматического переноса освоения. Нельзя механически отобразить pass в A/B/C с наследованием статуса.
2. **Версии.** `geek.Graph` и README: одна заменяемая версия на курс, после пересборки остаётся только feedback. Handoff: неизменяемые версии, evidence привязано к dataset/session/question. Для воспроизводимости разумно хранить snapshot/hash графа у сессии, даже если UI показывает только одну активную версию.
3. **Язык.** Контракты описывают русский content. Фактический full_text содержит английские извлечения: например AI-01-01 и AI-04-16. JSON Schema язык не проверяет. Простой экспорт валиден структурно, но не выполняет требование русского содержания. Нужен проверенный русский текст с сохранением оригинала и provenance; массовый перевод сейчас не выполнялся.
4. **Система оценивания.** Geek: четыре критерия 0/1/2 → A–D и автономная модель; handoff: pass/gap/uncertain от внешнего оценщика с контролем качества. Таблица соответствия и качество рубрик не установлены. В текущих данных **112 из 132** рубрик — буквально provides с префиксом «Демонстрирует: ». Упомянутые в документах 117 относятся к предыдущей ревизии, это не фактическое число текущего пакета.
5. **Пробелы и план.** Geek называет пробелом самую глубокую неосвоенную тему с освоенными предпосылками; handoff хранит suspected_gap для каждого неуспешного ответа и отдельно unknown/insufficient_evidence. Без согласования статусов теряется смысл результатов.
6. **РПД и DG.** Master исключил РПД из текущего scope и начинает с терминальных тем; handoff хранит РПД-покрытие, 5 отсутствующих тем и DG-навигацию. Их можно оставить в исследовательском слое без изменения DAG/API. 20 DG не означают диагностику за 20 вопросов.
7. **Статус документации master.** В таблице плана README контракты и фикстура ещё «не начаты», но они уже присутствуют в api и описаны в api/README. Для проверки использованы реальные файлы коммита 18620bc.

## Расхождения внутри handoff

Уже описаны в основном документе и подтверждены кодом: `Question` не имеет question_id, использует question вместо API prompt; engine не принимает student_id; summary не возвращает API status_by_topic и вызывает next_question, тем самым меняя active/worklist. Production-идемпотентность и хранение сессий отсутствуют намеренно.

Дополнительно воспроизведено `review_observations.py`:

- **План обрывает обход на mastered_observed.** Для цепочки AI-01-01 → AI-01-07 → AI-01-08 при unknown / mastered_observed / suspected_gap первая тема не попадает в план. Это противоречит буквальному «все ещё не освоенные предки» в handoff. Отсечение может быть отдельной политикой, но её нужно согласовать; пять тестов этот случай не проверяют.
- **Нет runtime-проверки outcome.** Вызов submit с `'invalid'` записывает такой исход в evidence и устанавливает insufficient_evidence через else. Аннотация Outcome не валидирует вход Python. При подключении к API нужна явная валидация до изменения сессии.
- **Неполный контракт evidence.** OpenAPI/TS Evidence не содержит question_id, dataset_id, session_id, хотя developer handoff требует эти связи в журнале. Часть контекста можно восстановить по сессии, но это не выражено в самостоятельном DTO.
- **Описание ответа графа в OpenAPI допускает отсутствие full_text**, хотя canonical schema требует его. Нужна отдельная схема публичной проекции; рубрика также обязательна в Question DTO, хотя доступ к критериям должен зависеть от роли.

Исходный код не исправлялся: задача текущего этапа — baseline, аудит и оценка совместимости.

## Текст для Феди (подготовлен, не отправлен)

Федя, посмотрели актуальный master и твой общий DAG-контракт. Основная структура подходит: мы проверили экспорт 132 тем и 145 связей в Graph, сохранили ID, направление prerequisite и порядок изучения. Менять шесть базовых полей ради загрузки не нужно.

Но использовать этот Graph как единственный источник данных было бы потерей информации: исчезнут рубрики, исходные страницы, обоснования и статус проверки связей, версия датасета и диагностические группы. Предлагаю оставить компактный Graph для runtime, а расширенную версионированную запись хранить рядом по dataset_id и node_id. Для диагностики сохранить snapshot/hash версии у сессии и явно задавать режим переноса освоения; для текущего невалидированного курса он должен быть выключен. Если sidecar неудобен, те же метаданные можно добавить в новую версию контракта, согласованно в Python API и backend API.

Отдельно нужно договориться о шкале и рубриках: перевод pass в A/B/C с зачётом предков сейчас необоснован. Исходные тексты ещё английские, поэтому полученная проекция доказывает совместимость структуры, но перед показом требует перевода и проверки контента. Эти вопросы не решаются переименованием полей.
