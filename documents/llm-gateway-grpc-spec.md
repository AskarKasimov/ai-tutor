# LLM Gateway — gRPC и общие protobuf-контракты

Дата: 16.10.2026. Статус: **реализовано; интеграция проверена с тестовой Redpanda и fake upstream, реальные LLM endpoint требуют отдельной проверки**.

Документ дополняет [спецификацию gateway](llm-gateway-spec.md). Правила выбора модели и приоритетов сохраняются; семантика отмены и восстановления изменяется по разделу 7 и имеет приоритет над прежним правилом о продолжении задания после обрыва HTTP. Внутренние клиенты backend и course-graph используют gRPC; HTTP остаётся доступен.

## 1. Цель и согласованные решения

Добавить gRPC как второй транспорт существующего LLM Gateway. Go-сервисы используют общий сгенерированный клиент, другие языки генерируют клиентов из тех же `.proto`. Оба входа обслуживают одну очередь и возвращают результат одной генерации при повторе с одинаковым ключом.

Согласовано в обсуждении:

- Исходные protobuf-контракты и сгенерированный код размещаются в `services/shared`.
- Существующий HTTP API сохраняется.
- Один процесс gateway обслуживает HTTP на `8010` и gRPC на `8011`.
- Caddy направляет gRPC по пути сервиса `/llmgateway.v1.Gateway/*` на тот же внешний HTTPS-хост и порт.
- Сейчас корневой Compose всегда запускает gateway; профили `observability` и `swagger` включают только дополнительные сервисы. Backend и course-graph подключены к gateway по внутреннему gRPC.
- Сам Caddy не переносится под профиль: он продолжает обслуживать frontend и backend.
- Если сервис-клиент прерывает вызов, gateway прекращает ненужное ожидание в очереди и отменяет активный запрос к LLM. Правило действует для HTTP и gRPC; несколько ожидающих один ключ клиентов учитываются по разделу 7.

Детали контракта, лимитов и сборки приведены ниже. Критерий успеха: стандартный gRPC-клиент вызывает gateway напрямую в Docker и через Caddy; транспорт не меняет диспетчеризацию и идемпотентность.

В scope нет streaming, gRPC-Web, публичной клиентской аутентификации, отдельного хоста или RPC опроса/отмены заданий. Backend (включая Geek и перевод OCR) и course-graph используют gRPC; upstream по-прежнему вызывается по HTTP. Добавление транспорта не доказывает улучшения производительности LLM.

## 2. Общий модуль контрактов

```text
services/shared/
  go.mod
  go.sum
  README.md
  proto/llmgateway/v1/gateway.proto
  gen/go/llmgateway/v1/gateway.pb.go
  gen/go/llmgateway/v1/gateway_grpc.pb.go
  tools/                    # генерация и закреплённые версии инструментов
```

Go-модуль: `github.com/AskarKasimov/ai-tutor/services/shared`.

Protobuf package: `llmgateway.v1`. Значение `go_package`: `github.com/AskarKasimov/ai-tutor/services/shared/gen/go/llmgateway/v1;llmgatewayv1`.

В shared находятся контракты, сгенерированные сообщения и client/server stubs. В нём нет планировщика, конфигурации моделей, доступа к Redpanda, предметных типов backend или транспортных адаптеров gateway. Shared не импортирует backend и gateway; прикладные сервисы зависят от shared.

Единственный источник контракта — `.proto`. Go- и Python-код коммитится, вручную не редактируется. Из корня репозитория `services/shared/tools/generate.sh services/shared/gen` воспроизводимо генерирует оба клиента; `services/shared/tools/generate.sh --check` генерирует во временный каталог и сравнивает результат с репозиторием, не меняя рабочие файлы. Версии `protoc`, `protoc-gen-go` и `protoc-gen-go-grpc` явно закрепляются в файле инструментов; `latest` не используется. Совместимые версии закреплены в `services/shared/tools/versions.env` и проверяются чистой генерацией.

Python-генерация документируется с закреплёнными инструментами и тем же include root `services/shared/proto`. Готовый Python-пакет и его публикация не нужны до появления потребителя; копировать `.proto` в backend нельзя.

Go-потребители добавляют `require` shared и локальный `replace` на `../shared`. До публикации версий используется локальная версия `v0.0.0`. Это позволяет собирать отдельные модули с `GOWORK=off`; `go.work` допустим как удобство разработки, но не является обязательным условием CI и Docker. Backend подключает shared так же (`replace ../shared`) для gRPC-клиента Geek.

Номера удалённых полей и их имена резервируются. Совместимые расширения добавляются новыми номерами, смысл существующих полей не меняется. Несовместимый контракт получает package `llmgateway.v2` и отдельный маршрут. CI проверяет совместимость относительно версии контракта в целевой ветке; первая версия создаёт исходную точку сравнения.

## 3. RPC и запрос

```proto
syntax = "proto3";
package llmgateway.v1;
option go_package = "github.com/AskarKasimov/ai-tutor/services/shared/gen/go/llmgateway/v1;llmgatewayv1";

service Gateway {
  rpc Complete(CompleteRequest) returns (CompleteResponse);
}

message CompleteRequest {
  repeated Message messages = 1;
  Complexity complexity = 2;
  bool urgent = 3;
  GenerationParameters parameters = 4;
  string routing_profile = 5;
}

message Message {
  Role role = 1;
  optional string content = 2;
}

enum Role {
  ROLE_UNSPECIFIED = 0;
  ROLE_SYSTEM = 1;
  ROLE_USER = 2;
  ROLE_ASSISTANT = 3;
}

enum Complexity {
  COMPLEXITY_UNSPECIFIED = 0;
  COMPLEXITY_LOW = 1;
  COMPLEXITY_MEDIUM = 2;
  COMPLEXITY_HIGH = 3;
}

message GenerationParameters {
  optional double temperature = 1;
  optional double top_p = 2;
  optional double presence_penalty = 3;
  optional double frequency_penalty = 4;
  optional int64 seed = 5;
  optional int64 max_tokens = 6;
  optional int64 max_completion_tokens = 7;
  StopSequences stop = 8;
  optional ResponseFormat response_format = 9;
  optional ReasoningEffort reasoning_effort = 10;
}

message StopSequences {
  repeated string values = 1;
}

enum ResponseFormat {
  RESPONSE_FORMAT_UNSPECIFIED = 0;
  RESPONSE_FORMAT_TEXT = 1;
  RESPONSE_FORMAT_JSON_OBJECT = 2;
}

enum ReasoningEffort {
  REASONING_EFFORT_UNSPECIFIED = 0;
  REASONING_EFFORT_LOW = 1;
  REASONING_EFFORT_MEDIUM = 2;
  REASONING_EFFORT_HIGH = 3;
}
```

Это нормативная форма запроса. Отсутствие complexity, нулевые и неизвестные значения обязательных enum отклоняются. Для optional enum пропуск допустим, явно заданные `UNSPECIFIED` и неизвестные значения — ошибка. Непустой список сообщений обязателен; content обязан присутствовать, пустая строка допустима, как в HTTP. Urgent по умолчанию false. `routing_profile` — необязательное имя настроенного профиля; пустое значение соответствует текущей маршрутизации, неизвестный профиль возвращает `InvalidArgument`. Фильтр профиля применяется и к urgent. Поле добавлено новым номером 5 и входит в idempotency fingerprint; старые сохранённые запросы без поля остаются default.

Optional числовые поля сохраняют различие между пропуском и нулём: адаптер не подставляет значение, которое клиент не прислал. Проверки конечности чисел, диапазонов, положительных бюджетов, их взаимного исключения и возможностей пула совпадают с HTTP. Присутствующий stop содержит от одной до четырёх строк; отдельный message сохраняет различие между пропуском и пустым списком.

HTTP допускает stop-строку и stop-массив. Для общей канонизации stop-строка преобразуется в массив из одного элемента; порядок массива сохраняется. Общий валидатор и upstream-адаптер используют эту форму. Изменение канонизации требует правила совместимости с сохранёнными хешами, описанного в разделе 6.

Полей model, stream и n нет: модель выбирает gateway, ответ полный, число вариантов равно одному. JSON Schema, tools и мультимодальные сообщения не поддерживаются. Неизвестные protobuf-поля допускаются для wire-совместимости, но никогда не превращаются в параметры upstream; действуют только известные поля контракта.

## 4. Ответ и metadata

```proto
message CompleteResponse {
  string request_id = 1;
  bytes completion_json = 2;
}
```

В первой версии запрос типизирован, а полный Chat Completion возвращается как UTF-8 JSON в `completion_json`. Это сознательная граница v1: текущий gateway сохраняет и возвращает JSON upstream; protobuf-обёртка не должна терять дополнительные поля choices, usage и provider extensions или менять числовую точность. Клиент декодирует JSON после успешного RPC. Это не полностью типизированный protobuf-ответ; отдельную типизированную проекцию можно добавить совместимыми полями после определения требований клиентов.

`completion_json` содержит ровно сохранённое тело успешного HTTP-ответа; ошибки в него не упаковываются. `request_id` — ID задания gateway, а completion `id` внутри JSON остаётся ID upstream. Успех возвращается только после долговечной записи результата.

| Metadata | Направление | Правило |
| --- | --- | --- |
| `idempotency-key` | Запрос | Необязательный аналог HTTP `Idempotency-Key`; пробелы по краям удаляются, пустое значение означает отсутствие ключа. Несколько значений отклоняются как `InvalidArgument`. |
| `x-request-id` | Ответ | Gateway задаёт ID и передаёт его initial metadata при первой возможности. При успешном RPC он совпадает с полем ответа. До создания задания допустим отдельный ID попытки, как у HTTP. |

Клиентский `x-request-id` не определяет ID задания. При отказе Caddy, TLS или декодера gRPC приложение не гарантирует metadata и структурированные детали. Лимиты metadata ограничиваются настройкой сервера; отсутствие bearer-аутентификации сохраняется.

## 5. Общий прикладной слой

```text
HTTP handler ─┐
              ├─ validate / submit / await ─ Redpanda ─ scheduler ─ upstream HTTP
gRPC handler ─┘
```

Из текущего HTTP handler выделяются общий нормализованный запрос, проверка пула, регистрация/публикация задания, учёт активных ожидающих клиентов, отмена исполнения, ожидание и результат с транспортно-независимой ошибкой. HTTP-обработчик отвечает за JSON, заголовки и HTTP status; gRPC-обработчик — за protobuf, metadata и gRPC status. Вызов HTTP handler через внутренний HTTP-клиент или `httptest.ResponseRecorder` не используется.

Один экземпляр Service, один диспетчер, один набор лимитов очереди, один счётчик выполняющихся запросов к каждому инстансу и общее хранилище ключей обслуживают оба транспорта. Ограничение `max_connections` сохраняет имя для совместимости конфигурации, но прикладной смысл — общий предел одновременно обслуживаемых вызовов HTTP и gRPC, включая ожидание ответа. Один HTTP/2-канал не обходит его множеством RPC. Дополнительный предел streams защищает gRPC-транспорт до входа в прикладной слой.

Хранимые задания и ответы остаются в существующем JSON-формате Redpanda. Отмена записывается как terminal `failed` с новым кодом ошибки, без нового статуса и topic. Protobuf не становится форматом очереди. Новая очередь и второй активный диспетчер не требуются.

## 6. Идемпотентность и канонизация

Сейчас HTTP использует фиксированный client ID `internal`; gRPC использует тот же namespace. Передача произвольного client ID в metadata не вводится. Ключи остаются общими для всех внутренних потребителей: клиенты должны выбирать уникальные ключи, например с префиксом имени сервиса и UUID операции. Отдельные пространства клиентов требуют будущей аутентификации и отдельного решения.

После преобразования в общий запрос оба транспорта вычисляют одинаковый семантический хеш. Пропуск urgent равен false; существующие числовые значения по умолчанию и response_format нормализуются одинаково. Ключ, ID, deadline вызова и транспорт в хеш не входят. Повтор не меняет сложность, срочность, дедлайн задания или место в очереди.

- Тот же ключ и запрос: присоединение к ожиданию либо сохранённый ответ/ошибка.
- Тот же ключ и другой запрос: HTTP `409`, gRPC `AlreadyExists`, причина `idempotency_conflict`.
- HTTP → gRPC и gRPC → HTTP работают так же, как повторы внутри одного транспорта.
- Без ключа каждая попытка является новым заданием; транспортный сбой не доказывает, что генерация не началась.
- После зафиксированной отмены тот же ключ возвращает сохранённую ошибку отмены и не возобновляет генерацию. Для намеренно нового запуска клиент создаёт новый ключ. Если успех был зафиксирован раньше отмены, повтор возвращает сохранённый успех.

При новой канонизации stop необходимо уметь проверить старый хеш задания: для сравнения нормализуется его сохранённый Request, а не только входящая попытка. Поддержка нужна и для восстановленных заданий, и для незавершённых публикаций. Старые сохранённые записи не переписываются массово, ID задания и ключ остаются прежними. Регрессионный тест использует запись, созданную прежней реализацией, с обеими формами stop.

Оба транспорта используют общую реализацию retention: терминальные результаты хранятся 24 часа после `FinishedAt`. Неопределённо занятый upstream-слот сохраняется и после этого срока, пока его освобождение не подтверждено.

## 7. Дедлайны, отмена и повторы

### Связь вызова клиента и исполнения

Общий предел жизни задания — время регистрации плюс `request_deadline`. Дополнительно работа нужна только пока есть хотя бы один активный клиент, ожидающий результат. Отмена RPC, истечение его deadline или обнаруженный обрыв HTTP снимают этого клиента с ожидания. Gateway не ждёт общего дедлайна, если клиентов больше нет.

Отмена относится к отдельному HTTP-запросу/RPC, а не ко всему HTTP/2-соединению. Завершение другого RPC и закрытие неиспользуемого канала не отменяют чужие задания. При незаметном сетевом обрыве действие начинается после обнаружения транспортом; мгновенное обнаружение сетевого разделения не обещается. Клиентам задаётся конечный deadline; проверки через Caddy должны подтвердить распространение отмены до gateway.

Если context уже отменён до регистрации, новое задание не создаётся. После регистрации у задания есть собственные context/cancel и счётчик активных ожидающих вызовов. Регистрация ожидающего, его отключение и решение об отмене синхронизируются с назначением задания. Нельзя привязать общий upstream context только к первому RPC: при конкурентных повторах живой клиент должен продолжать получать результат.

Если один ключ одновременно ожидают несколько клиентов, отключение одного снимает только его ожидание. Отключение последнего отменяет задание без периода ожидания переподключения. Присоединение повтора и отмена последнего клиента имеют единый порядок: либо повтор успел присоединиться и работа продолжается, либо отмена уже началась и повтор получает её результат. Отменяемое задание не оживает.

### Остановка работы

- Задание в очереди: исключить из назначения, снять резерв ресурсов и сохранить отмену. Поздняя доставка записи Redpanda не должна запускать его.
- Задание исполняется: вызвать cancel его context, переданного исходящему HTTP-запросу LLM, прекратить чтение и закрыть response body. Не затрагивать соединения и контексты других заданий.
- Задание ждёт upstream retry/backoff: прервать задержку, не назначать новую попытку и не занимать слот.
- Публикация неоднозначна: остановить обычные попытки публикации и надёжно записать terminal-отмену по тому же ID. Уже отправленная запись может всё равно попасть в topic; consumer проверяет отмену и не воскрешает задание.

Локальная блокировка назначения и cancel выполняются сразу после решения об отмене; запись отмены в Redpanda не задерживает остановку HTTP-вызова. Сохранение выполняется с отдельным ограниченным служебным context, не с уже отменённым context клиента. Если состояние не удалось надёжно записать, gateway снимает readiness, запрещает новые назначения до восстановления согласованности и не выдаёт отмену за гарантированно сохранённую.

Слот инстанса освобождается ровно один раз после выхода локального upstream-вызова и закрытия тела ответа. Переклассифицировать намеренную отмену в upstream failure, retry или отказ circuit breaker нельзя. Закрытие запроса прекращает работу gateway с LLM; фактическая остановка генерации на сервере модели зависит от его поддержки отключения клиента. Для каждого реального endpoint это проверяется отдельно, по серверной активности/метрикам; fake upstream доказывает только распространение cancel до транспорта.

### Состояние, гонки и восстановление

Отмена сохраняется в существующем состоянии `failed`, с type `request_cancelled`, code `request_canceled`, HTTP status `409`. Повтор через gRPC получает `Canceled` с этим reason, через HTTP — сохранённую JSON-ошибку `409`; по code она отличима от конфликта ключа. Это новый прикладной код, а не новый успешный ответ. При восстановлении незавершённого запроса без клиентов используется тот же terminal-формат с code `client_disconnected`.

Успех и отмена конкурируют за один terminal-переход, упорядоченный общим механизмом сохранения состояния. Если успех уже долговечно записан, отмена его не меняет. Если первой выбрана отмена, поздний ответ upstream не превращает задание в succeeded. Учёт слота и памяти идемпотентен независимо от порядка завершения worker и сохранения отмены. При невозможности сохранить выбранный исход дальнейшие назначения блокируются до согласования состояния.

После рестарта прежних подключений уже нет. Восстановленные queued-задания и поздние входные записи, не связанные с активными вызовами текущего процесса, завершаются как `client_disconnected` до включения диспетчера; они не запускаются в фоне и не получают окно для переподключения. Восстановленные running сохраняют прежнее правило `execution_interrupted`, поскольку результат старого upstream-вызова неоднозначен; автоматического повторного исполнения нет. По умолчанию их слот остаётся занят. Если для инстанса явно включён проверенный `abort_on_disconnect`, gateway освобождает слот при восстановлении прерванного запроса, поскольку закрытие старого HTTP-соединения останавливает генерацию на этом upstream. Проверка относится к конкретным версии endpoint и сетевому пути и должна повторяться после их изменения. Иначе только явный `server_execution_limit` (серверный предел полного выполнения, включая очередь upstream) разрешает освобождение по таймеру: окно отсчитывается от `FinishedAt` неоднозначного исхода, для восстановленного `running` — от рестарта. Клиентские `timeout`/`upstream_timeout` сами по себе этого не разрешают. Отсутствие/`0s` или неизвестный `FinishedAt` отключает таймер; retry/backoff не сокращает окно последней попытки. Terminal-отмена и успех воспроизводятся как сохранённые исходы. Это намеренное изменение прежнего восстановления ожидающей очереди.

Клиент, чей deadline истёк, получает локальный `DeadlineExceeded`; при явной отмене — `Canceled`, если транспорт позволяет доставить ответ. Это не гарантирует такой же сохранённый исход: другой клиент мог продолжить ожидание, а успех мог опередить отмену. При истечении общего дедлайна сохраняются правила таймаута задания; если итог не удалось надёжно сохранить, возвращается `Unavailable / state_unavailable` без обещания terminal-записи.

Автоматический retry policy и hedging на gRPC-клиенте не включаются. Повтор с тем же ключом выясняет исход, но не возобновляет отменённое задание. Существующие ограниченные upstream-повторы допустимы только пока задание не отменено и остаются активные ожидающие клиенты.

## 8. Ошибки

Приложение возвращает gRPC status и стандартный `google.rpc.ErrorInfo`: domain `llmgateway`, reason — существующий машинный код gateway, metadata — безопасные `type` и `request_id`. При доступной задержке повторения добавляется `google.rpc.RetryInfo`. Тексты запросов, адреса инстансов, токены и сырые upstream-ошибки в детали не попадают.

| Ситуация | HTTP | gRPC |
| --- | --- | --- |
| Ошибка контракта, контекста модели или параметров | 400 | InvalidArgument |
| Конфликт ключа | 409 | AlreadyExists |
| Сохранённая отмена / потеря клиентов | 409 | Canceled |
| Превышен размер запроса | 413 | ResourceExhausted |
| Перегрузка, лимит вызовов, исчерпанные upstream 429 | 429 | ResourceExhausted |
| Ошибка upstream, некорректный ответ, execution_interrupted | 502 | Internal |
| Gateway не готов, недоступны очередь или состояние | 503 | Unavailable |
| Сохранённый таймаут задания/upstream | 504 | DeadlineExceeded |
| Отмена ожидания клиента | Ответ может не дойти | Canceled |

Статус сам по себе не разрешает повторную генерацию: клиент учитывает ключ и reason. Неизвестный RPC получает стандартный `Unimplemented`. Для ошибок, сформированных gRPC-runtime до handler, наличие ErrorInfo не гарантируется.

## 9. Listener, лимиты и жизненный цикл

В конфигурацию добавляются `grpc_listen_address` (по умолчанию `:8011`), `grpc_max_receive_bytes` (2 MiB), `grpc_max_send_bytes` (40 MiB) и `grpc_max_concurrent_streams` (128). Значения проверяются при старте. Это начальные эксплуатационные пределы, не подтверждённый нагрузкой SLA.

Оба транспорта дополнительно применяют действующий `max_body_bytes` к общему каноническому JSON запроса: нельзя обходить лимит через более компактное protobuf-представление. HTTP сохраняет также исходный лимит размера тела. Ограничения protobuf-пакета включают обёртку, а gRPC-клиенту следует явно задать предел ответа не меньше серверного, чтобы большой completion не упирался в библиотечный default.

Допустимый успешный результат должен помещаться и в gRPC-ответ, и в существующие ограничения upstream/Redpanda. Если сохранённый HTTP-результат превышает gRPC send limit, повтор через gRPC получает ResourceExhausted с request ID и причиной `response_too_large`; сохранённое задание не меняется и новая генерация не начинается. Объём ответа проверяется до отправки, чтобы вернуть прикладную причину.

Оба listener привязываются до перехода процесса в readiness. Ошибка bind любого обязательного listener завершает запуск с ненулевым кодом. Ошибка работающего listener снимает readiness и запускает общий shutdown.

При остановке readiness снимается для обоих транспортов, новые прикладные запросы отвергаются, HTTP Shutdown и gRPC GracefulStop выполняются параллельно. Один общий grace period ограничивает ожидание; по его истечении вызывается gRPC Stop, закрываются оставшиеся соединения и завершается общий runtime. Рабочие вызовы используют общий механизм сохранения и восстановления gateway.

HTTP-ручки `/health/live`, `/health/ready`, `/metrics` доступны внутри сети и через общий маршрут Caddy `/llm-gateway/*`. Дополнительно gRPC health service использует ту же readiness и публикуется только внутри Docker. Reflection в первой версии отключён; диагностика использует `.proto`. Метрики получают низкокардинальные labels `transport=http|grpc` и status; очередь и in-flight upstream не удваиваются, request ID и промпты не становятся labels.

## 10. Caddy и Compose

Этот раздел фиксирует состояние на 16.10.2026 и первоначальное предложение. В текущем корневом dev Compose gateway и Redpanda обязательны и запускаются без профиля; `observability` включает Prometheus/Grafana, а `swagger` — backend Swagger. gRPC-клиенты backend и course-graph подключаются к `llm-gateway:8011` внутри Docker. Внешний gRPC-маршрут через Caddy и профиль `gateway`, описанные ниже, не являются текущим способом подключения сервисов.

В существующий HTTPS-блок Caddy добавляется отдельный handle, до fallback frontend:

```caddyfile
handle /llmgateway.v1.Gateway/* {
    reverse_proxy h2c://llm-gateway:8011
}
```

Путь не переписывается: `/llmgateway.v1.Gateway/Complete` доходит до gRPC-сервера целиком. Клиент указывает только hostname и внешний HTTPS-порт; `/grpc` или `/llm-gateway` к target не добавляется.

Клиент → Caddy: TLS и HTTP/2 с проверкой сертификата. Caddy → gateway: h2c внутри доверенной Docker-сети. Клиент доверяет используемому проектом CA; отключение проверки сертификата не является штатной настройкой. Дополнительные CORS-правила не нужны для native gRPC.

gRPC health и reflection не добавляются в маршрут сервиса Gateway; HTTP health и metrics доступны через Caddy `/llm-gateway/*`. Gateway и Redpanda запускаются корневым Compose без профиля; недоступный upstream может вызвать транспортную ошибку прокси. `8011` доступен контейнерам как `llm-gateway:8011` без проброса на хост; HTTP опубликован на `127.0.0.1:8010`. Профиль `swagger` включает документацию, `observability` — мониторинг.

Доступ через Caddy сохраняет текущую модель доверенного окружения без клиентской аутентификации. Подключение gRPC не является основанием выставлять сервис в публичный Интернет.

## 11. Сборка в монорепозитории

Build context gateway — корень проекта `ai-tutor`, Dockerfile — `services/llm-gateway/Dockerfile`. COPY используют пути относительно корня; это относится к сервисному Compose и корневому extends.

В builder сохраняется структура соседних модулей: `/src/services/llm-gateway` и `/src/services/shared`. Сначала копируются go.mod/go.sum обоих модулей, затем загружаются зависимости, затем исходники и сгенерированные файлы. Сборка выполняется с `GOWORK=off` и локальным replace. Protoc не требуется в runtime или при обычной сборке образа. Runtime получает бинарник; конфигурация и правила моделей передаются в YAML через `GATEWAY_CONFIG`. Корневой `.dockerignore` исключает `.env`, сертификаты и прочие файлы вне необходимых исходников из build context.

Backend Dockerfile и dev mounts включают shared. Shared README описывает обязательное присутствие соседнего модуля при standalone-сборке потребителя. Отдельная публикация shared во внешний registry сейчас не нужна.

## 12. Проверки и критерии приёмки

1. Чистая генерация воспроизводит закоммиченный Go-код; проверка совместимости различает добавление поля и несовместимое изменение номера/типа.
2. Shared и gateway собираются и проходят `go test ./...`, gateway дополнительно `go test -race ./... -count=1` и `go vet ./...` с `GOWORK=off`. Образ собирается с корневым context без protoc на host.
3. Табличные тесты валидатора покрывают пропуск/ноль optional, неизвестные enum, обязательный content, NaN/Inf, stop, конфликт бюджетов, JSON mode и возможности пула. HTTP сохраняет прежние ответы и статусы.
4. С fake upstream и реальной тестовой Redpanda одинаковые HTTP/gRPC-запросы с одним ключом, в том числе конкурентные и после рестарта, вызывают одну генерацию. Несовпадение содержимого даёт конфликт. Восстановление старого хеша stop проверяется отдельной фикстурой.
5. Для HTTP и gRPC отмена после приёма и короткий клиентский deadline последнего ожидающего клиента отменяют queued-задание либо активный upstream-вызов. Fake upstream наблюдает отменённый context и закрытие тела; новые retry не стартуют, слот освобождается один раз. То же проверяется сквозь Caddy. Уже отменённый context до регистрации не создаёт задания.
   Отдельные race-тесты покрывают двух клиентов с одним ключом, отключение одного и последнего, конкурентное переподключение, гонку успеха с отменой, отмену во время публикации/backoff и недоступность Redpanda при сохранении отмены. Повтор отменённого задания другим транспортом возвращает ошибку без новой генерации. После рестарта queued-задания без клиентов не запускаются, terminal-отмена не теряется при поздней доставке входной записи.
6. Общая перегрузка, недоступность очереди, ошибки сохранения, upstream timeout и retry-after дают согласованные статусы и детали. Все RPC делят лимит вызовов и очередь с HTTP.
7. Проверены ответы больше 4 MiB с настроенным клиентом, превышения receive/send/application limits и сохранность результата после отказа отправки. JSON сохраняет точные байты и числа исходного результата.
8. `caddy validate` проходит. Стандартный сгенерированный клиент вызывает Complete через TLS Caddy и напрямую по h2c внутри Docker. gRPC status и error details проходят через proxy; HTTP endpoint продолжает работать.
9. Оба маршрута gateway доступны без профиля; `swagger` включает docs. gRPC health/reflection не публикуются через маршрут Gateway; HTTP health и metrics доступны через `/llm-gateway/*`.
10. Занятый gRPC-порт не позволяет процессу объявить readiness. Общая остановка ограничена grace period и сохраняет действующие правила восстановления незавершённых заданий.

Интеграционные тесты без Redpanda явно отмечаются как пропущенные. Fake upstream не подтверждает доступность реальных моделей. Изменение не принимается только по успешному health или сборке protobuf.

## 13. Документация и границы поставки

Реализация включает shared, транспортный адаптер и общий слой gateway, конфигурацию listener/лимитов, Docker/Compose/Caddy, генерацию и проверки CI, документацию Python-генерации. README проекта ссылается на эту спеку и разделяет реализованный HTTP и новый gRPC после его фактического появления. OpenAPI остаётся контрактом HTTP, protobuf — контрактом gRPC.

HTTP не удаляется, существующие вызовы не переводятся автоматически. Откат транспорта состоит в удалении внешнего маршрута и возврате предыдущего образа с совместимыми JSON-заданиями; shared сам по себе не требует миграции данных. Перед полным откатом gRPC-клиенты переводятся на HTTP или останавливаются. Поддержка старых хешей, запись отмены в понятном прежнему коду статусе failed и отсутствие protobuf-записей в Redpanda обязательны для такого отката. Старый образ не обеспечивает новую отмену при отключении клиента; возврат к нему также возвращает прежнюю семантику исполнения очереди.

## 14. Технические основания

- [Protobuf Go generated code](https://protobuf.dev/reference/go/go-generated/): go_package и размещение сгенерированных пакетов.
- [Proto3 language guide](https://protobuf.dev/programming-guides/proto3/): presence, optional и совместимость полей.
- [gRPC error handling](https://grpc.io/docs/guides/error/): статусы и структурированные детали ошибок.
- [Go multi-module workspaces](https://go.dev/doc/tutorial/workspaces): работа с соседними модулями и отличие workspace от replace.
- [gRPC cancellation](https://grpc.io/docs/guides/cancellation/): обработчик должен самостоятельно останавливать прикладную работу при отмене RPC.
- [Go net/http](https://pkg.go.dev/net/http#NewRequestWithContext): context исходящего запроса управляет подключением, отправкой и чтением ответа.
