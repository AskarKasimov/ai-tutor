# LLM Gateway — спецификация сервиса

Дата: 15.10.2026. Статус: **реализация v1 начата**. Первый сервисный контур находится в `services/llm-gateway/`; критерии совместимости реальных endpoint, нагрузочные показатели и часть эксплуатационных метрик требуют завершения и проверки.

## 1. Задача и границы

Вынести очередь, выбор модели и балансировку LLM-запросов из backend в отдельный сервис `llm-gateway`. Сейчас команда располагает четырьмя развёрнутыми LLM с OpenAI-compatible HTTP API. Backend будет существенно меняться; транспорт к моделям не должен зависеть от его предметных модулей.

Название **LLM Gateway** отражает единую точку входа и скрытие инфраструктуры моделей. `LLM Provider` легко спутать с поставщиком самой модели. Альтернатива — `LLM Dispatcher`, если в названии важнее подчеркнуть диспетчеризацию.

### Подтверждено

- Самостоятельный микросервис в этом монорепозитории, очередь на Redpanda.
- Одна прикладная HTTP-операция: OpenAI-compatible запрос без выбора модели клиентом.
- Обязательная сложность: по ней сервис детерминированно выбирает модель, без отдельной router-модели.
- Необязательный boolean срочности: срочный запрос получает приоритет перед ожидающими обычными.
- Параллельная работа с четырьмя существующими развёртываниями; число четыре не зашито в реализацию.
- В v1 только полный ответ; streaming не нужен (согласовано отдельно).

### Предложения этой спеки

Следующие решения требуют ревью: название, три уровня сложности, точный набор поддерживаемых параметров, строгий приоритет без защиты обычных запросов от голодания, один активный диспетчер и восстановление состояния из Redpanda. Конкретные адреса, идентификаторы моделей, их возможности и производительность пока не проверены.

В scope нет учебной логики, хранения диалогов, изменения промптов, генерации графа, вызова инструментов, embeddings, мультимодальности, публичного доступа из браузера, дополнительных ручек статуса заданий и автоматического определения сложности. Сервис может передавать только явно поддержанный контракт.

## 2. Термины

| Термин | Значение |
| --- | --- |
| Запрос | Одна операция получения Chat Completion; может ожидать исполнения или выполняться. |
| Сложность (`complexity`) | Оценка требуемой способности модели, которую задаёт вызывающий код; не длина контекста и не срочность. |
| Срочность (`urgent`) | Приоритет начала исполнения, независимый от сложности. |
| Модель | Конкретный идентификатор модели в API upstream. |
| Инстанс | Развёртывание модели с адресом, возможностями и лимитом параллельных запросов. Разные инстансы могут обслуживать одну модель. |
| Пул | Разрешённые для уровня сложности инстансы. |
| Диспетчер | Компонент gateway, который выбирает следующий запрос и резервирует слот инстанса. |

## 3. Контракт HTTP

### Запрос

`POST /v1/chat/completions`, `Content-Type: application/json`.

Gateway доступен только из доверенной локальной сети, клиентская Bearer-аутентификация отсутствует. Токены upstream хранятся отдельно в локальной конфигурации gateway. Клиент не передаёт адрес upstream или его секреты.

```json
{
  "messages": [
    {"role": "system", "content": "Верни JSON с кратким объяснением."},
    {"role": "user", "content": "Объясни разницу между BFS и DFS."}
  ],
  "complexity": "medium",
  "urgent": true,
  "temperature": 0.3,
  "max_tokens": 2048,
  "response_format": {"type": "json_object"},
  "stream": false
}
```

| Поле | Правило v1 |
| --- | --- |
| `messages` | Обязательный непустой массив. Роли `system`, `user`, `assistant`; `content` — строка. Сохраняются содержание и порядок сообщений. |
| `complexity` | Обязательное перечисление `low`, `medium`, `high`. Пропуск, `null` и другие значения — `400`. |
| `urgent` | Необязательный boolean, по умолчанию `false`. Строки, числа и `null` — `400`. |
| `model` | Запрещён, даже если совпадает с конфигурацией. Наличие — `400`. Gateway подставляет upstream `model` сам. |
| `stream` | Отсутствует или `false`; `true` — `400 unsupported_parameter`. |
| `temperature`, `top_p`, `stop`, `presence_penalty`, `frequency_penalty`, `seed` | Необязательные стандартные параметры Chat Completions. Передаются без изменения после проверки типа, диапазона и возможностей пула. |
| `max_tokens`, `max_completion_tokens` | Необязательные положительные целые, одновременно задавать нельзя. Адаптер конкретного upstream проверяет поддержку выбранного поля. Нельзя молча уменьшать бюджет. |
| `response_format` | Необязательный; в v1 `text` или `json_object`. JSON Schema — отдельное расширение после проверки upstream. |
| `reasoning_effort` | Необязательный `low`, `medium`, `high` для совместимости с существующими клиентами. Это параметр генерации, не замена `complexity`. |
| `n` | Отсутствует или `1`. |
| Остальные поля | `400 unsupported_parameter`, включая `tools`, `tool_choice` и мультимодальный контент. Нет молчаливого игнорирования. |

Для параметров, не поддерживаемых ни одним инстансом выбранного пула, вернуть `400 unsupported_parameter` до постановки в очередь. Несовместимый контекст не обрезать; превышение контекстного окна — `400 context_length_exceeded`. Способ подсчёта токенов задаётся адаптером модели; размер HTTP-тела проверяется независимо.

`complexity` и `urgent` удаляются перед отправкой upstream. Gateway не добавляет промпты и не преобразует смысл ответа.

Это **совместимость с подмножеством Chat Completions**, с двумя расширениями и без клиентского `model`. Стандартный SDK, требующий `model`, потребует тонкого адаптера; обещания работы любого OpenAI SDK без изменений нет.

### Ответ

Соединение остаётся открытым на время очереди и генерации. Успех — `200` и объект Chat Completion: `id`, `object: "chat.completion"`, `created`, `model`, `choices`, `usage` при наличии у upstream. `model` в ответе — фактически использованная модель. `finish_reason: "length"` сохраняется; gateway не выдаёт такой ответ за завершённый по `stop`.

Заголовок `X-Request-ID` содержит идентификатор gateway и возвращается также при ошибке. Физический инстанс, URL и секреты в ответ не попадают. Успех клиенту отдаётся только после долговечной записи результата в Redpanda.

Не возвращать `202`: отдельного API опроса результата в v1 нет.

### Повторы одного HTTP-запроса

Необязательный `Idempotency-Key` позволяет безопасно переподключиться через ту же операцию. Ключ уникален в пределах учётных данных клиента; без него каждый вызов считается новым запросом.

- Тот же ключ и семантически то же JSON-тело: дождаться существующего задания либо вернуть сохранённый результат/ошибку, без новой генерации.
- Тот же ключ с другим телом, включая другую срочность или сложность: `409 idempotency_conflict`.
- Канонизация JSON исключает влияние порядка ключей; значения по умолчанию нормализуются до вычисления хеша.
- Результаты и ключи хранятся 24 часа с завершения. После этого повтор может стать новым заданием; это часть контракта.
- Обрыв HTTP-соединения не отменяет долговечное задание. Оно выполняется до результата или общего дедлайна; повтор с ключом присоединяется к нему. Отдельной отмены в v1 нет.

## 4. Выбор модели и балансировка

`low` — простое извлечение и преобразование; `medium` — обычная генерация и анализ; `high` — сложное рассуждение и проверка. Это ориентиры для авторов вызывающего кода, не автоматические эвристики gateway. Распределение учебных операций по уровням определяется в backend отдельно.

Конфигурация явно сопоставляет каждому уровню непустой список инстансов. У одного инстанса могут быть несколько уровней, а все три уровня на старте могут ссылаться на одни и те же четыре развёртывания. Нельзя выводить их различия в качестве из самого факта наличия четырёх endpoint.

Для каждого инстанса задаются `id`, `base_url`, upstream `model`, ссылка на секрет, `max_in_flight`, поддерживаемые параметры, контекстное окно и таймаут. Из допустимых и доступных инстансов выбирается имеющий наименьшее отношение `in_flight / max_in_flight`; при равенстве — round-robin. Лимит общий для всех уровней сложности, использующих инстанс.

Слоты резервируются атомарно до вызова upstream. При четырёх инстансах с `max_in_flight: 1` одновременно исполняются максимум четыре запроса, по одному на инстанс. Значение `1` — безопасная начальная настройка, повышается по результатам измерений.

Если подходящие инстансы заняты или временно недоступны, запрос ожидает до дедлайна. В другой пул самовольно не переносится: особенно запрещено понижать сложность ради скорости. Состояние circuit breaker исключает неработающий инстанс из новых назначений; начальные параметры — три последовательные транспортные ошибки/`5xx`, пауза 15 секунд, затем один пробный запрос. `4xx` клиента breaker не открывают.

## 5. Очередь и срочность

Redpanda — долговечный транспорт заданий и состояний. Она хранит упорядоченный лог, а не поддерживает вставку сообщения в его начало. Приоритет реализует диспетчер gateway.

Предлагается один входной topic `llm.requests.v1` с одной partition и один compacted topic `llm.state.v1`, также с одной partition. Один активный процесс gateway владеет HTTP-входом, потреблением и диспетчеризацией. Внутри процесса исполнения параллельны; Kafka-consumer не привязан к одному инстансу LLM. Горизонтальное масштабирование и автоматический failover gateway не входят в v1; второго активного владельца нужно исключить настройками развёртывания.

Один consumer последовательно принимает задания и регистрирует их в долговечном состоянии. Диспетчер строит из него две логические очереди: urgent и normal. Обе упорядочены по offset входного сообщения; повтор с тем же ключом не создаёт новую позицию. Нельзя заранее резервировать слоты под длинный локальный пакет обычных запросов.

При каждом освобождении слота:

1. Рассмотреть срочные ожидающие запросы, для которых есть совместимый свободный инстанс.
2. Выбрать самый ранний из них; если таких нет — самый ранний исполнимый обычный.
3. Пропустить запрос, заблокированный своим пулом, чтобы он не блокировал другие пулы.

**Гарантия срочности:** зарегистрированный срочный запрос опережает все зарегистрированные обычные, которые ещё не получили слот и конкурируют за подходящий ему инстанс. Срочные между собой идут FIFO. Новая срочная задача не прерывает выполняющуюся и не вытесняет её из слота. Запись, ещё не прочитанная из входного topic, пока не участвует в выборе; лаг приёма контролируется отдельно. Абсолютный порядок относительно ещё не зарегистрированных сообщений не обещается.

Это строгий приоритет: непрерывный поток срочных запросов может задерживать обычные до дедлайна. Aging, квоты и резервирование части слотов под normal меняют эту семантику и не включаются без отдельного решения.

## 6. Жизненный цикл и восстановление

Состояния: `queued → running → succeeded | failed`; из `queued` возможен `expired`. Повтор после подтверждённого отказа до начала генерации может вернуть задание в `queued` с исходной позицией. Все записи имеют версию схемы, request ID, client ID, idempotency key/hash, исходный offset, время поступления, дедлайн, параметры, номер попытки и выбранный инстанс. Терминальное состояние содержит полный HTTP-результат.

Предлагаемый протокол без дополнительной БД:

1. HTTP-обработчик валидирует запрос и публикует его с `acks=all`; недоступность Redpanda не приводит к обходу очереди прямым вызовом модели.
2. Consumer проверяет идемпотентность и транзакционно записывает `queued` в state topic вместе с commit входного offset. Локальная очередь обновляется только после commit транзакции. Повтор доставки не создаёт второе задание.
3. Перед вызовом модели диспетчер долговечно записывает `running` с идентификатором попытки. Успех этой записи обязателен для начала HTTP-вызова upstream.
4. По завершении записывает `succeeded`/`failed`, затем уведомляет ожидающих HTTP-клиентов. Старый результат попытки не может перезаписать терминальное состояние.
5. При запуске gateway восстанавливает последние committed-состояния до зафиксированной границы state topic с `read_committed`; только затем принимает трафик и продолжает входной consumer с committed offset.

State topic ключуется стабильной идентичностью задания; при наличии `Idempotency-Key` она детерминированно включает client ID и ключ. Это позволяет восстановить индекс ключей без отдельного хранилища. Все изменения состояния сериализуются одним владельцем. Для транзакций используется стабильный `transactional.id`, который блокирует записи старого producer; это не заменяет ограничения на число активных gateway и не может остановить уже отправленный LLM-вызов.

После рестарта `queued` восстанавливаются, просроченные становятся `expired`. Восстановленный `running` имеет неопределённый исход: upstream мог успеть выполнить запрос. В v1 он завершается `failed / execution_interrupted` и **не запускается автоматически снова**. Повтор с прежним ключом возвращает эту ошибку; новый ключ означает осознанную новую генерацию. Клиентские HTTP-соединения после рестарта не восстанавливаются, клиент переподключается сам.

Неопределённая попытка продолжает занимать слот своего инстанса: после таймаута или рестарта нельзя считать upstream свободным только по закрытию клиентского соединения. Слот освобождается при подтверждённом завершении/отмене, по документированному серверному пределу времени генерации либо после операторской проверки. Если такой предел у upstream неизвестен, автоматическое освобождение по таймеру запрещено. Это правило сохраняется отдельно от терминального ответа клиенту и восстанавливается из состояния попытки.

Гарантия — долговечность ожидающих заданий и дедупликация по ключу в пределах срока хранения. Exactly-once выполнение на внешнем OpenAI-compatible endpoint не гарантируется. При сетевом таймауте нельзя считать, что upstream прекратил генерацию.

Compaction не является TTL. Фоновая уборка публикует tombstone для терминальных состояний старше 24 часов; незавершённые состояния не удаляются по возрасту до истечения дедлайна. Для state topic нельзя включать удаление актуальных записей по времени. Входной topic хранится минимум 7 суток; при превышении допустимого лага readiness снимается, потеря входных offsets не маскируется сбросом на latest.

## 7. Дедлайны, перегрузка и ошибки

Предлагаемые стартовые настройки: общий дедлайн 180 секунд от поступления в gateway, upstream timeout максимум 120 секунд и не больше остатка общего дедлайна; HTTP-тело до 1 МиБ; до 1000 незавершённых заданий; буфер полезной нагрузки незавершённых заданий до 256 МиБ. Значения конфигурируемые и проверяются под реальной нагрузкой. Retention и лимит размера сообщений Redpanda должны вмещать сериализованное задание и полный результат; превышение лимита результата даёт контролируемый `502`.

Общий дедлайн включает публикацию, ожидание, повторы и генерацию. Время HTTP-клиента и прокси должно быть больше него с транспортным запасом. Истёкший запрос не начинает новую генерацию. Проверка лимитов незавершённых заданий выполняется последовательно при регистрации, с учётом уже выполняющихся; превышение завершается сохранённой ошибкой `429`. Число HTTP-соединений и незарегистрированных публикаций также ограничено, чтобы очередь не росла через входной буфер.

Автоматический повтор — максимум один, только при доказанном отказе до отправки запроса upstream (например, не удалось установить соединение) либо явном `429` upstream. Учитывается `Retry-After` и оставшийся дедлайн; повтор не занимает слот во время задержки. Таймаут после отправки тела, разрыв во время чтения, произвольный `5xx` и ошибка формата ответа не повторяются автоматически: генерация уже могла состояться.

Ошибки имеют OpenAI-подобную оболочку:

```json
{
  "error": {
    "message": "Превышено время ожидания LLM-запроса.",
    "type": "gateway_timeout",
    "param": null,
    "code": "request_deadline_exceeded"
  }
}
```

| HTTP | Ситуация |
| --- | --- |
| `400` | Невалидный контракт, `model`, streaming, неподдерживаемые параметры, слишком длинный контекст. |
| `409` | Конфликт idempotency key. |
| `413` | Слишком большое HTTP-тело. |
| `429` | Перегрузка gateway или исчерпанные повторы upstream `429`; по возможности `Retry-After`. |
| `502` | Ошибка/некорректный ответ upstream либо `execution_interrupted` после рестарта. |
| `503` | Не готов gateway, недоступна Redpanda, невозможно надёжно принять/сохранить запрос. |
| `504` | Истёк общий дедлайн или таймаут исполнения upstream. |

При неоднозначном результате публикации или потере соединения клиент повторяет тот же ключ: ошибка транспорта не доказывает, что задание не принято. Ошибки upstream нормализуются, без передачи внутренних URL, токенов и сырых диагностических тел.

## 8. Развёртывание и эксплуатация

Предлагаемое размещение — `services/llm-gateway/`, самостоятельный Go-модуль, Dockerfile и сервисный Compose; Redpanda подключается к корневому Compose как инфраструктура. Go выбран для соответствия текущему backend, но сервис не импортирует его `internal` и не использует предметную БД. Существующие адаптеры backend переводятся на gateway отдельной задачей.

Одна прикладная ручка не исключает служебных `/health/live`, `/health/ready` и `/metrics`, доступных только во внутренней сети. Readiness требует загрузки конфигурации, восстановления состояния и доступности Redpanda. Работоспособность моделей отражается отдельно: нельзя объявлять их доступными по одному успешному health gateway.

Минимальные метрики: число и возраст ожидающих по сложности/срочности, лаг входного consumer, длительность очереди и генерации, сквозная latency, слоты каждого инстанса, ошибки, retries, таймауты, срабатывания breaker и идемпотентные повторы. Request ID связывает логи HTTP, Redpanda и upstream. В логах и labels нет текстов диалогов, API-ключей и полных тел запросов/ответов.

Поскольку Redpanda сохраняет промпты и результаты, доступ к topics ограничивается ACL, транспорт защищается, диски и резервные копии — по правилам инфраструктуры. Tombstone не гарантирует немедленного физического удаления данных: очистка сегментов и backup retention настраиваются отдельно.

Graceful shutdown: снять readiness, прекратить приём и новые назначения, завершить активные вызовы в пределах grace period и сохранить результаты. Не успевшие закончиться остаются `running` и обрабатываются по правилу восстановления. При потере Redpanda новые генерации не стартуют; уже полученный результат удерживается до сохранения в пределах дедлайна, иначе клиент получает транспортную/`503` ошибку без обещания сохранённого успеха.

Для production Redpanda предполагается replication factor 3 на трёх брокерах; одноброкерный dev-режим не защищает от потери диска. Одна partition не ограничивает LLM-параллелизм, но throughput входного лога и время восстановления нужно измерить. Gateway v1 имеет перерыв обслуживания при рестарте; многорепличный режим требует отдельного протокола владения слотами и ответами.

## 9. Связь с текущим репозиторием

В README, AGENTS.md и `documents/backend-architecture.md` пока описан прежний план: «клиент к 4 LLM» внутри backend и gRPC для Python. Пользовательское решение о самостоятельном сервисе заменяет эту архитектурную границу; текущий транспорт gateway — HTTP. Go- и Python-клиенты обращаются к нему по HTTP; дополнительные транспорты не входят в v1. Детали этой спеки пока имеют статус предложений.

Текущие адаптеры assessment/taskgen/learning обращаются к моделям напрямую. В частности, learning передаёт `response_format: json_object`, `max_tokens` и `reasoning_effort`; миграция должна сохранить эти возможности либо явно изменить вызывающий код после проверки моделей. `reasoning_effort` не используется для выбора пула.

Переход: реализовать и проверить gateway → настроить инстансы и измерить параллелизм → перевести адаптеры backend и Python на HTTP-контракт → обновить README, AGENTS.md и архитектурные документы. Удаление существующих модулей этой спекой не разрешается. Единый OpenAPI backend не меняется: для отдельного сервиса при реализации создаётся собственный контракт с пометкой planned до подключения операции.

## 10. Критерии приёмки

1. Валидный запрос без `model` возвращает полный Chat Completion; пропуск сложности, неверный boolean, клиентский `model` и `stream: true` отвергаются до вызова LLM.
2. `complexity` и `urgent` не попадают upstream; сообщения и разрешённые параметры сохраняются, upstream `model` берётся из конфигурации.
3. Четыре fake upstream с лимитом 1 одновременно получают четыре запроса; пятый ждёт. Один инстанс, входящий в несколько пулов, не превышает общий лимит.
4. Пока все слоты заняты, зарегистрированы normal A, normal B, urgent C, urgent D. После освобождения совместимых слотов C и D назначаются раньше A и B; уже исполняющиеся запросы не прерываются. Между C и D сохраняется FIFO.
5. Занятый пул `high` не блокирует `low` со свободным слотом. Вне настроенного пула запросы не исполняются даже при отказе всех его инстансов.
6. Перегрузка ограничивает задания, байты и входные соединения. Дедлайн включает очередь, просроченное задание не начинает вызов модели.
7. Повтор с одинаковым ключом, включая конкурентный, создаёт одну генерацию; другое тело даёт `409`. Повтор после разрыва соединения получает существующий результат.
8. После аварийного завершения `queued` восстанавливаются, `running` не запускаются повторно автоматически, терминальные результаты доступны по ключу до истечения срока. Проверяются сбои до/после каждой границы записи состояния и commit offset.
9. Недоступность Redpanda не приводит к прямому обходному вызову LLM или к выдаче несохранённого успешного ответа. Повтор доставки входной записи не дублирует задание.
10. Потеря одного инстанса исключает новые назначения в него; breaker допускает восстановление. Неоднозначно выполненные генерации не повторяются автоматически.
11. Отдельные тесты подтверждают JSON mode и `reasoning_effort` на реальных endpoint перед переводом существующих клиентов. Fake upstream не доказывает совместимость развёрнутых моделей.
12. Нагрузочный прогон измеряет p50/p95/p99 ожидания и генерации, потребление памяти, backlog и время восстановления. Значения `max_in_flight` и таймаутов подтверждены измерениями; численный SLA до этого не заявляется.

## 11. Основания и альтернативы

- Рекомендуется единый диспетчер с состоянием в Redpanda: минимальное число инфраструктурных зависимостей, но требуется аккуратная реализация транзакций и восстановления.
- Redpanda плюс отдельное хранилище состояний упрощает выбор приоритетных заданий и последующее масштабирование, но добавляет зависимость и согласование двух хранилищ. Это альтернатива, не часть предлагаемой v1.
- Простые Kafka-consumer на каждый LLM-инстанс недостаточны: назначение partitions само по себе не учитывает сложность, доступные слоты и общий приоритет.

Технические основания: [Redpanda: порядок внутри partition](https://www.redpanda.com/guides/kafka-architecture-kafka-partition), [consumer offsets](https://docs.redpanda.com/streaming/current/develop/consume-data/consumer-offsets/), [транзакции](https://docs.redpanda.com/streaming/25.3/develop/transactions/), [compaction и tombstone](https://docs.redpanda.com/streaming/current/manage/cluster-maintenance/compaction-settings/), [OpenAI: Create chat completion](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create). Документация OpenAI задаёт форму API, но не подтверждает поддержку параметров четырьмя развёртываниями команды.
