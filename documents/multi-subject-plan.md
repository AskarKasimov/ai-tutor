# План поддержки нескольких предметов и явного запуска диагностики

Статус: backend S1–S4 реализован, 9 октября 2026. Backend тренировки D1–T2 из [training-backend-plan.md](training-backend-plan.md) готов; frontend F1 — следующий этап.

## Порядок исполнения для Luna

Выполнять этапы **S1 → S2 → S3 → S4 → D1 → T1 → T2 → F1**. S1–S4 описаны ниже; D1–T2 — в плане тренировки, F1 — в обоих документах. На каждом этапе менять только перечисленную ответственность, запускать узкие тесты и фиксировать результат. Не начинать frontend до D1 и T2: до этого backend не умеет надёжно сообщить, какая диагностика завершена и доступна ли тренировка. Перед кодом прочитать `AGENTS.md`, `services/frontend/AGENTS.md` при этапе F1 и фактические файлы в карте ниже. Если решение из этих документов расходится с кодом, сначала записать расхождение и исправить план; не добавлять неоговорённый fallback на первый предмет. В таблице `features/`, `entities/` и `queries/` означают соответственно `services/backend/internal/features/`, `services/backend/internal/entities/` и `services/backend/internal/shared/postgres/queries/`.

## Почему нужен отдельный этап

Сейчас БД хранит одну активную карту: `competency_map_state` — singleton, `competency_map_imports` допускает одну строку, а `competency.Repository.Replace` удаляет прежний импорт целиком. `POST /variants` не принимает предмет и собирает вариант по всей активной карте. При открытии `/` frontend автоматически вызывает `POST /variants`, затем `POST /diagnostic-sessions`. Экран выбора не существует. Если просто добавить селектор, второй импорт сотрёт первый предмет.

## Целевой сценарий

Администратор создаёт предмет с устойчивым ID и названием, затем импортирует его карту CSV/XLSX. Импорт одного предмета атомарно заменяет только его активную карту и задания. На главной студент выбирает предмет, затем действие «Диагностика» или «Тренировка». Диагностика создаёт вариант и сессию только после явного нажатия кнопки запуска. Тренировка доступна лишь после завершённой диагностики этого предмета; перед стартом студент видит темы предстоящей тренировки. Вариант содержит задания только выбранного предмета; результат, фидбэк и будущая тренировка сохраняют его ID и название. Повторный импорт или переименование предмета не меняют исторические снимки.

Текущая карта переходит в предмет «Введение в ML» без потери активных заданий и сохранённых вариантов. Старые варианты продолжают читаться из снимков. Диагностические сессии до этапа долговечного хранения остаются в памяти и при перезапуске backend будут потеряны. Пустой предмет виден в админке, но студенту не предлагается для старта, пока из его карты нельзя собрать вариант.

## Данные и миграция

1. Новая миграция создаёт `subjects(id, name, active_revision, created_at)` и предмет «Введение в ML». Существующий активный импорт связывается с ним. `competency_map_imports` получает `subject_id`; ограничение на единственный импорт заменяется ограничением «один активный импорт на предмет». Глобальный числовой `revision` остаётся уникальным, чтобы существующие FK на ревизию сохранились. `competency_map_state.revision` использовать только как глобальный счётчик, а активную ревизию читать из `subjects.active_revision`. Выделение следующей ревизии сериализовать при параллельных импортах; вариант берёт share lock строки выбранного предмета, импорт обновляет ту же строку в транзакции.
2. `variants` получает `subject_id` и снимок названия предмета. Существующие варианты backfill привязывает к ML. Новые диагностические сессии и тренировки наследуют предмет из сохранённого варианта, не из выбора клиента. При чтении исторического результата используется снимок.
3. Импорт удаляет только предыдущий импорт выбранного предмета и его зависимые активные данные; карты, задачи, очереди озвучки и материалы других предметов остаются. Ревизия замены обновляется в той же транзакции. Существующие снимки вариантов и готовые аудиофайлы сохраняются.
4. Материалы, LLM taskgen, каталог задач, поиск и фоновая аудиоочередь получают предметный контекст там, где используют активную карту или задания. Материалы одного предмета не должны попадать в контекст генерации другого. Глобальные справочники таксономии/уровней остаются общими.

Применённые миграции не переписывать. Перед применением новой миграции проверить её на копии существующей БД: backfill активной карты, сохранённых вариантов и повторное чтение после импорта второго предмета.

## Backend API

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/subjects` | Доступный студенту каталог с ID, названием и признаком готовности диагностики по правилу отбора variantgen. |
| POST | `/admin/subjects` | Создать предмет; только admin. |
| POST | `/admin/subjects/{subject_id}/competency-map/import` | Заменить карту указанного предмета. |
| GET | `/subjects/{subject_id}/competency-map` | Прочитать активную карту предмета. |
| POST | `/variants` | Создать вариант по обязательному `subject_id` из тела запроса. |

`GET /variants` фильтрует историю по `subject_id`; `GET /variants/{id}` включает снимок предмета. При создании сессии backend берёт предмет из варианта и проверяет владельца; отдельный `subject_id` в запросе старта не нужен. Для неизвестного предмета — 404, для предмета без подходящих заданий — существующая предметная ошибка 409 с причиной. Все маршруты и схемы отражаются в едином OpenAPI. `GET /subjects/{subject_id}/learning-state` добавляется на этапе D1 после постоянного хранения диагностик; контракт описан в плане тренировки.

Нынешние глобальные `/competency-map` и `/admin/competency-map/import` нельзя тихо трактовать как «первый предмет» после появления нескольких карт. В целевом API они удаляются при одновременном обновлении frontend и OpenAPI; новые клиенты используют только предметные маршруты. Для старого клиента ответ 404 предпочтительнее записи в неправильный предмет.

## Frontend

Главная страница студента сначала показывает список предметов. После выбора предмета показывает действия «Диагностика» и «Тренировка», а также состояние диагностики этого предмета. Выбор предмета не создаёт вариант; создание варианта и сессии происходит только по нажатию «Начать диагностику». Пока нет завершённой диагностики, «Тренировка» недоступна с понятным объяснением и переходом к обязательной диагностике. Активную диагностику можно продолжить. Для завершённой диагностики вход в тренировку ведёт сначала на экран её тем, а не сразу к вопросу. `sessionStorage` хранит ID предмета вместе с `variantId`/`sessionId`, чтобы после обновления вкладки восстановить уже начатую диагностику. Кнопка «Новая диагностика» возвращает к выбору предмета; завершённая диагностика остаётся доступной через backend после этапа D1. Ошибки загрузки списка, пустой список и недоступный предмет имеют отдельные состояния.

Админский экран позволяет создать предмет, выбрать его и импортировать карту в него. В mock режиме используются те же контракты каталога и запуска, с одним демонстрационным предметом.
