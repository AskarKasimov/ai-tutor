# Голосовой тренажёр

> Новое видение от 15.10.2026 — [видение Geek и course-graph](../README.md): устный экзамен Geek по графу курса из материалов. Документ описывает прежнюю модель «карта компетенций → вариант», которую реализует текущий код; новые решения сюда не вносятся.

Состояние: 15 октября 2026, целевой сценарий — по решениям встречи 10 октября 2026. [Видение и термины](../README.md), [единый API](../api/openapi.yaml).

## Сейчас

Frontend всегда работает с backend (mock-режим удалён 12.10.2026). Карточка курса предлагает одно действие «Начать/Продолжить обучение»: запуск создаёт вариант и диагностическую сессию, показывает задания карты и отправляет голосовые ответы в API. После записи студент проверяет расшифровку и отправляет или перезаписывает ответ; после отправки видно только «Ответ принят»; прогресс — полоса в процентах. Итог показывает диагностический балл, общий фидбэк («Что хорошо» — освоенные проверенные ОР, «Что доработать» — пробелы по составляющим) и разбор ответов с оценками. Кнопка «Подтянуть слабые темы» ведёт к вопросу «Сколько у тебя часов?» и плану обучения с чатом наставника. Диагностики, фидбэк, планы и их чат сохраняются в PostgreSQL.

Администратор импортирует карту ML CSV/XLSX в отдельной админ-панели `/admin`. Отдельный taskgen создаёт и сохраняет новые задания через LLM; импорт материалов реализован.

## Целевой сценарий прежней модели (исторический)

Решения встречи 10.10.2026 для AI Journey.

1. Преподаватель добавляет полные задания в текущую карту и увеличивает число ОР с TRUE. Формат прежний; ручных связей и дополнительных документов для сборки не требуется. В демо-сценарии загрузка карты не показывается: карта будет генерироваться отдельными процессами.
2. Студент выбирает предмет и начинает один процесс: проверка → итог → план → тренировка. Отдельного выбора «Диагностика» или «Тренировка» нет.
3. Вариант строится по всей карте без выбора темы из готовых TRUE-ОР с допустимыми таксономией и важностью. На компетенцию выбираются основной и ровно два базовых разных ОР; компетенция с меньше чем тремя такими ОР пропускается с причиной. Если ни одна не подходит, вариант не создаётся.
4. При сравнении ОР для выбора основного таксономия важнее важности: основной — наибольший ранг Блума, при равенстве — большая важность. Базовые — два самых простых из остальных ОР (`competency-map-v4`). Случайно выбирается только конкретный аналог внутри выбранного ОР.
5. Вариант сохраняется со снимками заданий и профилей. Повторное чтение возвращает выбранные задания, в том числе после переимпорта карты.
6. Студент отвечает голосом на все задания, включая multiple choice: называет вариант словами и объясняет. Кнопка микрофона обязательна. Голос наставника — мужской, взрослый, низкий.
7. Backend диагностической сессии принимает голосовой ответ и вызывает assessment application с variant ID и ID позиции. Грейдер получает сохранённый снимок и роль. Основной оценивается в 0/1/3, basic — в 0/1; сессия использует роль-зависимую оценку без преобразования. Основной с оценкой 3 пропускает базовые, с 0/1 требует базовых. После ответа балл и вердикт студенту не показываются; прогресс — status bar в процентах, выполненные задания «схлопываются».
8. Итог — общий фидбэк по проверенным ОР с указанием составляющей. Верный ответ не объявляет всю компетенцию освоенной. Нулевые основной и два разных базовых ОР одной составляющей означают «изучить полностью»; иначе неверный или частичный проверенный результат — «дополнительно изучить». Пропуск и вопросы из разных составляющих не доказывают полный пробел. Балл и пометка «Не проверено» не показываются. Внутренняя диагностическая сумма учитывает основные и предъявленные базовые задания включённых компетенций, максимум 3N (3 балла на компетенцию). Технический сбой не превращается в учебный ноль.
9. После итога студента спрашивают «Сколько у тебя часов?» (1 / 3 / 5 / 10+; по запросу заказчика 11.10.2026). Новый план `learning` включает проверенные пробелы; при полном пробеле — ОР соответствующей составляющей из той же ревизии карты. Верные базовые повторно не назначаются. После переимпорта используются сохранённые проверенные задания. Созданные ранее планы не пересобираются. План содержит время на теорию и отработку.
10. Обучение по плану работает по проверенным пробелам и не изменяет исходную диагностику: оглавление со статусами слева, чат наставника справа, прогресс сверху. Стратегию тренировки, правила теории и практики и промпты генерации заданий и теории готовит Марина.

## Реализованное API сессии

Состояние сессии и принятые ответы хранятся в PostgreSQL и переживают перезапуск backend. Реализованы запуск, чтение прогресса, сохранённая озвучка инструкции, голосовой ответ, пропуск задания (`/skip`, оценка 0; в UI кнопки нет) и результат диагностики. Отправка ответа требует `Idempotency-Key`; повтор принятого запроса возвращает сохранённый результат. Истёкшая lease позволяет повторить обработку после сбоя.

Сессия вызывает assessment application, который обращается к настроенной модели. Ошибки STT/grading не записывают score и не меняют позицию.

## Предметный frontend flow

Главная не создаёт вариант при загрузке или выборе предмета. «Начать обучение» запускает диагностику, «Продолжить обучение» возвращает туда, где студент остановился, — в незавершённую диагностику или в план обучения; «Пройти проверку заново» начинает новую диагностику. Состояние берётся из `GET /subjects/{subject_id}/learning-state`.

План обучения создаётся один раз на диагностику (`POST /diagnostic-sessions/{id}/learning-plan` с часами). Урок текущего ОР открывается автоматически: наставник пишет теорию и вопрос, студент отвечает голосом. Верно — ОР пройден; неверно — разбор и новый вопрос; после трёх попыток — «надо повторить». Пройденные темы открываются только для чтения, будущие закрыты.

## Ответственность модулей

Variantgen реализует создание, список, чтение варианта и чтение отдельной позиции. Публичное чтение сразу возвращает main и два basic (в снимках `competency-map-v1`/`v2` — от нуля до двух) без эталонов, criteria, ОС и сырого снимка; внутренний reader предоставляет полные данные и связанные свойства грейдингу. Чтение позиции не выбирает новое задание и не управляет показом базовых.

Приём ответов и порядок диагностики реализованы модулем `diagnostic`, итоговый фидбэк — `diagnosticfeedback`, план обучения — `learning`.

Прежний модуль `training` сохранён на backend без UI: preview «Неосвоенные темы» / «Частичные пробелы в знаниях» / свободная тренировка, бесконечные раунды упражнений из снимков банка и Socratic-чат `training-tutor-v2`. Репетитор сам определяет, когда ответ достаточно полный, после чего backend оценивает его по шкале 0/1/2; ошибка STT/assessment/Tutor не создаёт попытку с нулевым баллом. Настройки Tutor и наставника плана обучения задаются через `BACKEND_TUTOR_*`; URL и модель по умолчанию наследуются от assessment.

Правила отбора — [алгоритм](Алгоритм_составления_варианта.md); HTTP-контракт — [OpenAPI](../api/openapi.yaml).


## Подтверждение голосового ответа

В диагностике и learning остановка записи (в том числе по лимиту 90 секунд) запускает только STT. Студент проверяет расшифровку, затем нажимает «Отправить ответ» или «Перезаписать ответ». Прослушивания своего аудио и ручного редактирования расшифровки нет. В диагностике управление остаётся в правой панели; в learning сохраняется прежняя строка записи. Только явная отправка добавляет учебный ответ и запускает оценивание.

Операции `/diagnostic-sessions/{id}/answers/transcription` и `/learning-plans/{id}/answers/transcription` используют сохранённый текст текущего пользователя без повторного STT. Диагностика связывает ключ идемпотентности с позицией и ID расшифровки; learning сверяет номер темы, исходный вопрос и номер попытки, чтобы повтор ответа не засчитывался даже при одинаковом тексте уточнения. Позднее распознавание после смены задания игнорируется. Неотправленная расшифровка не влияет на прогресс; при выходе из экрана черновик интерфейса удаляется. Старые multipart-операции остаются совместимыми.
