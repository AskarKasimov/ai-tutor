# Голосовой тренажёр: диагностика и тренировка

## Назначение и актуальный сценарий

Студент выбирает дисциплину и тему, отвечает голосом на задания банка, получает оценку и объяснение. Полный MVP объединяет диагностику и тренировку в **одной учебной сессии (`Session`)**. Банк включает авторские задания; согласованное расширение — генерация ИИ по теме/свойствам с немедленной доступностью успешно сохранённых заданий.

**Уточнение от 5 октября 2026:** карта и её банк целиком заменяются повторным импортом; история студента и начатые сессии сохраняют собственные снимки. Происхождение задания, ОС 1:1 и связи свойств описаны в [PLAN.md](../PLAN.md). Этапные OpenAPI ещё требуют соответствующего обновления; отдельный срок генерации не установлен.

Основа этого сценария — план этапов до 1 октября, 7 октября, 14 октября и 1 ноября 2026 года. Диагностика MVP содержит **семь основных заданий выбранного ОР (темы)**. Это заменяет прежнее правило «один случайный ОР и одно задание на каждую составляющую всего курса». Тренировка продолжается внутри той же сессии; отдельную сессию тренировки создавать не нужно.

[Контракты по этапам](../api/README.md) описывают постепенную реализацию. До 1 октября работает голосовой сценарий с текстом вопроса; до 7 октября добавляются учебная база и оценка одного ответа; до 14 октября — полный сценарий ниже. Этап до 1 ноября добавляет гарантии восстановления и повторы обработки.

## Участники и подготовка данных

- **Студент** выбирает курс и тему. Каждый ответ — отдельная запись на конкретное задание. Распознанный текст отображается без сверки, подтверждения или редактирования студентом.
- **Преподаватель/admin** через формы по одной записи создаёт курсы, составляющие РПД, дерево образовательных результатов (ОР), задания и критерии. Загружает РПД, карту компетенций и учебные материалы.
- **Система** фиксирует набор заданий, распознаёт речь, находит фрагменты материалов, проверяет ответы через LLM и сохраняет результаты.

**ОР (образовательный результат) — это тема курса.** Отдельной сущности темы нет. ОР принадлежит составляющей РПД и может иметь дочерние ОР. **Один ОР содержит несколько заданий** с общими свойствами; каждое задание принадлежит одному ОР. Назначение `main`, `basic` или `training` относится к выдаче в сессии. Максимальный балл ответа — 2: полностью верное объяснение; 1 — частичное понимание с ошибкой; 0 — неверно/нет понимания. Критерии и необязательный эталон дополняют задание; решение выносит LLM. Вердикт и подтверждение ОР используются для ветвления.

Для каждого основного задания преподаватель явно указывает **два разных базовых ОР из его дочерних ОР**. У каждого из этих дочерних ОР должно быть готовое базовое задание. Эта связь сохраняется в `basic_outcome_ids`; LLM не придумывает ветвление. Базовые задания проще основных. Тренировочные задания подготовлены по ОР, которые могут оказаться неподтверждёнными.

Подготовка проверяет дерево ОР, задания, критерии, готовность материалов и достаточность банка для этапа. Для полного MVP нужны минимум семь подходящих основных заданий у каждого ОР, допущенного к диагностике, и базовые задания для всех веток. Повторный импорт заменяет активную карту и задания. Снимки выдач и учебного графа начатой сессии сохраняют вопросы и оценки независимо от замены карты; обязательной публикации отдельной версии карты нет.

## Диагностика

1. Студент выбирает курс и ОР (тему) и начинает сессию с `course_id` и `outcome_id`. Система случайно выбирает без повторов **семь основных заданий этого ОР** из текущего подходящего банка. Выбранный ОР должен иметь `diagnostic_eligible=true`. Набор заданий и нужный для продолжения учебный граф закрепляются снимком за сессией.
2. Интерфейс показывает вопрос/варианты текстом и озвучивает отдельную инструкцию. Студент записывает отдельный голосовой ответ; интерфейс показывает состояния записи и обработки.
3. Система распознаёт запись. Готовая расшифровка отображается и отправляется на оценивание по `transcription_id` сохранённой расшифровки. Клиент не передаёт исправленный текст.
4. LLM получает расшифровку, рубрику, задание, эталон при наличии и найденные фрагменты опубликованных материалов. Возвращает балл, вердикт, результаты по критериям, подтверждение ОР и объяснение. Сервер проверяет структуру результата и допустимость балла.
5. После `partial` или `incorrect` по основному заданию система вставляет **два базовых задания**: по одному на каждый связанный базовый ОР. Они выполняются перед следующим основным заданием. Ответ на базовое задание не запускает дополнительную ветку.
6. После оценки всех основных и назначенных базовых заданий система формирует итог диагностики. Балл — сумма **только семи основных** оценок. Базовые ответы уточняют пробелы и не входят в диагностический балл.
7. В список неподтверждённых ОР включается каждый проверенный основной или базовый ОР, по которому хотя бы один ответ имеет `outcome_confirmed=false`. Дубликаты удаляются; непроверенные ОР не объявляются пробелами. Если список пуст, сессия завершается. Иначе студент видит итог и переходит к тренировке.

Таким образом, семь — число основных заданий, а не ограничение общей длины диагностики: при ошибках добавляются базовые задания.

Оценка отдельного ответа доступна сразу после проверки. Итог диагностики появляется после всей диагностической части и затем остаётся неизменным, включая исходный список пробелов.

## Тренировка

1. После диагностического фидбека студент запускает тренировку **в той же сессии с тем же `id`**.
2. Система закрепляет **два разных тренировочных задания на каждый неподтверждённый ОР**. Берутся задания именно соответствующего неподтверждённого ОР из закреплённого банка сессии, которые ещё не использовались в этой сессии. Целевой размер — `2 × число неподтверждённых ОР`.
3. Студент отвечает отдельной записью на каждое задание. Распознавание и проверка LLM работают по тем же правилам.
4. Тренировочные оценки сохраняются отдельно и не меняют диагностический балл или исходный список пробелов. После оценки закреплённого набора система выдаёт итоговый тренировочный фидбек и завершает сессию с `training_completed`.
5. Если банк не позволяет назначить полный набор, система выдаёт доступные задания. После их выполнения возвращается `tasks_exhausted`. Если доступных заданий нет, сессия сразу завершается с этой причиной и объяснением.

Тренировка заканчивается после фиксированного набора, даже если ответы содержат ошибки. Повторная диагностика и бесконечное назначение новых заданий в MVP не предусмотрены. Повторный запрос запуска тренировки возвращает уже закреплённый набор или завершённый результат.

## Состояния и данные

| `Session.phase` | Значение |
| --- | --- |
| `diagnostic` | Основные и назначенные базовые задания выполняются или проверяются. |
| `diagnostic_feedback` | Диагностический итог готов, есть пробелы; ожидается переход к тренировке. |
| `training` | Студент выполняет закреплённые тренировочные задания. |
| `completed` | Сессия завершена: `no_gaps`, `training_completed` или `tasks_exhausted`. |

`task` — запись в банке. `assignment` — её выдача в сессии, с порядком, состоянием, ссылкой на ответ и причиной назначения базового задания. `current_assignment_id` указывает единственное активное задание. Его состояния: `awaiting_submission`, `processing`, `evaluated`, `processing_failed`.

| Данные | Что сохраняется |
| --- | --- |
| Учебная база | Курсы, компетенции/составляющие, ОР (темы) и их свойства/связи, банк с происхождением заданий, критерии/эталоны и материалы. |
| Расшифровка (`Transcription`) | Владелец, идентификатор, распознанный текст и время создания. Возвращается после синхронного распознавания; фонового job нет. |
| Учебная сессия (`Session`) | Владелец, курс, снимок учебных связей/банка, выбранный ОР, фаза, закреплённые выдачи, активное задание, отдельные диагностический и тренировочный итоги, причина завершения. |
| Ответ (`Answer`) | Задание, выдача или `null` при отдельной проверке, ссылка на сохранённую расшифровку, текст, состояние, оценка или ошибка обработки. |
| Оценка | Снимок критериев и материалов, балл, максимальный балл, вердикт, подтверждение ОР, результаты по критериям, объяснение и использованные фрагменты. |

Учебная сессия отличается от сессии авторизации. Все времена в HTTP API — Unix timestamp **в секундах**, тип `integer/int64`. `completed_at=null`, пока операция или сессия не завершена.

## Ошибки и восстановление

Технический сбой не является отрицательной оценкой. При нераспознанной речи студент видит ошибку и предложение повторить запись. При сбое LLM ответ остаётся `processing_failed`; переход к следующему заданию и выдача базовых заданий не выполняются до успешной оценки. После сбоя можно отправить новую запись на то же активное задание. Оценённый ответ не заменяется повторной отправкой.

Распознавание и синтез выполняются синхронно: `POST /api/v1/voice/transcriptions` возвращает `200` с готовыми `id`, `text`, `created_at`, а `POST /api/v1/voice/syntheses` — `200 audio/wav`. До ответа интерфейс показывает обработку. Голосовые jobs и поллинг отсутствуют. Ошибки входных данных или нераспознанная речь возвращаются в `422`, сбой модели — в `502`, недоступность — в `503`, превышение времени ожидания — в `504`.

Оценивание ответа и индексирование материалов остаются асинхронными: `202 Accepted` и чтение результата отдельным `GET`. Аудио загружается один раз; оценивание принимает `transcription_id` сохранённой расшифровки владельца. Одна расшифровка не используется для разных ответов.

На этапе до 1 ноября добавляются повтор проверки сохранённого ответа и `Idempotency-Key` для создающих запросов. Голосовой запрос повторяется исходным `POST`. Для него сохраняется успешный ответ — JSON расшифровки или WAV; отдельной retry-ручки нет. Ключ сохраняется не менее 24 часов; повтор с тем же содержимым возвращает исходный результат, с другим — `409`. Состояние сессии восстанавливается после перезапуска или разрыва соединения через её `GET`: набор заданий, ответы и балл сохраняются, ветвление не дублируется.

## Границы модулей и доступ

Голосовой модуль вызывает GigaAM для распознавания и VoxCPM2 для озвучивания. Учебная база хранит опубликованные данные и предоставляет фрагменты материалов. Модуль оценивания проверяет один ответ. Модуль сессий закрепляет задания и атомарно меняет фазу после сохранённой оценки. Разделение на логические модули не требует отдельного HTTP-сервиса для каждого из них.

Общий API работает по HTTPS, в том числе на IP-адресах корпоративной сети через VPN с доверенным сертификатом. Access- и refresh-токены передаются в `Secure; HttpOnly; SameSite=Lax` cookies. Студент видит только свои расшифровки, ответы и сессии; преподаватель/admin управляет учебной базой. Подробности: [авторизация](auth.md).

Аудио принимается в WAV, Ogg/Opus или WebM/Opus до 25 МиБ. Контракт не ограничивает длительность. Удалённый GigaAM выбирает обычное распознавание до 25 секунд и longform для длинных записей; для longform серверу моделей нужны зависимости/VAD. Синтез принимает текст до 500 символов. Сроки хранения аудио и расшифровок нужно определить при реализации.

## Проверка при реализации

Проверить выбор семи основных заданий выбранного ОР из подходящего банка, неизменность закреплённого снимка после импорта, два базовых задания только после `partial/incorrect` по основному, отсутствие рекурсивного ветвления, диагностический балл только по основным ответам, уникальный список проверенных неподтверждённых ОР, два неиспользованных тренировочных задания на каждый пробел, завершение по числу или исчерпанию банка, сохранение одного `Session.id` и неизменность диагностического итога. Отдельно проверить отсутствие подтверждения расшифровки, права владельца и восстановление без повторного ветвления после технических сбоев.
