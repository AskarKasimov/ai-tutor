# ТЗ: ускорение VoxCPM2 и потоковая озвучка Geek

Дата: 18.10.2026. Статус: спецификация для последующей реализации; изменения runtime ещё не выполнены.

Основание: запрос на первые четыре направления оптимизации — `torch.compile`, уменьшение числа шагов, кеш подготовленного референса и потоковая выдача звука. Числа, протокол и конфигурация ниже — предлагаемые инженерные решения этой спецификации, а не результаты измерений или ранее утверждённые продуктовые требования.

## 1. Цель и границы

Уменьшить время синтеза и время до первого слышимого звука в диалоге Geek, сохранив выбранный мужской голос, полноту русского текста и повторное воспроизведение. Отличать ускорение вычислений от более раннего начала воспроизведения.

В объём входят:

1. Опциональная компиляция модели на CUDA с прогревом.
2. Сравнение 20 и 10 шагов с переключением на 10 только после проверки качества.
3. Ограниченный кеш признаков постоянного референса в памяти процесса.
4. Поток VoxCPM → backend → браузер, включая отмену, ошибки и совместимость с WAV-кешем.

Вне объёма: Nano-vLLM/vLLM-Omni, замена модели, квантование, увеличение числа GPU, batching, удаление общей блокировки модели, изменение учебной логики и STT. Общая пропускная способность очереди не считается решённой этим ТЗ.

## 3. Измерения и условия приёмки скорости

До изменений подготовить воспроизводимый набор из 30 русских реплик: 10 коротких до 100 символов, 10 длиной 100–500, 10 длинных 501–2000. Включить числа, сокращения, термины, вопросы, последнее короткое слово и границу разбиения. Зафиксировать тексты, SHA-256, seed, CFG, референс, версии модели/torch/CUDA, GPU/CPU, RAM/VRAM и лимиты контейнера без секретов.

Измерять отдельно:

- холодный старт с уже скачанными весами, компиляцию, подготовку референса и прогрев;
- ожидание блокировки, кодирование референса, генерацию, упаковку/передачу;
- TTFА сервиса: от принятия запроса до первого PCM-фрейма; TTFA браузера: от нажатия «воспроизвести» до подачи первого аудиосэмпла на выход AudioContext;
- полное время, длительность выходного аудио и RTF = время генерации / длительность аудио;
- p50/p95, ошибки, повторы badcase, пик RAM/VRAM и число провалов буфера при проигрывании.

Сравнивать варианты на одном устройстве, с одинаковым референсом и отключённым кешем готового WAV. Для каждого варианта — прогрев и три измеренных прохода набора; отдельно проверить S3 hit и два конкурирующих запроса. В браузерном сравнении использовать одно сетевое окружение. Влияние компиляции, шагов, кеша признаков и стриминга показывать по отдельности и совместно. Длительность WAV учитывать: более короткое или обрезанное аудио не является ускорением.

Цели допуска на целевой CUDA-сервер, относительно исходного варианта 20 шагов / без compile / без кеша признаков:

- Совместные пункты 1–3: p50 времени генерации ниже минимум на 20%, p95 полного времени не хуже baseline более чем на 5%.
- Стриминг: p50 TTFA браузера ниже минимум на 30% на репликах длиннее 100 символов; первый звук появляется до окончания генерации всей части.
- Ни одна оптимизация не допускает пропущенных фрагментов, обрезанного конца, подмены голоса, NaN/Inf в аудио или новых необработанных ошибок.

Это пороги выпуска, не обещание ускорения. Если порог или качество не достигнуты, сохранить переключатель выключенным и приложить измерения; не объявлять оптимизацию принятой. Для CPU обязательна функциональная совместимость, численный порог ускорения не задан.

## 4. Компиляция и прогрев

Добавить `VOXCPM_OPTIMIZE=off|auto|on`, по умолчанию `off` для совместимости. `auto` включает оптимизацию только на CUDA; `on` требует CUDA, иначе ошибка конфигурации. На CPU не менять precision и не добавлять CUDA-зависимости.

Включение означает `VoxCPM.from_pretrained(..., optimize=True)` и прогрев реальным синтезом короткой русской реплики с рабочим голосом и числом шагов. Прогреть оба используемых пути: полный WAV и streaming. Операции выполняются под существующей блокировкой, до допуска пользовательского трафика. Веса остаются в постоянном volume.

Разделить liveness и readiness: `/health` сохранить с прежним смыслом; новый `/ready` возвращает 503 до окончания загрузки/прогрева и 200 после. При выключенной оптимизации readiness также требует загрузки и прогрева рабочего профиля. Отдельно логировать время загрузки, компиляции/первого inference и прогрева, запрошенный и фактический режим, устройство и причину отказа.

Проверить текущий upstream-код: он может перехватывать исключения compile. Нельзя считать `optimize=True` доказательством работы компиляции. При ошибке, включая отложенную ошибку первого inference: в `auto` один раз пересоздать eager-модель, прогреть и явно зарегистрировать fallback; в `on` оставить readiness=503. Не пытаться повторно компилировать модель на каждом пользовательском запросе.

## 5. Десять шагов и стабильный голос

Сохранить разрешённый диапазон `inference_timesteps` 1–50 и явное значение запроса. До прохождения сравнения значения по умолчанию остаются 20. После приёмки согласованно поменять на 10: default API VoxCPM, `DefaultTTSInferenceTimesteps`, `.env.example`, `.env.prod.example` и документацию. Явное 20 продолжает работать; параметры применяются без пересборки весов, backend env требует пересоздания backend.

Отвязать идентичность рабочего голоса от числа шагов целевого синтеза. Добавить на стороне TTS необязательный `VOXCPM_REFERENCE_WAV` — путь к закреплённому WAV в постоянном volume. При `use_reference=true` и заданном пути использовать этот файл, не генерируя замену при смене шагов/seed/CFG целевой реплики. Для существующих клиентов без этой настройки сохранить прежний алгоритм автосоздания референса. При `use_reference=false` не использовать ни закреплённый референс, ни его кеш признаков.

При развёртывании закрепить копию уже используемого голоса 510/2/20, записать SHA-256 и проверить WAV. Отсутствующий или некорректный явно заданный файл — ошибка readiness, без молчаливой генерации другого голоса. Не удалять старые референсы и volumes. Включение compile может немного менять численный результат даже с тем же seed; битовое совпадение выходов не требуется.

Сравнение 20/10 проводить на одном закреплённом референсе, при одинаковых seed=510 и CFG=2. Два русскоязычных слушателя независимо прослушивают слепые пары всех 30 реплик: полнота, разборчивость чисел/терминов, тембр, артефакты и финальное слово. Любая новая потеря/повтор слова или смена голоса блокирует переключение default; расхождения слушателей разобрать до допуска. Артефакты и оценки приложить к отчёту без пользовательских персональных данных.

Профиль S3-кеша должен учитывать модель/ревизию, хеш голоса, seed, CFG, шаги и версию обработки текста/разбиения. Существующий кеш нельзя использовать под новым профилем только потому, что текст совпал. Текст учебной реплики не менять ради ускорения; существующий completion suffix сохранить.

## 6. Кеш подготовленного референса

Добавить кеш результата `tts_model.build_prompt_cache(reference_wav_path=...)` в памяти процесса. Это кеш признаков референса, а не общий mutable KV-cache разных запросов. Реализацию скрыть в небольшом адаптере API, сохранив логику normalize, seed, badcase retries и преобразования waveform существующего `core.py`; не обходить её прямым вызовом внутреннего генератора без эквивалентных проверок.

Ключ: ревизия/экземпляр модели + SHA-256 байтов референса + device + dtype + версия подготовки признаков и её параметры. Seed/CFG/шаги целевого синтеза не входят в ключ закреплённого референса. Другой референс, изменённые байты файла и перезагрузка модели дают miss. Хеш определяется по содержимому, а не только по пути или mtime.

`VOXCPM_REFERENCE_CACHE_SIZE` — число записей LRU, по умолчанию 4, допустимо 0–16; 0 отключает кеш. Кеш и генерация используют общую блокировку модели; признаки не дописываются результатом целевого синтеза. Если upstream изменяет cache in-place, передавать изолированную копию изменяемых частей. Тензоры референса не удерживают граф autograd. Ошибочный результат не сохраняется; eviction и перезагрузка модели освобождают ссылки на тензоры. Постоянной сериализации GPU-тензоров на диск нет.

Критерии: повторные запросы и части длинной реплики кодируют один неизменный референс один раз до eviction; отключение/eviction не меняет голос и текст; два разных голоса не влияют друг на друга. Отдельно показать cache hit/miss, время build и память. Не обещать фиксированного множителя ускорения коротких реплик без измерения.

## 7. Потоковый протокол и совместимость

### 7.1. VoxCPM → backend

Добавить `POST /synthesize/stream` с тем же JSON и валидацией, что `/synthesize`; старый endpoint остаётся полным `audio/wav`. Для потока использовать `generate_streaming()` через адаптер с кешем признаков. Части длинного текста идут последовательно, между ними те же 150 мс тишины. Не обрезать аудиочанки и не кодировать каждый как отдельный WAV.

Формат потока — `application/x-ndjson`, UTF-8, один объект на строку:

```json
{"type":"start","version":1,"sample_rate":48000,"channels":1,"encoding":"pcm_s16le"}
{"type":"audio","seq":0,"data":"<base64 PCM>"}
{"type":"end","chunks":1,"samples":4800}
```

`sample_rate` берётся из модели, а не из константы; пример не задаёт длину чанка. `samples` — число mono-сэмплов всего потока, включая межчастевые паузы. Нумерация `seq` непрерывна с нуля; непустые PCM-блоки имеют чётную длину. Один `start`, ноль или более `audio`, ровно один терминальный `end` либо `error`. Нулевое аудио не считается успешным синтезом. Перед PCM16-преобразованием проверить конечность float и ограничить амплитуду диапазоном PCM.

Ошибки валидации и конфигурации до открытия потока возвращаются обычным HTTP-статусом. После открытия: `{"type":"error","code":"SYNTHESIS_FAILED"}` и закрытие; детали только в серверном логе. EOF без `end`, пропуск seq, неверная base64 или нечётный PCM означают оборванный поток. Максимум декодированных данных одного потока 64 МиБ; максимум строки 256 КиБ, следовательно большие чанки делятся перед base64. Потребители не предполагают совпадения сетевого read и строки/PCM-блока.

Badcase retry после отправки первого PCM запрещён: уже услышанное нельзя откатить. Для streaming установить `retry_badcase=false`; в WAV-пути сохранить текущие retries. Это различие обязательно проверить на слух и в тестах; не скрывать повторную генерацию внутри потока. Если оно ухудшает качество, streaming не включать по умолчанию.

### 7.2. Backend → браузер

Добавить аутентифицированный `GET /diagnostic-sessions/{id}/turns/{turn_id}/audio/stream?part=reply|question` с тем же NDJSON. Отсутствие `part` означает всю реплику, как у существующего `/audio`. Проверки владельца, типа реплики и пустой части выполняются до обращения к TTS или общему кешу. Браузер не получает адрес модели. Обновить контракт через исходники handler и генератор OpenAPI; текущие WAV-ручки сохранить.

На S3 hit backend читает валидный WAV и передаёт его PCM тем же протоколом без TTS. На miss сразу передаёт PCM и одновременно накапливает его в ограниченном буфере до 64 МиБ для финального WAV. S3-запись публикуется только после корректного `end` и проверки формата/числа сэмплов; ошибка и обрыв не оставляют пригодный кеш. Сбой S3 после успешного синтеза логируется как cache write failure, но уже доставленное полное аудио завершается `end`.

Singleflight для одинакового ключа сохранить между WAV, streaming и warmer: один producer синтеза. Первый поток получает live-данные; остальные потребители ждут завершённого WAV и затем получают его в своём формате. Live broadcast нескольким слушателям в эту итерацию не входит. Если WAV/warmer уже начал работу, потоковый запрос присоединяется как ожидающий WAV; такой запрос отдельно помечается в измерениях TTFA. После завершения producer ожидающие получают результат из его памяти даже при ошибке записи S3.

Результат фонового прогрева не отменяется из-за одного ушедшего слушателя. Для исключительно пользовательского producer без оставшихся потребителей передать cancel до TTS. Производитель, начатый warmer, сохраняет свой ограниченный контекст и не становится бесконечной задачей через `context.WithoutCancel`. Существующий `BACKEND_VOICE_TIMEOUT` ограничивает общую работу producer; каждый слушатель может прекратить своё ожидание независимо.

### 7.3. Проигрыватель

Получать поток через fetch/ReadableStream с cookies; инкрементально разбирать NDJSON и подавать PCM через AudioWorklet в AudioContext. Не вызывать `response.blob()`/`arrayBuffer()` для всего потока и не использовать браузерный синтез речи. Учитывать sample rate через ресемплинг с сохранением состояния между чанками; отдельный decodeAudioData для сырых PCM-блоков не подходит.

Начальный буфер — 200 мс либо весь остаток после `end`, если он короче. Очередь проигрывания ограничена 2 секундами; применять backpressure к чтению. При underrun ставить тишину без потери сэмплов и учитывать событие; после `end` доиграть очередь. Сохранить порядок `reply` → `question`; вопрос запрашивается после завершения получения reply и может готовиться во время его проигрывания. `onStart` вызывается один раз при реальном начале звука или при окончательном отказе/остановке, как требуется текущему экрану.

Stop, смена реплики, уход со страницы и старт записи студента отменяют fetch, очищают очередь и прекращают старый звук. Autoplay denial возвращает доступную кнопку ручного воспроизведения. Ошибка после первого звука останавливает поток и показывает существующее состояние ошибки; автоматическое воспроизведение с начала запрещено. Повтор — только явным действием пользователя. Успешно полученный целый результат можно кешировать для повтора; частичный не кешируется.

Если AudioWorklet/ReadableStream отсутствуют или новый endpoint возвращает 404/406/501 до первого аудио, использовать старый WAV-путь. Произвольные сетевые ошибки/5xx не запускают скрытый повтор TTS. Проверить браузерные ограничения фактических целевых Chrome, Firefox и Safari; указать версии в отчёте.

## 8. Ресурсы, наблюдаемость и выпуск

Блокировку модели сохранять на время генерации, но не сетевого drain: очередь между генератором и HTTP — максимум 8 PCM-блоков по 64 КиБ. Если отправитель не освобождает место 5 секунд, отменить producer и закрыть поток. Проверять отмену между шагами/чанками и при ожидании очереди/lock; освобождение lock — в finally. Закрывать генератор при disconnect. Тест с медленным читателем обязан показать ограниченную память и доступность модели для следующего запроса. Для backend-буфера и Worklet также доказать заданные границы памяти.

В Caddy и обоих HTTP-хопах проверить реальный flush на каждом событии; отключить буферизацию/сжатие данного потока, выставить `Cache-Control: no-store`, не задавать Content-Length. Проверка через реальный reverse proxy обязательна: один только streaming endpoint без ранних байтов в браузере не принимается.

Добавить метрики времени ожидания модели, build reference, генерации, TTFA, cache hit/miss, fallback compile, прерываний/ошибок потока и badcase retries. Frontend фиксирует TTFA и underrun в тестовом отчёте. Не использовать текст, seed, session ID или хеш каждого файла как неограниченные labels Prometheus. Существующие суммарные метрики должны учитывать streaming без двойного подсчёта.

`BACKEND_TTS_STREAMING_ENABLED=false` по умолчанию управляет новым потоком, отключённая ручка возвращает 406. URL `/synthesize/stream` формировать из настроенного URL `/synthesize` с сохранением origin и поддержкой префикса пути; не подставлять произвольный адрес из запроса браузера. Frontend пробует поток, fallback при 406 работает без отдельного публичного адреса модели.

Порядок выпуска: сначала TTS с дополнительной ручкой и старым default 20 → backend с выключенным streaming → frontend с fallback → проверка закреплённого голоса и прогрева → отдельные измерения compile/cache/10 шагов → включение прошедших проверку настроек → streaming после сквозной проверки. Между релизами backend умеет работать со старым TTS: 404/406/501 нового provider endpoint до PCM переводят запрос на WAV один раз. Откат: выключить streaming, вернуть 20 шагов и `VOXCPM_OPTIMIZE=off`; корректно пересоздать backend/TTS и прогреть. Старые голоса/объекты S3 сохраняются, выбирать их только по правильному профилю.

## 9. Этапы реализации и проверяемые результаты

| Этап | Область изменений | Доказательство готовности |
| --- | --- | --- |
| A. Baseline и закрепление голоса | `voxcpm2/api.py`, `API.md`, новые тесты конфигурации | Зафиксированы окружение и набор; профиль 510/2/20 закреплён; повреждённый заданный WAV блокирует readiness. |
| B. Compile/readiness | API и при необходимости адаптер upstream optimize, Compose TTS | Тесты off/auto/on, CPU, отложенной ошибки, однократного eager fallback; прогрев обоих путей; фактический CUDA-замер. |

| D. Шаги и профиль | `services/backend/internal/app/config.go`, env, `geek/application/speech.go`, TTS defaults | Старые явные 20 работают; 10 не меняет закреплённый WAV; S3 namespace различает профили; слепое сравнение и замеры. |

| G. Frontend streaming | `use-turn-audio.ts`, API adapter/types, новый PCM player/Worklet | Раздробленные строки/base64, sample rate, underrun, короткое аудио, stop/смена/запись, autoplay, ошибка после начала, повтор и WAV fallback. |
| H. Сквозной выпуск | Caddy, README обоих репозиториев, API.md, checklist, отчёт | Звук начинается до завершения генерации через proxy; CPU smoke и CUDA-замеры; браузерная матрица; пороги раздела 3 и проверенный откат. |

Каждый этап начинается с тестов на своё наблюдаемое поведение. Mock-тесты не заменяют CUDA-бенчмарк и прослушивание. Runtime без GPU можно проверить на fake-модели; отчёт обязан отличать эти проверки от реального inference.

Команды после реализации: в `tts-stt/voxcpm2` — `uv run --no-sync python -m pytest -q tests/http` в настроенном окружении; в backend — `go test -race ./... -count=1`, `go vet ./...`, `go build -o bin/api ./cmd/api`; во frontend — `npm run format:check`, `npm run lint`, `npm run typecheck`, `npm test -- --run`, `npm run build`. После изменения API — `bash scripts/generate-openapi.sh` из backend и проверка, что повторный запуск не меняет результат. Для затронутых Compose/env — проверки конфигурации по AGENTS.md; для TTS проверить CPU Compose и GPU override. DB-интеграционные тесты запускать с `TEST_DATABASE_URL`, иначе явно назвать пропуск.

Итог реализации: ссылки на согласованные коммиты обоих репозиториев, manifest/результаты замеров и прослушивания, использованные настройки, матрица проверок и список оставшихся ограничений. До этого документ и отдельные unit-тесты не являются подтверждением ускорения.
