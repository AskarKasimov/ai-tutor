# Backend

Go API и PostgreSQL. Команды выполняются из `services/backend`, если не указано иначе. Видение (Geek, course-graph, LLM gateway) — в [корневом README](../../README.md).

## Реализовано и запланировано

Реализованы auth с cookies, каталог и создание предметов (курсов), синхронные STT/TTS, загрузка материалов курса с фоновым конвейером (OCR через `services/course-graph`, перевод через LLM gateway, очистка и темы) и хранением в S3 и PostgreSQL, сборка графа курса по кнопке. Учебная модель (карта компетенций, варианты, assessment, taskgen, диагностика, фидбэк, план, тренировка и озвучка заданий) восстановлена в общем приложении.

Реализована диагностика Geek — устный экзамен по графу курса (раздел ниже).

Учебные audio upload endpoints (`diagnostic-sessions/{id}/answers`, `training-sessions/{id}/answers`, `learning-plans/{id}/answers` и `training-sessions/{id}/exercises/{exercise_id}/chat/turns`) допускают `uploads.max_bytes` в `config/dev.yaml` плюс multipart overhead. Остальные JSON маршруты сохраняют лимит 32 KiB. Импорт `POST /learn/admin/materials` принимает до 100,000 Unicode-символов, включая корректно экранированный JSON. Готовое task audio публикует `/learn/task-audio/{id}/file`; другой сохранённый URL не принимается.

Запланированы (planned в [OpenAPI](../../api/openapi.yaml)):

- статус сборки отдельной ручкой (`GET /admin/subjects/{subject_id}/graph/build`): пока он входит в `GET .../graph`;
- пакет для преподавателя в админке (данные для него уже хранятся).

## Общие курсы

`subjects` хранит общий курс без признака режима. Один ID разделяется учебными и экзаменационными API; каждая предметная таблица сохраняет ownership по `subject_id` и остается независимой. Каталоги возвращают отдельные `learning_ready` и `exam_ready`, а `ready` служит совместимым projection поля текущего API. Миграция `00013_shared_courses.sql` удаляет `subjects.mode`, не меняя ID/имена и сохраняя прежние labels для отката; одинаковые имена не объединяются.

`GET /subjects` требует авторизацию. Студентам возвращаются только готовые курсы с прежними флагами; поле `preparation` им не передаётся. Admin видит все курсы, а оба каталога и оба POST создания возвращают admin-снимок `preparation`. Он агрегируется одним SQL-запросом на каталог из состояния последней сборки, опубликованного графа, текущих материалов и их OCR/очистки, активной ревизии учебной карты и существующего `learning_ready`. Статусы подготовки не меняют готовность и допуск студентов. `exam_ready` по-прежнему означает, что Geek может использовать опубликованный граф: по карте компетенций или по материалам при наличии материалов, как у `geekgraph.Stored`.

Состояние экзамена отдельно описывает подготовку выбранного источника: отсутствие источника, очередь, фактическую работу, терминальную ошибку, неполные метаданные, необходимость запуска сборки или актуальную публикацию. Источник выбирается последней задачей, затем опубликованным графом, сохранённой exam-картой и материалами. Старый опубликованный граф сохраняет `exam_ready=true` во время или после неудачного обновления. Для обучения состояние зависит от активной ревизии и того же `learning_ready`, который используется каталогом и запуском обучения; импорт карты сам по себе не означает готовность.

## Учебная диагностика

Диагностика `/learn` использует учебную проекцию карты компетенций и не меняет правила экзамена Geek. Двухлистовая XLSX-карта загружается через единый маршрут импорта графа: первый лист готовит граф Geek, второй сохраняется как учебная проекция. Структура связывается по компетенции, составляющей и ОР; задания, критерии и эталоны остаются привязанными к своим листам. Учебная редакция активируется в одной транзакции с публикацией подготовленного графа. CSV и однолистовой импорт обучения сохраняют прежний маршрут. В каждой составляющей основное задание оценивается в 0, 1 или 3 балла (2 не допускается), базовое — в 0 или 1. Полный ответ на основное задание пропускает базовые; при частичном или неверном ответе и при пропуске диагностика переходит к базовым заданиям.

Для общей оценки балл каждого заданного задания делится на его максимум, затем доли усредняются по составляющим и компетенциям; каждая компетенция весит 5 баллов. Таким образом, 3/3 и 1/1 дают одинаковую долю 100%, а не разный вес. В план подготовки входят компетенции с результатом ниже 90%.

Политика общего итогового экрана: отдельная совместимость со старыми форматами сессий и миграция под них не предусматривались, поскольку реальных пользователей и данных не было. Это не отменяет указанных ниже локальных правил чтения ранее сохранённых полей Geek.

Готовность обучения и сборка диагностического варианта используют общие пределы содержимого задания: вопрос до 5000 символов, инструкция до 500, эталон до 2000, до 12 вариантов ответа длиной до 500 каждый. Импорт карты исключает некорректную ячейку из банка и возвращает предупреждение с её строкой и колонкой. Проверка `learning_ready` и генератор варианта требуют не меньше трёх различных подходящих ОР внутри одной составляющей. Курс готов, если есть хотя бы одна такая составляющая; ОР разных составляющих и несколько заданий одного ОР не суммируются. Сохранённая диагностика или план обучения открываются по снимку, даже если после переимпорта курс больше не готов к новому старту.

Выбор заданий учебной диагностики и exam-графа выполняется отдельно по каждой составляющей: нужно не меньше трёх подходящих ОР; остальные составляющие пропускаются. Существующие варианты и диагностики сохраняют свою версию алгоритма.

`GET /learn/subjects/{subject_id}/diagnostic-outline` — авторизованный предпросмотр
блоков будущей диагностики. `variantgen` читает активную карту под shared-lock
предмета и применяет общий с созданием варианта отбор `constituent-map-v1`.
Предпросмотр не выбирает случайные задания, не создаёт ID, не сохраняет варианты
и сессии. Возвращает только ID/названия компетенций, составляющих и выбранных ОР
с ролями main/basic; вопросы, эталоны, criteria и ОС не возвращаются.
Отсутствие подходящих компетенций — 200 с пустым списком. После переимпорта
предпросмотр отражает новую карту, сохранённые варианты продолжают читать снимки.

Короткие подписи компетенций и составляющих в графе готовит LLM gateway (`low`): 2–5 слов по исходному названию, без кодов и канцелярита. Ответ `diagnostic-outline` сохраняет исходные `name` и добавляет `display_name`; карточки и диагностика используют исходные названия. Результаты кэшируются в PostgreSQL по названию и версии промпта; при смене названия подпись готовится заново. Генерация идёт последовательно пакетами до 24 названий; все проверенные партии сохраняются одной транзакцией только после успеха всех вызовов модели. Ожидание очереди и каждая партия отдельно получают `llm_gateway.timeout` (по умолчанию 120 с); операции с кэшем — по 10 с. HTTP write deadline для этого ответа учитывает ожидание, число партий и операции с БД; frontend сохраняет отмену при уходе со страницы и выходе из аккаунта без отдельного 30-секундного ограничения. При сбое — 503 с возможностью повтора, без частичного сохранения кэша и без создания варианта или сессии. Граф доступен и на стадии тренировки перед повторным запуском диагностики; снимок уже начатой диагностики не подменяется.

Импорт учебной карты принимает необязательный заголовок `X-Expected-Map-Revision`: при несовпадении с текущей ревизией возвращается 409, карта не заменяется. Интерфейс всегда передаёт последнюю увиденную ревизию.

## Диагностика Geek

В путях этого раздела подразумевается префикс `/api/v1/exam`.

Модуль `features/geek`, правила — в [README](../../README.md#geek-устный-экзамен-и-будущая-тренировка). Обход графа и оценка — чистый код в `entities/exam`: модель возвращает вердикт (`answered` / `dont_know` и диалоговые вердикты), признак полноты `answer_complete`, К1–К4 и строки-основания, а A–D, статусы, засчитывание пререквизитов, спуск, пробелы, прогресс и оценку курса считает код; темы на C идут в итоге отдельным списком `weak_spots`. Темы верхнего уровня идут по покрытию графа (`coverageOrder`: больше ещё не покрытых тем с пререквизитами — раньше; ничьи перемешиваются при старте диагностики), лимит вопросов (по умолчанию 8, `geek.question_limit` в `config/dev.yaml`) задаёт размер выборки. Лимит считает основные, дополнительные вопросы и переформулировки. Хороший полный ответ на одну главную концепцию (answer_complete=true, все проверенные критерии на 2) закрывает тему. К1/К2 обязательны; непроверенные К3/К4 модель возвращает как null, код сохраняет их в `NodeState.Unassessed` и исключает из таблицы. Иначе один дополнительный вопрос уточняет существенное затруднение в той же концепции. Реплики без предметного содержания оцениваются как ответы; «не знаю» на дополнительном вопросе сохраняет уже показанные знания. Переформулировка ограничивает максимум до B и не повышает одинаковые баллы; К1=К2=1 дают C. Лимит остаётся жёстким.

- `POST /diagnostic-sessions` — начать или продолжить (одна активная на курс), `Idempotency-Key` обязателен; без графа — `409 GRAPH_NOT_READY`.
- `POST /diagnostic-sessions/{id}/answers` — синхронный ответ (расшифровка, текст или «не знаю»): реплика студента и следующая реплика Geek в том же ответе. Модель вызывается до сохранения: при сбое `503 MODEL_UNAVAILABLE`, сессия не меняется, повтор с тем же ключом. Повтор после успеха возвращает сохранённый результат; тот же ключ с другим телом — `422 IDEMPOTENCY_KEY_REUSED`.
- `GET /diagnostic-sessions/{id}/feedback` — абзац общего вывода от модели: пишется один раз при первом открытии итога и хранится в `geek_result_summaries`; при сбое модели 503 и повтор. Структура текста и отчёт общие с диагностикой обучения (`entities/resultsummary`)
- `GET /diagnostic-sessions?subject_id=…` — свои диагностики курса, новые первыми (до 50), с оценкой у завершённых; `GET /diagnostic-sessions/{id}`, `GET /diagnostic-sessions/{id}/result` (только завершённая; у каждой вершины — `requires`, прямые пререквизиты в снимке графа, для карты тем на странице итога).
- `GET /diagnostic-sessions/{id}/turns/{turn_id}/audio` — WAV реплики Geek: синтез частями до 500 символов, склейка и кэш в S3 (`geek/voice/{voice_hash}/geek/v2/{session}/{turn}.wav`). `?part=reply` — только реакция на прошлый ответ (поле `reply` реплики), `?part=question` — вопрос или завершение после неё; части кэшируются по тексту и настройкам голоса (`geek/speech/{sha256}.wav`), поэтому подготовленный вопрос графа синтезируется один раз для всех студентов. `?part=intro` — предозвученная вводная (поле `audio_intro`), `?part=transition` — переход к следующему вопросу (поле `audio_transition`), `?part=reply&chunk=N` — блок фидбека с номером от нуля (всего `reply_audio_parts`). Пустая часть — `404 TURN_PART_NOT_FOUND`.

### Оценивание

Полнота ответа оценивается отдельно от К1–К4 по явно запрошенным частям вопроса: для answered модель обязана вернуть boolean `answer_complete`, иначе парсер повторяет запрос. При false код не ставит A даже за максимальные К1–К4: максимум B и дополнительный вопрос о недостающей части, если позволяет лимит. После самостоятельного дополнения возможна A. Пример требуется только при явном запросе; причинная связь внутри примера заменяет отдельный общий абзац. Пропуск запрошенного примера фиксируется полнотой, а не двойным штрафом по корректности и логике. Поле сохраняется в `NodeState`; nil в старых сессиях сохраняет прежнюю совместимость.

Geek использует `reasoning_effort=low` для оценивания, объяснений и формулировок вопросов; `complexity` и `urgent` не меняются. Текст темы передаётся оценщику. Системная инструкция отличает содержательное объяснение своими словами от тавтологии и перечисления терминов; К2 относится только к запрошенному действию, чтобы не требовать причины у вопроса «что показывает?».

Общее правило примеров: оценщик принимает разумные предметно корректные примеры вне теории, соответствующие вопросу, в том числе гипотетические. `assessment_guidance` для этого не обязателен. Системный промпт больше не запрещает такие примеры, сохраняя ограничение вопросов содержанием темы. Критерии оценивают качество показанных знаний, `answer_complete` — покрытие вопроса.

Правило оценки отдельного вопроса в файловом графе задаётся необязательным `assessment_guidance` вершины: оно передаётся только оценщику как уточнение преподавателя. В маленькой фикстуре AI-01-01 просит одну область ИИ, пример задачи и объяснение полезности ИИ; объяснение оценивается лояльно по смыслу, без требования совпадения с теорией. Текст теории не менялся.

Оценка курса считается при чтении через `exam.OverallScore` и `exam.CourseGrade`: каждая компетенция весит 5 баллов, доля задания усредняется по составляющей, доля составляющей — по компетенции, пороги 90/70/60; те же функции использует итог диагностики обучения. Сессия хранится одной строкой `geek_sessions` (снимок графа, состояние обхода и транскрипт в `state`) с версией для конкурентных обновлений; ключи повтора — в `geek_requests`. Если граф курса пересобран (сменилась версия), активная диагностика получает статус `cancelled`.

### Числовые рубрики и правила карты

Перед рубричным оцениванием отдельный маршрутизатор получает только последний вопрос и последнюю реплику, без предыдущих ответов, эталона и рубрики. Паузы, обращения и повтор не отправляются в подсчёт баллов. Частичный ответ с «остальное не знаю» считается ответом. Для каждого положительного пункта модель приводит `quote`. Цитата не влияет на балл и не останавливает ход: если её нет в указанной реплике студента, код убирает её из результата и пишет в лог `rubric quote not in the answer`. Модель может соединять разные части ответа, с многоточием или без; пробелы и регистр при сверке не учитываются.

Рубричный оценщик делает первичную оценку и отдельную сверку всех предметных оценок, включая заявленный максимум: сверка ищет как лишние требования, так и приписанный студенту расчёт или вывод. Оба вызова остаются low/0.2. Повтор после невалидного JSON получает конкретную ошибку схемы. Служебные реплики не проходят через сверку баллов; прежний общий штраф К2 за повторение не применяется к рубрике — происхождение содержания проверяется по её пунктам.

Geek: задания с числовой рубрикой КК оцениваются по её отдельным пунктам, без перевода в универсальные К1–К4. Допустимые целые уровни и максимум извлекаются кодом из явных шкал «КN / Пункт рубрики N» или «Балл (макс. N)». Каждый положительный балл требует ссылки на содержательную реплику студента. В JSON-снимке `geek_sessions.state.exam.nodes.*.rubric` сохраняются пункты, шкалы, баллы, основания и строки; миграция не нужна, публичный HTTP-контракт не меняется. Сумма и A–D рассчитываются в `entities/exam`: полный балл и полный ответ — A, от 75% — B, положительный остаток — C, ноль — D; помощь ограничивает букву до B без изменения сырых баллов. Уточнение получает невыполненные пункты и учитывает предыдущие ответы. Нечисловые авторские правила остаются на прежней шкале. Неполная или противоречивая числовая шкала отклоняется без записи попытки. Новая логика применяется при следующих ответах, сохранённые итоги не пересчитываются.

Качественные правила с заголовками К1/К2 без числовой шкалы остаются на прежнем оценщике. Дробные/отрицательные максимумы и начальные уровни не обрезаются и не теряются при импорте: неподдерживаемая числовая шкала отклоняется целиком. Переформулировка и уточнение авторского задания сохраняют явно запрошенные устные расчёты и сравнения; модель не выполняет их за студента. Повторы и служебные просьбы не расходуют попытку, содержательная подсказка учитывается как помощь.

### Вопросы и фидбек

Фидбек формируется после решения движка. `Evaluate` возвращает только оценивание, затем `Exam.Apply` определяет итог и следующий шаг. `FeedbackRequest` передаёт выбранное задание, накопленное состояние, вердикт, закрытие и следующий шаг. При открытой теме код выбирает вводную из шести вариантов на исход, не повторяя последнюю из той же группы: явно объявляет переформулировку или уточнение без подсказок и второго вопроса. «Основа верная» допустима только при К1=К2=2. Дополнительного вызова модели для вводной нет.

При закрытии темы `Feedback` делает отдельный вызов `low`, reasoning `low`: за A — конкретная похвала за мысль или пример студента без обязательного «но»; при пробеле — короткий разбор недостающего смысла, а не новое задание. Полный ответ после переформулировки поддерживается без выдуманного недостатка из-за ограничения максимумом B. Учитываются все ответы темы, в том числе до «не знаю» на уточнении. Максимум 80 слов, пустой или слишком длинный JSON-ответ повторяется один раз с описанием нарушения. Длину ответа студента, слова-паразиты и стиль не оцениваем. Реплика остаётся в `reply` и озвучивается перед вопросом; разбор закрытой темы помечается `recap` и не попадает в новую тему. Сбой фидбека не сохраняет оценку и ход; повтор с тем же ключом допускается.

У карты компетенций и оценщик, и фидбек видят эталон и `assessment_guidance` именно случайно выбранного варианта из снимка сессии. Качественные правила без числовой шкалы уточняют оценку по К1–К4; числовая рубрика оценивается отдельно по её пунктам, без универсальных К1–К4. `Node.Outcomes` отдельно не передаются; контекст и эталон выбранного задания из карты сохраняются. Свои предметно корректные примеры допустимы в пределах задания и его рубрики. При C и D остаётся защита ещё не проверенных пререквизитов, к которым новый движок спускается дальше; после A/B уже зачтённые пререквизиты не защищаются. Правила карты без лимита, выбор вариантов, слабые места C и новая агрегация курса не меняются. Известная нестабильность low на разговорных ответах и формальной логике этим переносом не объявляется исправленной.

Короткие подтверждения вроде «Я вижу» и «Понятно» направляются на оценку как ответы. На дополнительном вопросе оценщик учитывает все ответы по теме и сохраняет ранее показанные знания, если студент их явно не опроверг.

Для показа распознавание и использование имени студента временно отключены: сохранённое имя не передаётся в инструкции для вопросов, обратной связи и пояснений; генерация получает запрет обращаться к студенту по имени, в том числе указанному в диалоге. Сам диалог остаётся доступен оценщику для проверки ответа.

Заранее подготовленные вопросы: `PrepareQuestions` дописывает недостающий основной вопрос и переформулировку каждой вершины (`exam.Node.Rephrase`; `medium`, не `urgent`; промпт переформулировки видит только сам вопрос). `graph.Worker` перед публикацией сборки вызывает `builtQuestions` (`internal/app/questions.go`): шесть раундов по недостающим вершинам с паузой от 10 с, удваивающейся (около 5 минут), затем ошибка сборки с отдельным сообщением — опубликованный граф остаётся прежним; `question` и `rephrase` записываются в темы, остальные поля сборки не меняются. Граф по карте компетенций проходит тот же шаг: у его тем основной вопрос уже есть (задание карты), готовятся только переформулировки. Графа-фикстуры по умолчанию нет; файлы фикстур используются для тестов и просмотра. Логи — `worker: graph_questions`. Geek берёт подготовленную переформулировку только к подготовленному основному вопросу; иначе (граф или диагностика до решения) генерирует её в рантайме. Дополнительный вопрос всегда генерируется в рантайме.

Новая политика вопросов помечает карточки `topics-v4`; при пересборке графа backend не переиспользует старые карточки. Уже сохранённые вопросы опубликованных графов и фикстур автоматически не меняются.

Для подготовки основных вопросов реализована функция `PrepareQuestions` (application Geek): она заполняет отсутствующий первый вопрос через gateway, сохраняя остальные вопросы и исходный граф. При ошибке вопрос остаётся пустым — Geek генерирует его в рантайме. Её вызывают `graph.Worker` перед публикацией графа (через `builtQuestions`, см. выше; без подготовленных вопросов граф не публикуется) и CLI. Для файла графа есть подкоманда:

```bash
BACKEND_CONFIG=config/dev.yaml go run ./cmd/api prepare-questions ../../api/fixtures/course-graph.json /tmp/graph.json
```

### Озвучка

Фоновая озвучка вопросов: `geek.Warmer` (одна очередь, по одному запросу, без приоритета над студентами) синтезирует основные вопросы и переформулировки в тот же кэш частей. Ошибка синтеза или S3 (в том числе бакет, ещё не созданный `RunStorageSetup`) логируется (`prepared question not voiced; retrying`), текст уходит в конец очереди и повторяется с паузой от 1 с до 5 мин до успеха. Очередь не ограничена и не дублирует ожидающий текст. `graph.Worker` ставит в очередь тексты всех тем перед публикацией графа из материалов или по карте компетенций. Очередь живёт в памяти, поэтому при старте `RunBackground` снова ставит вопросы всех опубликованных графов (`graph.Worker.PrepareVoices`, запрос `ListPublishedCourseGraphs` — то же условие, что у Geek); уже закэшированный текст стоит одного чтения S3. Студенты и очередь используют один `SpeechCache`: одновременные промахи одного ключа ждут один синтез (singleflight); он идёт отдельно от контекста первого запроса, поэтому ушедший слушатель не обрывает остальных. Логи — с полем `worker: speech_warmer`.

Сессия Geek возвращает `audio_intro`, `audio_transition` и `reply_audio_parts`, но текущий интерфейс эти части не запрашивает: он воспроизводит `part=reply` целиком и затем `part=question`, а реплику без отдельной реакции — без `part`. Для длинного текста TTS по-прежнему соблюдает техническое ограничение длины одного запроса.

### Модель, логи и смоук

Граф берётся только из БД (`geekgraph.Stored`): собранный из материалов или по карте компетенций; у курса без него — `409 GRAPH_NOT_READY`. Граф по карте (`source: competency_map`) экзаменуется без лимита вопросов; правило оценки карты приходит в `assessment_guidance` темы. LLM — gRPC-клиент LLM gateway (`llmgateway.v1.Gateway/Complete` из модуля `services/shared`, адрес `services/backend/config/dev.yaml` (`llm_gateway.address`)): без `model`, `complexity` — всё во время сессии `low` (оценка, фидбек закрытой темы, основной вопрос в рантайме, дополнительный вопрос, переформулировка, объяснение после «Не знаю»), заранее подготовленный основной вопрос (`QuestionRequest.Ahead`) — `medium`; вызовы во время сессии помечены `urgent` и опережают фоновую работу в очереди gateway; `RESPONSE_FORMAT_JSON_OBJECT`; невалидный ответ повторяется один раз. Отмена контекста (студент ушёл, истёк таймаут) отменяет запрос и в gateway. Промпты, ответы модели, `request_id` gateway и тексты студентов логируются. В тестах gateway заменяет локальный gRPC-сервер с детерминированными ответами.

Логи — JSON в stdout, уровень задаёт `logging.level` в `config/dev.yaml`; общие поля описаны в [README](../../README.md#итоговые-решения). Каждый HTTP-запрос завершается записью `http request`; при ошибке в ней есть `error_code`, `error_message` и причина `error` из `fault.WithCause`, а `/health` пишется на уровне `debug`. Фоновые задачи материалов и графа получают свой `trace_id` и поле `worker`. Каждый вызов LLM из любого модуля логирует перехватчик gRPC-клиента (`llm call`: `gateway_request_id`, `complexity`, длительность, размер ответа); текст запроса и ответа (`llm call content`) пишется только на уровне `debug`. Ответ модели можно посмотреть и без `debug`: он хранится в топике `llm.state.v1` под ключом `gateway_request_id`.

Также в логах: каждый вызов голосового gateway (`voice gateway call`: операция, длительность, `gateway_request_id`, gRPC-код), кэш озвучки (`geek audio cache hit/miss`), выдача части (`geek turn audio`), завершение и отмена диагностики с версией графа. Запрос, отменённый браузером, пишется как `499 CLIENT_CLOSED_REQUEST` на уровне info; у ошибок в логе запроса есть причина за кодом ошибки.

Сквозной прогон для репетиции: `scripts/geek-smoke.sh [base-url] [strong|weak|mixed]` создаёт курс от админки, регистрирует студента и отвечает на все реплики до итога.

## Экзаменационная карта

Авторские карты с колонками «ID темы» и «Пререквизиты» сохраняют все включённые строки и явные связи, вместо отбора трёх ОР на составляющую. Необязательная колонка «Текст темы» сохраняет теорию. Без этих заголовков алгоритм старых карт не меняется. Подробности используемых и игнорируемых полей — [авторская карта Geek](../../documents/geek-authored-competency-map.md). Это импорт графа Geek, не парсер карты `/learn`.

Карта компетенций: `POST /api/v1/exam/admin/subjects/{subject_id}/graph/competency-map` (multipart: `file` — .xlsx до 25 МиБ). Книга читается стандартной библиотекой (`coursegraph/infrastructure/xlsx`, `First` — только первый лист: остальные листы не разбираются и не тратят лимиты, общими остаются только shared strings), граф строит `coursegraph.BuildMapGraph` (`internal/entities/coursegraph`) по первому листу (второй — для учебной диагностики): колонки по началу заголовка («Компетенция» и «Таксономия» — синонимы), на составляющую основное задание (наивысший Блум, затем важность) и два самых простых, только ОР с TRUE и заданием; темы `map-row-<строка>`, рёбра пререквизитов и иерархии «основное → базовое». Все «Задание N» ОР с критериями того же номера по порядку становятся `variants` темы (`exam.Variant`: вопрос, переформулировка, эталон, рубрика); `exam.NewExam` выбирает вариант каждой темы случайно и хранит в сессии только его. Ошибки — 422: `COMPETENCY_MAP_INVALID` (ячейки с `path: file`), `COMPETENCY_MAP_EMPTY`; 409 — сборка уже идёт. Для двухлистовой книги после проверки обоих листов учебная редакция и карта Geek сохраняются; задание сборки и активация новой учебной версии фиксируются одной транзакцией. Учебный режим готов сразу после ответа импорта. Geek использует прежний опубликованный граф до успешной сборки новой версии; сбой не откатывает обучение. `map.learning_revision` и `graph_map_revision` в снимке `/graph` показывают версии карты и опубликованного графа отдельно. Worker готовит переформулировки всех вариантов, ставит вопросы в очередь фоновой озвучки (не дожидаясь её) и публикует граф так же, как сборку из материалов.

Импорт exam-карты допускает отсутствующие критерии у отдельных заданий и полное отсутствие колонок критериев. Только для таких вариантов назначается общая числовая рубрика корректности и покрытия вопроса (два пункта 0/1/2, максимум 4); все явно заданные части вопроса обязательны. Граф содержит `assessment_warnings` с номерами строк и заданий, использующих общую рубрику; метаданные сохраняются при подготовке вопросов. Повреждённая заполненная рубрика остаётся ошибкой; соседние критерии или эталоны не заимствуются. Парсер учебной карты `/learn` не менялся.

После успешного сохранения импорта экзаменационной карты backend пишет отдельный `WARN` для каждого задания с общей рубрикой: `subject_id`, `filename`, `sheet`, `row`, `column`, `message`. Отклонённый импорт и задания с авторскими критериями таких предупреждений не создают.

При подготовке экзамена API показывает прогресс `prepare_questions`: готовые темы из общего количества; при временном сбое — `retry_questions`, при публикации — `publish`. Для КК это этапы 1/2 и 2/2, после сборки из материалов — 6/7 и 7/7. Необязательное `remaining_seconds` — приблизительное время текущего этапа по завершённым в этом запуске темам; оно отсутствует до двух завершений и при повторных раундах. Озвучка идёт в фоне и не блокирует публикацию. Прогресс не сохраняется в БД.

После окончательного сбоя подготовки экзаменационной карты доступна кнопка «Повторить подготовку карты», в том числе без PDF и до первой публикации. Повтор готовит сохранённую карту с проверкой её fingerprint; исключённые задания не возвращаются, XLSX заново не импортируется. Опубликованный граф сохраняется до успешной подготовки, затем действует обычная отмена активных диагностик при смене графа.

`POST /exam/admin/subjects/{subject_id}/graph/competency-map/retry` требует admin и `X-Expected-Map-Fingerprint` из `map.fingerprint`. Только failed-сборка карты с тем же fingerprint ставится в pending со сбросом attempts. Проверка и постановка выполняются под блокировкой карты в одной транзакции; 409 `COMPETENCY_MAP_CHANGED` при смене карты, `GRAPH_RETRY_NOT_AVAILABLE` при смене состояния или другом источнике сборки.

Исключение заданий без критериев доступно только для успешно опубликованной актуальной экзаменационной карты. Подтверждение сохраняет fingerprint карты и перечень заданий; смена карты в другой вкладке отклоняет операцию с 409 `COMPETENCY_MAP_CHANGED`. Перед сохранением fingerprint проверяется атомарно; устаревшая или неудачно подготовленная замена не меняется.

`POST /exam/admin/subjects/{subject_id}/graph/competency-map/skip-missing-criteria` после подтверждения admin исключает только варианты с общей рубрикой из сохранённой карты. Темы без вариантов и ссылки на них удаляются, остальные варианты сохраняются. Пустой экзамен отклоняется без изменений; повтор без новых исключений ничего не пересобирает. В графе сохраняется `assessment_skipped`; для возврата нужен повторный импорт XLSX. Сам файл не меняется. Публикация изменённого графа отменяет активные диагностики, как при обычном импорте.

## Единый OpenAPI

```bash
bash scripts/generate-openapi.sh
```

Swag генерирует реализованный API во временный файл; merge-openapi обновляет implemented-операции, уже включённые в единый контракт, и сохраняет planned. Исключённые операции не возвращаются автоматически. Новую работающую ручку нужно явно добавить/перевести из planned в implemented в контракте. Неиспользуемые схемы удаляются. Swagger использует этот же YAML.

CI проверяет повторяемость генерации и валидирует реальные ответы по implemented-схемам. Planned-схемы проверяются отдельно без объявления их работающими. Загрузка (включая манифест с неделей и видом), список, каталог видов, правка метаданных и замена PDF описаны как implemented и проверяются контрактными тестами. Swag/yq запускаются через go run с закреплёнными версиями, первый запуск требует загрузки инструментов.

## Запуск

Общий dev-стек запускается из корня через `./dev.sh -d` после настройки локального `.env` с DB/S3 секретами. Нужны Docker Compose и mkcert. Backend читает настройки приложения из `config/dev.yaml`; для локального CLI по умолчанию используется этот путь, а `BACKEND_CONFIG` выбирает другой полный YAML.

Общий разбор WAV, разбиение и склейка находятся в `services/audio`; backend задаёт правила допустимого входа, а voice gateway использует тот же парсер. Интеграционные фикстуры backend используют настоящий handler/provider voice gateway через его `testkit` с локальными HTTP-моделями и журналом в памяти.

Backend импортирует сгенерированный клиент gateway из соседнего модуля `services/shared` (`replace ../shared` в `go.mod`), поэтому Docker собирает его из корня репозитория (`Dockerfile.dockerignore` пропускает только `services/backend`, `services/shared`, `services/audio` и тестовый модуль voice gateway). Dev-контейнер монтирует backend, shared и audio в `/work/backend`, `/work/shared` и `/work/audio`, а модуль voice gateway — для интеграционных тестов. Air следит за backend, shared и audio: изменение контракта в `services/shared` тоже пересобирает API. LLM gateway, voice gateway и course-graph входят в общий dev stack; Air следит также за YAML в сервисном каталоге. При изменении YAML процесс автоматически перезапускается внутри контейнера.

Для отдельного backend Compose из этой папки:

```bash
docker compose --env-file ../../.env up -d --build
```

Уже должны работать db, LLM gateway и внешняя сеть. Для голосовых запросов нужен voice gateway; его неготовность не блокирует запуск API, в том числе через корневой Compose. BACKEND_DATABASE_URL переопределяет подключение; по умолчанию db:5432 и DB_PASSWORD. API слушает :8002 за Caddy HTTPS. Публичный префикс /api/v1 удаляется proxy. Secure cookies требуют HTTPS.

Настройки адресов, таймаутов, голоса, лимитов, S3 layout и workers задаются в `config/dev.yaml`. Loader проверяет YAML-типы полей: целые числа, строки и булевы значения не принимаются с coercion;  Ошибки проверки настроек указывают путь поля в YAML. YAML merge keys (`<<`) не поддерживаются. Поля приложения не читаются из прежних BACKEND_* env и не переопределяются ими. Единственные секреты backend — `BACKEND_DATABASE_URL`, `BACKEND_S3_ACCESS_KEY` и `BACKEND_S3_SECRET_KEY`; Compose собирает URL БД из `DB_PASSWORD` и передаёт S3 credentials из `.env`. `BACKEND_CONFIG` — указатель файла, а не override отдельных полей. Изменение YAML автоматически перезапускает процесс, активный запрос может завершиться ошибкой.

Backend обращается к voice gateway через отдельные gRPC-адаптеры `Recognizer` и `Synthesizer`. В `voice.address`, `voice.profile`, `voice.timeout` задаются адрес gateway, профиль голоса и срок ожидания с учётом очереди. При первом запросе TTS API получает и кэширует версию профиля через `DescribeVoice`; временная недоступность voice gateway не мешает запуску API; ключи кэша Geek включают профиль и эту версию. Одновременные запросы версии объединяются в один RPC с общим voice timeout; каждый вызывающий запрос может прекратить ожидание по своему контексту. При изменении настроек голоса gateway отвергает устаревшую версию: перезапустите gateway, затем backend. Адреса моделей, разбиение длинных STT-записей и параметры VoxCPM находятся в `services/voice-gateway/config/dev.yaml`. Подробности — в [README voice gateway](../voice-gateway/README.md). Ранее сохранённые учебные аудиофайлы остаются доступными и автоматически не пересоздаются; переиспользование учебного аудио по-прежнему ограничено префиксом `task-audio/v2/`.


При старте API в фоне проверяет S3-бакет и создаёт его при `storage.s3.create_bucket: true` в `config/dev.yaml`, повторяя попытки до успеха. HTTP write timeout — максимум из STT с записью в S3, `course_graph.timeout` в `config/dev.yaml`, ответа Geek (оценка и следующий вопрос, каждый с одним повтором), синтеза длинной реплики и учебных операций (STT плюс до четырёх последовательных вызовов LLM), затем добавляется 30 секунд. Lease учебных диагностик, тренировок и чатов рассчитан на этот же предел запроса, чтобы операция не теряла резервацию, пока ещё обрабатывается. Health проверяет API и БД, не модели и не S3.

COMPOSE_PROFILES=swagger включает Swagger под /docs/. После обновления YAML пересоздайте swagger, потому что образ копирует спецификацию при старте.

Из этой папки для Go-процесса нужны Go из `go.mod`, PostgreSQL и секреты из локального env. Приложение само файл .env не читает: укажите secrets в shell, а настройки сервиса берутся из YAML.

```bash
BACKEND_CONFIG=config/dev.yaml go run ./cmd/api migrate
BACKEND_CONFIG=config/dev.yaml go run ./cmd/api
```

STT принимает multipart audio (WAV/Ogg/WebM) до 25 МиБ, сохраняет расшифровку владельца и возвращает id/text/created_at. TTS принимает text до 500 символов и возвращает WAV. Backend отправляет эти операции voice gateway по gRPC; HTTP модели вызываются только со стороны gateway. Frontend не знает адресов моделей. В backend настроены gRPC-лимиты для передачи больших записей и WAV; отмена и deadline передаются gateway.


## Live reload в Docker

Корневой `./dev.sh -d` использует Dockerfile target `dev` с Air. Исходники backend смонтированы в `/work/backend`, общий модуль контрактов — в `/work/shared`; Air пересобирает и перезапускает API при изменениях Go-файлов, SQL, `go.mod`, `go.sum` и YAML в обоих. Конфигурация watcher — `.air.toml`; polling позволяет подхватывать изменения через Docker Desktop. Модули Go, кеш сборки и каталог `.air` с dev-бинарником находятся в Docker volumes. Миграции применяются штатным запуском API; SQLC-запросы требуют отдельной генерации Go-кода. Runtime target backend сохраняется для сборки и smoke-проверок.

## БД и импорт

Goose применяет встроенные SQL-миграции при старте или migrate; запуск сериализован advisory lock. Перед миграциями API до 60 секунд ждёт, пока PostgreSQL начнёт принимать соединения: `pg_isready` считает БД здоровой и во время восстановления после сбоя (SQLSTATE 57P03). `00001_initial.sql` создаёт пользователей, auth-сессии и токены, расшифровки, предметы и материалы курса (`subject_materials`: файл, S3-ключи исходника и распознанного текста, статус OCR). `00002_geek.sql` — диагностики Geek (`geek_sessions`, одна активная на студента и курс) и ключи повтора (`geek_requests`). `00003_material_cleaning.sql` — задания очистки и тем (`material_cleaning_jobs`: lease, попытки, очищенный текст и S3-ключи отчёта). `00004_course_graph.sql` — view `course_graph_inputs` (fingerprint набора материалов курса, если все обработаны), задания сборки (`course_graph_jobs`) и опубликованный граф (`course_graphs`, один на курс, JSON сборки). `00005_material_ocr.sql` — OCR-задания (`material_ocr_jobs`); ставит их и ранее загруженным материалам, чтобы те прошли новый конвейер из исходного файла. `00006_material_ocr_report.sql` — S3-ключ сырого OCR, отчёт OCR у материала и стадия задания. `00007_material_metadata.sql` добавляет каталог `material_kinds` и nullable неделю/вид у материала; существующие материалы сохраняются без выдуманных метаданных. `00008_material_kind_labels.sql` устанавливает подписи видов «Лабораторная» и «Туториал». `00009_material_metadata_graph_inputs.sql` включает week/kind/label/filename и cleaning report в fingerprint и требует классификацию для `inputs_ready`; старые публикации становятся stale до пересборки при сохранении самих графов и результатов. `00010_competency_map_graph.sql` — импортированные карты компетенций (`course_graph_maps`: файл, лист, fingerprint и граф карты), источник `source` (`materials` или `competency_map`) у сборки и опубликованного графа и view `course_graph_job_inputs` — входы сборки обоих источников. `00011_learning.sql` добавляет таблицы восстановления legacy обучения, а `00012_learning_table_ownership.sql` переносит учебное состояние в собственные `learning_*` объекты и `learning_subject_state`; `00013_shared_courses.sql` объединяет каталог и удаляет `subjects.mode`. `00014_learning_graph_labels.sql` добавляет независимый кэш `learning_graph_labels` (SHA-256 от версии промпта и исходного названия → короткая подпись); исходная карта и снимки диагностик не изменяются. `00015_geek_result_summaries.sql` добавляет `geek_result_summaries`: общий вывод модели по завершённой диагностике, один на сессию. Все пути обучения опубликованы под `/api/v1/learn`, Geek — под `/api/v1/exam`. Установленные миграции не переписываются: ownership rename оформлен forward migration. Goose не применяет миграцию с номером меньше уже применённого.

Учебные и экзаменационные данные находятся в одной PostgreSQL, но имеют независимых владельцев и алгоритмы. Каталог курсов общий. `learning_*` хранит учебную проекцию карты, `course_graph_maps` — сохранённую карту для Geek; версии режимов активируются отдельно. При двухлистовом импорте `learning_subject_state.pending_revision` временно сериализует сохранение. Транзакция, которая сохраняет карту Geek и ставит сборку, также переключает эту редакцию в `active_revision`; `course_graphs` сохраняет предыдущую публикацию Geek до успешного завершения сборки. `course_graphs.map_revision` фиксирует редакцию учебной карты, из которой построен Geek-граф; снимок `/graph` отдельно возвращает текущий `map.learning_revision` и опубликованный `graph_map_revision`. Диагностические сессии, оценивание, план, тренировка, варианты, банк заданий, генерация и аудио остаются в учебном контексте. Никакие данные или volumes автоматически не сбрасываются.

Forward-миграция `00016_unified_course_map.sql` добавляет временную ожидающую учебную редакцию и её связь с картой графа. Forward-миграция `00017_course_graph_learning_revision.sql` сохраняет версию обучения у Geek-графа и восстанавливает её для уже совпадающих публикаций. При paired import учебная редакция активируется при сохранении общей карты и задания сборки, не дожидаясь Geek; `FinishCourseGraph` публикует только Geek-граф и его `map_revision`.

Админские запросы на `/admin` и `/admin/learn` вызывают `POST /auth/teacher` без тела и пароля, передавая заголовок `X-AI-Tutor-Portal: admin`; без него маршрут отвечает 404. С этим заголовком auth-маршруты и защищённые запросы используют отдельные cookies `admin_access_token`/`admin_refresh_token`, поэтому сессии ученика и админки в одном браузере независимы. Backend атомарно создаёт общий аккаунт `user:shared-teacher` с ролью admin и обычную cookie-сессию. Повторные входы используют тот же аккаунт и независимые сессии; logout отзывает только текущую. Общий адрес `shared-teacher@ai-tutor.invalid` зарезервирован и не принимается обычной регистрацией/парольным входом.

Дополнительный персональный admin может назначаться после регистрации:

```bash
docker compose -f ../../docker-compose.yaml exec db psql -U ai_tutor -d ai_tutor \
  -c "UPDATE users SET role='admin' WHERE email='teacher@example.edu';"
```

Admin создаёт предмет через `POST /admin/subjects` с JSON-телом `{"name":"..."}`; устойчивый ID создаёт backend. Материалы загружаются `POST /admin/subjects/{subject_id}/materials` (multipart, поля `items` и `file`, до 48 файлов по 50 МиБ): исходник сохраняется в S3, материал получает статус `pending` и OCR-задание. Дальше фоновые workers с lease в PostgreSQL (60 с, продление каждые 10 с, до 3 попыток; по два воркера на этап — `materialWorkers`, задания захватываются `FOR UPDATE SKIP LOCKED`, поэтому каждое достаётся одному воркеру, а course-graph сам ограничивает OCR одним документом и выделение тем — двумя): `OCRWorker` распознаёт файл в `services/course-graph` и переводит английский текст на русский через LLM gateway (ошибка перевода — предупреждение, остаётся исходный OCR), `CleaningWorker` вызывает `/topics/extract` (очистка и темы, отчёт кэшируется в S3). Стадии видны в `processing` и `cleaning` у материала.

Редактор материалов получает виды из `GET /admin/material-kinds` (каталог в БД). Загрузка принимает JSON-поле `items` — массив `{client_id, week, kind}` — и повторяющиеся `file` в том же порядке. PDF проверяются по расширению и сигнатуре. Ответ содержит `uploaded`, `failed`, `results` с исходным `client_id`, включая частичные ошибки. Запрос без `items` отклоняется, принимаются только PDF; лимиты — 48 файлов и 50 МиБ на файл.

`PATCH .../materials/{material_id}` меняет `week` и/или `kind` без повторного OCR, изменения времени обработки и кэша тем; фактическая правка меняет fingerprint графа, а повтор тех же значений не инвалидирует его. `PUT .../materials/{material_id}/raw` принимает один PDF: сохраняет новый исходник, атомарно сбрасывает OCR и очистку и ставит новое durable OCR-задание. Неделя и вид сохраняются. Ответ возвращает `pending`; затем выполняется тот же конвейер OCR → перевод → очистка/темы. Ошибка записи исходника или БД оставляет предыдущий материал активным. Старые lease не могут опубликовать результат; граф становится неактуальным до обработки и пересборки по кнопке.

Граф курса (префикс `/api/v1/exam`): `GET /admin/subjects/{subject_id}/graph` — опубликованный граф и состояние сборки (`status`, `stale` — семантически значимые входы изменились после публикации, `inputs_ready` — все материалы обработаны и классифицированы, `progress` — ход идущей сборки: этап, номер этапа из пяти и готовые порции вызовов модели на нём, на этапе `topics` — материалы; есть только при `processing`). Worker передаёт course-graph `X-Build-ID` — курс и случайный ID каждого вызова (не lease-токен: при повторном захвате номер попытки тот же, а прежний вызов может ещё идти) и раз в 2 с опрашивает `GET /graph/build/progress`; прогресс живёт в памяти API. Кнопка «Собрать граф» — `POST .../graph/build`: 202 ставит сборку, 409 — сборка уже идёт, 422 — материалы не готовы или отсутствует week/kind (`MATERIAL_METADATA_INCOMPLETE` с ID). `graph.Worker` передаёт course-graph карточки тем из отчёта очистки только версии `topics-v4`; более старые (`topics-v3` и раньше — вопросы прежних политик) не переиспользуются, и материал извлекается заново: это повторные вызовы модели и время пересборки. Worker передаёт metadata snapshot и публикует граф, только если fingerprint не изменился во время работы. Geek читает опубликованный граф (`geekgraph.Stored`): версия — хеш содержимого, граф из материалов у курса без материалов не отдаётся, ошибка БД возвращается как ошибка. Поле `graph_source` показывает, по какому графу Geek экзаменует курс: `built` — собранный из материалов (граф опубликован и у курса есть материалы); `competency_map` — собранный по карте; `none` — графа нет. `build_source` — источник последней запрошенной сборки, `map` — файл и лист последней импортированной карты.

Geek возвращает источники в пробелах завершённого результата из snapshot сессии. `GET /diagnostic-sessions/{id}/materials/{material_id}/raw` выдаёт связанный с snapshot PDF владельцу диагностики; чужой/несвязанный ID — 404, удалённая или заменённая редакция — 410 `SOURCE_UNAVAILABLE`.

Восстановление упавших заданий: `bash scripts/recover-failed-jobs.sh [--dry-run] [--stage all|ocr|cleaning|graph] [--material-id ID] [--subject-id ID] [--stalled --token T]` (из корня — `scripts/recover-failed-jobs.sh`). `--material-id` ограничивает и граф — курсом этого материала. Каждое действие пишется JSON-строкой аудита в stdout. `GET` на тот же путь возвращает список, `DELETE .../materials/{material_id}` удаляет материал, `GET .../materials/{material_id}/raw` отдаёт исходный файл.

### Прогресс фоновой озвучки

`GET /api/v1/exam/admin/subjects/{subject_id}/audio-preparation?direction=exam|learn` (admin) отдаёт снимок выбранного направления; второе поле равно `null`. Если выбранный снимок временно недоступен, его поле тоже равно `null`; ошибка одного направления не блокирует другое. Exam использует in-memory наборы уникальных SpeechCache ключей опубликованного графа; после рестарта штатная фоновая очередь проверяет S3 cache и не синтезирует уже сохранённые WAV повторно. Версия экзаменационного снимка включает идентификатор голоса из voice-gateway; при недоступности шлюза такой снимок временно недоступен. Доступность графа для прогресса сверяется с БД на каждом запросе; если граф стал доступен после завершения стартового восстановления, его снимок восстанавливается лениво. Learning агрегирует read-only одним запросом assets задач активной ревизии и их queue/lease/retry статусы. Обычное чтение снимка не запускает S3/TTS; ленивое восстановление ставит вопросы в фоновую очередь, которая проверяет S3 и при отсутствии WAV запускает TTS. GET не меняет приоритет и не влияет на `exam_ready`/`learning_ready`. При ошибке чтения опубликованных графов восстановление повторяется с backoff; до завершения восстановления отсутствующий в реестре снимок возвращается как `null`, а не `no_graph`. Для существующего курса без графа сохраняется `observed_at` состояния `no_graph`; запрос отсутствующего курса отвечает 404. `observed_at` учебного снимка сохраняется между одинаковыми наблюдениями в процессе backend и меняется при изменении ревизии или счётчиков. Счётчики взаимоисключающие; `state` следует их задокументированному precedence в OpenAPI.

## Проверки

Объём и команды локальных проверок — в [правилах backend](AGENTS.md#тесты). Для DB-тестов задайте `TEST_DATABASE_URL`, например:

```bash
export TEST_DATABASE_URL='postgres://ai_tutor:YOUR_PASSWORD@localhost:5432/ai_tutor?sslmode=disable'
```

Интеграционные тесты создают отдельную PostgreSQL schema, модели и S3 заменяются локальными HTTP-серверами. Без TEST_DATABASE_URL DB-тесты пропускаются; CI поднимает PostgreSQL. Общая HTTP-фикстура использует быстрый тестовый хешер паролей; тесты регистрации и входа используют настоящий Argon2id с рабочими параметрами. Независимые HTTP DB-тесты выполняются параллельно, каждый в своей схеме и с пулом до четырёх соединений; рабочий migrator с блокировкой проверяется отдельно в `shared/postgres`. Тесты, меняющие окружение процесса, и внешний S3 smoke (`TEST_S3_ENDPOINT`) остаются последовательными. SQLC: `bash scripts/generate-sql.sh`. Архитектура: [backend-architecture.md](../../documents/backend-architecture.md).
