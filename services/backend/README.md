# Backend

Go API и PostgreSQL. Команды выполняются из `services/backend`, если не указано иначе.

## Реализовано и запланировано

Реализованы auth, каталог предметов, администрирование предметов, синхронные STT/TTS, импорт текущей карты CSV/XLSX, карта/каталог,
assessment по снимкам вариантов, LLM-генерация задач, импорт материалов с FTS,
variantgen (сборка, снимки, список и чтение вариантов), постоянная очередь аудио в
PostgreSQL с фоновым TTS/S3 worker и HTTP API диагностических
сессий. Диагностики, принятые ответы и бесконечные тренировки сохраняются в PostgreSQL
и доступны после перезапуска. Общий педагогический фидбэк строится по завершённой диагностике один раз и хранится в
`diagnostic_feedback` (миграция 00009): проверенные результаты, пробелы и советы берутся из
сохранённых разборов ответов, модель пишет только общий абзац строго по ним.
Итог указывает составляющую и конкретный проверенный результат, не объявляя всю
компетенцию освоенной. «Изучить полностью» выводится только при нулевых ответах на
основной и два различных базовых результата одной известной составляющей;
пропуск вопроса и вопросы из разных составляющих такого вывода не дают.
Остальные пробелы помечаются «Дополнительно изучить»; верные базовые видны как
освоенные проверенные результаты. Исторический фидбэк обновляется один раз до
новой версии анализа; последующие чтения сохраняют текст этой версии.
Новые планы `learning` используют те же пробелы: неверные/частичные проверенные
результаты и, при полном пробеле, результаты только соответствующей составляющей.
При переимпорте карты используются снимки проверенных заданий, а не новая карта.
Уже созданные планы, ответы, прогресс и чат автоматически не пересобираются.

Единый контракт — [api/openapi.yaml](../../api/openapi.yaml): implemented — работает,
planned — проект. `/tasks/generate` и `/admin/materials` сохраняются как API отдельного taskgen.
`/assessments/evaluate` принимает позицию сохранённого варианта. Диагностическая сессия вызывает тот же assessment
application по `variant_id`, `variant_task_id` и `transcription_id`, без HTTP-вызова
собственного backend. Оценивание выполняет assessment через API модели.
Assessment напрямую реализует порт сессии; оба модуля используют результат из `entities/assessment`.
Баллы определяются содержанием ответа по эталону и критериям сохранённого задания:
основной — 0 за отсутствие верных существенных элементов, 1 за частичный ответ,
3 за полный; тренировочный — 0/1/2 по тем же уровням полноты; базовый — 1 только
за полный ответ, иначе 0.
Выполнение голосовой инструкции само по себе баллов не приносит; нарушение
обязательной инструкции по-прежнему даёт 0. Boolean `answer_correctness` означает
полное выполнение предметного критерия: при false модель различает 0 и 1 по
эталону и рубрике и объясняет содержательную неполноту ответа.
Явно требуемое объяснение относится к полноте предметного ответа: правильный
вывод без него даёт 1/3 за основной и 1/2 за тренировочный, а не 0 за нарушение
инструкции. Если задание просит только назвать или выбрать ответ, объяснение
не добавляется как скрытое
требование. Разговорный стиль не оценивается без соответствующего критерия.

Сессии доступны через `POST /diagnostic-sessions`, `GET /diagnostic-sessions/{id}`,
`GET /diagnostic-sessions/{id}/current/audio?variant_task_id=...`,
`POST /diagnostic-sessions/{id}/current/audio/regenerate`,
`GET /task-audio/{id}/file`, `POST /diagnostic-sessions/{id}/answers`
и `GET /diagnostic-sessions/{id}/result`. Ответы проходят STT и, при доступном
грейдере, сохраняют score/max_score/verdict/criterion_results/feedback от assessment.
Шкала уже ограничена ролью задания и сессией не преобразуется. Повтор ключа идемпотентен; параллельный ответ
отклоняется, пока текущий обрабатывается. Assessment возвращает `max_score` по роли:
3 для main, 2 для training и 1 для basic; сессия сохраняет эту оценку без повторного преобразования.
В диагностике main даёт 3 за полностью верный ответ, 1 за частичный и 0 за неверный; basic — 1 или 0. Сумма включает основные и предъявленные базовые, максимум — 3 балла на компетенцию. При main=3 базовые пропускаются.
Результат доступен только после завершения.
Контракт — единый [OpenAPI](../../api/openapi.yaml).

### Практика в плане обучения

Модуль `learning/infrastructure/modelapi` использует `BACKEND_TUTOR_*`.
Проверка ответа отделена от генерации повторного вопроса: верный ответ требует
вывода и применения принципа к существенным условиям текущего случая. Общий
пересказ предыдущего объяснения без такой связи не завершает урок.
Верный ответ проверяется одним обращением; неверный, если попытки остались, —
проверкой, генерацией другого случая и редакторской проверкой. Редактор получает
предыдущий вопрос; замены чисел недостаточно. Каждый вызов имеет provider timeout,
общий бюджет проверки — три таких интервала, HTTP учитывает ещё распознавание речи.
Выходной лимит — 4096 токенов с reasoning=medium; обрезанный ответ не принимается.
Буквальные `\\n\\n` в прозе нормализуются в абзацы после декодирования JSON;
кодовые escape-последовательности и LaTeX сохраняются. Интерфейс применяет такую
же нормализацию для уже сохранённых уроков.
Первый запрос пишет теорию с прежними уровнями подробности; второй создаёт
вопрос по точному тексту этой теории; третий редактирует вопрос, проверяя
достаточность данных и отсутствие требований к не объяснённым знаниям.
Практика предлагает оценить конкретное предложение или вывод и обосновать
ответ по условиям ситуации вместо перечисления терминов и функций.
Редактура остаётся модельной проверкой и не гарантирует качество каждого вопроса.

Теория сохраняется сразу после первого ответа модели и доступна через сообщения
темы, пока генерация и редактура практики продолжаются. Интерфейс опрашивает
сообщения раз в 1,5 секунды, показывает теорию и статус подготовки практики;
запись ответа включается только после появления вопроса. Догрузка практики
не прокручивает теорию, которую студент читает. При сбое или перезагрузке страницы
повторный `/open` продолжает с сохранённой теории, не создавая её заново.

Теория пишется по-русски: если текст вне кода и формул не русский, модель
запрашивается ещё раз в пределах того же интервала, а повторный сбой возвращается
как ошибка формата. Теория имеет один `BACKEND_TUTOR_TIMEOUT`, генерация и редактура практики вместе —
ещё один. HTTP-ответ `/open` возвращается после готовности практики. Теория хранится
в снимке ОР плана и сообщении чата; миграция БД не требуется. Готовые уроки
не пересоздаются. Проверка ответа получает сохранённую теорию и предыдущие разборы из чата этого ОР
и учитывает требуемое обоснование. После неверного ответа следующий вопрос
редактируется по теории и разбору; проверка ответа, генерация нового вопроса и
редактура имеют отдельные provider timeout в общем бюджете трёх интервалов.
Схемы HTTP-ответов и три учебные попытки сохраняются.

### Тренировка

`GET /subjects/{subject_id}/learning-state` возвращает последнюю завершённую диагностику,
активную диагностику и доступность тренировки. `GET /diagnostic-sessions/{id}/training/preview`
читает темы без создания сессии: «Неосвоенные темы» для неверных базовых ответов и
«Частичные пробелы в знаниях» для неполного основного при отсутствии неверных базовых.
Отличный результат даёт `free_practice` по всем готовым TRUE-заданиям предмета.
Для непроверенных ОР исходная оценка в preview равна null.

`POST /diagnostic-sessions/{id}/training` принимает JSON, `Idempotency-Key` и
`plan_revision` из preview для свободного режима. Смена активной карты между preview
и запуском даёт 409 `TRAINING_PREVIEW_STALE`. На диагностику создаётся одна тренировка;
повтор ключа возвращает её даже после переимпорта. `GET` того же пути находит созданную сессию.

`GET /training-sessions/{id}` возвращает сохранённое упражнение, раунд, счётчик ответов
и последние баллы целей. В секции после инструкции работает постоянный Socratic-чат:
`GET /training-sessions/{id}/exercises/{exercise_id}/chat` читает историю,
`POST .../chat/turns` принимает текст или multipart-аудио с `revision`, `kind` и
`Idempotency-Key`; `/retry` продолжает сохранённую реплику, `/cancel` отменяет только
незавершённую. Обычная реплика не оценивается и не меняет упражнение. Только `kind=check`
запускает доверенное итоговое оценивание по шкале 0/1/2. Проверка остаётся актуальной,
пока чат не изменился; `POST /training-sessions/{id}/exercises/{exercise_id}/next`
атомарно сохраняет её как attempt, закрывает старый чат и создаёт следующее упражнение.
Исторический чат остаётся доступен для чтения. Legacy `/answers` и `/skip` сохраняются
для совместимости и закрывают старый чат атомарно.

Все writers сериализуются на строке training session. Idempotency replay проверяется
до current-exercise/revision проверки; lease и fencing token защищают от позднего ответа
после cancel/retry. STT сохраняет расшифровку до вызова Tutor, поэтому повтор не требует
новой записи. Ошибка provider не создаёт нулевую попытку. Настройки Tutor задаются через
`BACKEND_TUTOR_*`; URL и model по умолчанию наследуются от assessment, timeout — 60s.
`BACKEND_TUTOR_ENABLED=false` сохраняет чтение истории, но отправка возвращает 503.

`GET /training-sessions/{id}/history?limit=20&cursor=...` выдаёт историю страницами;
`current/audio?exercise_id=...` возвращает метаданные сохранённого WAV. Снимки и готовая
озвучка остаются доступны после переимпорта. Эталоны и criteria скрыты; доступ проверяет владельца.
Тренировочные ответы не меняют диагностику. `ExerciseProvider` сейчас копирует сохранённое
задание; его порт позволяет подключить будущую генерацию похожих упражнений.

### Сохранённая озвучка заданий

Импорт карты и taskgen в той же транзакции создают audio asset и ставят его в
`pending`. Worker стартует только из `cmd/api` после миграций; `Handler()` и
healthcheck его не запускают. Он ограничен `BACKEND_AUDIO_WORKERS`, проверяет S3
объект перед TTS, сохраняет WAV и завершает запись со стабильным file URL. Пять
неудачных попыток дают `failed`. При штатной остановке worker возвращает своё
прерванное задание в `pending` без расходования попытки; следующий запуск может
сразу его забрать. При аварийном отключении или недоступной БД во время остановки
задание восстанавливается без расходования прерванной попытки после истечения lease: `BACKEND_VOICE_TIMEOUT` +
3 × `BACKEND_S3_TIMEOUT` + 30 секунд (с текущими dev-настройками — до четырёх минут
с момента claim). Claim и проверка перед TTS требуют связь с активной ревизией
карты; при замене карты устаревшие pending/processing assets переходят в
терминальный `cancelled`. Уже готовые assets доступны историческим снимкам. S3 outage не блокирует импорт, текстовые задания или
ответы. `/health` проверяет только API и PostgreSQL.

По умолчанию локальный Compose запускает RustFS. Настройки `BACKEND_S3_*` и
`BACKEND_AUDIO_*` описаны в корневых `.env.example` и `.env.prod.example`;
внешний endpoint должен указывать на существующую закрытую корзину, с
`BACKEND_S3_CREATE_BUCKET=false`. Браузер обращается к
`GET /diagnostic-sessions/{id}/current/audio?variant_task_id=...` за статусом, затем
к authenticated `GET /task-audio/{id}/file` только для готовой озвучки.
Запрос метаданных текущего задания диагностики или тренировки поднимает его
`pending`-запись на первое место среди ожидающих. Уже выполняющаяся озвучка
завершается без прерывания; после неё worker берёт приоритетную запись.
Свободный worker просыпается сразу. Приоритет хранится в БД и сохраняется после
перезапуска. Повторный запрос готовой или обрабатываемой записи не меняет её TTS.
Каждый WAV сохраняется и становится доступен независимо от остальных записей
карты. Если запись текущего задания ещё `pending`/`processing`, frontend
показывает загрузку на кнопке озвучки, проверяет статус раз в секунду и запускает
воспроизведение при `ready`. Браузерный синтез речи не используется.
Начало записи ответа, смена задания и уход с экрана
отменяют ожидание. Импорт самой карты остаётся атомарным: очередь видит новые
задания после фиксации транзакции импорта, без ожидания TTS.
Если сохранённый WAV отсутствует или повреждён либо генерация завершилась статусом
`failed`, клиент может по действию пользователя вызвать
`POST /diagnostic-sessions/{id}/current/audio/regenerate` с текущим
`variant_task_id`. Сервер проверяет сохранённый объект и возвращает его без TTS,
если файл исправен; иначе синхронно восстанавливает WAV из сохранённой инструкции,
только пока задание принадлежит активной ревизии карты. Вызов требует cookie-auth
и ограничен общим лимитом TTS worker; `401`/`403` и ошибки S3 не приводят к синтезу.

Для безопасной диагностики очереди можно прочитать только метаданные, не текст
инструкции:

```sql
SELECT id, status, attempts, last_error_code, bucket, storage_uri, updated_at
FROM audio_assets
ORDER BY created_at, id;
```

Правила variantgen — [алгоритм](../../documents/Алгоритм_составления_варианта.md).
Преподаватель не размечает базовые связи и не загружает дополнительные документы.
Компетенция включается, только если в ней не меньше трёх готовых TRUE-ОР с допустимыми
таксономией и важностью; иначе она пропускается с причиной. Основной — наибольший ранг
Блума, при равенстве — большая важность; два базовых — самые простые из остальных.
Версия алгоритма — `competency-map-v4`; сохранённые варианты v1–v3 сохраняют прежний состав.
Снимки сохраняются в PostgreSQL и читаются независимо от активной карты; публичный API
возвращает main и массив basic (два в v3, 0–2 в снимках v1/v2), но
скрывает эталоны, criteria и ОС. Внутренний reader с проверкой владельца отдаёт
грейдингу полный снимок, включая связанные свойства карты; composition root предоставляет
его через доменный `variant.TaskReader`. В исходной карте ОС хранится текстом в `educational_content`, отдельного ID ОС нет. Ответы, оценка и тренировка остаются вне variantgen.

## Единый OpenAPI

```bash
bash scripts/generate-openapi.sh
```

Swag генерирует реализованный API во временный файл; merge-openapi обновляет
implemented-операции, уже включённые в единый контракт, и сохраняет planned.
Исключённые операции не возвращаются автоматически. Новую работающую ручку
нужно явно добавить/перевести из planned в implemented в контракте.
Неиспользуемые схемы удаляются. Swagger использует этот же YAML.

CI проверяет повторяемость генерации и валидирует реальные ответы по implemented-
схемам. Planned-схемы проверяются отдельно без объявления их работающими.
Swag/yq запускаются через go run с закреплёнными версиями, первый запуск требует
загрузки инструментов. YAML не встраивается в API-бинарник.

## Запуск

Общий dev-стек запускается из корня через `./dev.sh -d` после настройки `.env`.
Нужны Docker Compose и mkcert. Серверный `./prod.sh` использует готовые сертификаты
и сеть `ai-tutor_default`; параметры находятся в `.env.prod.example`.

Для отдельного backend Compose из этой папки:

```bash
docker compose --env-file ../../.env up -d --build
```

Уже должны работать db и внешняя сеть. BACKEND_DATABASE_URL переопределяет
подключение; по умолчанию db:5432 и DB_PASSWORD. API слушает :8002 за Caddy HTTPS.
Публичный префикс /api/v1 удаляется proxy. Secure cookies требуют HTTPS.

Backend всегда обращается к API моделей. БД и S3 используют обычные volumes.
Обязательны все
BACKEND_STT_URL, BACKEND_TTS_* (URL и параметры голоса), BACKEND_ASSESSMENT_* и BACKEND_TASKGEN_* из
корневого шаблона: taskgen сохраняется отдельным действующим модулем. Таймауты, адрес
прослушивания и лимит загрузки обязательны. После изменения env пересоздайте API.
Все запросы VoxCPM, включая фоновую озвучку заданий, передают `BACKEND_TTS_SEED`,
`BACKEND_TTS_CFG_VALUE` (0–5) и `BACKEND_TTS_INFERENCE_TIMESTEPS` (1–50).
Шаблоны env задают соответственно 510, 2 и 20. Перед отправкой текста в VoxCPM
backend добавляет `!!!...`, чтобы озвучка завершала последнее слово; уже имеющийся
суффикс не дублируется. Текст задания в БД и интерфейсе не меняется.
Уже сохранённые WAV в S3 сохраняют прежнее звучание и требуют повторного синтеза.
По решению встречи 10.10.2026 голос наставника — мужской, взрослый, низкий. Сервис VoxCPM по умолчанию создаёт референс голоса на фиксированной фразе
для комбинации seed/CFG/шагов и сохраняет его в постоянном volume. Последующие
запросы и все части длинного текста используют этот референс. Первый запрос
для новой комбинации требует дополнительной генерации. Параметр `use_reference=false`
на API модели отключает клонирование; backend использует значение по умолчанию `true`. Worker копирует готовый
WAV с тем же текстом инструкции, поэтому смена голоса требует отдельной переозвучки.
HTTP write timeout учитывает последовательные STT и грейдинг: максимум суммы их
таймаутов и таймаута taskgen, плюс 30 секунд для обработки и записи ответа.
Аудиоответ диагностики имеет тот же лимит загрузки, что `/voice/transcriptions`.
Frontend всегда обращается к backend через HTTP API.

COMPOSE_PROFILES=swagger включает Swagger под /docs/. После обновления YAML
пересоздайте swagger, потому что образ копирует спецификацию при старте.
Frontend и API публикуются одним HTTPS origin. Health проверяет API/БД, не модели.

Из этой папки для Go-процесса нужны Go 1.26 и PostgreSQL. Полный набор env — в
корневом .env.example; приложение само файл .env не читает.

```bash
go run ./cmd/api migrate
go run ./cmd/api
```

STT принимает multipart audio (WAV/Ogg/WebM) до 25 МиБ, сохраняет расшифровку и
возвращает id/text/created_at. TTS принимает text до 500 символов и возвращает WAV.
Без longform/VAD весов удалённый GigaAM отклоняет записи длиннее ~25 с (503). Поэтому
16-bit PCM WAV длиннее 20 с распознаётся частями до 20 с, разрезанными по самому тихому
месту, и текст частей склеивается; Ogg/WebM отправляются как есть.
HTTP модели разворачиваются отдельно; frontend не знает их адресов.

## Live reload в Docker

Корневой `./dev.sh -d` использует Dockerfile target `dev` с Air.
Исходники смонтированы в `/src`; Air пересобирает и перезапускает API при изменениях
Go-файлов, SQL, `go.mod` и `go.sum`. Конфигурация watcher — `.air.toml`;
polling позволяет подхватывать изменения через Docker Desktop.
Модули Go, кеш сборки и каталог `.air` с dev-бинарником находятся в Docker volumes.
Миграции применяются штатным запуском API; SQLC-запросы требуют отдельной генерации Go-кода.
Адреса и параметры моделей задаются в `.env`.
Локальный Compose backend продолжает использовать готовый production-бинарник.

## БД и импорт

Goose применяет встроенные SQL-миграции при старте или migrate; запуск сериализован
advisory lock. История расходной dev-БД объединена в пять миграций:
`00001_initial.sql` — базовая схема с предметами, картами и материалами;
`00002_variants.sql` — снимки вариантов;
`00003_task_audio.sql` — аудио, очередь и связи;
`00004_diagnostic.sql` — диагностика;
`00005_training.sql` — тренировка.
Новая БД содержит пустой каталог предметов. Предметы и ссылки на них создаются
явно, без предметных значений по умолчанию. FK активной ревизии использует
`ON DELETE SET NULL`, поэтому атомарная замена импорта сохраняет снимки вариантов.
Эта история требует чистой dev-БД: прежняя история из десяти миграций несовместима.
Согласованный сброс удаляет учебные аккаунты, карты и сессии; для будущих БД
с настоящими данными новые изменения оформляются следующими миграциями.

Админ-панель (`/admin`) сама вызывает `POST /auth/teacher` без тела и пароля,
передавая заголовок `X-AI-Tutor-Portal: admin`; без него маршрут
отвечает 404. С этим заголовком auth-маршруты и защищённые запросы используют
отдельные cookies `admin_access_token`/`admin_refresh_token`, поэтому сессии
ученика и админки в одном браузере независимы. Backend атомарно создаёт общий аккаунт
`user:shared-teacher` с ролью admin и обычную cookie-сессию. Повторные входы
используют тот же аккаунт и независимые сессии; logout отзывает только текущую.
Общий адрес `shared-teacher@ai-tutor.invalid` зарезервирован и не принимается
обычной регистрацией/парольным входом. Схему БД сбрасывать не нужно.

Дополнительный персональный admin по-прежнему может назначаться после регистрации:

```bash
docker compose -f ../../docker-compose.yaml exec db psql -U ai_tutor -d ai_tutor \
  -c "UPDATE users SET role='admin' WHERE email='teacher@example.edu';"
```

Admin создаёт предмет через `POST /admin/subjects` с JSON-телом `{"name":"..."}`.
Устойчивый ID создаёт backend. `GET /subjects` требует авторизацию: студентам
возвращаются только предметы с готовым вариантом, admin видит все предметы и поле
`ready`, в том числе пустые. Готовность использует ту же eligibility-проверку, что
variantgen: активная ревизия и компетенция с тремя TRUE-ОР с поддерживаемой таксономией,
важностью 1–5 и заданием с непустыми вопросом, голосовой инструкцией и эталоном.

Затем загрузите карту созданного предмета (подставьте ID из ответа создания):

```bash
curl 'https://localhost:8443/api/v1/admin/subjects/{subject_id}/competency-map/import' \
  -b teacher-cookies.txt -F 'file=@map.xlsx'
```

Предметная версия импорта — `POST /admin/subjects/{subject_id}/competency-map/import`;
чтение карты — `GET /subjects/{subject_id}/competency-map`. Импорт изменяет только
выбранный предмет, а глобальный номер ревизии увеличивается при каждом импорте.
Глобальные aliases `/admin/competency-map/import` и `/competency-map` удалены.
Клиенты обязаны передавать выбранный `subject_id`; удаление маршрутов не меняет
схему БД, активные карты или исторические снимки.

CSV — UTF-8, разделитель запятая или точка с запятой, необязательный BOM.
XLSX — книга из одного листа карты или книга на оба режима стенда: тогда читается второй
лист (первый — для симуляции экзамена). Текущий ML формат сохраняет колонки компетенции,
уровня темы, составляющей, ОР, TRUE/FALSE, таксономии, ALDs, важности, РПД, Задание N и ОС;
незнакомые колонки пропускаются, пробелы вокруг заголовков не учитываются. Таксономия —
существительные (Знание…Анализ) или глаголы Блума (Помнить…Анализировать; Оценивать и
Создавать — как Анализ). Уровень темы компетенции действует для её составляющих без своего.
«Раздел РПД» не в формате «Р.N …» — текст лекции, он становится ОС ОР вместо колонки ОС.
Необязательные колонки «Время на теорию» и «Время на практику» — целые минуты 0–600
(допускается «15,0»); пустые значения план обучения заменяет на 15 + 15 минут.
Парсер распознаёт произвольное число Задание N. Пустые родительские поля наследуются
внутри блока; профиль ОР нормализуется в типизированные свойства.
Полные ячейки содержат четыре блока без подписей: вопрос, варианты, голосовую инструкцию и эталон. Блоки разделяются `\n\n\n` (две пустые строки). Варианты — нумерованный Markdown-список, либо `[]` для задания без выбора. Goldmark выделяет элементы списка, сохраняя их Markdown. Неверное число блоков, пустые поля и некорректные списки дают предупреждения `TASK_INVALID_BLOCK_COUNT`, `TASK_EMPTY_PART`, `TASK_INVALID_OPTIONS`; ячейка сохраняется как источник, но не становится заданием. Прежний формат с подписями больше не принимается.
Неполные сохраняются как source с предупреждением, не попадают в tasks.
Старый парный CSV с Ком/Сост/ОР и Критерии N также поддержан нынешним кодом.

Импорт атомарно заменяет карту и выдаёт новые ID/revision; ошибка сохраняет прежнюю
активную карту. Пользователи и расшифровки не удаляются при обычном импорте.
Текущий CSV даёт 13 компетенций, 17 составляющих, 101 ОР, 18 TRUE, 13 полных
заданий и 41 неполную ячейку. Для варианта отдельно подсчитываются готовые TRUE-ОР каждой компетенции.

GET /subjects/{subject_id}/competency-map читает выбранную карту; GET /tasks фильтрует
задания выбранного предмета через `subject_id`, а GET /tasks/{id} принимает тот же
параметр и возвращает профиль только из активной карты. Пропущенный или пустой `subject_id` отклоняется с 422. Эталоны/критерии студенту не выдаются.
`POST /tasks/generate` и `POST /admin/materials` также принимают `subject_id`;
оба запроса требуют непустой ID предмета. Материалы с одинаковым названием
хранятся и заменяются отдельно в каждом предмете, а контекст taskgen включает
материалы только выбранного предмета. Импорт материалов доступен только admin.
Фильтры `/tasks` и пагинация `/variants` отклоняют неизвестные, повторные, пустые
и некорректно закодированные query-параметры с 422.
`POST /variants` требует `subject_id` в JSON и создаёт снимок только активной карты
этого предмета. `GET /variants?subject_id=...` возвращает его cursor-страницы истории;
`GET /variants/{id}` включает ID и снимок названия предмета, а
`GET /variants/{id}/tasks/{task_id}` — отдельную позицию. Все ручки требуют авторизацию
и ограничивают чтение владельцем. Повтор успешного POST с тем же `Idempotency-Key`
возвращает прежний вариант; использование ключа с другим предметом даёт 409.
`POST /assessments/evaluate` принимает `transcription_id` и пару `variant_id` /
`variant_task_id`, читает доверенный снимок варианта и возвращает `score`, `max_score`,
`verdict`, результаты критериев и три строки feedback. Результат не сохраняется
assessment-модулем; диагностическая сессия хранит принятую оценку в PostgreSQL.

## Проверки

```bash
export TEST_DATABASE_URL='postgres://ai_tutor:YOUR_PASSWORD@localhost:5432/ai_tutor?sslmode=disable'
go test -race ./... -count=1
go vet ./...
go build -o bin/api ./cmd/api
```

Интеграционные тесты создают отдельную PostgreSQL schema, модели заменяются локальными
HTTP-серверами. Без TEST_DATABASE_URL DB-тесты пропускаются; CI поднимает PostgreSQL.
Общая HTTP-фикстура использует быстрый тестовый хешер паролей, чтобы повторная
подготовка пользователей не замедляла `-race`. Тесты регистрации с сохранением
хеша и входа используют настоящий Argon2id с рабочими параметрами.
Независимые HTTP DB-тесты выполняются параллельно, каждый в своей схеме и с пулом
до четырёх соединений. Их миграции применяют те же SQL-файлы без общего advisory
lock; рабочий migrator с блокировкой проверяется отдельно в `shared/postgres`.
Тесты, меняющие окружение процесса, и внешний S3 smoke остаются последовательными.
SQLC: `bash scripts/generate-sql.sh`.
