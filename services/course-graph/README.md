# Course Graph (Граф курса и распознавание)

Сервис `services/course-graph/` отвечает за построение графа курса из учебных материалов (лекций, лабораторных и туториалов). Сервис вынесен в отдельный контейнер с FastAPI из-за объёмных зависимостей анализа документов (PyTorch, Docling) и изоляции ресурсов от Go-backend.

## Конвейер обработки

Обработка объединена в два основных LLM-прохода после OCR:

1. **OCR и конвертация** (`course_graph/ocr/converter.py`): извлечение структурированного Markdown с LaTeX-формулами из PDF/Markdown/TXT через Docling с резервным извлечением текста через pypdf. — **Реализован**.
2. **Очистка + темы** (`course_graph/topics/extract.py`): один основной проход по порциям возвращает удаления, темы, `requires`, `provides`, вопрос и привязку к исходным блокам. Текст не переписывается. Вопрос — на рассуждение с развёрнутым ответом, без вопросов на факты, да/нет и с выбором. Тема с объясняющим текстом короче 120 символов (без заголовков, картинок и ссылок) присоединяется к ближайшей теме того же материала без вызова модели (`merged_thin_topics` в отчёте) — к той, где объединённые `requires` и `provides` укладываются в 128 пунктов карточки; если такой нет, тема остаётся отдельной. Итоговые карточки проверяются по контракту `Topic`. — **Реализован**.
3. **Поиск + пререквизиты** (`course_graph/topics/retrieval.py`, `graph.py`): поиск отдельных знаний по всем темам курса; LLM проверяет небольшой список кандидатов с цитатами. Стрелка значит «тема опирается на тему», кандидаты более поздних недель исключены. Связь с неверной цитатой отбрасывается одна, а не вместе с пачкой: модель один раз переспрашивается только по её требованию. — **Реализован**.
4. **Структура** (`course_graph/topics/structure.py`): синонимы, достраивание слабо связанных тем, слияние одиночных, транзитивная редукция — см. «Структура графа» ниже. — **Реализован**.
5. **Проверки и сохранение**: Python проверяет покрытие, ID, цитаты, ацикличность; backend по кнопке «Собрать граф» оркестрирует сборку и хранит один JSONB-снимок графа в PostgreSQL. — **Реализован**.

Одинаковые нормализованные названия объединяются с сохранением источников.
Иерархия (`hierarchy`,
«раздел → тема» по `parent_title`) строится только для явно указанных существующих
родительских тем, отдельно от пререквизитов; раздел становится кандидатом в пререквизиты
своей подтемы. Источники сохраняют citation и
metadata snapshot материала (неделю, код/подпись вида, имя и revision); при
использовании кэша Python заменяет metadata текущими входами backend. Geek
получает sources вместе с темами, а иерархия остаётся только для админской
проверки.

## API и интеграция

- `GET /health` — проверка работоспособности сервиса (`{"status": "ok", "service": "course-graph"}`).
- `GET /ready/models` — готовность весов OCR: `ready/state/stage/updated_at/progress`. В progress только наблюдаемые байты и имена моделей кеша; это не процент готовности. Liveness остаётся быстрым и не означает, что модели готовы.
- `POST /ocr/convert` — конвертация документа в Markdown (multipart-форма с полем `file`). Backend передаёт стабильный `X-Job-ID` материала. Повтор с тем же ID и тем же именем/содержимым присоединяется к текущей работе или возвращает результат; другое содержимое с тем же ID получает `409`. Успешный ответ сохраняет формат `{"markdown":"...","report":{...}}`.
- `POST /topics/extract`, `POST /clean`, `POST /graph/links`, `POST /graph/build` — этапы 2–6, описаны ниже и в [api/course-graph.yaml](../../api/course-graph.yaml).
- `GET /ocr/jobs/{id}` — состояние `queued|running|succeeded|failed`, стадия, timestamp и известный прогресс страниц; после успеха содержит тот же результат OCR. Неизмеримый прогресс передаётся как `null`. Состояние запроса живёт в памяти процесса; после рестарта повторный POST с тем же ID может использовать постоянный OCR-кеш. Поддерживается прежний алиас `POST /convert`.

В общей инфраструктуре сервис запускается в контейнере `course-graph` (`services/course-graph/docker-compose.yaml`), доступен backend по адресу `http://course-graph:8000` через переменную `BACKEND_COURSE_GRAPH_URL`.

## Автоматическая очистка материалов

Перед очисткой backend (`OCRWorker`, стадия `translation`) переводит английский
текст на русский через LLM gateway по gRPC (`complexity=low`; gateway отдаёт его свободному инстансу, который ответит быстрее). Проверяются также английские абзацы в преимущественно русском документе.
Код, формулы и служебные маркеры временно заменяются идентификаторами и затем
восстанавливаются дословно; пропуски, дубли и перестановки не принимаются.
Проверяется сохранение строк и столбцов таблиц. Неудачный перевод не останавливает
материал: дальше идёт исходный OCR, а предупреждение попадает в
`ocr_report.pipeline_warnings` и `error_message` материала.

OCR использует закреплённую версию Docling 2.139.0. Обогащение кода/формул
включено, CPU использует float32 и фактический KV-cache. Код из текстового слоя
PDF обходит генеративное обогащение только если текст того же PDF-прямоугольника
точно совпадает с распознанным текстом. Для целых однострочных правил Prolog
разрешено только склеивание исходных строк пробелом, если все операторы,
внутристрочные пробелы и строковые литералы совпадают; в результате сохраняются
исходные переносы. Многострочные правила и языки со значимыми отступами этим
исключением не пользуются. Сканы, частичный текст и расхождения
проходят обычное обогащение. Правила Prolog,
ошибочно принятые за формулы, сохраняются только при точном совпадении с тем же
текстовым прямоугольником PDF. Для картинок
дополнительно извлекаются подписи; пространственный смысл схем не восстанавливается.
Ошибки и неполное распознавание отражаются в `report.warnings`; backend сохраняет
их в существующем `error_message` материала при непустом распознанном тексте.
`parsed` с предупреждением не означает полное распознавание всех иллюстраций.
Если доступный native-код и результат визуального OCR расходятся по токенам
(строковые литералы сравниваются целиком), выдаётся предупреждение и
`content_complete=false`. Автоматической подмены при расхождении нет; стабильный
результат с таким предупреждением можно читать из кеша.
Пустой (в том числе после удаления служебных токенов и тега языка) или упёршийся
в лимит токенов ответ модели отклоняет только свой элемент:
соседние ответы той же пачки сохраняются, элемент остаётся с текстом Docling до
обогащения. Формула затем идёт на адресный повтор, а потерянный код даёт
предупреждение и `content_complete=false`.
Структурная проверка LaTeX отмечает оборванные индексы: `_`/`^` без аргумента
(`x^`, `x_}`) отправляют формулу на повтор, а без исправления она становится `unresolved`.
Текстовый слой читается из той же области, что нашёл Docling: его bbox на
отображаемой странице переводится в систему PDF с учётом `/Rotate` и CropBox.
Распознанная формула сверяется с текстовым слоем PDF в её области: обе стороны
приводятся к одному алфавиту (минус U+2212, `≤ ≥ ≠ ±`, греческие буквы и их
варианты, имена `\sin`, `\log`, `\max` и подобные — как обычные буквы, знаки логики,
множеств и стрелок `∀ ∃ ∈ ∉ ⊆ ∪ ∧ ⇒ →` — как операторы; регистр букв сохраняется),
и противоречием считаются другой оператор, цифра или буква, лишний
или пропущенный член. Порядок символов вместе с местом операторов (`x+y=z` против
`x=y+z`) сравнивается только у формул без сумм,
интегралов, пределов, дробей, корней и окружений: их части текстовый слой хранит
не в порядке чтения. Только при противоречии формула идёт на адресный повтор;
повтор, отличающийся лишь записью (`_{1}`/`_1`, `\le`/`\leq`, `\dfrac`/`\frac`),
подтверждает исходную формулу, иначе она становится `suspect`.
Кеш `ocr-v9-content-cache` сохраняет завершённый результат, включая стабильные
нераспознанные формулы с предупреждениями. Временные ошибки обогащения,
незавершённые документы и fallback после сбоя Docling не становятся финальным
кешем. Ключ учитывает SHA-256 содержимого, настройки и выбранный парсер;
PDF и TXT/Markdown с одинаковыми байтами не смешиваются; имя без расширения — PDF,
с тем же ключом и той же проверкой формул, что и `.pdf`. Старые записи остаются
на диске, но не используются новым пространством ключей. Чтение проверяет
SHA-256, настройки, `work_complete` и схему отчёта по `OcrReport` (типы полей,
`formula_summary`, `formula_regions`): запись, нарушающая контракт, — cache miss.
Запись атомарна (временный файл и rename); при сбое записи или rename временный
файл удаляется, прежняя запись остаётся целой. Имя PDF подставляется
при выдаче, исходные заголовки TXT/Markdown не меняются.

Одновременные задания с одинаковым содержимым и парсером делят одно вычисление,
даже с разными `X-Job-ID` и без дискового кеша. Статусы и результаты заданий
остаются раздельными. TXT/Markdown не занимают слот Docling, а чтение дискового
кеша вынесено из event loop. Чтение native-текста держит не более четырёх пар
PDFium page/textpage и освобождает их после документа. Адресный повтор формулы
учитывает систему координат bbox и освобождает bitmap, изображение и страницу.

Таймаут документа
по умолчанию отключён; ограничения отдельных сетевых запросов остаются. Модельный
bootstrap один раз инициализирует PDF pipeline и lazy CodeFormula engine при запуске.
До готовности весов `/ready/models` сообщает `loading`, а ошибки загрузки —
`failed`; liveness не задерживается. Весовые файлы хранятся в постоянном
`course_graph_models`. Для стабильного HTTP-транспорта перед импортом Hugging Face
задаются `HF_HUB_DISABLE_XET=1` и `HF_HUB_DOWNLOAD_TIMEOUT=30` (это idle timeout
одного скачивания, а не общий лимит времени OCR). Ход bootstrap логирует кешированные
байты/модели и время, а URL с подписанными параметрами редактируются.

После успешного сохранения OCR-текста в S3 backend атомарно сохраняет материал
и задачу в `material_cleaning_jobs`. Фоновый обработчик читает текст из S3 и
вызывает внутренний `POST /topics/extract` (`{"markdown":"...","material_id":"..."}`). Загрузка не ждёт очистку.
Ранее загруженные материалы миграция `00005` ставит в OCR-очередь: они проходят
конвейер заново из исходного файла в S3.

Текст разбивается на блоки с исходными символьными координатами. Короткие слайды
объединяются до 1500 символов, чтобы не отправлять каждый пункт отдельным ID.
Пачка — до 6000 символов и 45 блоков, одновременно обрабатываются две пачки;
`max_chars` и `max_blocks` настраиваются в запросе. Модель возвращает удаления и
карточки тем; серверный default размера задаётся `COURSE_GRAPH_TOPIC_MAX_CHARS`.
Формулы и код не разрезаются и не удаляются; слишком большой
неделимый блок завершает этап ошибкой с рекомендацией увеличить лимит.
Учебные задачи и примеры сохраняются; правила сдачи, баллы, контакты и пустые
благодарности удаляются. Сомнительные или смешанные блоки остаются.
При пропущенных блоках модель получает список ID для исправления; при повторной
ошибке порция дробится, не более трёх уровней. При предложении удалить более 60%
материала этап завершается ошибкой: исходник остаётся, частичные темы не публикуются.
Старый внутренний `/clean` сохранён для совместимости и по-прежнему выполняет
только консервативную очистку без тем.

Python не обращается к моделям напрямую: `course_graph/llm/client.py` вызывает
LLM gateway по gRPC (`llmgateway.v1.Gateway/Complete`) по адресу
`COURSE_GRAPH_LLM_GATEWAY_ADDR` (по умолчанию `llm-gateway:8011`, gateway — профиль
Compose `gateway`) с timeout `COURSE_GRAPH_LLM_TIMEOUT` (300 с на запрос). Вызов, завершившийся
`DEADLINE_EXCEEDED` или `UNAVAILABLE` (например, upstream не уложился в 120 с gateway), повторяется
один раз: gateway ставит упавший инстанс после исправных, и повтор обычно уходит на другую модель.
Раньше один медленный вызов ронял всю сборку графа после 15 минут готовых проходов. Модель не
передаётся: только `complexity` — `low` для всех этапов (`STAGE_COMPLEXITY` в `api.py`, решение 18.10.2026). `low` может исполнить любой инстанс, и gateway отдаёт запрос свободному, который по замерам ответит быстрее (спецификация gateway, раздел 5), поэтому запросы сборки могут распределяться по всем моделям. Каждый проход графа (синонимы, пререквизиты, привязка одиночных тем, вопросы) держит до четырёх LLM-запросов одновременно — `GRAPH_CONCURRENCY` в `topics/graph.py`, по числу инстансов gateway; сама сборка на сервисе одна. Очистка, синонимы и обновление вопросов передают `reasoning_effort: low`, а выделение тем и проверка пререквизитов — нет (`completer(..., reasoning=True)`): модель рассуждает по умолчанию. Без рассуждения Qwen3.6 возвращал удаления с выдуманными причинами и чужими ID блоков, проверка их отвергала, и материал падал с «Не удалось очистить материал». Механические ошибки модели исправляются кодом в сторону сохранения текста, а не отбраковкой ответа: ID не из порции (удаление или блок темы) игнорируется, блок с неразрешённой причиной удаления остаётся и присоединяется к ближайшей теме (даже если в повторах того же ID есть и допустимая причина — порядок не важен), блок, который тема использует, не удаляется, повтор блока в теме схлопывается, тема без своих блоков отбрасывается. Число таких исправлений — `tolerated_foreign_ids`, `tolerated_invalid_reasons`, `tolerated_used_removals` в отчёте. Ответ совсем без тем по-прежнему отвергается (исправление и дробление порции).
Stubs генерируются в `services/shared/gen/python` (`services/shared/tools/generate.sh`)
и в образ копируются из корневого контекста сборки; proto в сервис не копируется.
Адреса моделей и ключи хранятся только в конфигурации gateway.

Оригинал остаётся в `parsed/`, результат и JSON-журнал удалений — в
`subjects/{subject_id}/cleaned/{material_id}/{attempt_token}.{md,json}`.
Backend проверяет SHA-256 исходника и точное соответствие результата журналу.
JSON-журнал дополнительно содержит `topics_version`, `topics`, `quality`, настройки
и число запросов/адаптивных разбиений. Карточка хранит `id`, `title`, списки строк
`requires` и `provides`, `question`, полный `text`, `sources` (материал, блок,
символьные координаты, точный текст, страница/неделя, вид, подпись, имя и
непрозрачная редакция при наличии), `parent_title`. Backend использует недели
для двух проходов дедупликации и переносит provenance в snapshot диагностики.
`GET /admin/subjects/{subject_id}/materials` возвращает дополнительное поле
`cleaning`: статус `pending / processing / ready / failed`, число попыток,
очищенный текст, S3-ключи результата и отчёта, сообщение ошибки.
`parsed_text` и прежний OCR-статус сохраняют своё значение.
Предупреждения о сохранении всего текста находятся в JSON-журнале;
`ready` означает завершение обработки, а не экспертное подтверждение качества.

Очередь переживает перезапуск backend. Lease задачи — 60 секунд, worker продлевает
его каждые 10 секунд, общего лимита работы нет (`BACKEND_COURSE_GRAPH_TIMEOUT=0s`);
после ошибки — до трёх попыток с задержкой 30 и 60 секунд. Истёкший lease можно забрать повторно; устаревший обработчик
не может перезаписать результат нового. Ошибка очистки не удаляет исходник.
После исчерпания попыток автоматическая обработка прекращается; повторная
загрузка создаёт новую задачу; администратор может сбросить упавшие задания
утилитой `scripts/recover-failed-jobs.sh` (см. [backend README](../backend/README.md)).

Для локального запуска: `docker compose up -d --build course-graph api` из корня.
Если остался контейнер старого сервиса `ocr`, сначала остановите его: он занимает
тот же порт 8005. Для этапов 2–6 нужен LLM gateway: `COMPOSE_PROFILES=gateway`.

## Поиск зависимостей и сборка по кнопке

Сборку запускает администратор кнопкой «Собрать граф» (`POST
/admin/subjects/{subject_id}/graph/build`), когда все материалы курса распознаны и
очищены (`inputs_ready`). Состав входов определяется ID материалов и ключами
S3-отчётов. Миграция `00004` добавляет очередь `course_graph_jobs`, view
`course_graph_inputs` и один актуальный снимок `course_graphs` на курс. Backend
`features/coursegraph` каждые 10 секунд берёт запрошенную сборку с текущим составом
входов. Три попытки, lease 60 секунд с продлением каждые 10 секунд; если материалы
изменились во время сборки, граф не публикуется и сборка повторяется с новым
составом. Ошибка сохраняет предыдущий успешный снимок.

Worker читает исходники и карточки из S3 и вызывает внутренний `/graph/build`.
Для старых отчётов без карточек сервис выполняет совместное извлечение заново.
Проверяется соответствие сохранённых фрагментов исходным координатам.
`GET /admin/subjects/{subject_id}/graph` требует admin и возвращает состояние,
`stale`, `inputs_ready`, ошибку, время обновления и сам граф. В админке это
карточка графа (`CourseGraphCard`): кнопка сборки, статус, статистика, разделы и
пререквизиты; страница опрашивает материалы и граф, пока идёт обработка или сборка.

Embedding-модель `intfloat/multilingual-e5-small` загружается на CPU, кеш весов —
в volume `course_graph_models`. Настройки сервера: `COURSE_GRAPH_EMBEDDING_MODEL`,
`COURSE_GRAPH_EMBEDDING_THREADS` (по умолчанию 4). Используются `query:` для
требований и `passage:` для предлагаемых знаний. Embeddings кешируются в памяти;
поисковый индекс строится отдельно для текущего курса, внешние курсы не участвуют.
Поиск точный векторный плюс совпадения терминов, ранги объединяются через RRF.
Это линейное сканирование индекса на одно требование, а не ANN: вычисления поиска
при росте курса могут быть квадратичными, но попарных LLM-запросов нет.

Для каждого требования отбирается до 5 тем. Фрагменты источников также выбираются
по смысловой близости, чтобы русские требования находили английские свидетельства.
Порции второго прохода ограничены 16000 символами JSON, цитаты — 1400 символами
на тему/требование. `/graph/links` принимает готовые карточки и настройки
`per_requirement`, `max_chars`, `evidence_chars`. LLM должна отразить каждое
требование, в том числе неподтверждённое, и дать дословные цитаты с обеих сторон.
Циклические связи не включаются в граф и сохраняются в `rejected_links`.
Неподтверждённые требования не означают доказанное отсутствие знания в курсе.
`semantic_quality=not_expert_validated`: проверки структуры и цитат не заменяют
разметку преподавателя и не дают измерения precision/recall.

## Структура графа

Цель — глубокий граф без одиночных тем (решение 18.10.2026 в [корневом README](../../README.md)).
Проходы `/graph/links` и `/graph/build` по порядку:

1. **Синонимы.** Кандидаты в дубли — три ближайшие по эмбеддингу темы со сходством
   не ниже 0,9 или темы с общими словами названия (Jaccard ≥ 0,6). Решение «одно ли это
   понятие» принимает LLM (`low`, порции по 20 пар); общее и частное, часть и целое
   дублями не считаются. Ответ должен решить каждую переданную пару ровно один раз
   (порядок A/B не важен); повтор, противоречие или чужая пара — исправление ответа,
   а затем отсутствие решения, но не слияние. Группа, где решения вместе несовместимы
   (A = B, B = C, но A ≠ C — в одной порции или в разных), не сливается вовсе. Тема ранней недели сохраняет ID и вопрос
   (понятие то же), остальные попадают в `aliases`.
2. **Пререквизиты по требованиям** — как описано выше. Если у требования есть и
   подтверждённая, и отвергнутая связь, повторно спрашивается только отвергнутая:
   подтверждённая остаётся при любом втором ответе. Ответ проверяется по записям:
   связь с ошибкой схемы (пустая цитата, нет поля, не тот тип) отвергается одна.
   Покрытие требований проверяется отдельно: отсутствующее или повреждённое решение
   переспрашивается один раз только по соответствующим требованиям. Подтверждённые
   связи сохраняются даже при пустом или повреждённом исправлении. Явный отказ
   с `prerequisite_ids=[]` и причиной принимается сразу; пропуск ответа после
   исправления отмечается отдельно и не превращается в выдуманный отказ модели.
3. **Достраивание** (`complexity=low`). Второй раз проходят темы без связей, практика
   (все источники — `lab`/`tutorial`) без пререквизита из лекции и подтемы, не связанные
   со своим разделом. Для каждой LLM получает до 8 кандидатов (название, ОР и короткие
   evidence): раздел, до четырёх лекций той же или ближайшей ранней недели (для практики)
   и ближайшие по эмбеддингу темы; в одном вызове до 8 тем. Модель выбирает, на какие
   кандидаты тема опирается и какие опираются на неё, и подтверждает каждую связь двумя
   дословными цитатами из показанных evidence (`topic_evidence`, `candidate_evidence`) —
   они проверяются так же, как в основном проходе. Связь без цитат, с выдуманной или
   чужой цитатой, из более поздней недели или в обе стороны уходит в `rejected_links`.
   Такие рёбра помечены `via: "attach"` и не имеют `requirement`.
   Attach-записи валидируются по отдельности: повреждённая запись сохраняется в
   диагностике с `raw`, корректные соседи остаются. Один повтор получает только
   темы с повреждёнными связями, пропущенными или повторными решениями. Для каждой
   запрошенной темы нужны единственный ID и оба списка `prerequisites` и `dependents`:
   два пустых списка — явный отказ от связей, отсутствие темы — ошибка покрытия.
   После неудачного повтора остаётся `incomplete_topic_decision`; подтверждённые
   связи не теряются при пустом или невалидном втором ответе. Исправленная связь заменяет её прежнюю диагностику,
   если исходные ID позволяли однозначно определить пару.
4. **Циклы.** Сначала добавляются рёбра по порядку недель, затем остальные, затем
   достроенные; ребро, замыкающее цикл, уходит в `rejected_links`.
5. **Одиночные темы** сливаются с самой похожей связанной темой (тот же материал
   предпочтительнее): текст, источники и знания переходят в неё, ID — в `aliases`,
   запись — в `merged_isolated`. Слияние не делается, если оно сдвинет неделю темы
   (самую раннюю из её источников) раньше её пререквизита или позже её зависимой темы,
   либо если `provides` или `requires` превысят 128 пунктов: знания не обрезаются.
   Тогда берётся следующая похожая тема, а если подходящей нет — тема остаётся одиночной
   (`quality.isolated`). Если связанных тем нет вовсе, темы остаются как есть.
6. **Вопрос объединённой темы.** Карточка, в которую влилась одиночная тема, получает
   новый основной вопрос по всему тексту (`low`, по правилам вопроса course-graph).
   Модель получает до 6000 символов, и каждый источник карточки входит в них своей
   долей, поэтому влитый фрагмент не отрезается; если на источник не приходится и
   200 символов, вопрос не готовится.
   Если вопрос подготовить не удалось, слияния в эту карточку откатываются: старый
   вопрос не публикуется для расширенной темы. Нетронутые карточки вопрос не меняют.
7. **Проверка недель.** После слияний все рёбра ещё раз проверяются на порядок недель;
   нарушившие уходят в `rejected_links` (`week_order`).
8. **Транзитивная редукция.** Ребро A → C убирается, если есть путь A → … → C; убранные
   рёбра — в `transitive_links`. Засчитывание в Geek транзитивно и не меняется, а спуск
   при D идёт по ступеням.

Структурные проходы ограничивают весь пользовательский JSON, включая обёртку и
`correction`: синонимы — 12000 символов, достраивание — 24000, обновление вопросов —
20000. Одиночная запись сверх бюджета не отправляется модели: пара синонимов
остаётся раздельной, attach-тема получает `budget_exceeded` в `rejected_links`,
а слияние, для которого нельзя обновить вопрос, откатывается. Исходные знания
не обрезаются; соседние записи, помещающиеся в бюджет, продолжают обрабатываться.
Повтор с исправлением тоже не отправляется, если превышает бюджет. Лимит 6000
выше относится только к тексту для вопроса, а не к полному JSON карточки.

`requirements` описывают итоговый граф: ID слитых тем заменены на канонические, одно
решение на пару «тема — требование», пререквизиты — только из опубликованных рёбер, а
требование, которое объединённая карточка объясняет сама, из списка уходит.
Согласование выполняется после транзитивной редукции: удалённый прямой пререквизит
не остаётся в `requirements`; его обоснование и цитаты доступны в `transitive_links`.
Промежуточный узел транзитивного пути не подставляется вместо подтверждённого источника
знания. `quality.unresolved_requirements` считает требования без прямого опубликованного
ребра, включая перенесённые в `transitive_links`; это не число пробелов студента. В `quality` —
`synonyms_merged`, `attached_links`, `isolated_merged`, `isolated`, `questions_refreshed`,
`transitive_links` и `depth` (самая длинная цепочка в темах, считается по
топологическому порядку без рекурсии); `requests` считает логические вызовы модели этапами,
а `retried_requests` — их повторы после таймаута или недоступности gateway (тот же счётчик есть
в отчёте `/topics/extract`): gateway получает `requests + retried_requests` вызовов.
Извлечение тем просит перечислять в `requires` все знания, на которые
опирается тема, общими терминами — так поиск находит больше пререквизитов. Уже
сохранённые карточки (`topics-v2`) не переизвлекаются: проходы 1 и 3–8 работают и на них.
Эмбеддинги и матрицы сходства считаются в отдельном потоке (`asyncio.to_thread`), а
encoder сериализует свои вызовы: сборка графа не блокирует event loop сервиса.

## Воспроизводимая проверка реальной LLM

Из контейнера в сети Compose с доступом к LLM gateway:

```bash
python -m course_graph.evaluate --dataset /path/topics_reviewed_v2.json --output /tmp/eval --sweep 4000,6000 --materials 2 --targets 8
```

Скрипт сохраняет исходные запросы/ответы без секретов, карточки, кандидатов,
граф и метрики времени/покрытия. Основной текст для проверки очистки собирается
по уникальным страницам датасета. Для проверки связей используются готовые
карточки с непустым основным текстом; карточки только из РПД исключаются.
Это раздельная проверка этапов; upload → S3 → worker → PostgreSQL проверяется
дополнительно. Обязательных экспертных меток в этом датасете нет: численные
precision/recall без отдельной разметки не заявляются.

## Проверки

```bash
uv venv .venv
. .venv/bin/activate
uv pip install -r requirements.txt
python -m pytest tests
```

pytest добавляет в `sys.path` `../shared/gen/python` (см. `pyproject.toml`). Stubs
перегенерируются из корня `services/shared/tools/generate.sh services/shared/gen`
(версии — в `services/shared/tools/versions.env`). `tests/test_llm_gateway.py`
проверяет стык Python → gateway настоящим gRPC-сервером по контракту `llmgateway.v1`.
Тесты проверяют сохранность текста/формул, смешанные слайды, неверные ответы
модели и ограниченную параллельность. Очередь и S3-адаптер проверяются Go-тестами
backend с `TEST_DATABASE_URL` (HTTP-фикстура S3, изолированная схема PostgreSQL).

Замер первого OCR и пяти чтений кеша на выбранных физических страницах, без
изменений S3, БД и запущенного API:

```bash
PYTHONPATH=. python scripts/benchmark_ocr.py '../../documents/materials/Tutorial 4. Prolog.pdf' --pages 21 --output /tmp/ocr-benchmark/prolog.json
```

Скрипт использует отдельный временный кеш и сохраняет Markdown, SHA-256 исходника,
версии пакетов, время, peak RSS и число inference-пакетов. Повторный запуск —
новый холодный document cache; кеш весов остаётся прежним. Результаты и ограничения
проверки 18.10 — в [отчёте](../../documents/ocr-performance-2026-10-18.md).

### Лёгкая dev-сборка

`COURSE_GRAPH_INSTALL_DOCLING=false docker compose build course-graph` из корня
собирает образ без Docling. PyTorch остаётся зависимостью embeddings для поиска.
Очистка и темы доступны полностью; PDF обрабатываются
через pypdf, а Markdown/TXT — напрямую. Эта сборка не распознаёт текст на сканах
и не восстанавливает формулы средствами Docling. Полная сборка по умолчанию
сохраняет Docling: `docker compose build course-graph`.
Собранный образ можно запустить командой `docker compose up -d --no-build course-graph api`.

### CPU или GPU

Устройство OCR выбирает `COURSE_GRAPH_DEVICE` в `.env`: `cpu` (по умолчанию) или
`gpu`. Сервис по-прежнему называется `course-graph`, compose подставляет вариант
`course-graph-cpu` или `course-graph-gpu`:

- `cpu` — PyTorch ставится CPU-сборкой (`UV_TORCH_BACKEND=cpu`, без CUDA и triton);
- `gpu` — CUDA-сборка `cu128` (CUDA 12.8 — первая с поддержкой RTX 50xx), контейнер
  получает `gpus: all`. Layout, RapidOCR и модель формул и кода работают на CUDA.
  Нужны NVIDIA GPU с драйвером 570+ и NVIDIA Container Toolkit (на Windows —
  Docker Desktop с WSL 2). Если CUDA недоступна, загрузка моделей завершается
  ошибкой, а не молча переходит на CPU.

После смены значения пересоберите образ: `docker compose up -d --build course-graph`.
Embeddings поиска остаются на CPU в обоих вариантах. Кеш OCR от устройства не зависит:
на цифровых PDF результат CPU и GPU совпадает побайтно, на рукописных сканах
RapidOCR может отличаться отдельными словами. На RTX 5060 Laptop целые PDF
распознаются в 5–8 раз быстрее CPU, пик памяти CUDA — 3,5 ГБ
([замеры](../../documents/ocr-performance-2026-10-18.md#cpu-и-gpu)).

Загрузки uv хранятся в кеше BuildKit
(`--mount=type=cache`): при изменении `requirements.txt` пакеты берутся из кеша,
а не скачиваются заново. Кеш очищает `docker builder prune`.

### Повторное использование готового OCR-образа

Если локально уже есть образ OCR с Docling, его можно использовать как базовый,
чтобы не скачивать PyTorch и остальные тяжёлые пакеты заново:

```bash
COURSE_GRAPH_BASE_IMAGE=ai_tutor-ocr:latest docker compose build course-graph
```

Зависимости проверяются из `requirements.txt`. Если в базовом образе torch другой
сборки (CPU вместо CUDA или наоборот), он переустанавливается под выбранный
`COURSE_GRAPH_DEVICE`, а сборка проверяет итоговый вариант. Затем в образ копируется актуальный
код `course_graph` и stubs gateway из `services/shared/gen/python`; контекст сборки —
корень репозитория (`Dockerfile.dockerignore` пропускает только нужные каталоги). По умолчанию базовый образ —
`python:3.11-slim`; повторное использование локального образа необязательно.

Сквозной smoke-тест на фрагментах репозиторного датасета (создаёт отдельный курс):

```bash
python services/course-graph/scripts/validate_upload.py --dataset notebooks/Dataset_100%__topics+pr+oc__v4.1.pdf/topics_reviewed_v2.json --output /tmp/course-graph-upload
```

Команда выполняется из корня, обращается только к localhost, использует dev TLS
и проверяет очистку благодарности, источники, связь между разными файлами и готовый
снимок графа. Идентификатор созданного курса сохраняется в отчёте для просмотра.
