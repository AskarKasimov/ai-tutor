# Course Graph (Граф курса и распознавание)

Сервис `services/course-graph/` отвечает за построение графа курса из учебных материалов (лекций, лабораторных и туториалов). Сервис вынесен в отдельный контейнер с FastAPI из-за объёмных зависимостей анализа документов (PyTorch, Docling) и изоляции ресурсов от Go-backend.

## Конвейер обработки

Обработка объединена в два основных LLM-прохода после OCR:

1. **OCR и конвертация** (`course_graph/ocr/converter.py`): извлечение структурированного Markdown с LaTeX-формулами из PDF/Markdown/TXT через Docling с резервным извлечением текста через pypdf. — **Реализован**.
2. **Очистка + темы** (`course_graph/topics/extract.py`): один основной проход по порциям возвращает удаления, темы, `requires`, `provides`, вопрос и привязку к исходным блокам. Текст не переписывается. — **Реализован**.
3. **Поиск + пререквизиты** (`course_graph/topics/retrieval.py`, `graph.py`): поиск отдельных знаний по всем темам курса; LLM проверяет небольшой список кандидатов с цитатами. — **Реализован**.
4. **Проверки и сохранение**: Python проверяет покрытие, ID, цитаты, ацикличность; backend автоматически оркестрирует пересборку и хранит один JSONB-снимок графа в PostgreSQL. — **Реализован**. Связность не обязательна: независимые темы допустимы.

Одинаковые нормализованные названия объединяются с сохранением источников.
Семантическое объединение синонимов пока не реализовано. Иерархия строится только
для явно указанных существующих родительских тем, отдельно от пререквизитов.

## API и интеграция

- `GET /health` — проверка работоспособности сервиса (`{"status": "ok", "service": "course-graph"}`).
- `POST /ocr/convert` — конвертация документа в Markdown (multipart-форма с полем `file`). Возвращает `{"markdown": "...", "report": {...}}`: движок, SHA-256, страницы, длительность, попадание в кеш и предупреждения о неполном распознавании. Поддерживается также алиас `POST /convert`.

В общей инфраструктуре сервис запускается в контейнере `course-graph` (`services/course-graph/docker-compose.yaml`), доступен backend по адресу `http://course-graph:8000` через переменную `BACKEND_COURSE_GRAPH_URL`.

## Автоматическая очистка материалов

Перед очисткой backend переводит английский текст на русский через общий клиент
LLM. Проверяются также английские абзацы в преимущественно русском документе.
Код, формулы и служебные маркеры временно заменяются идентификаторами и затем
восстанавливаются дословно; пропуски, дубли и перестановки не принимаются.
Проверяется сохранение строк и столбцов таблиц. Неудачный перевод получает
`status=failed` с объяснением; исходный OCR остаётся в S3, граф по нему не строится.

OCR использует закреплённую версию Docling 2.139.0. Обогащение кода/формул
включено, CPU использует float32 и фактический KV-cache. Код из текстового слоя
PDF сохраняется при расхождении с генеративным распознаванием. Правила Prolog,
ошибочно принятые за формулы, восстанавливаются по координатам PDF. Для картинок
дополнительно извлекаются подписи; пространственный смысл схем не восстанавливается.
Ошибки и неполное распознавание отражаются в `report.warnings`; backend сохраняет
их в существующем `error_message` материала при непустом распознанном тексте.
`parsed` с предупреждением не означает полное распознавание всех иллюстраций.
Результат с признаками неполного распознавания не кешируется. Таймаут документа
по умолчанию 3600 с, backend-запроса OCR — 4200 с; время не сокращается отключением
обработки формул.

После успешного сохранения OCR-текста в S3 backend атомарно сохраняет материал
и задачу в `material_cleaning_jobs`. Фоновый обработчик читает текст из S3 и
вызывает внутренний `POST /topics/extract` (`{"markdown":"...","material_id":"..."}`). Загрузка не ждёт очистку.
Старые материалы миграция автоматически не ставит в очередь.

Текст разбивается на блоки с исходными символьными координатами. Короткие слайды
объединяются до 1500 символов, чтобы не отправлять каждый пункт отдельным ID.
Пачка — до 6000 символов и 45 блоков, одновременно обрабатываются две пачки;
`max_chars` и `max_blocks` настраиваются в запросе. Модель возвращает удаления и
карточки тем; серверный default размера задаётся `COURSE_GRAPH_TOPIC_MAX_CHARS`.
Формулы и код не разрезаются и не удаляются; слишком большой
неделимый блок завершает этап ошибкой с рекомендацией увеличить лимит.
Учебные задачи и примеры сохраняются; правила сдачи, баллы, контакты и пустые
благодарности удаляются. Сомнительные или смешанные блоки остаются.
При пропущенных блоках модель получает список ID для исправления; при повторной
ошибке порция дробится, не более трёх уровней. При предложении удалить более 60%
материала этап завершается ошибкой: исходник остаётся, частичные темы не публикуются.
Старый внутренний `/clean` сохранён для совместимости и по-прежнему выполняет
только консервативную очистку без тем.

Python не обращается к моделям напрямую: `COURSE_GRAPH_LLM_GRPC_TARGET`
(по умолчанию `api:8003`) указывает на внутренний backend gRPC-шлюз.
`BACKEND_LLM_BASE_URLS` задаёт от одного до четырёх URL совместимых API с `/v1`,
через запятую; `BACKEND_LLM_MODEL` — общую модель. Пустые настройки используют
`BACKEND_ASSESSMENT_BASE_URL` и `BACKEND_ASSESSMENT_MODEL`.
`BACKEND_LLM_API_KEY` необязателен. Все настройки и ключ остаются на сервере.
Пул допускает один запрос на каждый endpoint; при одном endpoint запросы
к модели выполняются последовательно. Остальные прежние потребители моделей
пока используют свои существующие адаптеры.

Оригинал остаётся в `parsed/`, результат и JSON-журнал удалений — в
`subjects/{subject_id}/cleaned/{material_id}/{attempt_token}.{md,json}`.
Backend проверяет SHA-256 исходника и точное соответствие результата журналу.
JSON-журнал дополнительно содержит `topics_version`, `topics`, `quality`, настройки
и число запросов/адаптивных разбиений. Карточка хранит `id`, `title`, списки строк
`requires` и `provides`, `question`, полный `text`, `sources` (материал, блок,
символьные координаты, точный текст, страница/неделя при наличии), `parent_title`.
`GET /admin/subjects/{subject_id}/materials` возвращает дополнительное поле
`cleaning`: статус `pending / processing / ready / failed`, число попыток,
очищенный текст, S3-ключи результата и отчёта, сообщение ошибки.
`parsed_text` и прежний OCR-статус сохраняют своё значение.
Предупреждения о сохранении всего текста находятся в JSON-журнале;
`ready` означает завершение обработки, а не экспертное подтверждение качества.

Очередь переживает перезапуск backend. Задача резервируется на 7 минут,
работа ограничена 6 минутами; после ошибки — до трёх попыток с задержкой
30 и 60 секунд. Истёкший lease можно забрать повторно; устаревший обработчик
не может перезаписать результат нового. Ошибка очистки не удаляет исходник.
После исчерпания попыток автоматическая обработка прекращается; повторная
загрузка создаёт новую задачу. Отдельной ручки повторного запуска пока нет.

Для локального запуска: `docker compose up -d --build course-graph api` из корня.
Если остался контейнер старого сервиса `ocr`, сначала остановите его: он занимает
тот же порт 8005. Внутренний gRPC-порт 8003 не публикуется на хост и в Caddy.

## Поиск зависимостей и автоматическая сборка

Backend `features/coursegraph` каждые 10 секунд проверяет курсы, у которых все
материалы распознаны и очистка готова. Состав входов определяется ID материалов и
ключами S3-отчётов. Миграция `00012` добавляет очередь `course_graph_jobs`, view
`course_graph_inputs` и один актуальный снимок `course_graphs` на курс.
Три попытки, lease 45 минут, работа до 41 минуты; устаревший token/состав входов
не может заменить граф. Ошибка сохраняет предыдущий успешный снимок.

Worker читает исходники и карточки из S3 и вызывает внутренний `/graph/build`.
Для старых отчётов без карточек сервис выполняет совместное извлечение заново.
Проверяется соответствие сохранённых фрагментов исходным координатам.
`GET /admin/subjects/{subject_id}/graph` требует admin и возвращает состояние,
`stale`, ошибку, время обновления и сам граф. Новый frontend для графа не добавлен.

Embedding-модель `intfloat/multilingual-e5-small` загружается на CPU, кеш весов —
в volume `course_graph_models`. Настройки сервера: `COURSE_GRAPH_EMBEDDING_MODEL`,
`COURSE_GRAPH_EMBEDDING_THREADS` (по умолчанию 4). Используются `query:` для
требований и `passage:` для предлагаемых знаний. Embeddings кешируются в памяти;
поисковый индекс строится отдельно для текущего курса, внешние курсы не участвуют.
Поиск точный векторный плюс совпадения терминов, ранги объединяются через RRF.
Это линейное сканирование индекса на одно требование, а не ANN: вычисления поиска
при росте курса могут быть квадратичными, но попарных LLM-запросов нет.

Для каждого требования отбирается до 5 тем. Фрагменты источников также выбираются
по смысловой близости, чтобы русские требования находили английские свидетельства.
Порции второго прохода ограничены 16000 символами JSON, цитаты — 1400 символами
на тему/требование. `/graph/links` принимает готовые карточки и настройки
`per_requirement`, `max_chars`, `evidence_chars`. LLM должна отразить каждое
требование, в том числе неподтверждённое, и дать дословные цитаты с обеих сторон.
Циклические связи не включаются в граф и сохраняются в `rejected_links`.
Неподтверждённые требования не означают доказанное отсутствие знания в курсе.
`semantic_quality=not_expert_validated`: проверки структуры и цитат не заменяют
разметку преподавателя и не дают измерения precision/recall.

## Воспроизводимая проверка реальной LLM

Из контейнера с доступом к backend gRPC:

```bash
python -m course_graph.evaluate --dataset /path/topics_reviewed_v2.json --output /tmp/eval --sweep 4000,6000 --materials 2 --targets 8
```

Скрипт сохраняет исходные запросы/ответы без секретов, карточки, кандидатов,
граф и метрики времени/покрытия. Основной текст для проверки очистки собирается
по уникальным страницам датасета. Для проверки связей используются готовые
карточки с непустым основным текстом; карточки только из РПД исключаются.
Это раздельная проверка этапов; upload → S3 → worker → PostgreSQL проверяется
дополнительно. Обязательных экспертных меток в этом датасете нет: численные
precision/recall без отдельной разметки не заявляются.

## Проверки

```bash
uv venv .venv
. .venv/bin/activate
uv pip install -r requirements.txt
python -m pytest -q
```

Для генерации gRPC-кода установите также `grpcio-tools==1.70.0`, затем из корня:
`bash services/backend/scripts/generate-llm-proto.sh`.
Тесты проверяют сохранность текста/формул, смешанные слайды, неверные ответы
модели и ограниченную параллельность. Очередь и S3-адаптер проверяются Go-тестами
backend с `TEST_DATABASE_URL` (HTTP-фикстура S3, изолированная схема PostgreSQL).

### Лёгкая dev-сборка

`COURSE_GRAPH_INSTALL_DOCLING=false docker compose build course-graph` из корня
собирает образ без Docling. PyTorch остаётся зависимостью embeddings для поиска.
Очистка и темы доступны полностью; PDF обрабатываются
через pypdf, а Markdown/TXT — напрямую. Эта сборка не распознаёт текст на сканах
и не восстанавливает формулы средствами Docling. Полная сборка по умолчанию
сохраняет Docling: `docker compose build course-graph`.
Собранный образ можно запустить командой `docker compose up -d --no-build course-graph api`.

### Повторное использование готового OCR-образа

Если локально уже есть образ OCR с Docling, его можно использовать как базовый,
чтобы не скачивать PyTorch и остальные тяжёлые пакеты заново:

```bash
COURSE_GRAPH_BASE_IMAGE=ai_tutor-ocr:latest docker compose build course-graph
```

Зависимости проверяются из `requirements.txt`, затем в образ копируется актуальный
код `course_graph`, включая `/clean` и gRPC-клиент. По умолчанию базовый образ —
`python:3.11-slim`; повторное использование локального образа необязательно.

Сквозной smoke-тест на фрагментах репозиторного датасета (создаёт отдельный курс):

```bash
python services/course-graph/scripts/validate_upload.py --dataset notebooks/Dataset_100%__topics+pr+oc__v4.1.pdf/topics_reviewed_v2.json --output /tmp/course-graph-upload
```

Команда выполняется из корня, обращается только к localhost, использует dev TLS
и проверяет очистку благодарности, источники, связь между разными файлами и готовый
снимок графа. Идентификатор созданного курса сохраняется в отчёте для просмотра.
