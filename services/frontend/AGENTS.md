# Руководство по разработке фронтенда

Это руководство обязательно для разработчиков и агентов, которые меняют
`services/frontend/`. Оно описывает соглашения этого приложения; не заменяйте их
общими шаблонами React-проектов без отдельного решения команды.

## Быстрый старт

Фронтенд — TypeScript-приложение на React 19 и Vite. В нём используются:

- TanStack Router для файловых маршрутов;
- TanStack Query для серверного состояния;
- Radix Themes как базовая библиотека компонентов;
- i18next / react-i18next для пользовательских строк;
- SCSS Modules для компонентных стилей;
- Vitest и Testing Library для тестов.

Перед началом работы изучите соседний маршрут или компонент с похожей
задачей. Сохраняйте существующие границы слоёв и стиль импортов.

## Структура и границы слоёв

| Путь | Ответственность |
| --- | --- |
| `src/app/` | Запуск приложения, провайдеры и глобальные стили. |
| `src/routes/` | Экраны и файловые маршруты TanStack Router. |
| `src/shared/` | Переиспользуемые UI-компоненты, доменные типы и утилиты без привязки к экрану. |
| `src/data/` | Контракты источников данных и React Query-хуки. |
| `src/mocks/` | Реализации и фикстуры для тестов и локальных сценариев. |
| `src/platform/` | Узкие адаптеры к браузерным API. |
| `src/i18n/` | Инициализация локализации и переводы. |

Правила зависимостей:

- Маршрут получает данные только через hooks из `src/data/`, а не вызывает
  источник данных напрямую.
- Контракты источников данных живут в `src/data/`; конкретные тестовые
  реализации — в `src/mocks/`. При появлении HTTP-клиента он реализует тот же
  контракт в отдельном инфраструктурном модуле.
- Типы предметной области добавляйте в `src/shared/domain.ts`, пока они не
  стали достаточно крупной областью для отдельного модуля.
- Адаптеры к браузерным API изолируйте в `src/platform/`.
  Компоненты не должны читать глобальные API напрямую.
- Не переносите экранную разметку в `shared/` преждевременно: компонент должен
  обслуживать как минимум два независимых потребителя.

## Маршруты и компоненты

- Создавайте маршруты в `src/routes/` через `createFileRoute` и используйте
  фактический путь в его строковом литерале.
- `src/routeTree.gen.ts` генерируется плагином TanStack Router. Никогда не
  редактируйте его вручную; после изменения маршрутов Vite обновит файл.
- Переходы выполняйте с `useNavigate`, а не через ручные изменения URL.
- Для стандартной разметки предпочитайте компоненты Radix Themes. Нативный элемент
  используйте, когда Radix Themes не покрывает задачу.
- У каждого экрана должны быть понятные состояния: загрузка, ошибка с
  возможностью повторить действие, пустой результат и успешное содержимое.
  Добавляйте эти состояния, когда экран начинает получать данные.
- Не скрывайте ошибки пустым экраном и не подменяйте ошибку пустым состоянием.

## Данные и React Query

- Один ресурс — один именованный query-hook в `src/data/queries.ts` или в
  выделенном модуле рядом с ним. Имя начинается с `use` и заканчивается на
  `Query`, например `useLessonsQuery`.
- Ключи запросов должны быть стабильными, сериализуемыми и включать параметры,
  которые меняют результат: `['lessons', filters]`, а не только `['lessons']`.
- Изменения данных оформляйте через `useMutation`; после успеха инвалидируйте
  затронутые query-ключи. Не меняйте кэш из компонентов вручную без причины.
- Не создавайте `QueryClient` во время рендера экрана. Используйте
  `createQueryClient` и `AppProviders` из `src/app/providers.tsx`.

## Локализация и доступность

- Любая новая пользовательская строка добавляется в `src/i18n/i18n.ts` и
  выводится через `t('namespace.key')`. Не оставляйте новый текст литералом в
  JSX, включая `placeholder`, `aria-label` и сообщения об ошибках.
- Группируйте ключи по назначению (`navigation`, `query`, `routes`), а не по
  названию компонента. Используйте осмысленные английские ключи; значения для
  текущей локали — русские.
- Выбирайте семантические элементы и обеспечивайте доступное имя для каждого
  интерактивного элемента. Иконка без видимого текста должна иметь `aria-label`;
  декоративная иконка — `aria-hidden`.
- Сохраняйте корректную иерархию заголовков: на экране есть один `h1`, карточки
  и секции используют следующие уровни.
- Проверяйте клавиатурную навигацию и не заменяйте `button`/`a` кликабельными
  `div`.

## Стили

- Стили компонента или маршрута храните рядом с ним в `*.module.scss` и
  импортируйте как `styles`. Не используйте строковые глобальные имена классов.
- `src/app/global.scss` предназначен только для глобальной основы приложения:
  CSS-переменных, фона, базовой высоты и общих медиа-правил. Не добавляйте туда
  стили конкретных экранов.
- Используйте токены Radix (`--space-*`, `--gray-*`, `--accent-*`) и `--app-*`.
  Новый цвет, отступ или тень,
  повторяющиеся в двух и более местах, оформляйте токеном в `global.scss` с
  вариантом для тёмной темы, если он нужен.
- Не ломайте светлую или тёмную тему жёстко заданным цветом без обоснования.
  Проверяйте контраст текста, элементов управления и состояний ошибки.
- Не используйте inline-стили, если свойство можно выразить существующим классом
  или CSS-переменной. Допустимое исключение — действительно динамическое
  значение, зависящее от данных.

## Тесты и проверка

- Для нового пользовательского поведения добавляйте или обновляйте тест Vitest
  рядом с кодом (`*.test.ts` / `*.test.tsx`). Тестируйте наблюдаемый результат:
  роли, доступные имена, текст, переход или отрисованные данные — не детали
  реализации.
- Для маршрутов используйте `createMemoryHistory`, `createRouter` и
  `RouterProvider`, как в `src/routes/routes.test.tsx`. Для query-hooks и
  компонентов, использующих их, оборачивайте тест в `QueryClientProvider` с
  `createQueryClient`.
- Не отключайте TypeScript, ESLint или тесты ради прохождения сборки. Исправьте
  причину или кратко зафиксируйте блокирующее внешнее ограничение в PR.
- Перед передачей изменений выполните из `services/frontend/`:

  ```bash
  npm run lint
  npm run typecheck
  npm test -- --run
  npm run build
  ```

## Правила работы агентов

- Сначала прочитайте этот файл, ближайшие тесты и используемые компоненты; затем
  предлагайте минимальное изменение, сохраняющее текущие соглашения.
- Не изменяйте сгенерированные файлы, lock-файлы, зависимости, конфигурацию
  сборки или общие токены, если задача этого прямо не требует.
- Не подменяйте рабочий источник данных моками и не меняйте публичные контракты
  источников данных без одновременного обновления всех реализаций и тестов.
- Не выполняйте массовые рефакторинги вместе с продуктовой задачей. Вынесите их
  в отдельное предложение, если они не нужны для корректности текущей правки.
- В итоговом сообщении указывайте изменённые файлы, выполненные команды
  проверки и их фактический результат. Если проверка не запускалась, прямо
  назовите причину.
