# Frontend AI Tutor

React 19, TypeScript, Vite 8,
TanStack Router (файловые маршруты), TanStack Query, i18next / react-i18next,
SCSS Modules, Vitest и Testing Library. Для UI используется Radix Themes.

## Запуск

Требуется Node.js 22.12+ и npm. Из этой директории:

```bash
npm ci
npm run dev
```

Откройте http://localhost:5173. На `/` находится голосовой тренажёр.
Для микрофона нужен HTTPS или localhost. Фронтенд всегда использует HTTP API backend.

## Целевой сценарий AI Journey

По решениям встречи 10.10.2026 ([план](../../documents/ai-journey-plan.md)) UI
меняется; ниже по разделам описано текущее поведение. Цель: один процесс
проверка → итог → план → тренировка без выбора действия; ответ голосом на все
задания, включая multiple choice, с кнопкой микрофона; после ответа без балла и
вердикта (сделано); прогресс — status bar в процентах (в диагностике сделано), выполненные задания «схлопываются»;
итог без балла и «не проверено» — освоенные компетенции и неосвоенные темы с ОР;
план «тема — ОР» с временем на теорию и отработку и кнопкой «Начать тренировку»;
после тренировки — обратная связь, прогресс-бар слева и «Продолжить тренировку».
Вопрос о времени на тренировку до AI Journey не показывается. Импорт карты в
демо-сценарии не показывается. Браузерная озвучка (`speakInstruction`) и TTS
должны звучать мужским взрослым голосом.

## Диагностика

Сетевые операции принадлежат data hooks TanStack Query: auth и карту читают queries;
импорт карты, создание варианта/сессии, отправка ответа, STT и оценка выполняются
mutations. `apiFetch` остаётся транспортом, но вызывается только из API-модулей,
подключённых как `queryFn` или `mutationFn`. POST-команды не выполняются в `queryFn`.
Владельцы операций: `useCurrentUserQuery` / `useAuthenticateMutation` / `useLogoutMutation`;
`useCompetencyMapQuery` / `useImportCompetencyMapMutation`; `useDiagnosticSession`
(start, progress и submit) / `useDiagnosticResultQuery` / `useDiagnosticAudioQuery`;
`useDiagnosticVoice`; `useLearningPlanQuery` / `useCreateLearningPlan` / `useLessonMessages` /
`useLessonActions` / `useVoiceRecorder` (план обучения).
Queries передают свой `AbortSignal`; владелец mutation передаёт сигнал явно и
отменяет его до сброса UI-состояния. `mutation.reset()` не отменяет HTTP-запрос.
Ключи включают пользователя и идентификатор сессии/задания, а lifecycle guard
использует epoch авторизации, чтобы поздний ответ прежней сессии не изменил новую.
Мутации автоматически не повторяются; ручной повтор диагностики и ответа сохраняет
те же idempotency keys и данные запроса. Микрофон, MediaRecorder, локальные таймеры,
blob URL и playback остаются под управлением браузерных hooks.

Карточка курса на главной предлагает одно действие: для студента диагностика и
обучение — один процесс. «Начать обучение» запускает проверку знаний,
«Продолжить обучение» возвращает в незавершённую диагностику или, после неё, в
план обучения; «Пройти проверку заново» начинает новую диагностику. Под описанием
курса — четыре цветные плитки шагов (пройдите проверку голосом, найдите пробелы,
получите персональный план, подготовьтесь по плану к экзамену); лозунг «Подтянем до уверенного уровня в кратчайшие
сроки» — на экране входа ученика; кнопки — крупные плитки с коротким пояснением. Каталог и карты всегда
запрашиваются по явному `subject_id`; выбор предмета сам по себе не создаёт
вариант. Запуск проверки отправляет `POST /api/v1/variants` с этим ID,
затем начинает диагностику (`POST /api/v1/diagnostic-sessions`). Вопрос, варианты,
роль main/basic и голосовая инструкция приходят с backend. Длинные вопросы
показываются меньшим шрифтом с сохранением переносов. Frontend не исправляет
содержимое банка: если импорт содержит буквальные `\n`, они остаются видимыми
как исходный текст задания. Неподходящая или пустая
карта показывает отдельную ошибку с повтором запроса, без подстановки демозаданий.

Кнопка «Прослушать инструкцию» сначала читает JSON-статус через
`GET /api/v1/diagnostic-sessions/{id}/current/audio?variant_task_id={taskId}`.
При `ready` браузер получает сохранённый WAV по `audio_url` через
`GET /api/v1/task-audio/{id}/file`; при `pending` показывает подсказку и не запускает
TTS. Демо тренажёра использует локальный WAV-сигнал. Запись отправляется целиком
как multipart `audio` + `variant_task_id` в
`POST /api/v1/diagnostic-sessions/{id}/answers`. Backend выполняет STT и оценку
по сохранённому снимку; браузер не отправляет свою оценку, эталон или текст задания.
При ошибке отправки запись остаётся доступной для прослушивания и повтора.
Повтор использует то же аудио и `Idempotency-Key`, новый вариант и старт сессии
также повторяются с исходными ключами. Ошибка не считается учебным нулём.

После принятого ответа панель записи только подтверждает его («Ответ принят» или
«Вопрос пропущен»), без плеера записи; балл, вердикт и отзыв студенту не
показываются ни в диагностике, ни в тренировке, навигатор тренировки не окрашивает
вопросы по баллу. Оценки остаются в API для итога. Кнопка «Следующее задание» стоит на месте
кнопки записи и показывает текущее задание из серверного прогресса.

Запись управляется кругом с микрофоном: нажатие начинает запись, повторное — завершает;
отдельной кнопки записи нет, кнопки под кругом появляются только после ошибки.

В диагностике вместо навигатора под шапкой — полоса прогресса в процентах. Каждая
компетенция весит 1/N: основное с оценкой 2 закрывает её долю, иначе основное и каждый
базовый добавляют по трети. Процент считается по серверной позиции
(`current_competency`, `current_step`), поэтому не уменьшается и растёт после каждого
задания; до последнего ответа он не превышает 99%. Backend управляет пропуском базовых после
основного с оценкой 2; прогресс учитывает выполненные и пропущенные позиции.
Количество заданий не фиксировано.

Завершённый результат читается через
`GET /api/v1/diagnostic-sessions/{id}/result`: итоговая сумма только основных,
максимум, расшифровки и оценки принятых ответов, пропущенные базовые и невключённые
компетенции. Непроверенные базовые обозначаются как «не проверено», без оценки 0.
Общий педагогический фидбэк читается отдельно через
`GET /api/v1/diagnostic-sessions/{id}/feedback` и показывает резюме, сильные
стороны, подтверждённые пробелы и рекомендации. Ошибка его загрузки не скрывает
диагностический результат; запрос можно повторить.
«Начать заново» создаёт новый вариант и диагностическую сессию.

ID варианта/сессии и ключи создания сохраняются в `sessionStorage` отдельно по
пользователю и адресу API. При перезагрузке вкладки frontend читает существующую
сессию через `GET /api/v1/diagnostic-sessions/{id}`; диагностики, результаты,
тренировки и история ответов хранятся в PostgreSQL и переживают перезапуск backend.
При недоступном хранилище используется память вкладки. Незаписанные ответы и
локальное аудио при перезагрузке теряются. HTTP 401 возвращает на экран входа.

Контракты — в [едином OpenAPI](../../api/openapi.yaml), правила отбора —
в [алгоритме](../../documents/Алгоритм_составления_варианта.md). HTTP transport
находится в `src/shared/api/`, endpoints — у owning entities/features, hooks и
сценарии — в соответствующих slice `model/`. Bootstrap подключает HTTP-адаптеры и per-slice providers.
В план обучения студент попадает кнопкой «Подтянуть слабые темы» в итоге диагностики
или «Продолжить обучение». Если плана ещё нет, на весь экран показывается вопрос
«Сколько у тебя часов?» с плитками 1 / 3 / 5 / 10+ часов; один клик создаёт план,
повторно вопрос не задаётся. Экран плана: слева оглавление «компетенция → ОР» с временем
и статусом (пройдено / сейчас / впереди / надо повторить), ниже — ОР «если останется время»;
справа чат с теорией, практикой и разбором; сверху прогресс плана в процентах. Урок текущей темы
открывается автоматически. Ответ записывается микрофоном внизу чата (как и в диагностике, запись
останавливается через 1,5 минуты, а ответ длиннее 20 с отправляется как WAV 16 кГц); пока наставник
проверяет, расшифровка уже видна в чате и показан индикатор «думает». Пройденные темы
открываются только для чтения, будущие закрыты. Если проверка не удалась, ответ
сохраняется и его можно проверить ещё раз.

## Авторизация

Сайт ученика и админ-панель — отдельные сайты в одном приложении; экрана выбора
роли нет. Гость сайта ученика сразу попадает на `/login` с лозунгом и формой
входа/регистрации; ссылок на админку нет, выход возвращает на `/login`.
Админ-панель открывается по `/admin` (переходит на `/admin/competency-map`) и сама
входит без пароля в общий аккаунт через `POST /api/v1/auth/teacher`; при ошибке
показывает «Попробовать снова». Кнопки «Выйти» в админке нет — в шапке только профиль
общего аккаунта; истёкшая сессия входит снова сама. На страницах `/admin`
транспорт `apiFetch` добавляет к запросам API заголовок `X-AI-Tutor-Portal: admin`,
и backend держит для админки отдельные cookies — обе вкладки работают в одном
браузере независимо. Пока проверяется сессия, показывается загрузка.
Формы вызывают `/api/v1/auth/login` и `/api/v1/auth/register`, регистрация
сразу создаёт сессию. После перезагрузки пользователь загружается через
`/api/v1/auth/me`; кнопка «Выйти» завершает сессию. Пароль при регистрации —
15–128 символов, имя необязательно.

## Загрузка карты администратором

Экран `/admin/competency-map` доступен только пользователям с ролью `admin`.
Назначение роли описано в [backend README](../backend/README.md#бд-и-импорт).
Администратор выбирает предмет из каталога. Карта читается через
`GET /api/v1/subjects/{subject_id}/competency-map`: показываются версия, дата
импорта и количество компетенций, составляющих, ОР и заданий.

Выберите CSV/XLSX размером до 25 МиБ и подтвердите замену текущей карты и банка
заданий. Файл отправляется как multipart с полем `file` в
`POST /api/v1/admin/subjects/{subject_id}/competency-map/import`. CSV должен быть в UTF-8 с разделителем
запятая или точка с запятой; XLSX содержит один лист карты. Формат проверяет backend.
Пока импорт выполняется, выбор файла и повторная отправка заблокированы.
После успеха текущая карта обновляется, показываются счётчики импорта и таблица
предупреждений с номерами строк и названиями колонок. Неполные задания сохраняются
как источник и не включаются в банк. Ошибки парсера показываются с указанием строки;
при ошибке файл остаётся выбранным для повторной загрузки.

При потере ответа результат импорта может быть неизвестен: экран повторно запрашивает
текущую карту и предлагает проверить её перед новым импортом. Автоматический повтор
замены отключён. HTTP 401 возвращает пользователя на экран входа.
Импорт выполняется на backend, который разбирает содержимое CSV/XLSX.

Cookies сессии передаются вместе с запросами. Backend требует авторизацию;
при HTTP 401 интерфейс показывает сообщение о необходимости войти.
Таймаут отправки диагностического ответа — 240 секунд (STT и оценка выполняются последовательно), остальных операций — 120 секунд. Сервисы моделей вызывает backend, их адреса
во фронтенде не нужны.

Настройки находятся в общем корневом `.env` монорепозитория
(игнорируется Git), образец — корневой `.env.example`:

```dotenv
VITE_API_BASE_URL=/api/v1
VITE_API_PROXY_TARGET=http://127.0.0.1:8002
```

Авторизация, диагностика, тренировка, STT и аудио используют backend. Локальных источников данных нет.

Vite читает env из корня монорепозитория, в том числе при запуске из
`services/frontend`. В dev-режиме Vite проксирует `/api/v1` на локальный backend и удаляет префикс.
После изменения env перезапустите `npm run dev`.
Для проверки сессии с Secure cookies используйте HTTPS через Compose.
В Compose запросы идут на тот же origin через Caddy. Значение `/api/v1`
используется по умолчанию. Корневой dev Compose передаёт `VITE_API_BASE_URL`
как env Vite; после изменения `.env` пересоздайте frontend через `docker compose up -d frontend`.
Локальный Compose сервиса для production передаёт адрес API как аргумент сборки;
после их изменения пересоберите frontend.
Прямой `docker build` поддерживает `--build-arg VITE_API_BASE_URL=...`.
Изменение адреса API для статической сборки требует пересборки; runtime env nginx
не меняет уже собранный frontend.
HTTP-контракт и сценарии проверяются тестами. Backend использует API моделей
для STT/TTS и оценивания; их настройки обязательны и задаются в корневом `.env`.

Макет: https://www.figma.com/design/0QMZU6tpUJCFmtZKMkYn4B/?node-id=186-6.
В `public/assets/voice-trainer/` хранятся только два SVG: `logo.svg` и
`microphone.svg`, собранные из исходных слоёв макета, а также локальные Inter
Regular/Bold и их лицензия. Фоны, рамки, кнопки, прогресс и волна оформлены CSS.
Приложение не запрашивает шрифты или временные ассеты Figma во время работы.

## Структура

- `src/bootstrap/` — app-layer alias и composition root: entrypoint, providers, HTTP DI и router shell. Имя `bootstrap` выбрано вместо стандартного `app`; `src/app/` и `src/application/` не создаются.
- `src/routes/` — тонкий технический реестр TanStack Router с неизменными URL; `src/routeTree.gen.ts` генерируется автоматически.
- `src/pages/trainer/`, `src/pages/login/`, `src/pages/competency-map/` — уникальные экраны и их композиция. Trainer page содержит UI диагностики и тренировки без импорта другого page slice.
- `src/features/` — сценарии `auth`, `diagnostic-session`, `training`, `subject-selection` и `import-competency-map`, включая локальные hooks, порты и UI действий.
- `src/entities/` — модели и API владельцев `user`, `diagnostic-session`, `training`, `subject`, `assessment` и `competency-map`.
- `src/shared/api/` — HTTP transport и auth refresh; `src/shared/lib/` — браузерные audio/waveform adapters; `src/shared/i18n/` — локализация.
- Слои импортируют только вниз; slices одного слоя изолированы. Межслайсовые импорты используют `index.ts`; внутренние импорты slice относительные. Для взаимных entity типов разрешены только минимальные `@x/<consumer>` APIs.
- Чистые сценарии находятся в `model`/`lib` owning slice. `bootstrap` собирает per-slice providers и HTTP-адаптеры; предметные контракты не агрегируются в `shared`.
- `tests/` — отдельная иерархия тестов, зеркальная относительно `src/`: например, `src/features/auth/model/use-auth.ts` проверяется в `tests/features/auth/model/use-auth.test.tsx`.
- `tests/setup.ts` настраивает тестовую среду; `tests/support/query-wrapper.tsx` предоставляет общий wrapper для React Query тестов. Тесты и вспомогательные тестовые модули не размещаются в `src/`.

`src/routeTree.gen.ts` генерируется плагином Router при запуске Vite/Vitest или
сборке. После добавления маршрутов сначала запустите npm run dev либо npm run build,
затем typecheck. Правила разработки находятся в AGENTS.md.

## Проверки

Для форматирования исходников и конфигурации используйте `npm run format`.
Prettier использует одинарные кавычки и не добавляет точки с запятой в TS/JS.
Сгенерированный `src/routeTree.gen.ts`, lock-файл и статические ассеты исключены.

```bash
npm run format:check
npm run lint
npm run typecheck
npm test -- --run
npm run build
```

Эти же проверки выполняются в Frontend CI. `npm run preview` запускает
предпросмотр готовой сборки.

## Docker

Из корня монорепозитория:

```bash
docker build -t ai-tutor-frontend services/frontend
docker run --rm -p 8080:80 ai-tutor-frontend
```

Сборка обслуживается nginx на http://localhost:8080 с fallback для SPA-маршрутов.
Фронтенд включён в общий Docker Compose. Для общего dev-стека выполните
`./dev.sh -d` из корня после настройки `.env` и установки mkcert
по корневому README. Скрипт подготовит localhost-сертификаты и dev-сеть. Серверный `./prod.sh` запускает локальные Compose с готовыми
TLS-сертификатами. Адрес определяется HTTPS bind/port и именем сервера; Caddy
направляет `/api/v1` и `/api/v1/*` в backend, удаляя префикс `/api/v1`.
Проверка backend доступна на `/api/v1/health`; остальные пути идут во frontend.
Порт nginx доступен только внутри Docker-сети.

Для отдельной пересборки из этой папки:

```bash
docker compose --env-file ../../.env up -d --build
```

Локальный Compose подключается к внешней сети `ai-tutor_default`; nginx доступен Caddy как `frontend:80`.
Настройки `VITE_*` применяются при сборке. Для общего dev-стека продолжайте
использовать корневой Compose; не запускайте оба варианта одновременно.

## Live reload в Docker

Корневой `./dev.sh -d` использует Dockerfile target `dev`: Vite слушает порт 80
внутри контейнера, а Caddy проксирует HTTPS и HMR WebSocket. Исходники смонтированы
из `services/frontend/`, `node_modules` находится в отдельном Docker volume.
Polling включён только в контейнерном dev-стеке через `DEV_POLLING=true`.
Настройки `VITE_*` передаются как env; изменение `.env` требует пересоздания контейнера.
При изменении npm-зависимостей выполните `docker compose restart frontend` из корня:
при старте контейнер выполняет `npm ci`.
Локальный Compose этого сервиса использует production-сборку с nginx.
