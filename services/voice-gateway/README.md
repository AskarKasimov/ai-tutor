# Voice gateway

Отдельный Go-сервис для STT и TTS. Backend использует два gRPC-адаптера; gateway распределяет операции между экземплярами моделей. STT и TTS имеют отдельные очереди, пулы и лимиты. Количество экземпляров задаётся конфигурацией, жёсткого ограничения на число моделей нет.

## Путь запроса и контракт

`services/shared/proto/voicegateway/v1/gateway.proto` — общий контракт:

- `Transcribe`: аудиобайты и `media_type`; результат — текст и `request_id`.
- `Synthesize`: текст, `voice_profile` и `voice_revision`; результат — WAV, MIME и `request_id`.
- `DescribeVoice`: получение версии голосового профиля для кэша backend.

Backend обращается к gateway по gRPC в доверенной внутренней сети. Публичные HTTP-ручки `/voice/transcriptions` и `/voice/syntheses` обслуживает backend. Внешний клиент не выбирает экземпляр модели. Размер входного аудио — до 25 МиБ, частота WAV — от 8 до 192 кГц; PCM16 WAV ограничен до 100 возможных фрагментов при разбиении, текст TTS — 1–500 символов; gRPC настроен на сообщения до 26 МиБ на входе и 65 МиБ на выходе. Потоковая передача пока не поддерживается.

Gateway поддерживает HTTP API GigaAM (multipart `file`, необязательный query `model`, JSON `text`) и VoxCPM (JSON с текстом и настройками, WAV в ответе). Для одинакового API новые экземпляры добавляются YAML-конфигурацией. Другой протокол требует реализации в `internal/provider`. Общий разбор WAV и операции PCM16 находятся в `services/audio`; допустимые частоты задаются в вызывающих слоях.

Запрос STT попадает в очередь STT; TTS — в очередь TTS. Планировщик выбирает совместимый экземпляр с наименьшей долей занятых слотов, при равенстве распределяет назначения по кругу. Запросы несовместимого голосового профиля не блокируют другие профили. Лимит `slots` относится ко всему экземпляру, включая разбиение длинного STT-запроса. При переполнении очереди или лимита RPC данной операции возвращается `ResourceExhausted`. Автоматического повторного вызова модели при ошибке нет: ошибка возвращается вызывающему коду, а очередь продолжает обслуживать остальные задачи.

Сейчас фоновые и пользовательские обращения имеют одинаковый приоритет. Независимость двух очередей не изолирует их от отказа общего процесса, диска или Redpanda.

## Долговечное состояние и аудио

Каждая очередь использует отдельный однопартиционный компактируемый топик Redpanda: `voice.stt.v1`, `voice.tts.v1`. Запись содержит идентификаторы и состояние, без аудио, текста и ответов модели. Запрос и результат сохраняются на постоянном volume `voice_gateway_data`: запись во временный файл, fsync, rename и fsync каталога. В очередь передаются идентификаторы этих файлов.

Переходы: `queued` → `running` → `succeeded` либо `failed`. `queued` сохраняется до допуска к выполнению; `running` — до вызова модели; результат и конечное состояние — до успешного ответа клиенту. Неопределённый результат записи в Redpanda переводит процесс в неготовность и завершает его; Compose перезапускает сервис для восстановления.

При перезапуске gateway читает оба топика до барьера восстановления. Ожидавшие задачи завершаются отменой, поскольку прежние gRPC-клиенты потеряли соединения. Выполнявшиеся задачи становятся прерванными (`Aborted`), без повторного вызова модели. Успешные результаты сохраняются для повторов с тем же `idempotency-key`. Один ключ нельзя использовать с другими данными; это `AlreadyExists`. Backend автоматически создаёт ключ на один вызов адаптера; отдельное повторное действие пользователя создаёт новую задачу.

Входные файлы удаляются после завершения задачи. Результаты и конечные записи удаляются после `retention`; задачу с удержанным слотом очистка не удаляет. Если результат удалён по retention, пока повтор ожидает завершения, повтор получает `NotFound` вместо результата. Общий объём файлов ограничен `max_payload_bytes`; при достижении лимита новые задачи отклоняются. Метрика `voice_payload_bytes` показывает занятое место. Идентификаторы моделей в метриках имеют метку `model_instance`, чтобы не конфликтовать с меткой target `instance` в Prometheus. Осиротевшие файлы удаляются при восстановлении.

Поддерживается **один активный процесс gateway**. Он берёт файловую блокировку volume. Несколько реплик с разными дисками и общими топиками не поддерживаются; это не распределённый worker pool. При переносе на другой хост нужно перенести volume вместе с состоянием Redpanda: потеря аудиофайлов означает потерю сохранённых результатов.

Рабочее окружение gateway — Linux-контейнер. Backend-тесты с `testkit` также компилируются под Windows: volume блокируется через `LockFileEx`, блокировка освобождается при закрытии файла. На Windows тестовое хранилище синхронизирует файлы, но пропускает fsync каталога; гарантии восстановления gateway после сбоя относятся к Linux.

## Отмена и неопределённые слоты

Отмена ожидающей задачи удаляет её из очереди. После отправки HTTP-запроса disconnect или timeout не доказывает, что сервер модели прекратил вычисление. Такой слот сохраняется занятым, в том числе после перезапуска gateway. Ошибка или отмена во время установления соединения до его назначения HTTP-транспортом слот не удерживает. После назначения соединения gateway считает отправку возможной и сохраняет резерв при неопределённой ошибке.

`instances[].abort_on_disconnect: true` разрешает освобождать слот после прерванного вызова. Включать параметр можно только после фактической проверки остановки генерации на данном сервере модели и промежуточных proxy. В коммитной конфигурации он `false`: это поведение текущих серверов не подтверждено.

Для снятия удержанных слотов сначала остановите/перезапустите соответствующую модель и убедитесь, что прежняя генерация завершена. Затем выполните:

```bash
docker compose --env-file .env exec voice-gateway /voice-gateway release-held gigaam-1 --upstream-stopped
```

Команда обращается к административному Unix-сокету `admin.sock` в каталоге данных с правами 0600 и подтверждением остановки upstream. Сетевой HTTP endpoint операции не предоставляет. Она снимает только резервирования завершённых задач; активные вызовы не затрагиваются. Снятие сохраняется в Redpanda до допуска новых задач. До снятия резервирования сохраняйте соответствующий ID инстанса и достаточное число его слотов в конфигурации: иначе восстановление будет отклонено. HTTP-порт gateway опубликован только на loopback хоста; внутренние endpoints не имеют клиентской аутентификации и не должны публиковаться через Caddy.

## Конфигурация

Источник настроек — `config/dev.yaml`; `VOICE_GATEWAY_CONFIG` выбирает файл, но не переопределяет отдельные поля. YAML loader отклоняет неизвестные поля, неверные типы, дубликаты, несколько документов, неподдерживаемые API и профили без подходящих исполнителей.

| Поля | Значение |
| --- | --- |
| `grpc_address`, `http_address` | Внутренний RPC и HTTP health/metrics. |
| `log_level` | `debug`, `info`, `warn`, `error`; JSON в stdout. |
| `data_dir`, `max_payload_bytes`, `retention` | Постоянные файлы, их общий лимит и срок хранения результатов. |
| `request_timeout`, `max_connections` | Общий срок обработки с ожиданием очереди и число одновременных RPC отдельно для STT, TTS и DescribeVoice. |
| `brokers`, `stt_topic`, `tts_topic` | Redpanda и два разных однопартиционных топика. |
| `stt.max_waiting`, `tts.max_waiting` | Максимум ожидающих задач в каждой очереди. |
| `instances[].id`, `api`, `url`, `slots`, `timeout` | Идентификатор, протокол, адрес, параллельность и timeout вызова модели. |
| STT `model`, `longform` | Выбор GigaAM и серверная обработка длинных записей. |
| TTS `profiles` | Допустимые голосовые профили экземпляра. |
| `voices` | Голосовая идентичность и параметры VoxCPM. |

Для GigaAM при `longform: false` PCM16 WAV длиннее 20 с режется по тихим местам и распознаётся последовательно в пределах одного общего timeout. Ogg/WebM передаются целиком. `longform: true` передаёт WAV целиком и требует VAD-зависимостей и весов на сервере модели. Таймкоды не используются.

VoxCPM получает исходный текст с суффиксом `!!!`, если его ещё нет, без дополнительной инструкции о стиле. Профиль задаёт `seed`, `cfg_value` (0–5), `inference_timesteps` (1–50), `use_reference` и `use_prompt`. `identity` обозначает модель/её версию и установленный на сервере референсный голос: все экземпляры одного профиля должны давать один и тот же голос. При смене весов модели или референса меняйте `identity`; gateway не читает файлы весов на удалённом сервере.

Версия профиля — хэш идентичности, параметров и подготовки текста. Backend получает её при первом запросе TTS, кэширует в процессе и использует в кэше Geek; gateway отвергает синтез с устаревшей версией (`FailedPrecondition`). После изменения голоса/параметров перезапустите gateway, затем backend. Сохранённые учебные аудиофайлы автоматически не пересоздаются.

## Запуск и мониторинг

Основной запуск — `./dev.sh -d` из корня с настроенным `.env`. Корневой Compose запускает Redpanda, создаёт voice-топики и запускает voice gateway независимо от backend: неготовность голосового сервиса не блокирует старт API. Dev override включает Air; конфигурация и контракты отслеживаются вместе с Go-кодом. Для отдельного запуска Compose этой папки нужны уже работающие Redpanda и внешняя сеть `ai-tutor_default`; сначала запустите `voice-queue-init`.

В существующий Prometheus добавлен target `voice-gateway:8020`. Dashboard **Voice Gateway · STT и TTS** загружается в папку **Voice Gateway** существующей Grafana. Профиль root Compose — `observability`. Дашборд показывает очереди, занятые и удержанные слоты, назначения экземплярам, результаты вызовов, p95 ожидания и обработки, размер файлов и входные исходы, включая отказы допуска, очереди и дисковой квоты.

Метрики перед отправкой собираются в памяти; счётчики запросов копируются под короткой блокировкой. Запись HTTP-ответа выполняется после освобождения блокировок, поэтому медленный scrape не задерживает обработку RPC.

`/health/live` проверяет процесс; `/health/ready` — восстановление состояния и доступность Redpanda. Эти проверки не подтверждают доступность или качество моделей. `/metrics` не содержит аудио, текста и адресов моделей. Логи запроса и вызова модели содержат одинаковые `gateway_request_id` и `trace_id`, операцию, длительность, `error_code`, безопасную категорию `error` и стадию `stage`; при HTTP-ошибке также `upstream_http_status`. Содержимое, URL и сырые ошибки моделей не логируются. Счётчик `voice_requests_total{operation,code,reason}` учитывает исходы обработанных unary RPC, включая отказы до вызова модели; `voice_upstream_calls_total` — только выполненные вызовы моделей.

## Проверки

Из каталога сервиса, последовательно:

```bash
GOWORK=off GOMAXPROCS=2 go test -p 1 -parallel 2 -race ./... -count=1
GOWORK=off GOMAXPROCS=2 go vet -p 1 ./...
GOWORK=off GOMAXPROCS=2 go build -p 1 -o /tmp/voice-gateway ./cmd/voice-gateway
```

Для интеграционного теста запустите Redpanda из корня и задайте `TEST_KAFKA_BROKERS=localhost:19092` при запуске тестов. Тест создаёт отдельные временные топики, проверяет gRPC → обе очереди → HTTP моделей, большие сообщения, идемпотентность и восстановление результата, затем удаляет только свои топики. Без переменной этот тест явно пропускается. Модели в автоматических тестах — локальные заглушки; доступность реальных endpoints и качество голоса проверяются отдельно.
